*Почему открытый TCP-трафик читается на любом промежуточном узле и как TLS даёт три гарантии безопасности: конфиденциальность, целостность и проверку подлинности сервера.*

Представьте, что вы выложили `BookmarkFlow` на облачный сервер и открываете его из кафе через бесплатный Wi-Fi. Поверх обычного TCP все ваши команды, пароли и адреса закладок летят по сети открытым текстом. Точка доступа, маршрутизатор провайдера или чужой ноутбук в той же сети видят каждый байт — и могут не только прочитать трафик, но и незаметно подменить ответ сервера.

Такую подмену называют атакой **«человек посередине»** (*man-in-the-middle*, MITM). Чтобы защитить данные в пути, между транспортным TCP и прикладным протоколом (например, HTTP) встроили слой **TLS** (*Transport Layer Security*). Протокол **HTTPS** — это не отдельный «новый HTTP», а обычный HTTP поверх TLS (порт `443` вместо `80`).

## Три гарантии TLS

TLS решает три независимые задачи, и потеря любой из них ломает защиту целиком:

1. **Конфиденциальность (*confidentiality*).** Наблюдатель на линии видит лишь поток случайных зашифрованных байтов и не может прочесть URL, заголовки или тело.
2. **Целостность (*integrity*).** К каждому блоку прикрепляется криптографический код проверки. Изменение даже одного бита в пути немедленно обнаруживается, и соединение рвётся.
3. **Подлинность сервера (*authentication*).** Клиент убеждается, что говорит именно с настоящим сервером `go.dev`, а не с подставной машиной в соседнем кресле.

Шифрование без проверки подлинности бесполезно: вы просто аккуратно зашифруете свой пароль специально для злоумышленника.

## Гибридное шифрование: два вида ключей

Зашифровать трафик одним общим секретным ключом — **симметричное шифрование** — очень быстро: современные процессоры шифруют **гигабайты в секунду** аппаратно. Но у него есть тупик: как браузер и сервер, впервые встречаясь в открытой сети, договорятся о секрете, не пересылая ключ открытым текстом?

Эту проблему решает **асимметричное шифрование**. У сервера есть математически связанная пара ключей: **публичный** (доступен всем) и **приватный** (не покидает сервер). С их помощью две стороны вырабатывают общий секрет прямо поверх прослушиваемого канала. Минус один: асимметричные операции в **сотни и тысячи раз медленнее** симметричных, поэтому гнать через них гигабайты данных невыгодно.

TLS соединяет оба подхода в **гибридную схему**:
- во время короткого рукопожатия асимметричная криптография срабатывает **один раз**, чтобы согласовать временный одноразовый **сессионный ключ**;
- весь последующий HTTP-трафик шифруется быстрым **симметричным** алгоритмом на этом ключе.

## Сертификаты X.509, центры сертификации и SNI

Получить публичный ключ недостаточно: злоумышленник на пути может подсунуть вам *свой* публичный ключ. Чтобы клиент отличил подлинный ключ `go.dev` от подделки, действуют **сертификаты X.509** и **центры сертификации** (*Certificate Authority*, **CA** — например, Let's Encrypt или DigiCert).

Сертификат — это цифровой паспорт сервера, содержащий доменное имя (и список альтернативных имён `SAN`), публичный ключ, срок действия (`NotBefore` — `NotAfter`) и цифровую подпись CA. В каждую ОС и браузер заранее вшит список доверенных **корневых CA** (*root store*). Получив сертификат, клиент проверяет **цепочку доверия** до одного из корневых CA, срок действия и совпадение доменного имени.

Практическая деталь: на одном IP-адресе часто хостятся десятки доменов. Чтобы сервер знал, какой сертификат предъявить, в самом первом сообщении рукопожатия клиент передаёт расширение **SNI** (*Server Name Indication*) — имя нужного домена в открытом виде.

## Этапы рукопожатия TLS 1.3

Актуальная версия **TLS 1.3** уложила рукопожатие в **один круговой обмен** (*1 RTT*) поверх TCP:

```mermaid
sequenceDiagram
    participant C as Клиент (Go / браузер)
    participant S as Сервер (go.dev:443)
    Note over C,S: 1. TCP-рукопожатие (SYN / SYN-ACK / ACK)
    C->>S: ClientHello (TLS 1.3, SNI: go.dev, шифры, доля ключа)
    S-->>C: ServerHello + Certificate (X.509) + подпись + Finished
    Note over C: Проверка цепочки CA, срока и домена;<br/>вычисление общего симметричного ключа
    C->>S: Finished
    Note over C,S: 2. Готово — идёт зашифрованный HTTP-трафик
```

Математические детали эллиптических кривых, режимов шифрования и ротации ключей мы оставляем для **Тома 4**. В Go за TLS отвечает стандартный пакет `crypto/tls`, который возвращает обычный `net.Conn`:

```go
func inspectTLS(addr string) error {
	dialer := &tls.Dialer{
		NetDialer: &net.Dialer{Timeout: 3 * time.Second},
		Config:    &tls.Config{MinVersion: tls.VersionTLS12},
	}
	conn, err := dialer.Dial("tcp", addr)
	if err != nil {
		return err
	}
	defer conn.Close()

	state := conn.(*tls.Conn).ConnectionState()
	cert := state.PeerCertificates[0]
	fmt.Printf("Версия: %s, домен: %s, до: %s\n",
		tls.VersionName(state.Version),
		cert.Subject.CommonName,
		cert.NotAfter.Format(time.DateOnly),
	)
	return nil
}
```

Передайте `"go.dev:443"` — и Go сам подставит `go.dev` в SNI, проверит цепочку CA по системному хранилищу и откроет защищённое соединение.

## Подводные камни

**Ловушка 1. `InsecureSkipVerify: true` в коде.**  
Этот флаг отключает проверку подлинности сертификата: трафик останется зашифрованным, но клиент примет поддельный сертификат от любого злоумышленника. Для тестовых стендов добавляйте свой CA в `RootCAs`, а не выключайте проверку.

**Ловушка 2. Просроченный сертификат или сбитые часы.**  
Срок действия проверяется по локальным часам клиента. Если сертификат не продлили или системная дата сбилась, рукопожатие прервётся с `x509: certificate has expired or is not yet valid`.

> [!check] Проверь понимание
> Злоумышленник в публичном Wi-Fi подменил DNS-ответ для `bank.example` на свой IP и выдал самоподписанный сертификат с именем `bank.example`. Установит ли клиент соединение при стандартных настройках?
>
> Нет. Самоподписанный сертификат не выстраивает цепочку доверия к системным корневым CA, поэтому клиент прервёт рукопожатие до отправки любых данных.

## Практика

**Упражнение 1 (Базовое). Три гарантии на сбоях.**  
Какая гарантия TLS нарушена в каждом случае: (а) провайдер вставил рекламный скрипт в HTML-ответ; (б) чужой ноутбук в кафе перехватил токен доступа; (в) подставной сервер выдал себя за `api.bookmarkflow.example`?

> [!solution] Показать решение
> (а) **целостность**; (б) **конфиденциальность**; (в) **подлинность сервера**. TLS защищает сразу от всех трёх атак.

**Упражнение 2 (Практическое). Почините `tls.Dial` по IP.**  
Клиент подключается напрямую по IP к серверу с валидным сертификатом для `api.bookmarkflow.example`:
```go
conn, err := tls.Dial("tcp", "203.0.113.10:443", &tls.Config{})
```
Почему проверка сертификата упадёт и как это исправить без `InsecureSkipVerify`?

> [!solution] Показать решение
> При подключении по голому IP клиент не отправляет SNI и сверяет IP с именем домена в сертификате. Нужно явно указать `ServerName`:
> ```go
> cfg := &tls.Config{ServerName: "api.bookmarkflow.example", MinVersion: tls.VersionTLS12}
> conn, err := tls.Dial("tcp", "203.0.113.10:443", cfg)
> ```

**Упражнение 3 (Со звёздочкой \*). Что видит провайдер при HTTPS.**  
Вы открыли `https://go.dev/doc/effective_go`. Какие данные скрыты внутри TLS, а какие всё равно видны провайдеру?

> [!solution] Показать решение
> **Скрыты:** путь `/doc/effective_go`, параметры запроса, HTTP-заголовки (`Cookie`, `Authorization`) и всё тело обмена.
