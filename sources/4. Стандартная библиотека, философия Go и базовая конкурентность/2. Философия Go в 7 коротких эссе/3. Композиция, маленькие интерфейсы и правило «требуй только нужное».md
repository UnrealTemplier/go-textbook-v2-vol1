*Почему глубокие деревья наследования ломают код при росте проекта, как работают однометодные контракты стандартной библиотеки и зачем объявлять интерфейс на стороне потребителя.*

> «Новым типам проще удовлетворять маленьким интерфейсам. Хорошее практическое правило проектирования интерфейсов: требуйте только то, что вам действительно нужно.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

В классических учебниках по ООП программы строят как семейное древо: `BaseStorage` → `CachedStorage` → `FileCachedStorage` → `AuditedFileCachedStorage`. На старте дерево выглядит стройно. Через год оно превращается в бетонную плиту, где любое изменение предка непредсказуемо ломает потомков.

Создатели Go убрали наследование классов целиком, заменив его двумя простыми механизмами: **композицией структур** и **неявными маленькими интерфейсами**.

## Почему иерархии проигрывают композиции

Корень беды — **хрупкий базовый класс** (*fragile base class*). Когда наследник переопределяет один метод родителя, он неявно зависит от того, как устроены остальные методы родителя внутри.

Представьте, что вы унаследовали `CountingStore` от `FileStore`, чтобы считать вызовы `Get`. Через месяц коллега переписал `FileStore.Search` так, чтобы тот внутри вызывал `Get` для каждой записи. Вы не трогали `CountingStore`, но ваш счётчик внезапно сломался. К тому же реальные сущности редко ложатся в одно дерево: хранилищу могут одновременно понадобиться кэш, журнал и диск.

Композиция решает задачу плоско: `FileStore` не «разновидность `MemoryStore`», а структура, которая *держит* поле `mem *MemoryStore` и явно решает, какие методы делегировать напрямую, а после каких вызывать `save()` — ровно так мы собрали шаг 4 `BookmarkFlow` в Модуле 3.

## Сила однометодных контрактов

В Подразделе 4.1 вы уже видели главный козырь стандартной библиотеки Go: почти весь ввод-вывод держится на контрактах из **одного метода**:

```go
type Reader interface {
	Read(p []byte) (n int, err error)
}

type Writer interface {
	Write(p []byte) (n int, err error)
}
```

Рядом стоят `error` (`Error() string`) и `fmt.Stringer` (`String() string`). Чем меньше методов в интерфейсе, тем больше независимых типов ему удовлетворяют. Одна функция `io.Copy` перекачивает байты между `os.File`, `bytes.Buffer`, `strings.Reader` и любым вашим типом — хотя эти типы ничего не знают друг о друге.

Если нужен более широкий контракт, маленькие интерфейсы складываются из готовых деталей: `io.ReadWriter` встраивает `io.Reader` и `io.Writer`.

## Интерфейс на стороне потребителя

В Модуле 3 мы приводили совет Алана Донована и Брайана Кернигана: не плодите интерфейсы под единственную реализацию — интерфейс нужен там, где с двумя или более конкретными типами требуется работать единообразно.

В пару к этому идёт второе правило Go: **интерфейс объявляет потребитель, а не поставщик.** Благодаря неявной реализации пакет хранилища просто экспортирует конкретную структуру `*MemoryStore`, а вызывающая функция описывает ровно тот минимум методов, который ей нужен.

Посмотрим на функцию печати сводки закладок:

```go
package main

import (
	"fmt"
	"io"
	"strings"
)

type Bookmark struct {
	Title string
	Tags  []string
}

// Потребитель описывает только то, что ему нужно: чтение списка.
type BookmarkLister interface {
	List() ([]Bookmark, error)
}

func WriteSummary(w io.Writer, src BookmarkLister) error {
	items, err := src.List()
	if err != nil {
		return err
	}
	for i, b := range items {
		if _, err := fmt.Fprintf(w, "%d. %s [%s]\n", i+1, b.Title, strings.Join(b.Tags, ", ")); err != nil {
			return err
		}
	}
	return nil
}

type sliceSource []Bookmark

func (s sliceSource) List() ([]Bookmark, error) { return s, nil }

func main() {
	src := sliceSource{
		{Title: "Go Spec", Tags: []string{"go", "docs"}},
		{Title: "Go Blog", Tags: []string{"go", "essays"}},
	}
	var out strings.Builder
	if err := WriteSummary(&out, src); err != nil {
		fmt.Println("Ошибка:", err)
		return
	}
	fmt.Print(out.String())
}
```

Вывод терминала:

```text
1. Go Spec [go, docs]
2. Go Blog [go, essays]
```

Оцените три выгоды:

* По сигнатуре `WriteSummary` сразу ясно: она только **читает** закладки и **пишет** поток байтов, ничего не меняя в хранилище.
* Для теста не нужны заглушки под `Create`, `Update`, `Delete` и `Search` — хватает пятистрочного `sliceSource` и `&strings.Builder{}`.
* И `*MemoryStore`, и `*FileStore` подойдут сюда без единой правки.

Отсюда правило идиоматичного Go: **принимайте узкие интерфейсы, возвращайте конкретные структуры**. Более крупный интерфейс вроде `Store` на шаге 4 оправдан лишь тогда, когда вам действительно нужен общий многометодный контракт — например, для единого контрактного теста двух хранилищ.

> [!check] Проверь понимание
> Почему в Go удобно объявлять интерфейс в пакете-потребителе, а не рядом с реализацией?
>
> Благодаря неявной реализации поставщик не обязан знать о чужих интерфейсах. Потребитель описывает минимальный контракт ровно под свою задачу, уменьшая связность и упрощая тесты.

## Практика

**Упражнение 1 (Базовое). Сужаем контракт.**  
Функция `CountByTag(s Store, tag string) (int, error)` принимает шестиметодный `Store`, но вызывает только `s.Search(tag)`. Какой интерфейс стоит объявить на стороне потребителя?

> [!solution] Показать решение
> Однометодный интерфейс:
> ```go
> type BookmarkSearcher interface {
> 	Search(query string) ([]Bookmark, error)
> }
> ```
> Он сразу показывает, что функция работает только на чтение, и упрощает создание тестовой заглушки.

**Упражнение 2 (Практическое). Композиция вместо наследования.**  
Напишите обёртку `CountingLister` вокруг `BookmarkLister`, которая делегирует `List()` внутреннему источнику и считает число вызовов в `Calls() int`.

> [!solution] Показать решение
> ```go
> package main
>
> import "fmt"
>
> type Bookmark struct{ Title string }
>
> type BookmarkLister interface {
> 	List() ([]Bookmark, error)
> }
>
> type CountingLister struct {
> 	inner BookmarkLister
> 	calls int
> }
>
> func NewCountingLister(inner BookmarkLister) *CountingLister {
> 	return &CountingLister{inner: inner}
> }
>
> func (c *CountingLister) List() ([]Bookmark, error) {
> 	c.calls++
> 	return c.inner.List()
> }
>
> func (c *CountingLister) Calls() int { return c.calls }
>
> type staticLister []Bookmark
>
> func (s staticLister) List() ([]Bookmark, error) { return s, nil }
>
> func main() {
> 	cl := NewCountingLister(staticLister{{Title: "Go"}})
> 	_, _ = cl.List()
> 	_, _ = cl.List()
> 	fmt.Println("Вызовов List:", cl.Calls()) // Вывод: Вызовов List: 2
> }
> ```
> Обёртка сама реализует `BookmarkLister` и не зависит от внутренностей обёрнутого типа.

**Упражнение 3 (Со звёздочкой \*). Встраивание против явного поля.**  
Почему в `FileStore` (шаг 4 `BookmarkFlow`) мы использовали именованное поле `mem *MemoryStore`, а не анонимное встраивание `*MemoryStore`?

> [!solution] Показать решение
> Анонимное встраивание автоматически продвигает наружу все экспортируемые методы `*MemoryStore`. Если завтра в `MemoryStore` появится новый мутирующий метод (например, `Clear()`), он незаметно появится у `FileStore` и будет менять память в обход `f.save()`. Именованное поле защищает инвариант сохранности данных.
