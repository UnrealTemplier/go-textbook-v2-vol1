*Почему процессор всегда забирает из памяти по 64 байта за раз, как работает аппаратный префетчер и почему `[]Bookmark` обгоняет `[]*Bookmark` в разы.*

> «Память часто была самым дорогим компонентом компьютера. Когда на счету был каждый байт, этот дефицит навязывал программистам особую дисциплину: приходилось постоянно отдавать себе отчёт, сколько памяти занимает программа, а порой и прибегать к ухищрениям и рискованным приёмам, чтобы втиснуть её в доступный объём.»  
> — Брайан Керниган, *UNIX: A History and a Memoir*

В сервисе закладок `BookmarkFlow` нужно просуммировать количество просмотров по полумиллиону записей. Две функции делают ровно один и тот же проход `for _, b := range list { total += b.Views }`. Первая принимает слайс значений `[]Bookmark`, вторая — слайс указателей `[]*Bookmark`. Число итераций и сложений идентично, но второй вариант работает в три-пять раз медленнее.

Дело не в самом разыменовании указателя. Разгадка в том, какими порциями кэш процессора забирает байты из оперативной памяти.

## Модель кэш-линии 64 байта и аппаратного префетчера

Процессор никогда не читает из RAM один-единственный байт или одно 8-байтное поле `Views`. Вся оперативная память логически нарезана на блоки по **64 байта** — **кэш-линии** (*cache lines*). Когда ядро запрашивает адрес `0x1008` и получает промах кэша, контроллер памяти за те же ~100 нс приносит сразу всю 64-байтную полосу от `0x1000` до `0x103F` и кладёт её в L1:

```text
Кэш-линия 0 (64 байта): [ int64 #0 | int64 #1 | int64 #2 | ... | int64 #7 ]
                          ^                                       ^
                     промах (~100 нс)                    7 попаданий в L1 (~1 нс)
```

В одну 64-байтную кэш-линию помещается сразу восемь чисел `int64`. Прочитав нулевой элемент из RAM, следующие семь вы получаете практически бесплатно — они уже лежат в L1.

Но у процессора есть второй козырь — **аппаратный префетчер** (*hardware prefetcher*). Он следит за адресами, по которым ваша программа читает память. Как только префетчер замечает предсказуемый линейный шаг (линия 0 → линия 1 → линия 2), он перестаёт ждать промахов и заранее подгружает линии 3 и 4 в кэш, пока ядро ещё обсчитывает линию 2. В результате цикл по массиву почти не знает пауз на RAM.

## Локальность данных в памяти: пространственная и временная

Кэши и префетчер работают так хорошо лишь потому, что большинство реальных программ обладают свойством **локальности данных в памяти** (*data locality*). У него две стороны:

* **Пространственная локальность:** если программа только что обратилась к адресу `X`, с высокой вероятностью скоро понадобятся соседние адреса `X+8`, `X+16` — то есть данные в той же или следующей кэш-линии. Последовательный обход слайса — эталон пространственной локальности.
* **Временная локальность:** если программа обратилась к переменной `total` на текущей итерации, она почти наверняка снова обратится к ней через наносекунду на следующей итерации. Такие горячие данные надолго оседают в регистрах и L1.

Когда Деннис Ритчи в 1970-х добавлял в Си структуры `struct` для переписывания ядра Unix, компактное хранение полей подряд диктовалось жёстким лимитом в десятки килобайт памяти на машине PDP-11. Спустя полвека памяти стало в миллионы раз больше, но физика разрыва между скоростью CPU и RAM вернула то же самое правило: **держите данные, которые читаются вместе, физически рядом в памяти**.

## Почему `[]Bookmark` быстрее `[]*Bookmark`

В Go структуры и массивы хранят значения **напрямую**, без скрытых ссылок. Посмотрим на раскладку в памяти для двух слайсов закладок:

```text
[]Bookmark (значения подряд — одна непрерывная лента в памяти):
+------------+------------+------------+------------+
| Bookmark 0 | Bookmark 1 | Bookmark 2 | Bookmark 3 |  --> префетчер счастлив
+------------+------------+------------+------------+
|<----------- одна или две кэш-линии -------------->|

[]*Bookmark (слайс адресов + структуры, разбросанные по куче):
+--------+--------+--------+--------+
|  ptr0  |  ptr1  |  ptr2  |  ptr3  |   (сам слайс: по 8 байт на указатель)
+---+----+---+----+---+----+---+----+
    |        |        |        |
    v        |        v        |
[Bookmark 0] |   [Bookmark 2]  |        <-- разные 64-байтные кэш-линии
             v                 v
        [Bookmark 1]      [Bookmark 3]  <-- прыжки по случайным адресам
```

В варианте `[]Bookmark` процессор идёт по непрерывной ленте байтов. Кэш-линии используются на 100%, а префетчер без труда угадывает следующий адрес.

В варианте `[]*Bookmark` начинаются сразу три проблемы:
1. **Прыжки по указателям (*pointer chasing*):** на каждой итерации нужно сначала прочитать сам 8-байтный указатель из слайса, а потом сходить по этому адресу в совсем другой участок памяти.
2. **Слепота префетчера:** когда закладки создавались в разное время, редактировались и сортировались, их адреса в памяти разбросаны хаотично. Префетчер не видит закономерности и почти каждый переход превращается в промах кэша (~100 нс).
3. **Раздувание кэша:** сами указатели съедают лишние 8 байтов на элемент, а каждая 64-байтная кэш-линия, принесённая ради одного поля `Views`, засоряет кэш ненужными соседними байтами чужих объектов.

## Рабочий код: измеряем `[]Bookmark` против `[]*Bookmark`

Проверим модель на реальном коде. Чтобы имитировать живую программу, где закладки создавались, перекладывались и сортировались по разным правилам, перемешаем порядок указателей в `[]*Bookmark` — так адреса перестанут идти строго подряд:

```go
package main

import (
	"fmt"
	"math/rand/v2"
	"time"
)

type Bookmark struct {
	ID    int64
	Views int64
	Score int64
	Flags uint64
} // 32 байта: ровно две структуры на одну 64-байтную кэш-линию

func sumValues(items []Bookmark) int64 {
	var total int64
	for i := range items {
		total += items[i].Views
	}
	return total
}

func sumPointers(items []*Bookmark) int64 {
	var total int64
	for _, b := range items {
		total += b.Views
	}
	return total
}

func main() {
	const n = 500_000
	const runs = 30

	values := make([]Bookmark, n)
	ptrs := make([]*Bookmark, n)
	for i := range n {
		v := Bookmark{ID: int64(i), Views: int64(i % 100)}
		values[i] = v
		cp := v
		ptrs[i] = &cp
	}

	// Перемешиваем указатели, моделируя разброс адресов в долгоживущем сервисе.
	rng := rand.New(rand.NewPCG(10, 20))
	rng.Shuffle(len(ptrs), func(i, j int) {
		ptrs[i], ptrs[j] = ptrs[j], ptrs[i]
	})

	start := time.Now()
	var s1 int64
	for range runs {
		s1 = sumValues(values)
	}
	dValues := time.Since(start)

	start = time.Now()
	var s2 int64
	for range runs {
		s2 = sumPointers(ptrs)
	}
	dPtrs := time.Since(start)

	fmt.Printf("[]Bookmark:  sum=%d за %v\n", s1, dValues)
	fmt.Printf("[]*Bookmark: sum=%d за %v\n", s2, dPtrs)
	fmt.Printf("Разница:     %.2fx\n", float64(dPtrs)/float64(dValues))
}
```

Запуск показывает ощутимый разрыв при идентичной арифметике:

```text
[]Bookmark:  sum=24750000 за 14.2ms
[]*Bookmark: sum=24750000 за 78.6ms
Разница:     5.54x
```

Посмотрите на деталь в функции `sumValues`: мы пишем `for i := range items { total += items[i].Views }`, а не `for _, b := range items`, чтобы на каждой итерации не копировать целиком все 32 байта структуры (для 32 байтов компилятор часто оптимизирует это сам, но для крупных структур обращение по индексу гарантированно читает только нужное поле).

## Подводные камни

**Ловушка 1. Обход матрицы по столбцам вместо строк.**  
В Go двумерный массив `[N][N]int64` хранится **построчно** (*row-major*): элементы `grid[0][0]`, `grid[0][1]`, `grid[0][2]` лежат рядом в одной кэш-линии. Если перепутать порядок циклов и бежать сначала по строкам `grid[row][col]` при фиксированном `col`, каждый шаг прыгает на целую строку (`N * 8` байтов) — вы ломаете пространственную локальность и промахиваетесь мимо кэш-линии почти на каждом чтении.

**Ловушка 2. Слепой запрет на `[]*T`.**  
Слайс указателей — не антипаттерн сам по себе. Он оправдан в трёх случаях:
* на один и тот же объект должны ссылаться несколько мест программы (например, изменение закладки должно быть видно сразу в двух индексах);
* структура очень велика (сотни байтов или килобайты), и вы часто сортируете или переставляете элементы — менять местами 8-байтные указатели дешевле, чем копировать килобайтные структуры;
* в слайсе нужно отличать отсутствующее значение `nil`.

Для компактных структур данных, по которым вы бегаете циклами, `[]T` почти всегда и быстрее, и экономнее по памяти.

> [!check] Проверь понимание
> Сколько значений `int64` и сколько структур `Bookmark` (размером 32 байта) помещается в одну кэш-линию размером 64 байта?
>
> В 64 байта помещается `64 / 8 = 8` значений `int64` или ровно `64 / 32 = 2` структуры `Bookmark`.

## Практика

**Упражнение 1 (Базовое). Считаем загрузки кэш-линий.**  
У вас есть слайс `[]int32` длиной `1 024` элемента (каждый `int32` занимает `4` байта). Сколько 64-байтных кэш-линий процессору придётся загрузить при последовательном чтении всего слайса (считая, что начало слайса выровнено по границе 64 байтов)?

> [!solution] Показать решение
> Весь слайс занимает `1 024 × 4 = 4 096` байтов. Делим на размер одной кэш-линии: `4 096 / 64 = 64` кэш-линии (по 16 элементов `int32` в каждой). При каждом промахе кэша следующие 15 элементов оказываются уже в L1.

**Упражнение 2 (Практическое). Почини обход матрицы.**  
Функция ниже суммирует матрицу `4096 × 4096`, но работает подозрительно медленно. Найдите ошибку в порядке циклов, исправьте её и проверьте разницу во времени.

```go
func sumMatrixSlow(m *[4096][4096]int64) int64 {
	var total int64
	for col := range 4096 {
		for row := range 4096 {
			total += m[row][col]
		}
	}
	return total
}
```

> [!solution] Показать решение
> Во внутреннем цикле меняется `row`, поэтому каждое чтение прыгает на `4096 × 8 = 32 КБ` вперёд и полностью игнорирует остальные 7 чисел в загруженной кэш-линии. Достаточно поменять циклы местами, чтобы внутренний бежал по `col`:
> ```go
> package main
>
> import (
> 	"fmt"
> 	"time"
> )
>
> const dim = 2048
>
> func sumRowMajor(m *[dim][dim]int64) int64 {
> 	var total int64
> 	for row := range dim {
> 		for col := range dim {
> 			total += m[row][col]
> 		}
> 	}
> 	return total
> }
>
> func sumColMajor(m *[dim][dim]int64) int64 {
> 	var total int64
> 	for col := range dim {
> 		for row := range dim {
> 			total += m[row][col]
> 		}
> 	}
> 	return total
> }
>
> func main() {
> 	m := new([dim][dim]int64)
> 	for r := range dim {
> 		for c := range dim {
> 			m[r][c] = int64(r + c)
> 		}
> 	}
>
> 	t0 := time.Now()
> 	s1 := sumRowMajor(m)
> 	d1 := time.Since(t0)
>
> 	t0 = time.Now()
> 	s2 := sumColMajor(m)
> 	d2 := time.Since(t0)
>
> 	fmt.Printf("По строкам:  %d за %v\n", s1, d1)
> 	fmt.Printf("По столбцам: %d за %v\n", s2, d2)
> }
> ```
> Построчный обход обычно быстрее обхода по столбцам в 5–10 раз.

**Упражнение 3 (Со звёздочкой \*). Горячие и холодные поля.**  
Предположим, у структуры `Article` есть два горячих поля (`ID int64`, `Views int64` — их суммируют в отчёте миллион раз) и массив тяжёлых метаданных `Summary [256]byte`, который нужен только при открытии одной статьи.
