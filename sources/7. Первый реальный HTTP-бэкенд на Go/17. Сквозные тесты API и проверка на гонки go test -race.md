*Проверяем сквозной сценарий CRUD с сохранением на диск, тестируем сетевые вызовы в изоляции через `httptest.NewServer` и прогоняем API под детектором гонок `go test -race`.*

Одного `httptest.NewRecorder` хватает для проверки маршрутов и статусов, но он работает в обход реального сетевого стека. Как проверить две критичные вещи: что последовательность «создал → получил → обновил → перечитал с диска → удалил» действительно работает как целое, и что `LinkChecker` корректно ходит по HTTP за заголовками `HEAD`, не выходя при этом в настоящий Интернет?

В `project/final/server_test.go` эти задачи решают сквозной сценарий и реальный локальный тестовый сервер `httptest.NewServer`.

## Сквозной сценарий CRUD и проверка файла на диске

Обратите внимание на тест `TestBookmarkFlowHTTPCRUDAndPersistence` из `project/final/server_test.go`. В одном тесте последовательно проверяются все звенья цепи:

1. `GET /healthz` → статус `200`, непустой заголовок `X-Request-ID`.
2. `POST /api/v1/bookmarks` → статус `201`, присвоение `ID = 1`, нормализация тегов `"Go","docs"` в `["docs","go"]`.
3. `GET /api/v1/bookmarks?tag=docs` → счётчик `count == 1`.
4. `PUT /api/v1/bookmarks/1` → обновление названия на `"Official Go Docs"`.
5. **Переоткрытие хранилища с нуля (`OpenFileStore(dataPath)`)** — имитация перезапуска сервера. Мы убеждаемся, что обновлённая запись действительно пережила сохранение на диск через `writeFileAtomic`, а не осталась только в оперативной памяти.
6. `DELETE /api/v1/bookmarks/1` → `204 No Content`, и повторный `GET /api/v1/bookmarks/1` → `404 Not Found`.

Такой тест страхует сразу весь контракт API: от парсинга JSON и роутинга до записи на диск.

## Офлайн-тестирование внешнего HTTP через `httptest.NewServer`

Если в тесте `LinkChecker` указать адрес `https://go.dev`, тест станет ненадёжным (*flaky*): он упадёт без Интернета, замедлит CI или сломается, если сайт временно недоступен. Вместо этого в `TestBookmarkFlowCheckEndpointOffline` поднимается настоящий локальный HTTP-сервер прямо на свободном порту `127.0.0.1`:

```go
func TestBookmarkFlowCheckEndpointOffline(t *testing.T) {
	targetMux := http.NewServeMux()
	targetMux.HandleFunc("/ok", func(w http.ResponseWriter, _ *http.Request) {
		w.WriteHeader(http.StatusOK)
	})
	targetMux.HandleFunc("/missing", func(w http.ResponseWriter, _ *http.Request) {
		w.WriteHeader(http.StatusNotFound)
	})
	targetSrv := httptest.NewServer(targetMux)
	defer targetSrv.Close()

	store, err := OpenFileStore(filepath.Join(t.TempDir(), "check.json"))
	if err != nil {
		t.Fatalf("OpenFileStore failed: %v", err)
	}
	if _, err := store.Create(CreateInput{Title: "OK Page", URL: targetSrv.URL + "/ok"}); err != nil {
		t.Fatalf("create ok bookmark: %v", err)
	}
	if _, err := store.Create(CreateInput{Title: "Missing Page", URL: targetSrv.URL + "/missing"}); err != nil {
		t.Fatalf("create missing bookmark: %v", err)
	}

	checker := NewLinkChecker(targetSrv.Client(), 2)
	srv := NewServer(store, checker, slog.New(slog.DiscardHandler))

	rec := httptest.NewRecorder()
	srv.ServeHTTP(rec, httptest.NewRequest(http.MethodPost, "/api/v1/bookmarks/check", nil))
	if rec.Code != http.StatusOK {
		t.Fatalf("POST /check status = %d, body = %s", rec.Code, rec.Body.String())
	}
	...
}
```

Заметьте три сильных стороны `httptest.NewServer`:

- Он сам выбирает любой свободный порт в системе (`127.0.0.1:<случайный-порт>`) и кладёт его адрес в `targetSrv.URL`, поэтому параллельные тесты никогда не конфликтуют за порты.
- Вместо `nil` мы передаём в чекер `targetSrv.Client()` — этот настроенный клиент уже знает TLS-сертификат тестового сервера (если вы поднимете `httptest.NewTLSServer`).
- Вызов `defer targetSrv.Close()` в конце теста гасит все открытые клиентские соединения и закрывает сокет.

## Поиск гонок под `go test -race`

Даже если одиночный тест проходит, под реальной нагрузкой десятки горутин одновременно читают и изменяют `FileStore`, инкрементируют `atomic.Uint64` в `RequestIDMiddleware` и пишут в срез результатов `LinkChecker`. В [[8. Гонки данных и детектор go test -race]] мы уже запускали детектор гонок на слайсах и мапах — теперь проверим весь наш HTTP-бэкенд:

```bash
go test -race -v ./final
```

Реальный вывод в терминале подтверждает чистое прохождение всех тестов:


Но помните главное правило детектора гонок: `-race` ловит только те пути кода, которые **реально исполнились конкурентно** во время теста! Если в тесте запросы идут строго друг за другом, гонка внутри `FileStore` или `RequestIDMiddleware` не проявится. Чтобы по-настоящему испытать потокобезопасность, пишут отдельный конкурентный тест с `sync.WaitGroup` из 10–20 горутин, одновременно создающих, читающих и удаляющих закладки через реальный `httptest.NewServer(srv)`.

## Подводный камень: таймауты и зависшие горутины в `httptest.NewServer`

Если внутри обработчика тестового `targetSrv` забыть закрыть тест или повесить `time.Sleep(10 * time.Second)` для имитации медленного сайта, `defer targetSrv.Close()` будет ждать завершения активного HTTP-запроса, а при зависании напечатает `httptest.Server blocked in Close after 5 seconds, waiting for connections`. Если вам нужно симулировать «зависший» сервер и проверить таймаут клиента, используйте `select { case <-time.After(10 * time.Second): case <-r.Context().Done(): }`, чтобы тестовый обработчик сам мгновенно отпускал соединение после отмены.

> [!check] Проверь понимание
> Зачем в `TestBookmarkFlowHTTPCRUDAndPersistence` после `PUT` создаётся новый `reloadedStore, err := OpenFileStore(dataPath)`, вместо того чтобы просто проверить ответ `GET /api/v1/bookmarks/1`?
>
> `GET` на том же сервере читает данные из слайса `f.items` в оперативной памяти. Создание нового экземпляра `FileStore` из файла `dataPath` доказывает, что данные действительно были сериализованы и атомарно записаны на диск.

## Практика

**Упражнение 1 (Базовое). Проверка `defer targetSrv.Close()`.**  
Что случится, если в пакете есть 50 тестов с `httptest.NewServer(...)`, и в каждом забыли написать `defer targetSrv.Close()`?

> [!solution] Показать решение
> Каждый `httptest.NewServer` открывает TCP-сокет в операционной системе и держит горутину-слушатель до окончания работы всего тестового бинарника. В небольшом проекте это пройдёт незаметно (кроме утечки горутин и файловых дескрипторов), а в большом пакете тесты могут упереться в лимит дескрипторов `ulimit -n` или оставлять незакрытые Keep-Alive соединения.

**Упражнение 2 (Практическое). Конкурентный стресс-тест API под `-race`.**  
Напишите тест `TestConcurrentCreateAndList`, который поднимает `apiSrv := httptest.NewServer(srv)` (не забудьте `defer apiSrv.Close()`), запускает 10 горутин через `sync.WaitGroup`, и каждая горутина 5 раз по очереди шлёт `POST /api/v1/bookmarks` и `GET /api/v1/bookmarks` с помощью `apiSrv.Client()`. Прогоните его командой `go test -race`.

> [!solution] Показать решение
> ```go
> func TestConcurrentCreateAndList(t *testing.T) {
> 	store, err := OpenFileStore(filepath.Join(t.TempDir(), "race.json"))
> 	if err != nil {
> 		t.Fatalf("OpenFileStore failed: %v", err)
> 	}
> 	srv := NewServer(store, nil, slog.New(slog.DiscardHandler))
> 	apiSrv := httptest.NewServer(srv)
> 	defer apiSrv.Close()
>
> 	client := apiSrv.Client()
> 	var wg sync.WaitGroup
> 	for g := range 10 {
> 		wg.Add(1)
> 		go func(workerID int) {
> 			defer wg.Done()
> 			for i := range 5 {
> 				body := fmt.Sprintf(`{"title":"Item %d-%d","url":"https://go.dev"}`, workerID, i)
> 				resp, err := client.Post(apiSrv.URL+"/api/v1/bookmarks", "application/json", strings.NewReader(body))
> 				if err != nil {
> 					t.Errorf("POST failed: %v", err)
> 					return
> 				}
> 				resp.Body.Close()
> 				if resp.StatusCode != http.StatusCreated {
> 					t.Errorf("POST status = %d, want 201", resp.StatusCode)
> 				}
> 				listResp, err := client.Get(apiSrv.URL + "/api/v1/bookmarks")
> 				if err != nil {
> 					t.Errorf("GET failed: %v", err)
> 					return
> 				}
> 				listResp.Body.Close()
> 			}
> 		}(g)
> 	}
> 	wg.Wait()
> }
> ```
> Обратите внимание: внутри дочерних горутин используется `t.Errorf`, а не `t.Fatalf` (как вы помните из Модуля 4, вызывать `t.Fatalf` безопасно только в главной горутине теста).

**Упражнение 3 (Со звёздочкой \*). Проверка таймаута чекера без ожидания 5 секунд.**  
Дополните идею `TestBookmarkFlowCheckEndpointOffline`: как за **50 миллисекунд** (не заставляя тест спать все 5 секунд) убедиться, что `LinkChecker` корректно обрабатывает «зависший» внешний сайт и возвращает в JSON `Reachable == false` с непустым `Error`?

> Передайте тестовый `client := targetSrv.Client()` с коротким таймаутом `client.Timeout = 50 * time.Millisecond`, а на стороне `targetMux` для пути `/slow` ждите отмены контекста с небольшим запасом:
> ```go
> targetMux.HandleFunc("/slow", func(w http.ResponseWriter, r *http.Request) {
> 	select {
