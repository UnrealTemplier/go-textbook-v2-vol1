*Как горутины передают друг другу значения и синхронизируются без `time.Sleep`, почему канал закрывает только отправитель и какие три ошибки приводят к панике или вечной блокировке.*

> «Не общайтесь через общую память — вместо этого делитесь памятью через общение.»  
> — Роб Пайк, пословица Go *(цит. по The Go Programming Language)*

В прошлом уроке горутины проверяли ссылки, но не умели вернуть результат в `main`, а мы гадали паузу через `time.Sleep`. Нужен механизм, который одновременно **передаёт значение** между горутинами и **синхронизирует** их. В Go это канал.

## Модель синхронного рандеву

Представьте передачу эстафетной палочки из рук в руки. Первый бегун ждёт второго, если прибежал раньше; второй ждёт первого, если готов раньше. Расходятся они только в момент передачи. Граница аналогии: в Go передаётся типизированная копия значения, и сама передача гарантирует видимость всех записей отправителя до отправки.

Такая «труба без склада» — **небуферизированный канал** (*unbuffered channel*). Его создают через `make`:

```go
ch := make(chan string) // канал для передачи строк
```

Обе операции записываются стрелкой `<-`:

* **отправка** `ch <- "OK"` блокирует отправителя, пока другая горутина не прочитает значение;
* **приём** `msg := <-ch` (или просто `<-ch`) блокирует получателя, пока отправитель не передаст значение.

Небуферизированный канал ничего не хранит — обмен происходит синхронно (*рандеву*). Внутренняя структура канала в рантайме здесь не нужна — подробнее см. Том 5.

## Возвращаем результаты `BookmarkFlow` без `time.Sleep`

Пусть каждая горутина отправляет `CheckResult` в канал, а `main` принимает ровно `len(delays)` ответов:

```go
package main

import (
	"fmt"
	"time"
)

type CheckResult struct {
	URL     string
	Elapsed time.Duration
}

func checkURL(url string, delay time.Duration, out chan<- CheckResult) {
	time.Sleep(delay)
	out <- CheckResult{URL: url, Elapsed: delay}
}

func main() {
	delays := map[string]time.Duration{
		"https://go.dev":      80 * time.Millisecond,
		"https://pkg.go.dev":  120 * time.Millisecond,
		"https://go.dev/blog": 50 * time.Millisecond,
	}

	results := make(chan CheckResult)
	start := time.Now()

	for url, d := range delays {
		go checkURL(url, d, results)
	}

	for range len(delays) {
		res := <-results
		fmt.Printf("OK %s (%v)\n", res.URL, res.Elapsed)
	}
	fmt.Printf("Все проверки готовы за %v\n", time.Since(start).Round(time.Millisecond))
}
```

Вывод:

```text
OK https://go.dev/blog (50ms)
OK https://go.dev (80ms)
OK https://pkg.go.dev (120ms)
Все проверки готовы за 120ms
```

Ни одного `time.Sleep` в `main` нет! Цикл `for range len(delays)` останавливается на `<-results` ровно до прихода очередного ответа и завершается в ту же миллисекунду, когда отработает самая медленная горутина.

## Направленные каналы в параметрах функций

Обратите внимание на тип третьего параметра функции `checkURL`: не `chan CheckResult`, а `chan<- CheckResult`. Это **направленный канал**.

* `chan<- T` — канал **только для отправки** (стрелка указывает *в* канал).
* `<-chan T` — канал **только для чтения** (стрелка указывает *из* канала).

Обычный двунаправленный канал `chan T` автоматически преобразуется в направленный при передаче в функцию, но обратно — никогда. Если внутри `checkURL` кто-то по ошибке попытается прочитать из `out`, компилятор сразу остановит сборку:

```text
invalid operation: cannot receive from send-only channel out (variable of type chan<- CheckResult)
```

Такая аннотация документирует роль функции прямо в её сигнатуре и не даёт случайно перепутать стороны обмена.

## Закрытие канала `close` и обход `for range`

В примере выше `main` заранее знала, сколько элементов придёт (`len(delays)`). Но часто получатель не знает заранее, сколько значений отправит производитель — например, когда одна горутина читает ссылки из файла и отдаёт их по одной.

Чтобы сообщить получателю «данных больше не будет», отправитель вызывает встроенную функцию `close(ch)`. Получатель узнаёт о закрытии двумя способами:

1. **Идиома `comma ok`:**
   ```go
   url, ok := <-urls
   if !ok {
       // канал закрыт, url содержит нулевое значение ""
   }
   ```
2. **Цикл `for v := range ch`:** автоматически читает значения, пока канал открыт, и чисто выходит из цикла, как только канал закрыт.

Посмотрим на короткий конвейер «производитель → потребитель»:

```go
package main

import "fmt"

func emitBookmarks(list []string) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out) // закрывает только отправитель
		for _, url := range list {
			out <- url
		}
	}()
	return out
}

func main() {
	stream := emitBookmarks([]string{"https://go.dev", "https://pkg.go.dev"})
	for url := range stream {
		fmt.Println("Получена ссылка:", url)
	}
}
```

Здесь действует железное правило: **канал закрывает только отправитель**, никогда — получатель. И в отличие от файлов, закрывать канал ради памяти не нужно — сборщик мусора сам соберёт неиспользуемый канал; вызывайте `close`, только чтобы сообщить о конце потока.

## Три опасных состояния канала

Неверная операция с каналом приводит к вечной блокировке или панике:

| Операция | Открытый канал | Закрытый канал | `nil`-канал (`var ch chan T`) |
|---|---|---|---|
| **Отправка `ch <- v`** | Ждёт получателя | **Паника:** `send on closed channel` | **Блокируется навсегда** |
| **Приём `<-ch`** | Ждёт отправителя | Сразу нулевое значение и `ok == false` | **Блокируется навсегда** |
| **Закрытие `close(ch)`** | Закрывает канал | **Паника:** `close of closed channel` | **Паника:** `close of nil channel` |

Если все горутины зависли в ожидании, рантайм остановит процесс:

```text
fatal error: all goroutines are asleep - deadlock!
```

Обратите внимание: чтение из закрытого канала безопасно, а панику вызывают отправка в закрытый канал и повторный `close`.

> [!check] Проверь понимание
> Что произойдёт, если передать канал `in <-chan int` в функцию и вызвать внутри неё `close(in)`?
>
> Программа даже не скомпилируется (`invalid operation: cannot close receive-only channel in`). Запрет закрывать канал со стороны чтения встроен прямо в систему типов Go.

## Практика

**Упражнение 1 (Базовое). Что сломается?**  
Почему этот короткий код падает с `fatal error: all goroutines are asleep - deadlock!`? Назовите причину и почините программу с помощью горутины.

```go
package main

import "fmt"

func main() {
	ch := make(chan string)
	ch <- "https://go.dev"
	fmt.Println(<-ch)
}
```

> [!solution] Показать решение
> Канал `ch` небуферизированный. Строка `ch <- "https://go.dev"` блокирует горутину `main` до тех пор, пока кто-нибудь не прочитает из `ch`. Но чтение `<-ch` стоит строкой ниже в **той же самой** горутине — до него управление никогда не дойдёт.
>
> Исправление — вынести отправку в отдельную горутину:
> ```go
> package main
>
> import "fmt"
>
> func main() {
> 	ch := make(chan string)
> 	go func() {
> 		ch <- "https://go.dev"
> 	}()
> 	fmt.Println(<-ch)
> }
> ```

**Упражнение 2 (Практическое). Двухступенчатый конвейер ссылок.**  
Напишите две функции с направленными каналами:
1. `emitURLs(urls []string) <-chan string` — отправляет все адреса в канал и закрывает его.
2. `onlyHTTPS(in <-chan string) <-chan string` — читает адреса из `in`, пересылает дальше только начинающиеся с `"https://"` и закрывает выходной канал, когда `in` исчерпан.

Прочитайте итог через `for range` в `main`.

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"fmt"
> 	"strings"
> )
>
> func emitURLs(urls []string) <-chan string {
> 	out := make(chan string)
> 	go func() {
> 		defer close(out)
> 		for _, u := range urls {
> 			out <- u
> 		}
> 	}()
> 	return out
> }
>
> func onlyHTTPS(in <-chan string) <-chan string {
> 	out := make(chan string)
> 	go func() {
> 		defer close(out)
> 		for u := range in {
> 			if strings.HasPrefix(u, "https://") {
> 				out <- u
> 			}
> 		}
> 	}()
> 	return out
> }
>
> func main() {
> 	raw := []string{"http://old.example", "https://go.dev", "https://pkg.go.dev", "ftp://files.local"}
> 	for u := range onlyHTTPS(emitURLs(raw)) {
> 		fmt.Println("HTTPS:", u)
> 	}
> }
> ```
> Каждая стадия конвейера владеет своим выходным каналом и гарантированно закрывает его через `defer close(out)`, поэтому цепочка завершается чисто без утечек и дедлоков.

**Упражнение 3 (Со звёздочкой \*). Двойное чтение закрытого канала.**  
Проследите вывод программы ниже. Сколько чисел она напечатает и какими будут значения `v` и `ok` на каждой итерации?

```go
package main

import "fmt"

func main() {
	ch := make(chan int)
	go func() {
		ch <- 200
		close(ch)
	}()

	for i := range 3 {
		v, ok := <-ch
		fmt.Printf("шаг %d: v=%d ok=%t\n", i, v, ok)
	}
}
```

> [!solution] Показать решение
> Вывод программы:
> ```text
> шаг 0: v=200 ok=true
> шаг 1: v=0 ok=false
> шаг 2: v=0 ok=false
> ```
> На шаге 0 приходит реальное значение `200`. Затем отправитель закрывает канал, и все последующие чтения мгновенно возвращают нулевое значение типа `int` (`0`) и `ok = false` без блокировки и без паники.
