*Учимся привязывать HTTP-методы к маршрутам, извлекать параметры пути через `r.PathValue` и разбираться в правилах приоритета `http.ServeMux` в Go 1.22+.*

До выхода Go 1.22 стандартный `http.ServeMux` умел сопоставлять только путь, полностью игнорируя HTTP-метод и переменные сегменты вроде `/bookmarks/42`. Разработчикам приходилось внутри каждого обработчика писать `switch r.Method` и резать `r.URL.Path` через `strings.TrimPrefix` — либо тянуть сторонний роутер ради десятка маршрутов. Начиная с Go 1.22, расширенный синтаксис шаблонов встроен прямо в `http.ServeMux`.

## Синтаксис шаблонов маршрута

В Go 1.22+ строка шаблона в `mux.HandleFunc` и `mux.Handle` состоит из трёх необязательных или обязательных частей: `[МЕТОД ][ХОСТ]/ПУТЬ`:

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /healthz", s.handleHealth)
mux.HandleFunc("GET /api/v1/bookmarks", s.handleList)
mux.HandleFunc("POST /api/v1/bookmarks", s.handleCreate)
mux.HandleFunc("GET /api/v1/bookmarks/{id}", s.handleGet)
mux.HandleFunc("PUT /api/v1/bookmarks/{id}", s.handleUpdate)
mux.HandleFunc("DELETE /api/v1/bookmarks/{id}", s.handleDelete)
mux.HandleFunc("POST /api/v1/bookmarks/check", s.handleCheckAll)
```

Именно эти семь строк запускают маршрутизацию в `project/final/server.go`. Посмотрим на правила, которые работают за ними:

- **HTTP-метод перед пробелом.** Запись `"POST /api/v1/bookmarks"` сработает только на метод `POST`. Если не указать метод вообще (просто `"/healthz"`), шаблон примет любой метод. Обратите внимание: регистрация `"GET /path"` автоматически обрабатывает также метод `HEAD` (без тела ответа).
- **Именованный сегмент `{id}`.** Фигурные скобки внутри слэшей совпадают ровно с одним сегментом пути до следующего `/`. Значение извлекается в обработчике вызовом `r.PathValue("id")`.
- **Хвост с многоточием `{rest...}`.** Запись `"/files/{path...}"` захватывает весь оставшийся путь целиком, включая слэши (например, `"docs/2026/readme.md"`).
- **Точный конец `{$}`.** В старых версиях Go шаблон `"/"` был «ловушкой для всего», перехватывая любые несуществующие пути. Шаблон `"GET /{$}"` срабатывает **только** на точный корень `"/"`, не забирая `/unknown`.

## Автоматические `404` и `405`

Раньше при неверном HTTP-методе стандартный сервер молча отвечал `404 Not Found` или требовал ручных проверок в каждом обработчике. Теперь `http.ServeMux` сам различает две ситуации:

1. Путь не совпал ни с одним шаблоном → сервер отдаёт `404 page not found`.
2. Путь совпал с одним из шаблонов, но для другого метода (например, пришёл `PATCH /api/v1/bookmarks/1`) → мультиплексор отвечает статусом **`405 Method Not Allowed`** и сам добавляет заголовок `Allow: DELETE, GET, HEAD, PUT`.

Нам не нужно тратить ни строчки кода на проверку разрешённых методов внутри обработчиков.

## Правила приоритета и конфликт маршрутов

В списке маршрутов `BookmarkFlow` есть два похожих шаблона:

```text
GET  /api/v1/bookmarks/{id}
POST /api/v1/bookmarks/check
```

А что если добавить `"GET /api/v1/bookmarks/export"` рядом с `"GET /api/v1/bookmarks/{id}"`? Порядок регистрации в `ServeMux` значения не имеет — работает правило **«более конкретный шаблон побеждает»**:

- статический сегмент `/export` конкретнее подстановки `/{id}`;
- шаблон с методом (`"GET /items"`) конкретнее шаблона без метода (`"/items"`);
- точный сегмент `{id}` конкретнее хвоста `{rest...}`.

Поэтому запрос `GET /api/v1/bookmarks/export` попадёт в обработчик экспорта, а `GET /api/v1/bookmarks/42` — в `handleGet` с `r.PathValue("id") == "42"`.

Но что случится, если зарегистрировать два шаблона, ни один из которых не конкретнее другого? Например:

```go
package main

import (
	"fmt"
	"net/http"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /items/{id}/tags", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, r.PathValue("id"))
	})
	// Пересекаются при запросе GET /items/a/b, но ни один не конкретнее другого!
	mux.HandleFunc("GET /items/a/{section}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, r.PathValue("section"))
	})
}
```

При запуске этой программы `http.ServeMux` откажется гадать и сразу завершится паникой при регистрации второго маршрута:

```text
panic: pattern "GET /items/a/{section}" (registered at ...) conflicts with pattern "GET /items/{id}/tags" (registered at ...):
GET /items/a/{section} and GET /items/{id}/tags both match some paths, like "/items/a/tags".
But neither is more specific than the other.
GET /items/a/{section} matches "/items/a/x", but GET /items/{id}/tags doesn't.
GET /items/{id}/tags matches "/items/x/tags", but GET /items/a/{section} doesn't.
```

Эта паника — не ошибка Go, а защита от двусмысленных маршрутов на этапе старта приложения: вы узнаёте о конфликте в первые миллисекунды запуска, а не от пользователей в бою.

## Подводный камень: `{id}` принимает любые непустые строки

Шаблон `"/api/v1/bookmarks/{id}"` совпадает не только с числами, но и с текстом вроде `/api/v1/bookmarks/abc` или `/api/v1/bookmarks/-5`. Встроенных регулярных выражений внутри `{...}` нет. Проверять, что `id` — именно положительное целое число, обязан сам обработчик (в `BookmarkFlow` этим занимается `parseIDParam`).

> [!check] Проверь понимание
> В `BookmarkFlow` зарегистрирован маршрут `"GET /api/v1/bookmarks/{id}"`, но нет отдельного маршрута для метода `HEAD`. Какой статус вернёт сервер на запрос `HEAD /api/v1/bookmarks/1`?
>
> `200 OK` (если закладка 1 существует) с пустым телом: в Go 1.22+ регистрация метода `GET` автоматически разрешает и `HEAD`.

## Практика

**Упражнение 1 (Базовое). Определение победителя.**  
В `mux` в указанном порядке зарегистрированы три маршрута:
1. `"/files/{path...}"`
2. `"GET /files/{name}"`
3. `"GET /files/latest"`

Какой обработчик сработает для каждого из запросов: (а) `GET /files/latest`, (б) `POST /files/latest`, (в) `GET /files/2026/log.txt`?

> [!solution] Показать решение
> - (а) Сработает **3** (`"GET /files/latest"`): он совпадает точно по методу и статическому сегменту, поэтому конкретнее остальных.
> - (б) Сработает **1** (`"/files/{path...}"`): маршрут без метода принимает `POST`, тогда как маршруты 2 и 3 привязаны только к `GET`.
> - (в) Сработает **1** (`"/files/{path...}"`): в пути два сегмента после `/files/`, поэтому шаблон `{name}` с одним сегментом не подойдёт.

**Упражнение 2 (Практическое). Мини-сервер с `PathValue` и точным корнем.**  
Напишите программу `main`, которая регистрирует на новом `http.NewServeMux()`:
- `GET /{$}` — отдаёт `"BookmarkFlow API\n"`;
- `GET /api/v1/bookmarks/{id}` — читает `r.PathValue("id")`, проверяет через `strconv.Atoi` и при нечисловом или неположительном `id` возвращает статус `400 Bad Request`, а иначе печатает `Bookmark #<id>\n`.

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"fmt"
> 	"log"
> 	"net/http"
> 	"strconv"
> )
>
> func main() {
> 	mux := http.NewServeMux()
> 	mux.HandleFunc("GET /{$}", func(w http.ResponseWriter, _ *http.Request) {
> 		fmt.Fprintln(w, "BookmarkFlow API")
> 	})
> 	mux.HandleFunc("GET /api/v1/bookmarks/{id}", func(w http.ResponseWriter, r *http.Request) {
> 		id, err := strconv.Atoi(r.PathValue("id"))
> 		if err != nil || id <= 0 {
> 			http.Error(w, "некорректный id", http.StatusBadRequest)
> 			return
> 		}
> 		fmt.Fprintf(w, "Bookmark #%d\n", id)
> 	})
> 	log.Fatal(http.ListenAndServe(":8080", mux))
> }
> ```
> Точный корень `GET /{$}` не перехватывает ошибки пути: на запрос `GET /unknown` сервер честно вернёт `404`.

**Упражнение 3 (Со звёздочкой \*). Скрытый конфликт при регистрации.**  
Почему следующая пара шаблонов вызовет панику при запуске, и как разрешить конфликт, если вам действительно нужны оба пути?
```go
mux.HandleFunc("GET /users/{id}/profile", h1)
mux.HandleFunc("/users/me/{tab}", h2)
```

> [!solution] Показать решение
> При запросе `GET /users/me/profile` подходят оба шаблона. Первый конкретнее в методе (`GET` против любого метода) и последнем сегменте (`profile` против `{tab}`), а второй конкретнее во втором сегменте (`me` против `{id}`). Ни один из шаблонов не доминирует полностью, поэтому `ServeMux` паникует.
>
> Разрешить конфликт можно, добавив явный префикс или уточнив более частный маршрут с указанием метода и точного пути: например, вынести системный маршрут на `"GET /users/me/{tab}"` и добавить явный `"GET /users/me/profile"`, который перекрывает оба спорных шаблона, либо развести пути (`/users/{id}/...` и `/me/{tab}`).
