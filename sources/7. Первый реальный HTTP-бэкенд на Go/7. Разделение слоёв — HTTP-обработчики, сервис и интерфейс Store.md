*Учимся разделять HTTP-транспорт, доменные правила и хранилище через интерфейс `Store`, а также отображать ошибки домена в HTTP-статусы без привязки к деталям хранения.*

> «Новым типам проще удовлетворять маленьким интерфейсам. Хорошее практическое правило проектирования интерфейсов: требуйте только то, что вам действительно нужно.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

Соблазн начинающего бэкенд-разработчика прост: написать всю логику прямо внутри обработчика. Открыл `os.ReadFile` в `handleCreate`, распарсил JSON, проверил заголовок, добавил элемент, записал обратно на диск и отдал ответ. В первый день всё работает. На пятый день выясняется, что для теста обработчика приходится создавать реальные файлы, а при переходе на базу данных в Томе 2 придётся переписать каждый HTTP-обработчик с нуля.

Чтобы этого не случилось, код делят на слои с жёсткими границами.

## Три зоны ответственности и честный размер проекта

В HTTP-сервисе обычно выделяют три уровня:

1. **Транспортный слой (`Server` в `server.go`)** — говорит на языке HTTP: читает `r.PathValue`, декодирует JSON-тело, переводит ошибки домена в коды `404`/`422`/`500` и сериализует ответ. Он не должен знать про `os.Rename` и форматы хранения.
2. **Доменные правила и сервис** — проверяет бизнес-ограничения (длина `title`, допустимые схемы URL, нормализация тегов) и координирует сценарии.
3. **Слой хранения (`Store` в `store.go`)** — отвечает за сохранение, поиск и синхронизацию доступа к закладкам. Он не должен импортировать пакет `net/http` и знать про коды `422` или `404`.

Посмотрите, как прагматично это сделано в `project/final/`. Доменные правила у нас пока компактны — это функция `ValidateInput` и сентинел-ошибки `ErrNotFound` и `ErrValidation`. Заводить лишний промежуточный тип `BookmarkService`, который просто перекладывает каждый вызов из `Server` в `Store` без дополнительной логики, не нужно: это усложнило бы код ради пустой прослойки. Зато как только появятся составные сценарии (например, «при создании закладки сразу проверить доступность URL и записать в аудит»), между `Server` и `Store` легко встанет отдельный слой сервиса.

## Контракт `Store` и правило инверсии зависимостей

Взгляните на интерфейс хранилища из `project/final/store.go`:

```go
// Store описывает контракт хранилища закладок.
// В Томе 2 эту же границу легко переключить с JSON-файла на базу данных без правок HTTP-слоя.
type Store interface {
	Create(in CreateInput) (Bookmark, error)
	Get(id int) (Bookmark, error)
	List(filter ListFilter) ([]Bookmark, error)
	Update(id int, in UpdateInput) (Bookmark, error)
	Delete(id int) error
}
```

Ключевой момент — **что от чего зависит**. Структура `Server` хранит поле `store Store` (интерфейс), а не `*FileStore` (конкретную реализацию):

```text
Server ──(зависит от)──▶ Store (интерфейс) ◀──(реализует)── FileStore (диск)
                                           ◀──(реализует)── MemoryStore (тесты)
                                           ◀──(реализует)── База данных (Том 2)
```

Ни один обработчик в `server.go` даже не догадывается о существовании `FileStore`. Только функция `main()` на самом верхнем уровне программы выступает «сборщиком»: открывает `FileStore` и передаёт его в `NewServer(store, checker, logger)`.

В Модуле 3 (шаг 4) мы уже делали два варианта хранилища — `MemoryStore` и `FileStore`. В тестах HTTP-слоя это даёт огромную свободу: можно подсунуть в `NewServer` легковесную заглушку в памяти или имитировать ошибку диска в нужный момент, чтобы проверить возврат `500 Internal Server Error`.

## Перевод ошибок домена в HTTP-статусы

Если `Store` вернёт ошибку, он говорит в терминах домена: «закладка не найдена» (`ErrNotFound`) или «ошибка валидации» (`ErrValidation`). Он никогда не возвращает число `404` или `422` — иначе хранилище «протечёт» в HTTP и его станет неудобно вызывать из CLI или фоновых задач.

Обратный перевод выполняет ровно одна функция в `project/final/server.go`:

```go
func (s *Server) writeStoreError(w http.ResponseWriter, err error) {
	switch {
	case errors.Is(err, ErrValidation):
		writeJSONError(w, http.StatusUnprocessableEntity, err.Error())
	case errors.Is(err, ErrNotFound):
		writeJSONError(w, http.StatusNotFound, err.Error())
	default:
		s.logger.Error("store error", slog.Any("error", err))
		writeJSONError(w, http.StatusInternalServerError, "внутренняя ошибка хранилища")
	}
}
```

Обратите внимание на последнюю ветку `default`. Если при записи JSON на диск закончилось место или пропали права доступа, детальную системную ошибку (`err`) мы пишем **в серверный лог** для инженера, а наружу клиенту отдаём нейтральное сообщение `"внутренняя ошибка хранилища"`. Показывать внешнему пользователю внутренние пути каталогов ОС вроде `/var/lib/bookmarkflow/...: permission denied` небезопасно и бесполезно.

## Подводный камень: потерянная обёртка `%w`

Когда вы реализуете интерфейс `Store` в новом типе (например, в `MemoryStore` или будущем хранилище Тома 2), ошибка обязана оборачивать `ErrNotFound` или `ErrValidation` через `%w`, а не `%v`:

```go
return Bookmark{}, fmt.Errorf("%w: #%d", ErrNotFound, id) // правильно: errors.Is вернёт true
// fmt.Errorf("%v: #%d", ErrNotFound, id)               // ЛОВУШКА: errors.Is вернёт false, клиент получит 500!
```

Если случайно написать `%v`, цепочка ошибок порвётся, и вместо `404 Not Found` сервер начнёт отвечать клиенту `500 Internal Server Error`.

> [!check] Проверь понимание
> В `NewServer` первым параметром принимается `store Store`. Можно ли передать туда значение `*FileStore`, если `*FileStore` никак явно не упоминает слово `Store` в своём объявлении?
>
> Да. В Go интерфейсы реализуются **неявно** (*duck typing* на этапе компиляции): раз у `*FileStore` есть все пять методов с точными сигнатурами из `Store`, компилятор примет его без дополнительных объявлений.
