*Почему программа способна вести десятки сетевых задач на одном ядре процессора и в чём разница между структурой программы и числом ядер.*

В `BookmarkFlow` накопилось 50 закладок, и нужно проверить, живы ли все ссылки. Одна проверка занимает 200 мс: 2 мс работы процессора и 198 мс ожидания ответа по сети.

В обычном цикле `for` проверка 50 адресов растянется на 10 секунд. Процессор реально поработает всего 100 мс, а остальные 9,9 секунды будет простаивать.

## Одно ядро, но несколько дел в работе

Представьте повара с одной парой рук: нужно вскипятить воду (5 мин), поджарить тост (2 мин) и нарезать салат (3 мин). Последовательный повар стоит у чайника, затем ждёт тостер и лишь потом берётся за нож — 10 минут. Конкурентный ставит чайник, включает тостер и в паузе режет салат — завтрак готов за 5 минут, хотя руки по-прежнему одни.

Граница аналогии: человек переключается за секунды, а программа на Go — за доли микросекунды, и ОС сама будит её при приходе сетевых байтов.

Переведём картину на временную шкалу для четырёх ссылок (`A`, `B`, `C`, `D`), где `#` — 10 мс работы CPU, а `.....` — 90 мс ожидания сети:

```text
1. Последовательно на 1 ядре (400 мс):
Ядро 1: |#A.........|#B.........|#C.........|#D.........|
        0          100         200         300         400 мс

2. Конкурентно на 1 ядре (130 мс):
Ядро 1: |#A|#B|#C|#D|.......(простой CPU).......|готовы A,B,C,D|
        0  10 20 30 40                          100..130 мс

3. Конкурентно и параллельно на 4 ядрах (100 мс):
Ядро 1: |#A.........|
Ядро 2: |#B.........|
Ядро 3: |#C.........|
Ядро 4: |#D.........|
        0          100 мс
```

Конкурентная структура **на одном ядре** сократила время с 400 до 130 мс — больше чем втрое. Ещё три ядра сэкономили лишь 30 мс.

## Конкурентность и параллелизм: точное различие

В русском языке оба понятия часто сливают в «параллельность». Разделим их строго:

* **Конкурентность** (*concurrency*) — способ **устроить программу** так, чтобы она вела несколько независимых дел, переключаясь между ними. Это свойство архитектуры кода.
* **Параллелизм** (*parallelism*) — **физически одновременное** выполнение нескольких вычислений на нескольких ядрах CPU. Это свойство исполнения на железе.

Один из создателей Go Роб Пайк в докладе *Concurrency is not Parallelism* (2012) дал чеканную формулу: **конкурентность — это работа со множеством дел сразу (*dealing with lots of things at once*), а параллелизм — выполнение множества дел одновременно (*doing lots of things at once*)**.

Конкурентность не гарантирует параллелизма, но **делает его возможным**. Конкурентную программу рантайм Go выполнит с переключениями на одном ядре и автоматически разложит по 4 или 16 ядрам без правок кода. Последовательный цикл останется одноядерным на любом железе.

## Задачи ввода-вывода против вычислений CPU

Выигрыш зависит от того, во что упирается задача:

| Характер задачи | Где уходит время | Конкурентность (1 ядро) | Параллелизм (4 ядра) |
|---|---|---|---|
| **Ввод-вывод (I/O-bound):** сеть, диск, таймеры | 95–99% в ожидании | Огромное ускорение — ядро запускает новые запросы в паузах | Небольшая доп. выгода |
| **Вычисления (CPU-bound):** сжатие, видео, математика | Почти 100% в CPU | Ускорения нет | Ускорение до ~4 раз |

Сетевые утилиты вроде чекера закладок почти всегда упираются во ввод-вывод. Поэтому переход к конкурентности радикально ускоряет их даже на скромной одноядерной машине.

## Последовательная база для сравнения

Зафиксируем отправную точку на Go 1.24: `checkBookmark` имитирует ожидание сети через `time.Sleep`, а `main` обходит список подряд:

```go
package main

import (
	"fmt"
	"time"
)

type BookmarkCheck struct {
	URL   string
	Delay time.Duration
}

func checkBookmark(item BookmarkCheck) string {
	time.Sleep(item.Delay) // имитация ожидания ответа по сети
	return fmt.Sprintf("OK %s (%v)", item.URL, item.Delay)
}

func main() {
	items := []BookmarkCheck{
		{URL: "https://go.dev", Delay: 80 * time.Millisecond},
		{URL: "https://pkg.go.dev", Delay: 120 * time.Millisecond},
		{URL: "https://go.dev/blog", Delay: 60 * time.Millisecond},
	}

	start := time.Now()
	for _, item := range items {
		fmt.Println(checkBookmark(item))
	}
	fmt.Printf("Всего прошло: %v\n", time.Since(start).Round(time.Millisecond))
}
```

Запустим код:

```text
OK https://go.dev (80ms)
OK https://pkg.go.dev (120ms)
OK https://go.dev/blog (60ms)
Всего прошло: 260ms
```

Итоговое время равно **сумме** всех задержек: $80 + 120 + 60 = 260$ мс. Если бы все три проверки стартовали конкурентно, общее время упёрлось бы в **максимум** — около 120 мс. На списке из 50 ссылок разрыв вырастет с 2,2 раза до десятков раз.

## Две частые ловушки в рассуждениях

Первая ошибка — ждать ускорения от конкурентности там, где процессор уже загружен на 100% вычислениями на одном ядре. Если одна задача считает контрольные суммы 400 мс, разбив её на четыре куска по 100 мс на одном ядре, вы всё равно потратите 400 мс плюс крошечные накладные расходы на переключения.

Вторая ошибка — считать, что многоядерный процессор сам ускорит любую программу. Ядра не умеют «распилить» обычный последовательный цикл `for` пополам. Программист обязан сначала выразить независимость задач в структуре кода.

> [!check] Проверь понимание
> На сервере установлено 8 ядер CPU. Программа проверяет 30 ссылок в обычном цикле `for` без конкурентных конструкций. Сколько ядер одновременно занято этой программой и станет ли она быстрее, если перенести её на машину с 32 ядрами?
>
> Одновременно работает максимум 1 ядро: каждая следующая проверка ждёт завершения предыдущей. Переезд на 32 ядра не ускорит такой цикл ни на миллисекунду.

## Практика

**Упражнение 1 (Базовое). Оцените время выполнения.**  
Нужно выполнить 4 независимые сетевые проверки. Каждая тратит 5 мс работы CPU и 95 мс ожидания ответа по сети. Прикиньте итоговое время выполнения в трёх режимах: (а) последовательно на 1 ядре; (б) конкурентно на 1 ядре; (в) конкурентно и параллельно на 4 ядрах.

> [!solution] Показать решение
> * **(а) Последовательно на 1 ядре:** $4 \times (5 + 95) = 400$ мс. Каждая задача стартует только после полного завершения предыдущей.
> * **(б) Конкурентно на 1 ядре:** около **115 мс**. Ядро тратит первые $4 \times 5 = 20$ мс на запуск всех четырёх запросов; пока они ждут сеть, процессор свободен, и последний ответ приходит через 95 мс после четвёртого старта ($20 + 95 = 115$ мс).
> * **(в) Параллельно на 4 ядрах:** ровно **100 мс**. Все четыре ядра стартуют одновременно, тратят по 5 мс и ждут 95 мс.

**Упражнение 2 (Практическое). Потенциал ускорения в коде.**  
Доработайте пример `BookmarkCheck` из урока: напишите функцию `estimateTimes(items []BookmarkCheck) (seq, idealConcurrent time.Duration)`, которая без запуска `time.Sleep` вычисляет суммарное время последовательного прохода и идеальное время конкурентного запуска (максимум среди `Delay`). Выведите оба числа и во сколько раз конкурентный вариант быстрее.

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"fmt"
> 	"time"
> )
>
> type BookmarkCheck struct {
> 	URL   string
> 	Delay time.Duration
> }
>
> func estimateTimes(items []BookmarkCheck) (seq, idealConcurrent time.Duration) {
> 	for _, item := range items {
> 		seq += item.Delay
> 		if item.Delay > idealConcurrent {
> 			idealConcurrent = item.Delay
> 		}
> 	}
> 	return seq, idealConcurrent
> }
>
> func main() {
> 	items := []BookmarkCheck{
> 		{URL: "https://go.dev", Delay: 80 * time.Millisecond},
> 		{URL: "https://pkg.go.dev", Delay: 120 * time.Millisecond},
> 		{URL: "https://go.dev/blog", Delay: 60 * time.Millisecond},
> 		{URL: "https://example.org", Delay: 100 * time.Millisecond},
> 	}
> 	seq, conc := estimateTimes(items)
> 	fmt.Printf("Последовательно: %v, конкурентно: %v (ускорение в %.1f раз)\n",
> 		seq, conc, float64(seq)/float64(conc))
> }
> ```
> Для чисто сетевого ожидания теоретический предел конкурентного запуска упирается в самый медленный запрос, а не в сумму всех задержек.

**Упражнение 3 (Со звёздочкой \*). Предел параллелизма для CPU-задач.**  
У вас есть ровно 4 независимые задачи, каждая требует 100 мс чистой работы процессора без ожидания сети и диска. Сравните время выполнения на 1, 2, 4 и 8 ядрах при конкурентной структуре программы. Почему 8 ядер не обгонят 4?

> [!solution] Показать решение
> * **1 ядро:** 400 мс (CPU не простаивает, переключения не уменьшают объём вычислений).
> * **2 ядра:** 200 мс (по две задачи на ядро).
> * **4 ядра:** 100 мс (по одной задаче на ядро).
> * **8 ядер:** всё те же **100 мс**.
>
> Свободные 4 ядра простаивают, потому что программа предлагает только 4 независимые единицы работы. Параллелизм ограничен минимумом из двух величин: числа доступных ядер и числа независимых задач.

Конкурентность — это архитектура программы, а параллелизм — подарок от железа, который становится доступен благодаря этой архитектуре. Как именно запустить несколько независимых функций в Go без тяжёлых системных потоков, разберём в уроке [[2. Горутины — запуск go f() и чем они отличаются от потоков ОС]].
