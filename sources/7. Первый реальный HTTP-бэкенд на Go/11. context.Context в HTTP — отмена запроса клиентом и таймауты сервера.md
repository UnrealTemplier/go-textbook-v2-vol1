*Разбираем жизненный цикл `r.Context()` при отмене запроса клиентом и настраиваем четыре защитных таймаута `http.Server` против подвисших соединений.*

Представьте пользователя, который нажал кнопку «Проверить все 500 закладок», не дождался ответа и закрыл вкладку браузера. Если обработчик не следит за состоянием соединения, сервер продолжит впустую стучаться по сотням адресов ещё полминуты — для ответа, который уже некому читать. Другая сторона проблемы — «ленивый» клиент, открывший TCP-соединение и отправляющий по одному байту заголовка раз в минуту: без жёстких таймаутов пара сотен таких клиентов быстро забьёт свободные файловые дескрипторы процесса.

В Go обе задачи решаются двумя простыми инструментами стандартной библиотеки: `r.Context()` внутри обработчика и поля таймаутов в структуре `http.Server`.

## Как работает `r.Context()` в `net/http`

В [[9. Отмена и дедлайны — context.Context на практике]] мы научились создавать контекст с отменой и таймаутом вручную. Внутри HTTP-сервера `net/http` делает это за вас для каждого входящего запроса:

- `r.Context()` **отменяется автоматически** в трёх случаях: когда клиент оборвал соединение, когда истёк таймаут запроса или когда метод `ServeHTTP` завершил работу.
- Когда обработчик передаёт `r.Context()` дальше — в `LinkChecker.CheckAll(r.Context(), items)` или в `http.NewRequestWithContext(ctx, ...)` — любая долгая операция узнаёт об уходе клиента через канал `<-ctx.Done()` и мгновенно сворачивает работу.

Проверим отмену на минимальном 20-строчном сервере, который «тяжело работает» 5 секунд, но моментально останавливается при разрыве соединения:

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"time"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /slow", func(w http.ResponseWriter, r *http.Request) {
		log.Println("старт долгой задачи")
		select {
		case <-time.After(5 * time.Second):
			fmt.Fprintln(w, "готово")
			log.Println("задача завершена успешно")
		case <-r.Context().Done():
			// Клиент отключился (Ctrl+C в curl) — работа прервана.
			log.Println("клиент ушёл:", r.Context().Err())
		}
	})

	log.Fatal(http.ListenAndServe("127.0.0.1:8080", mux))
}
```

Если запустить этот пример, сделать `curl http://127.0.0.1:8080/slow` и через секунду нажать `Ctrl+C`, сервер тут же напечатает `клиент ушёл: context canceled`, не дожидаясь оставшихся четырёх секунд.

## Четыре таймаута `http.Server`: защита от медленных клиентов

Функция `http.ListenAndServe(addr, handler)` удобна для пятистрочных примеров, но опасна для реального сервиса: внутри она создаёт `http.Server` с **нулевыми таймаутами** (бесконечное ожидание). Медленный или зависший клиент может держать соединение открытым бесконечно.

Поэтому в `project/final/cmd/bookmarkflow/main.go` мы конструируем `http.Server` явно с четырьмя временными границами:

```go
	srv := &http.Server{
		Addr:              cfg.Addr,
		Handler:           api,
		ReadHeaderTimeout: 5 * time.Second,
		ReadTimeout:       10 * time.Second,
		WriteTimeout:      15 * time.Second,
		IdleTimeout:       60 * time.Second,
	}
```

Посмотрим на временную шкалу одного HTTP/1.1 Keep-Alive соединения, чтобы точно различать, что именно ограничивает каждый параметр:

```text
[TCP-приём]──ReadHeaderTimeout(5s)──▶[Заголовки прочитаны]──▶[Тело]──▶[ServeHTTP + Запись]──▶[Пауза Keep-Alive]
|<─────────── ReadTimeout (10s) ──────────────────────────>|                                 |<─IdleTimeout(60s)─>|
             |<─────────────── WriteTimeout (15s) ──────────────────────────>|
```

1. **`ReadHeaderTimeout: 5s`** — сколько секунд сервер ждёт чтения только заголовков запроса. Главный щит от атаки «медленных заголовков» (*Slowloris*).
2. **`ReadTimeout: 10s`** — общее время от приёма запроса до полного чтения его заголовков и тела `r.Body`.
3. **`WriteTimeout: 15s`** — ограничение от конца чтения заголовков запроса до полной отправки ответа клиенту. Включает в себя время работы вашего обработчика. Если ваш `POST /api/v1/bookmarks/check` работает 20 секунд при `WriteTimeout: 15s`, сервер разорвёт запись ответа, не дождавшись окончания.
4. **`IdleTimeout: 60s`** — сколько простаивает открытое Keep-Alive соединение в ожидании *следующего* запроса от того же клиента, прежде чем сервер вежливо закроет сокет.

## Контекст с дополнительным таймаутом на операцию

Порой серверу нужно ограничить отдельную операцию жёстче, чем весь `WriteTimeout`. Например, если обработчик делает внешний сетевой запрос, разумно обернуть `r.Context()` через `context.WithTimeout`:

```go
ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
defer cancel()
```

У такого дочернего контекста сработает **любое из двух событий, которое наступит раньше**: либо истекут 3 секунды, либо клиент разорвёт соединение. Не забывайте про `defer cancel()`, чтобы внутренний таймер освободился сразу после возврата из обработчика, не дожидаясь всех трёх секунд.

## Подводный камень: фоновая горутина и `r.Context()`

Что будет, если обработчик отправит ответ `202 Accepted`, а перед этим запустит фоновую горутину `go sendAudit(r.Context())`? Как только обработчик вернёт управление и сервер закончит писать ответ, `net/http` **отменит `r.Context()`**! Ваша фоновая горутина мгновенно получит `context canceled` и оборвёт работу. Для задач, которые обязаны пережить завершение HTTP-запроса, в Go используют `context.WithoutCancel(r.Context())` (появился в Go 1.21) или отдельный контекст жизненного цикла сервера, а не исходный `r.Context()`.

> [!check] Проверь понимание
> В `BookmarkFlow` настроены `ReadTimeout: 10s` и `WriteTimeout: 15s`. Пользователь вызывает `POST /api/v1/bookmarks/check` для 50 сайтов, и каждый проверяется с клиентским таймаутом 5 секунд — суммарно проверка занимает 18 секунд. Что произойдёт на 15-й секунде?
>
> Сработает `WriteTimeout` сервера: соединение закроется со стороны сервера до того, как `handleCheckAll` запишет JSON-ответ, а сам запрос не вернёт корректный `200 OK`. Именно поэтому на долгих проверках стоит ставить внутренний таймаут `context.WithTimeout` короче `WriteTimeout` (например, `12s`) либо ограничивать размер списка.

## Практика

**Упражнение 1 (Базовое). Выбор таймаута `http.Server`.**  
Какое из четырёх полей `http.Server` (`ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`) отвечает за каждую из следующих ситуаций?
1. Браузер держит открытое Keep-Alive соединение без новых запросов больше минуты.
2. Клиент прислал стартовую строку `GET / HTTP/1.1` и замолчал, не отправляя пустую строку конца заголовков.
3. Клиент с очень медленным интернетом загружает JSON-тело размером 900 КБ дольше 12 секунд.

> [!solution] Показать решение
> 1. **`IdleTimeout`** (время простоя между запросами в Keep-Alive).
> 2. **`ReadHeaderTimeout`** (максимальное время чтения заголовков).
> 3. **`ReadTimeout`** (время на чтение заголовков и тела запроса).

**Упражнение 2 (Практическое). Защита тяжёлого эндпоинта локальным дедлайном.**  
Напишите фрагмент обработчика `handleReport`, который оборачивает `r.Context()` в таймаут `2 * time.Second`, передаёт его в `buildReport(ctx)` и в случае истечения времени (`errors.Is(err, context.DeadlineExceeded)`) возвращает HTTP-статус `504 Gateway Timeout` с JSON-ошибкой `"превышено время формирования отчёта"`.

> [!solution] Показать решение
> ```go
> func handleReport(w http.ResponseWriter, r *http.Request) {
> 	ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
> 	defer cancel()
>
> 	data, err := buildReport(ctx)
> 	if err != nil {
> 		if errors.Is(err, context.DeadlineExceeded) {
> 			writeJSONError(w, http.StatusGatewayTimeout, "превышено время формирования отчёта")
> 			return
> 		}
> 		writeJSONError(w, http.StatusInternalServerError, "ошибка отчёта")
> 		return
> 	}
> 	writeJSON(w, http.StatusOK, data)
> }
> ```
> При обрыве связи со стороны клиента `err` будет оборачивать `context.Canceled`, а при срабатывании нашего 2-секундного таймера — `context.DeadlineExceeded`.

**Упражнение 3 (Со звёздочкой \*). Почему `http.TimeoutHandler` меняет поведение `ResponseWriter`?**  
В стандартной библиотеке есть готовая обёртка `http.TimeoutHandler(h, dt, msg)`. Подумайте, зачем ей приходится **буферизовать** весь ответ внутреннего обработчика `h` в памяти перед отправкой, и какая проблема возникнет, если завернуть в `TimeoutHandler` обработчик, отдающий файл на 500 МБ?

> [!solution] Показать решение
> Если бы внутренний обработчик сразу писал байты в сокет и в какой-то момент не уложился в `dt`, `TimeoutHandler` уже не смог бы поменять HTTP-статус на `503 Service Unavailable` (заголовки `200 OK` уже ушли по сети). Поэтому `TimeoutHandler` перехватывает весь вывод в буфер памяти. Для 500-мегабайтного потока такой буфер съест 500 МБ RAM на каждый одновременный запрос — поэтому большие потоковые ответы ограничивают не через `TimeoutHandler`, а через `r.Context()` и таймауты чтения/записи соединения.
