*Чем стек вызовов отличается от кучи, почему в Go безопасно возвращать `&x` из функции и во что обходятся лишние выделения в куче.*

> «Сборка мусора — огромное подспорье при написании корректных программ, но она не избавляет вас от необходимости думать о памяти. Вам не нужно выделять и освобождать память вручную, однако для написания эффективного кода всё равно приходится понимать время жизни переменных.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

Посмотрите на самый обычный конструктор в Go:

```go
func NewBookmark(url string) *Bookmark {
	b := Bookmark{URL: url}
	return &b
}
```

Разработчик на Си или C++ при взгляде на эти четыре строки инстинктивно вздрогнет: переменная `b` объявлена *внутри* функции `NewBookmark`, а значит, должна исчезнуть в момент выхода из неё. Возвращать адрес мёртвой локальной переменной — верный путь к падению программы или порче памяти.

В Go этот код абсолютно безопасен и считается нормой. Чтобы понять, как такое возможно, нужно знать две главные области памяти, в которых живут переменные вашей программы: **стек** и **кучу**.

## Две области памяти: стек и куча

Когда операционная система запускает скомпилированный бинарник Go, программе выдаётся виртуальное адресное пространство. Живые переменные, которые создаются во время работы кода, попадают в одну из двух зон с совершенно разными правилами жизни.

### 1. Стек вызовов (*stack*)

Стек работает по строгому правилу «последним пришёл — первым ушёл». Каждый вызов функции отрезает на вершине стека собственный компактный участок — **кадр стека** (*stack frame*). В нём лежат аргументы функции, адрес возврата и её локальные переменные. Как только функция завершается через `return`, указатель вершины стека `SP` просто сдвигается назад на одну инструкцию CPU — и весь кадр мгновенно освобождается.

Главные свойства стека:
* **Сверхбыстрое выделение и освобождение:** сдвиг одного регистра `SP`, без поиска свободных блоков и без участия сборщика мусора.
* **Отличная локальность данных:** активные кадры лежат плотно друг за другом и почти всегда горячи в кэше L1.
* **Свой стек у каждой горутины:** в Go горутина стартует со стеком всего **2 КБ** (против **1–8 МБ** у обычного потока ОС — разница в сотни и тысячи раз, поэтому программа спокойно держит сотни тысяч горутин). Если вложенность вызовов растёт и двух килобайт не хватает, рантайм Go автоматически выделяет более крупный стек и аккуратно переносит туда кадры.

### 2. Куча (*heap*)

Куча — это общая область памяти для данных, которые **должны пережить выход из функции**, разделяются между несколькими горутинами или имеют слишком большой (либо неизвестный заранее) размер.

В отличие от стека, объекты в куче рождаются и умирают в произвольном порядке. Поэтому выделение памяти в куче дороже: рантайму нужно найти подходящий свободный кусок, разметить его, а позже — когда на объект не останется ни одной ссылки — сборщик мусора должен обнаружить этот «мусор» и вернуть память обратно в оборот.

Разницу между двумя областями легко увидеть на схеме момента после вызова `NewBookmark`:

```text
   Стек горутины (растёт от 2 КБ)           Куча (общая память процесса)
   +------------------------------+         +------------------------------+
   | кадр main():                 |         |                              |
   |   bm (*Bookmark) ------------+-------->| Bookmark{URL: "https://..."} |
   |   localSum (int) = 42        |         |   (живёт, пока есть ссылка)  |
   +------------------------------+         +------------------------------+
   | кадр NewBookmark() — УДАЛЁН  |
   |   (освобождён после return)  |
   +------------------------------+
```

Переменная `localSum` нужна только внутри `main` — она живёт прямо на стеке. А структура `Bookmark`, адрес которой вернулся наружу, обязана пережить закрытие кадра `NewBookmark` — поэтому она живёт в куче.

## Почему в Go безопасно возвращать `&x`

В Си программист сам решает, где разместить переменную: обычное объявление всегда кладёт её на стек, а для кучи нужно явно вызвать `malloc` и не забыть `free`. Ошибся — получил утечку или обращение к мусору.

Авторы Go перевернули правило. **В Go место хранения переменной выбирает компилятор, а не синтаксис.** То, что вы написали `&b` или `new(Bookmark)`, ещё не гарантирует попадание в кучу, а обычное объявление `b := Bookmark{}` не гарантирует попадание на стек.

Во время компиляции Go анализирует время жизни каждой переменной:
* если адрес переменной никуда не уходит за пределы функции (даже если вы брали `&x` для локального вычисления), компилятор оставляет её **на быстром стеке**;
* если ссылка на переменную возвращается наружу (`return &b`), отправляется в канал или сохраняется в глобальной структуре, компилятор автоматически размещает переменную **в куче**, чтобы указатель оставался действительным после завершения функции.

*(Упрощение Тома 1: как именно компилятор доказывает время жизни переменных, какими флагами смотреть его решения и как устроен внутренний аллокатор Go, подробно см. Том 5.)*

## Рабочий код: значение против указателя и независимость адресов

Проверим на практике два конструктора для `BookmarkFlow`: один возвращает структуру по значению (для короткоживущих расчётов), второй — указатель на структуру в куче. Убедимся также, что два последовательных вызова `NewBookmarkPtr` возвращают **разные** адреса, а не перетирают одну и ту же мёртвую ячейку стека:

```go
package main

import "fmt"

type Bookmark struct {
	URL   string
	Views int
}

// NewBookmarkValue возвращает копию структуры — вызывающая сторона
// может держать её прямо в своём стековом кадре без выделения в куче.
func NewBookmarkValue(url string) Bookmark {
	return Bookmark{URL: url, Views: 1}
}

// NewBookmarkPtr возвращает указатель на локальную переменную b.
// Компилятор Go видит, что адрес покидает функцию, и размещает b в куче.
func NewBookmarkPtr(url string) *Bookmark {
	b := Bookmark{URL: url, Views: 1}
	return &b
}

// totalViews использует локальный указатель, но не отдаёт его наружу —
// переменная acc остаётся на стеке.
func totalViews(items []Bookmark) int {
	acc := 0
	p := &acc
	for i := range items {
		*p += items[i].Views
	}
	return acc
}

func main() {
	b1 := NewBookmarkPtr("https://go.dev")
	b2 := NewBookmarkPtr("https://pkg.go.dev")
	fmt.Printf("b1 @ %p -> %+v\n", b1, *b1)
	fmt.Printf("b2 @ %p -> %+v\n", b2, *b2)
	fmt.Println("Адреса разные:", b1 != b2)

	list := []Bookmark{
		NewBookmarkValue("https://go.dev"),
		NewBookmarkValue("https://go.dev/doc"),
	}
	fmt.Println("Всего просмотров:", totalViews(list))
}
```

Вывод программы (конкретные шестнадцатеричные адреса меняются при каждом запуске, но всегда различны):

```text
b1 @ 0xc000010240 -> {URL:https://go.dev Views:1}
b2 @ 0xc000010260 -> {URL:https://pkg.go.dev Views:1}
Адреса разные: true
Всего просмотров: 2
```

Обе структуры живы, не мешают друг другу и безопасно читаются после завершения `NewBookmarkPtr`.

## Подводные камни

**Ловушка 1. Лишние указатели в горячем цикле.**  
Если вспомогательная функция, вызываемая миллион раз в секунду, возвращает `*Stats` вместо простого значения `Stats` из двух чисел `int64`, каждый вызов выталкивает структуру в кучу. Вы платите трижды: за выделение памяти, за потерю локальности данных (урок 6) и за дополнительную уборку мусора (урок 8). Маленькие неизменяемые значения лучше передавать и возвращать по значению.

**Ловушка 2. Бесконечная рекурсия и переполнение стека.**  
Хотя стек горутины умеет расти от 2 КБ, он не бесконечен. В Go установлен защитный предел (по умолчанию `1 ГБ` на 64-битных системах). Забытое условие выхода из рекурсии быстро исчерпает лимит и аварийно остановит программу неисправимой ошибкой `fatal error: stack overflow` (перехватить её через `recover` нельзя).

**Ловушка 3. Неочевидная отправка в кучу через `fmt.Println`.**  
Функция `fmt.Println` принимает аргументы типа `any` (пустой интерфейс). Чтобы упаковать конкретное значение в интерфейс и передать его внутрь функции форматирования, компилятор часто вынужден разместить копию этого значения в куче. В обычном коде это мелочь, но внутри узкого горячего цикла печать или упаковка в `any` способна породить миллионы лишних выделений.

> [!check] Проверь понимание
> Верно ли утверждение: «В Go любая переменная, к которой применили оператор `&`, обязательно попадает в кучу»?
>
> Нет. Оператор `&` лишь берёт адрес переменной. Если этот адрес не покидает пределы текущей функции (как `p := &acc` в `totalViews`), компилятор оставляет переменную на быстром стеке. В кучу она уходит только тогда, когда компилятор не может гарантировать, что время её жизни закончится вместе с кадром функции.

## Практика

**Упражнение 1 (Базовое). Стек или куча?**  
Определите для каждой переменной (`a`, `b`, `c`) в фрагменте ниже, останется ли она на стеке или с высокой вероятностью окажется в куче, и объясните почему:

```go
func calc(x int) *int {
	a := x * 2
	b := a + 10
	c := &b
	_ = c
	return &a
}
```

> [!solution] Показать решение
> * `a` — **куча**: её адрес `&a` возвращается из функции наружу, значит переменная должна пережить завершение `calc`.
> * `b` — **стек**: хотя мы взяли её адрес `&b`, указатель `c` никуда за пределы `calc` не уходит.
> * `c` — **стек**: это обычная локальная переменная-указатель, которая умирает при выходе из `calc`.

**Упражнение 2 (Практическое). Убираем лишнее выделение в куче.**  
Функция `ParseRange` вызывается в цикле миллион раз для разбора границ диапазона `start..end`, но возвращает `*Range`, вынуждая каждый раз выделять память в куче. Перепишите её так, чтобы она возвращала значение `Range` (плюс `error`), и проверьте работу в `main`.

```go
type Range struct {
	Start int
	End   int
}

func ParseRange(a, b int) (*Range, error) {
	if a > b {
		return nil, errors.New("start > end")
	}
	return &Range{Start: a, End: b}, nil
}
```

> [!solution] Показать решение
> При ошибке функция возвращает нулевое значение `Range{}` и `err`, а при успехе — компактную 16-байтную структуру по значению. Она передаётся через регистры или стек без единого выделения в куче:
> ```go
> package main
>
> import (
> 	"errors"
> 	"fmt"
> )
>
> type Range struct {
> 	Start int
> 	End   int
> }
>
> func ParseRange(a, b int) (Range, error) {
> 	if a > b {
> 		return Range{}, errors.New("start > end")
> 	}
> 	return Range{Start: a, End: b}, nil
> }
>
> func main() {
> 	r, err := ParseRange(10, 25)
> 	fmt.Println(r, err)
>
> 	bad, err := ParseRange(30, 10)
> 	fmt.Println(bad, err)
> }
> ```

**Упражнение 3 (Со звёздочкой \*). Рост стека и граница рекурсии.**  
Напишите рекурсивную функцию `sumDown(n int) int`, которая складывает числа от `n` до `1`, и вызовите её для `n = 100_000`. Почему программа не падает с переполнением стека, хотя начальный стек горутины — всего `2 КБ`, а сто тысяч кадров требуют мегабайты памяти? Затем перепишите вычисление обычным циклом `for` и сравните расход стека.

> [!solution] Показать решение
> При глубине рекурсии `100 000` рантайм Go многократно обнаруживает, что текущий стек исчерпан, выделяет более крупный непрерывный сегмент (удваивая размер) и копирует туда кадры. Программа работает корректно, но тратит мегабайты памяти на кадры вызовов. Итеративная версия держит ровно один кадр (десятки байтов) при любом `n`:
> ```go
> package main
>
> import "fmt"
>
> func sumDownRec(n int) int {
> 	if n <= 0 {
> 		return 0
> 	}
> 	return n + sumDownRec(n-1)
> }
>
> func sumDownLoop(n int) int {
> 	total := 0
> 	for i := 1; i <= n; i++ {
> 		total += i
> 	}
> 	return total
> }
>
> func main() {
> 	fmt.Println("Рекурсия:", sumDownRec(100_000))
> 	fmt.Println("Цикл:    ", sumDownLoop(100_000))
> }
> ```

---

Со стеком всё просто: функция завершилась — кадр исчез за одну инструкцию. Но кто и когда убирает из кучи те структуры `Bookmark`, на которые программа перестала ссылаться, и во что эта автоматическая уборка обходится нашему процессору? Разберём в следующем уроке — [[8.
