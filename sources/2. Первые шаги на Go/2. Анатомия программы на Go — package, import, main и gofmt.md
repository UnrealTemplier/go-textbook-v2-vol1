*Из каких обязательных частей состоит каждый файл Go, почему компилятор отвергает «мусорный» код и как `gofmt` закрыл многолетние споры о стиле.*

> «Директивное утверждение единого формата снимает массу бессмысленных споров о мелочах и, что ещё важнее, открывает дорогу автоматическим преобразованиям исходного кода, которые были бы невозможны при произвольном форматировании.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

В предыдущем уроке вы написали пять строк и получили рабочий бинарник. Если перенести ту же программу с Python или JavaScript, пара вещей сразу покажется странной: зачем наверху строка `package main`, почему нельзя оставить лишний `import` на потом и отчего перенос фигурной скобки `{` на новую строку внезапно ломает сборку.

Все эти правила — не каприз авторов языка. За каждым стоит конкретное инженерное решение, которое экономит время команде, когда в проекте становится не 5, а 50 000 строк.

## Три этажа любого `.go`-файла

Любой файл исходного кода на Go устроен строго сверху вниз и состоит из трёх частей:

```go
// 1. Объявление пакета — всегда первая непустая строка кода
package main

// 2. Импорты — какие пакеты нужны этому файлу
import (
	"fmt"
	"runtime"
)

// 3. Объявления функций, переменных, констант и типов
func main() {
	fmt.Println("Go:", runtime.Version())
	fmt.Println("ОС/CPU:", runtime.GOOS, runtime.GOARCH)
}
```

Разберём каждый этаж.

**1. `package main`.** Код в Go организован в *пакеты* — логические папки с файлами, решающими одну задачу. Стандартная библиотека состоит из пакетов вроде `fmt` (форматированный ввод-вывод), `strings` (работа со строками) или `math` (математика). Пакет с особым именем `main` сообщает компилятору: «это не библиотека для подключения в другой проект, а самостоятельная исполняемая программа».

**2. `import (...)`.** Перечисляет пакеты, чьи функции используются в текущем файле. Когда импорт один, скобки опускают (`import "fmt"`). Когда их два и больше, их группируют в круглые скобки — по одному имени в двойных кавычках на строку, без запятых.

**3. `func main()`.** Точка входа в программу. Операционная система запускает скомпилированный бинарник, среда выполнения Go готовит память и передаёт управление вашей функции `main`. Когда `main` доходит до закрывающей `}`, программа завершается с кодом успеха `0`.

Обратите внимание на регистр букв в `fmt.Println` и `runtime.Version`:
* Имя с **заглавной** буквы (`Println`, `Version`, `GOOS`) **экспортировано** — его видно из других пакетов.
* Имя со **строчной** буквы (`helper`, `count`) скрыто внутри своего пакета.

В Go нет ключевых слов `public` и `private` — видимость читается прямо по первой букве имени.

## Компилятор-перфекционист: неиспользуемые импорты и ошибки

Попробуйте добавить в пример выше `"math"` в список импортов, не вызывая ни одной функции из `math`:

```go
import (
	"fmt"
	"math"
	"runtime"
)
```

При запуске `go run .` сборка оборвётся:

```text
./main.go:5:2: "math" imported and not used
```

В большинстве языков лишний импорт — в лучшем случае жёлтое предупреждение, которое годами висит в редакторе. В Go это **ошибка компиляции**. Причина практическая: компилятор Go тратит львиную долю времени на чтение зависимостей. Если в кодовой базе на миллионы строк копятся неиспользуемые импорты, сборка замедляется для всей команды, а чтение файла засоряется ложными связями. Жёсткое правило держит граф зависимостей чистым и помогает Go компилироваться за доли секунды.

То же правило скоро встретится вам и с локальными переменными: объявили переменную внутри функции и не прочитали её — компилятор остановит сборку.

## Тайна фигурной скобки и невидимых точек с запятой

Попробуйте перенести открывающую `{` у `func main()` на новую строку, как часто пишут в C# или C++:

```go
func main()
{
	fmt.Println("Попытка переноса скобки")
}
```

Вы получите неожиданную ошибку:

```text
./main.go:6:1: syntax error: unexpected semicolon or newline before {
```

Откуда взялась точка с запятой (`semicolon`), если вы её не ставили?

Внутри грамматики Go точки с запятой на самом деле есть, но расставляет их сам лексер компилятора по простому автоматическому правилу: если строка заканчивается идентификатором, числом, строкой, `return`, `break`, `continue`, `++`, `--` или закрывающей скобкой `)`, `]`, `}`, компилятор **автоматически дописывает `;` в конец строки**.

Поэтому код выше компилятор видит буквально так:

```go
func main(); // <-- точка с запятой вставлена после ")"!
{
```

Отсюда единственное железное правило: **открывающая фигурная скобка `{` всегда стоит на той же строке**, что `func`, `if`, `for` или `switch`. В остальном точки с запятой в Go почти никогда не пишут вручную.

## `gofmt`: один формат на весь мир

В других языках команды тратят часы на споры: табы или пробелы, 2 пробела или 4, ставить ли пробел перед скобкой. В Go этот спор закрыт раз и навсегда встроенной утилитой **`gofmt`**.

Попробуйте намеренно испортить отступы в `main.go`:

```go
package main
import "fmt"
func main(){
fmt.Println(  "кривое форматирование"  )
}
```

А затем выполните в терминале:

```bash
gofmt -w main.go
```

Флаг `-w` (*write*) перезаписывает файл на диске в каноническом формате (отступы табами, выровненные колонки, правильные пробелы вокруг операторов). Есть и обёртка `go fmt ./...`, которая прогоняет `gofmt` по всем файлам проекта. Настройте свой редактор так, чтобы `gofmt` (или `goimports`, который заодно сам добавляет и удаляет импорты) запускался автоматически при каждом сохранении файла.

## Комментарии: два вида и золотое правило

В Go два вида комментариев:
* Однострочные `// текст до конца строки` — основной рабочий инструмент.
* Многострочные `/* блок текста */` — реже, в основном для крупных шапок или временного отключения фрагмента.

Комментарий перед пакетом или функцией автоматически становится документацией (`godoc`):

```go
// printEnv печатает версию Go и платформу, на которой запущена программа.
func printEnv() {
	fmt.Println("Go:", runtime.Version())
}
```

Пишите комментарии про **зачем** и **какой контракт**, а не пересказывайте синтаксис (`// печатаем строку` над `fmt.Println` — лишний шум).

> [!check] Проверь понимание
> Как по одному только имени `strings.TrimSpace` и `strings.trimLeft` понять, какую из этих функций можно вызвать из вашего пакета `main`?
>
> Вызвать можно только `strings.TrimSpace` — её имя начинается с заглавной буквы `T`, значит она экспортирована. Функция `trimLeft` со строчной буквы скрыта внутри пакета `strings` и недоступна извне.

## Практика

**Упражнение 1 (Базовое). Почини программу.**  
В этом файле спрятаны три ошибки. Найдите все три глазами, затем проверьте догадку через `go run .` и исправьте код:

```go
package main

import (
	"fmt"
	"strings"
)

func main()
{
	fmt.println("BookmarkFlow стартует")
}
```

> [!solution] Показать решение
> Три ошибки:
> 1. Пакет `"strings"` импортирован, но не используется (`"strings" imported and not used`).
> 2. Открывающая `{` перенесена на новую строку — лексер вставит `;` после `main()`.
> 3. `fmt.println` написано со строчной буквы, а экспортированная функция называется `fmt.Println` (`undefined: fmt.println`).
>
> Исправленный код:
> ```go
> package main
>
> import "fmt"
>
> func main() {
> 	fmt.Println("BookmarkFlow стартует")
> }
> ```

**Упражнение 2 (Практическое). Проверьте `gofmt` в бою.**  
Создайте файл `info.go` с беспорядочными отступами и лишними пробелами, который выводит версию Go (`runtime.Version()`), ОС (`runtime.GOOS`), архитектуру (`runtime.GOARCH`) и число логических ядер процессора (`runtime.NumCPU()`). Запустите `gofmt -d info.go` (показать разницу без записи), а затем `gofmt -w info.go` и `go run info.go`.

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"fmt"
> 	"runtime"
> )
>
> func main() {
> 	fmt.Println("Версия Go:", runtime.Version())
> 	fmt.Println("Платформа:", runtime.GOOS, runtime.GOARCH)
> 	fmt.Println("Ядер CPU:", runtime.NumCPU())
> }
> ```
> Флаг `-d` (*diff*) показывает патч изменений в стиле Git, не меняя сам файл — этим же приёмом пользуются автоматические проверки в CI, чтобы не пускать неотформатированный код в репозиторий.

**Упражнение 3 (Со звёздочкой \*). Объясни почему.**  
Представьте, что вы перенесли длинное выражение сложения на следующую строку двумя способами:
```go
// Вариант A
total := 100 +
	200

// Вариант B
total := 100
	+ 200
```
Какой из вариантов скомпилируется, а какой сломается, и как это связано с правилом автоматической точки с запятой?

> [!solution] Показать решение
> Скомпилируется только **Вариант A**.
> В Варианте A строка заканчивается оператором `+` — после него лексер **не** вставляет точку с запятой и продолжает читать выражение на следующей строке. В Варианте B строка заканчивается числом `100`, поэтому лексер дописывает `;` (`total := 100;`), и одинокая строка `+ 200` вызывает синтаксическую ошибку. Поэтому при переносе длинных выражений оператор (`+`, `&&`, `||`) или запятую всегда оставляют в **конце** предыдущей строки.
