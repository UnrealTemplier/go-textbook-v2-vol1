*Как процессор держит рабочие числа в регистрах, зачем исполняет инструкции внахлёст на конвейере и почему непредсказуемый `if` в цикле стоит десятки тактов.*

> «Со временем 8-битные процессоры уступили место 16-битным, затем 32-битным и 64-битным, но эти более совершенные процессоры не научились решать принципиально иные задачи. Они просто выполняют те же самые задачи быстрее.»  
> — Чарльз Петцольд, *Code (2nd ed.)*

Возьмите слайс из миллиона случайных чисел от `0` до `255` и посчитайте сумму всех элементов, которые больше или равны `128`. Теперь отсортируйте этот же слайс по возрастанию и запустите **ту же самую функцию подсчёта**. Число итераций не изменилось, количество сложений совпадает до единицы — но на отсортированных данных цикл отработает в два-четыре раза быстрее.

Ответ на этот парадокс лежит не в языке Go, а внутри самого процессора: в его регистрах, конвейере инструкций и блоке предсказания ветвлений.

## Регистры: рабочие слоты внутри ядра

Оперативная память (RAM) для процессора — слишком медленный и далёкий склад. Прежде чем сложить два числа `a + b`, ядро загружает их в свои внутренние сверхбыстрые ячейки — **регистры** (*registers*).

Регистр — это крошечный набор триггеров прямо на кристалле CPU, шириной 64 бита на современных 64-битных процессорах (поэтому их и называют 64-битными). Чтение и запись регистра занимают долю наносекунды — один такт. У каждого ядра таких слотов немного (например, 16 регистров общего назначения в архитектуре `x86-64` и 31 в `ARM64`), и помимо них есть специальные служебные регистры:

* **указатель инструкций (`IP` / `PC`)** — хранит адрес следующей машинной команды в памяти;
* **указатель стека (`SP`)** — отмечает текущую вершину стека вызовов;
* **регистр флагов** — запоминает признаки последнего сравнения (равно, меньше, переполнение).

Компилятор Go старается держать счётчик цикла `i` и накопитель суммы `sum` именно в регистрах, не гоняя их туда-сюда в память на каждой итерации.

## Конвейер инструкций: сборочная линия и её границы

Исполнение одной машинной команды состоит из нескольких отдельных шагов. В упрощённой четырёхступенчатой модели их четыре:

1. **Выборка (`F`, Fetch)** — прочитать очередную команду по адресу из `IP`.
2. **Декодирование (`D`, Decode)** — понять, какая это операция и какие регистры ей нужны.
3. **Исполнение (`E`, Execute)** — выполнить сложение, сравнение или вычисление адреса в арифметико-логическом устройстве.
4. **Запись результата (`W`, Writeback)** — положить итог обратно в целевой регистр.

Если выполнять команды строго по очереди — не начинать вторую, пока четвёртый шаг первой не завершён, — три блока процессора из четырёх будут простаивать на каждом такте. Поэтому ещё в 1960-х инженеры применили **конвейер инструкций** (*instruction pipeline*).

Его удобно сравнить со сборочной линией на заводе. Аналогия бьёт точно в одно свойство: каждая отдельная машина по-прежнему проходит все четыре цеха за 4 часа (задержка одной команды не уменьшилась), но готовый автомобиль сходит с линии **каждый час** (пропускная способность выросла в четыре раза).

Вот где граница этой аналогии: у реального процессора в конвейере не 4, а 14–19 и более ступеней, он умеет запускать несколько независимых команд одновременно и даже переставлять их местами (*out-of-order execution*). И в отличие от одинаковых автомобилей на заводе, соседние команды программы часто зависят друг от друга: если команда №2 использует результат команды №1, она вынуждена ждать.

Поток инструкций в идеальном 4-ступенчатом конвейере выглядит так:

```text
Такт:         1    2    3    4    5    6    7
Команда 1:  [ F ][ D ][ E ][ W ]
Команда 2:       [ F ][ D ][ E ][ W ]
Команда 3:            [ F ][ D ][ E ][ W ]
Команда 4:                 [ F ][ D ][ E ][ W ]
```

Начиная с четвёртого такта конвейер заполнен полностью и завершает по одной команде на каждом такте.

## Предсказание ветвлений и цена промаха

Пока команды идут линейно друг за другом, конвейер работает на полной скорости. Но как только программа доходит до условного перехода `if v >= 128`, возникает затык: какая команда будет следующей — тело `if` или переход к следующей итерации? Процессор узнает ответ только на этапе исполнения `E` (в реальном CPU — спустя 15–20 тактов после выборки).

Останавливать конвейер на каждом `if` недопустимо: условные переходы встречаются каждые 5–10 инструкций. Поэтому процессор **угадывает** исход ветвления заранее с помощью аппаратного блока — **предсказателя ветвлений** (*branch predictor*). Он запоминает недавнюю историю конкретного перехода и загружает в конвейер команды самой вероятной ветки *спекулятивно*, не дожидаясь проверки условия.

* **Предсказатель угадал:** конвейер продолжает работу без единого такта простоя.
* **Предсказатель ошибся (*branch misprediction*):** все команды, уже зашедшие в конвейер по неверной ветке, выбрасываются (*pipeline flush*), регистры откатываются, и конвейер заполняется заново с правильного адреса.

На современном процессоре один промах предсказателя стоит **15–20 потерянных тактов** (около 5 наносекунд). В плотном цикле на миллионы итераций случайное ветвление с вероятностью 50/50 ошибается на каждом втором элементе — и превращает быструю сборочную линию в вечный «стоп-кран». На отсортированном же слайсе условие сначала полмиллиона раз подряд ложно, затем один раз переключается и полмиллиона раз подряд истинно: предсказатель ошибается буквально один-два раза на весь массив.

## Рабочий код: проверяем парадокс на реальном CPU

Сравним скорость одной и той же функции `splitSum` на перемешанных и отсортированных данных. В обеих ветках `if/else` обновляются разные накопители, поэтому компилятор генерирует настоящий условный переход, который проходит через предсказатель ветвлений CPU:

```go
package main

import (
	"fmt"
	"math/rand/v2"
	"slices"
	"time"
)

// splitSum раздельно суммирует элементы >= threshold и < threshold.
func splitSum(data []int, threshold int) (high, low int64, highCnt int) {
	for _, v := range data {
		if v >= threshold {
			high += int64(v)
			highCnt++
		} else {
			low += int64(v)
		}
	}
	return high, low, highCnt
}

func measure(data []int, runs int) (int64, int64, int, time.Duration) {
	start := time.Now()
	var h, l int64
	var cnt int
	for range runs {
		h, l, cnt = splitSum(data, 128)
	}
	return h, l, cnt, time.Since(start)
}

func main() {
	const n = 200_000
	const runs = 100

	rng := rand.New(rand.NewPCG(42, 1024))
	data := make([]int, n)
	for i := range data {
		data[i] = rng.IntN(256)
	}

	h1, l1, c1, unsortedDur := measure(data, runs)
	slices.Sort(data)
	h2, l2, c2, sortedDur := measure(data, runs)

	fmt.Printf("Перемешанный: high=%d low=%d cnt=%d, время=%v\n", h1, l1, c1, unsortedDur)
	fmt.Printf("Отсортирован: high=%d low=%d cnt=%d, время=%v\n", h2, l2, c2, sortedDur)
	fmt.Printf("Ускорение:    %.2fx\n", float64(unsortedDur)/float64(sortedDur))
}
```

На современном `x86-64`-процессоре вывод будет примерно таким (конкретные миллисекунды зависят от модели CPU, но кратный разрыв сохраняется):

```text
Перемешанный: high=19099476 low=6372243 cnt=99778, время=61.4ms
Отсортирован: high=19099476 low=6372243 cnt=99778, время=5.8ms
Ускорение:    10.51x
```

Обе суммы и счётчик совпадают до единицы, объём данных одинаков, код функции `splitSum` не менялся — десятикратную разницу дала исключительно предсказуемость ветвления.

## Подводные камни

**Ловушка 1. Преждевременная «бесбранчевая» акробатика.**  
Узнав про цену промаха предсказателя, легко поддаться соблазну переписывать каждый `if` на хитрые битовые маски. Не делайте так. Во-первых, в 95% обычного кода ветвления хорошо предсказуемы (например, `if err != nil` почти всегда ложен). Во-вторых, компилятор Go сам умеет заменять простые `if` на бесбранчевые машинные команды условного переноса (`CMOV`). Бесбранчевые трюки оправданы только в доказанно горячем цикле после замеров.

**Ловушка 2. Сортировка ради ускорения одного прохода.**  
Если вы отсортируете слайс только для того, чтобы один раз пробежаться по нему `splitSum`, время самой сортировки многократно перекроет выигрыш от предсказателя. Сортировка окупается лишь тогда, когда данные уже отсортированы по смыслу задачи или обходятся многократно.

> [!check] Проверь понимание
> В цикле обработки HTTP-запросов стоит проверка `if err != nil { return err }`, причём ошибки случаются в 0.01% случаев. Будет ли эта ветка заметно тормозить конвейер?
>
> Нет. Предсказатель ветвлений быстро выучит, что переход в тело `if` почти никогда не происходит, и будет угадывать исход в 99.99% случаев без сброса конвейера.

## Практика

**Упражнение 1 (Базовое). Пропускная способность конвейера.**  
Представьте упрощённый 5-ступенчатый конвейер без зависимостей и ветвлений, где каждая ступень занимает ровно `1` такт. Сколько тактов потребуется, чтобы полностью выполнить 1 инструкцию? А 100 инструкций подряд?

> [!solution] Показать решение
> * 1 инструкция пройдёт все 5 ступеней за **5 тактов**.
> * Для 100 инструкций первая завершится на 5-м такте, а каждая из оставшихся 99 будет выходить из конвейера по одной на такт: `5 + 99 = 104 такта` (вместо `500` тактов без конвейера).

**Упражнение 2 (Практическое). Убираем непредсказуемое ветвление.**  
Перепишите функцию `sumAbove(data []int, threshold int) int64` так, чтобы на 64-битных числах (или на `int`) обойтись без `if`: вычислите разность `diff := v - threshold`, сдвиньте знак арифметическим сдвигом вправо на 63 бита, инвертируйте маску и наложите её на `v` через `&`. Сверьте результат с обычной `sumAbove`.

> [!solution] Показать решение
> Если `v >= threshold`, то `diff >= 0`, знаковый бит равен `0`, сдвиг `int64(diff) >> 63` даёт `0`, а инверсия `^mask` даёт все единицы (`-1`) — значение `v` сохраняется. Если `v < threshold`, сдвиг даёт `-1` (все единицы), инверсия даёт `0` — к сумме прибавляется ноль:
> ```go
> package main
>
> import "fmt"
>
> func sumAboveBranchless(data []int, threshold int) int64 {
> 	var sum int64
> 	for _, v := range data {
> 		mask := ^(int64(v-threshold) >> 63)
> 		sum += int64(v) & mask
> 	}
> 	return sum
> }
>
> func main() {
> 	nums := []int{10, 128, 200, 50, 127, 255}
> 	fmt.Println(sumAboveBranchless(nums, 128)) // 583 (128 + 200 + 255)
> }
> ```
> Код работает без условного перехода, поэтому на случайных данных его скорость почти не зависит от порядка элементов. Заметный минус — читать такую запись значительно тяжелее, чем обычный `if`.

**Упражнение 3 (Со звёздочкой \*). Сравните три варианта на своих данных.**  
Сравните `splitSum` (на перемешанном и отсортированном слайсах) с бесбранчевой версией `splitSumBranchless` (на перемешанном слайсе) в одной программе. Замерьте время всех трёх прогонов и объясните, почему бесбранчевая версия резко обгоняет `if` на случайных данных, но может уступать ему на отсортированных.

> [!solution] Показать решение
> На случайных данных бесбранчевая версия полностью исключает сбросы конвейера и работает в разы быстрее. На отсортированных данных предсказатель угадывает `if` почти со 100% точностью, и в каждой ветке процессор обновляет только нужные переменные без лишних битовых операций:
> ```go
> package main
>
> import (
> 	"fmt"
> 	"math/rand/v2"
> 	"slices"
> 	"time"
> )
>
> func splitIf(data []int, threshold int) (high, low int64) {
> 	for _, v := range data {
> 		if v >= threshold {
> 			high += int64(v)
> 		} else {
> 			low += int64(v)
> 		}
> 	}
> 	return high, low
> }
>
> func splitBranchless(data []int, threshold int) (high, low int64) {
> 	for _, v := range data {
> 		mask := ^(int64(v-threshold) >> 63)
> 		high += int64(v) & mask
> 		low += int64(v) & ^mask
> 	}
> 	return high, low
> }
>
> func bench(fn func([]int, int) (int64, int64), data []int) (int64, int64, time.Duration) {
> 	start := time.Now()
> 	var h, l int64
> 	for range 100 {
> 		h, l = fn(data, 128)
> 	}
> 	return h, l, time.Since(start)
> }
>
> func main() {
> 	rng := rand.New(rand.NewPCG(7, 99))
> 	data := make([]int, 200_000)
> 	for i := range data {
> 		data[i] = rng.IntN(256)
> 	}
> 	h1, l1, d1 := bench(splitIf, data)
> 	h2, l2, d2 := bench(splitBranchless, data)
> 	slices.Sort(data)
> 	h3, l3, d3 := bench(splitIf, data)
> 	fmt.Printf("if (unsorted):         %d/%d за %v\n", h1, l1, d1)
> 	fmt.Printf("branchless (unsorted): %d/%d за %v\n", h2, l2, d2)
> 	fmt.Printf("if (sorted):           %d/%d за %v\n", h3, l3, d3)
> }
> ```
