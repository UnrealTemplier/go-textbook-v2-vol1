*Как Go автоматически освобождает ненужную память в куче, почему эта страховка не бесплатна и какие три привычки снимают лишнюю нагрузку со сборщика мусора.*

> «Сборка мусора — огромное подспорье при написании корректных программ, но она не избавляет вас от необходимости думать о памяти. Вам не нужно выделять и освобождать память вручную, однако для написания эффективного кода всё равно приходится понимать время жизни переменных.»
> — Алан Донован, Брайан Керниган (*The Go Programming Language*)

В прошлом уроке мы увидели, что стек очищается мгновенно при выходе из функции, а данные, переживающие вызов, попадают в кучу. В языке Си за каждый байт в куче отвечает сам программист: выделил блок через `malloc` — обязан ровно один раз вернуть его через `free`.

На практике ручное управление памятью порождает два разрушительных класса ошибок. Если забыть вызвать `free`, память постепенно заканчивается — возникает **утечка памяти** (*memory leak*), и процесс падает от нехватки ОЗУ. Если же освободить блок слишком рано, пока на него ссылается другая часть программы, обращение по устаревшему указателю читает или портит чужие данные — это ошибка **использования после освобождения** (*use-after-free*), один из главных источников критических уязвимостей безопасности.

## Интуиция: «пометь живое от корней — освободи остальное»

Авторы Go сняли с программиста обязанность вызывать `free`, поручив уборку встроенному **сборщику мусора** (*Garbage Collector*, GC). Его базовая идея проста и строится на понятии **достижимости** (*reachability*).

У программы есть набор исходных точек, которые точно нужны прямо сейчас — их называют **корнями** (*roots*). К корням относятся глобальные переменные и локальные переменные на стеках активных горутин. От корней сборщик идёт по указателям, как по ссылкам в графе объектов, и помечает всё, до чего удалось дотянуться:

```text
Корни (стеки, глобалы)        Куча (Heap)
+------------------+          +---------------+     +---------------+
| activeBookmarks  |--------->| [объект A] ✓  |---->| [объект B] ✓  |
+------------------+          +---------------+     +---------------+
| config           |----+
+------------------+    |     +---------------+     +---------------+
                        +---->| [объект C] ✓  |     | [объект D] ✗  | -> освободить
                              +---------------+     +---------------+
                                                           ^
                                                    +---------------+
                                                    | [объект E] ✗  | -> освободить
                                                    +---------------+
```

Дальше работает простое правило из двух шагов:

1. **Разметка (*mark*).** Сборщик обходит все объекты, достижимые от корней, и ставит на них отметку «живой».
2. **Очистка (*sweep*).** Всё, что осталось без отметки (как объекты `D` и `E` на схеме — даже если они ссылаются друг на друга), считается мусором и возвращается в пул свободной памяти для будущих выделений.

Эта модель объясняет важное следствие: сборщик освобождает только *недостижимые* объекты. Если вы забыли удалить старые записи из глобального слайса или мапы, они остаются достижимыми от корней, и GC честно будет хранить их вечно.

## Цена автоматической уборки

Сборщик мусора работает в фоновом режиме параллельно с вашим кодом, но бесплатным он не бывает. За безопасность памяти программа платит тремя ресурсами:

* **Процессорным временем.** Обход указателей и пометка объектов потребляют такты CPU, которые могли бы пойти на полезную работу программы.
* **Короткими паузами.** В начале и в конце цикла сборки рантайм ненадолго приостанавливает горутины (*stop-the-world*), чтобы согласовать состояние. В современном Go эти паузы обычно укладываются в доли миллисекунды, но при шквале мелких выделений циклы сборки запускаются чаще.
* **Запасом по памяти.** Чтобы не запускать уборку после каждого байта, сборщик даёт куче временно вырасти сверх объёма живых данных, прежде чем начать новый проход.

Точную механику конкурентного алгоритма, барьеров и тонких настроек рантайма мы разберём в Томе 5. На уровне повседневной разработки достаточно главного принципа: **чем меньше временного мусора вы создаёте в куче, тем реже просыпается GC и тем быстрее работает программа**.

## Три практических правила на каждый день

Посмотрим на конкретную задачу: нужно склеить 10 000 строк отчёта и собрать их в слайс. Сначала напишем наивный вариант, а затем применим три простых приёма — предвыделение слайса через `make([]T, 0, n)`, `strings.Builder` вместо `+=` в цикле и отказ от лишних промежуточных выделений:

```go
package main

import (
	"fmt"
	"runtime"
	"strconv"
	"strings"
)

func buildNaive(n int) (string, []string) {
	var items []string
	var report string
	for i := range n {
		entry := "bookmark-" + strconv.Itoa(i)
		items = append(items, entry)
		report += entry + "\n" // на каждом шаге создаётся новая строка
	}
	return report, items
}

func buildClean(n int) (string, []string) {
	items := make([]string, 0, n) // одна аллокация под весь слайс
	var b strings.Builder
	b.Grow(n * 16) // заранее резервируем буфер под итоговую строку

	for i := range n {
		entry := "bookmark-" + strconv.Itoa(i)
		items = append(items, entry)
		b.WriteString(entry)
		b.WriteByte('\n')
	}
	return b.String(), items
}

func measure(name string, fn func()) {
	runtime.GC()
	var before, after runtime.MemStats
	runtime.ReadMemStats(&before)
	fn()
	runtime.ReadMemStats(&after)

	allocKB := (after.TotalAlloc - before.TotalAlloc) / 1024
	mallocs := after.Mallocs - before.Mallocs
	fmt.Printf("%-6s: выделено %7d КБ, аллокаций: %d\n", name, allocKB, mallocs)
}

func main() {
	const count = 10_000
	measure("naive", func() { _, _ = buildNaive(count) })
	measure("clean", func() { _, _ = buildClean(count) })
}
```

Запуск программы показывает разницу на порядки:

```text
naive : выделено  706623 КБ, аллокаций: 29985
clean : выделено     511 КБ, аллокаций: 19902
```

Строки в Go неизменяемы: операция `report += entry + "\n"` в наивном цикле на каждой итерации копирует всю уже накопленную строку в новый участок кучи. Для 10 000 записей это превращается в **~690 МБ** мусора, который сборщику приходится постоянно выметать.

`strings.Builder` дописывает байты в один внутренний буфер, а `make([]string, 0, n)` избавляет слайс от цепочки перевыделений базового массива. Расход памяти падает почти в **1 400 раз** — без единого усложнения логики.

## Подводные камни

**Ловушка 1. «Хвост» отсечённого слайса держит память.**  
Если вы прочитали в слайс файл размером 10 МБ и сохранили из него небольшой подслайс `header := data[:64]`, заголовок `header` продолжает ссылаться на исходный 10-мегабайтный массив. Пока `header` достижим, GC не сможет освободить ни один байт этого массива. Решение — скопировать нужную часть в свежий слайс через `copy` или `slices.Clone`.

**Ловушка 2. Утечка горутин — это тоже утечка памяти.**  
Сборщик мусора не завершает заблокированные горутины. Пока горутина вечно ждёт чтения из канала, который никто не закроет, её стек и все переменные на нём остаются корнями и удерживают объекты в куче.

> [!check] Проверь понимание
> В функции создали два объекта `a` и `b`, которые ссылаются друг на друга (`a.peer = b`, `b.peer = a`). После выхода из функции никаких других ссылок на них нет. Освободит ли их сборщик мусора Go?
>
> Да. Сборщик Go опирается на достижимость от корней, а не на подсчёт ссылок. Поскольку от стеков и глобальных переменных до пары `(a, b)` добраться нельзя, оба объекта останутся непомеченными и будут освобождены.

## Практика

**Упражнение 1 (Базовое). Найдите живые и мёртвые объекты.**  
Глобальная переменная `cache` хранит слайс из двух указателей `[p1, p2]`. Внутри функции выполнили `cache = cache[:1]`, но элемент `cache[1]` перед этим не обнулили. Останется ли объект `*p2` в памяти до следующей переписи базового массива? Объясните почему.

> [!solution] Показать решение
> Да, объект `*p2` останется в памяти. Усечение `cache[:1]` меняет только длину `len` в заголовке слайса, но базовый массив по-прежнему хранит указатель `p2` в ячейке с индексом 1 — он достижим через базовый массив слайса. Чтобы разрешить сборщику освободить `*p2`, элемент нужно обнулить явно: `cache[1] = nil; cache = cache[:1]` (или воспользоваться `clear(cache[1:])`).

**Упражнение 2 (Практическое). Уберите лишние аллокации при склейке тегов.**  
Перепишите функцию `JoinTags(tags []string) string`, которая форматирует слайс тегов вида `["go", "memory", "gc"]` в строку `"#go #memory #gc"`, используя `strings.Builder` и предварительный расчёт нужной длины через `Grow`.

> [!solution] Показать решение
> Сначала считаем точную итоговую длину строки в байтах (сумма длин тегов плюс `#` перед каждым и пробелы между ними), один раз вызываем `Grow`, и далее пишем в буфер без повторных аллокаций:
> ```go
> package main
>
> import (
> 	"fmt"
> 	"strings"
> )
>
> func JoinTags(tags []string) string {
> 	if len(tags) == 0 {
> 		return ""
> 	}
> 	total := len(tags) + (len(tags) - 1) // символы '#' и пробелы
> 	for _, tag := range tags {
> 		total += len(tag)
> 	}
>
> 	var b strings.Builder
> 	b.Grow(total)
> 	for i, tag := range tags {
> 		if i > 0 {
> 			b.WriteByte(' ')
> 		}
> 		b.WriteByte('#')
> 		b.WriteString(tag)
> 	}
> 	return b.String()
> }
>
> func main() {
> 	fmt.Println(JoinTags([]string{"go", "memory", "gc"}))
> 	// Вывод: #go #memory #gc
> }
> ```
> При точном расчёте `Grow(total)` внутренний буфер выделяется ровно один раз, независимо от числа тегов.

**Упражнение 3 (Со звёздочкой \*). Безопасное извлечение префикса из большого буфера.**  
Напишите функцию `ExtractMagic(payload []byte, n int) []byte`, которая возвращает первые `n` байтов из `payload` (или меньше, если `len(payload) < n`), но гарантирует, что возвращённый слайс не удерживает в памяти исходный массив `payload`. Проверьте, что изменение исходного `payload[0]` после вызова не влияет на результат.

> [!solution] Показать решение
> Выделяем отдельный слайс точного размера и копируем байты через `copy`, разрывая связь с исходным массивом:
> ```go
> package main
>
> import "fmt"
>
> func ExtractMagic(payload []byte, n int) []byte {
> 	if n <= 0 || len(payload) == 0 {
> 		return nil
> 	}
> 	n = min(n, len(payload))
> 	out := make([]byte, n)
> 	copy(out, payload[:n])
> 	return out
> }
>
> func main() {
> 	big := []byte("BOOKMARK-DATA-PAYLOAD")
> 	magic := ExtractMagic(big, 8)
> 	big[0] = 'X'
> 	fmt.Println(string(magic)) // Вывод: BOOKMARK
> }
> ```
> Новый слайс `out` ссылается на собственный массив из 8 байтов, поэтому большой буфер `big` сможет освободиться сразу, как только исчезнут ссылки на него.
