*Почему в Go нет `try / catch`, как устроен встроенный тип `error`, зачем писать `if err != nil` и как строить плоский читаемый код с ранним выходом.*

> «В отличие от этого, программы на Go реагируют на ошибки обычными конструкциями управления потоком — такими как `if` и `return`. Бесспорно, такой стиль заставляет уделять обработке ошибок больше внимания — но ровно в этом и состоит его замысел.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

Если вы раньше писали на Python, Java или JavaScript, вы привыкли к исключениям: функция бросает `throw` / `raise`, а где-то тремя этажами выше блок `try / catch` пытается её поймать. Проблема в том, что по вызову `parsePort(raw)` в таком языке **невозможно увидеть**, может ли он внезапно «выстрелить» исключением и на какой строчке оборвётся исполнение.

В Go отказались от исключений для обычных рабочих сбоев. Ошибка — это **обычное возвращаемое значение** типа `error`, которое функция честно отдаёт последним результатом.

## Как выглядит `error` на реальной функции `strconv.Atoi`

Попробуем превратить текстовый ввод пользователя (например, идентификатор закладки `"42"` или опечатку `"abc"`) в целое число `int`. В стандартной библиотеке за это отвечает функция `strconv.Atoi` (*ASCII to integer*):

```go
package main

import (
	"fmt"
	"strconv"
)

func main() {
	id, err := strconv.Atoi("42")
	if err != nil {
		fmt.Println("Ошибка разбора:", err)
		return
	}
	fmt.Println("Разобрали ID:", id)

	badID, err := strconv.Atoi("abc")
	if err != nil {
		fmt.Println("Ошибка разбора:", err)
		return
	}
	fmt.Println("Разобрали ID:", badID)
}
```

Вывод программы:

```text
Разобрали ID: 42
Ошибка разбора: strconv.Atoi: parsing "abc": invalid syntax
```

Разберём механику по шагам:

1. Сигнатура функции — `func Atoi(s string) (int, error)`. Если функция в Go может завершиться сбоем (некорректный ввод, нет файла, оборвалась сеть), она **по соглашению возвращает `error` последним значением**.
2. Специальное значение **`nil`** для типа `error` означает **«ошибки нет, операция прошла успешно»**. (Технически `error` — это встроенный интерфейс с одним методом `Error() string`; подробно интерфейсы мы разберём в Модуле 3, а сейчас достаточно понимать `error` как значение, которое либо равно `nil`, либо содержит описание проблемы.)
3. Сразу после вызова вы проверяете `if err != nil`. Если ошибка есть — вы **не используете** первый результат (`badID` содержит нулевое значение `0`), а обрабатываете сбой и выходите.

Заметьте, насколько честной стала программа: вы не можете «забыть» о возможности ошибки, потому что компилятор заставит вас принять второе значение (а осознанно игнорировать его через `_` — красный флаг на любом код-ревью).

## Главная идиома Go: плоский «счастливый путь» (*early return*)

Сравните два стиля написания одной и той же функции проверки и расчёта.

**Плохо (глубокая лесенка `else`):**
```go
func parsePositiveID(raw string) (int, bool) {
	id, err := strconv.Atoi(raw)
	if err == nil {
		if id > 0 {
			return id, true
		} else {
			return 0, false
		}
	} else {
		return 0, false
	}
}
```

**Хорошо (ранний выход — идиома Go):**
```go
func parsePositiveID(raw string) (int, bool) {
	id, err := strconv.Atoi(raw)
	if err != nil {
		return 0, false
	}
	if id <= 0 {
		return 0, false
	}
	return id, true
}
```

Посмотрите на второй вариант глазами читателя:
* Все ошибочные случаи отсекаются сразу через короткие `if ... { return ... }` (*guard clauses*) и прижимаются к отступу.
* **Основная логика («счастливый путь») всегда идёт ровно вдоль левого края** — без вложенных `else` и уходящих за край экрана отступов.

Это правило настолько важно в Go, что его сформулировали как поговорку сообщества: *«выравнивайте счастливый путь по левому краю»* (*indent error flow, keep the happy path left-aligned*).

## `if` с инициализатором + `err`: коротко, но не всегда

Когда результат функции не нужен дальше — важна только ошибка — удобно сочетать `if` с инициализатором:

```go
if err := checkTitle(title); err != nil {
	fmt.Println("Некорректное название:", err)
	return
}
```

А вот если вам нужно само значение (`id, err := strconv.Atoi(raw)`), не прячьте его внутри заголовка `if` — иначе `id` исчезнет сразу после закрывающей скобки `if`. Оставьте `id, err := ...` отдельной строкой, затем `if err != nil { return ... }`, а ниже спокойно работайте с `id`.

## Три типичные ошибки новичков с `error`

1. **Молчаливое игнорирование `_`:** запись `id, _ := strconv.Atoi(userInput)` прячет баг. На вводе `"abc"` переменная `id` молча станет `0`, и программа либо удалит не ту запись, либо сломается далеко от места причины.
2. **Использование результата до проверки `err != nil`:** если `err != nil`, возвращённое значение обычно ненадёжно (нулевое или неполное). Всегда проверяйте `err` первой строкой.
3. **Затенение `err` внутри вложенного `if`:** та самая ловушка из урока 10. Если вы объявили `err` снаружи и написали `val, err := ...` внутри `if`, внешняя `err` не обновится.

> [!check] Проверь понимание
> Что выведет код ниже?
> ```go
> n, err := strconv.Atoi("007")
> fmt.Println(n, err == nil)
> ```
>
> Выведет `7 true`. Строка `"007"` — корректное десятичное число, `strconv.Atoi` разберёт его в `7` и вернёт `err == nil`.

**Упражнение 1 (Базовое). Безопасный разбор порта.**  
Напишите функцию `parsePort(raw string) (int, bool)`, которая принимает строку (например, `"8080"`, `"0"`, `"70000"`, `"http"`), разбирает её через `strconv.Atoi` и проверяет, что порт лежит в допустимом диапазоне `1..65535`. Используйте стиль раннего выхода (без единого `else`).

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"fmt"
> 	"strconv"
> 	"strings"
> )
>
> func parsePort(raw string) (int, bool) {
> 	port, err := strconv.Atoi(strings.TrimSpace(raw))
> 	if err != nil {
> 		return 0, false
> 	}
> 	if port < 1 || port > 65535 {
> 		return 0, false
> 	}
> 	return port, true
> }
>
> func main() {
> 	for _, sample := range []string{"8080", " 443 ", "0", "70000", "http"} {

> 	}
> }
> ```
> Заметьте: `strings.TrimSpace` убирает случайные пробелы по краям, а счастливый путь `return port, true` лежит ровно на левом крае.

```go
func parsePriceKop(rawRub, rawKop string) (int64, bool) {

				if kop >= 0 && kop < 100 {

				} else {
					return 0, false
				}
			} else {
				return 0, false
			}
		} else {
			return 0, false
		}
	} else {
		return 0, false
	}
}
```

> func parsePriceKop(rawRub, rawKop string) (int64, bool) {

**Упражнение 3 (Со звёздочкой \*). Объясни почему.**  
В Упражнении 1 наша `parsePort` возвращала `(int, bool)`. Когда пользователь вводит `"70000"` или `"http"`, в обоих случаях он получает одинаковый `false`. Почему для реального CLI-приложения вроде `BookmarkFlow` возвращать `(int, error)` гораздо полезнее, чем `(int, bool)`?

> [!solution] Показать решение
> Значение `bool` умеет сказать только «да» или «нет», скрывая причину. Если `parsePort` возвращает `error`, то при `"http"` программа честно сообщит «порт должен быть числом», а при `"70000"` — «порт вне диапазона 1..65535». Чем точнее ошибка, тем быстрее пользователь (и инженер на дежурстве) исправляет проблему.
