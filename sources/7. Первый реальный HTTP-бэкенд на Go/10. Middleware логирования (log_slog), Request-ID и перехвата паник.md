*Разбираем реальный код `project/final/middleware.go`: передачу `X-Request-ID` через контекст, запись HTTP-статуса обёрткой `statusRecorder` для `log/slog` и перехват паник без обвала сервера.*

Когда сервис работает в терминале под вашей командой, ошибку видно сразу. Но когда через сервер проходит тысяча запросов в минуту, а один из них падает, в журнале без привязки логов к конкретному запросу не разобраться: какая запись относится к упавшему `POST`, а какая к соседнему `GET`? А если обработчик поймает панику по разыменованию `nil`, без защиты упадёт весь HTTP-процесс, оборвав соединения сотням других пользователей.

В `project/final/middleware.go` эту тройную страховку обеспечивают `RequestIDMiddleware`, `LoggingMiddleware` и `RecoverMiddleware`.

## 1. Идентификатор запроса и неэкспортируемый ключ контекста

Первый слой `RequestIDMiddleware` решает задачу сквозной трассировки логов одного запроса:

```go
type ctxKey string

const requestIDKey ctxKey = "request_id"

// RequestIDFromContext возвращает идентификатор запроса из контекста.
func RequestIDFromContext(ctx context.Context) string {
	id, _ := ctx.Value(requestIDKey).(string)
	return id
}

func RequestIDMiddleware() Middleware {
	var seq atomic.Uint64
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			id := r.Header.Get("X-Request-ID")
			if id == "" {
				id = fmt.Sprintf("req-%d", seq.Add(1))
			}
			w.Header().Set("X-Request-ID", id)
			ctx := context.WithValue(r.Context(), requestIDKey, id)
			next.ServeHTTP(w, r.WithContext(ctx))
		})
	}
}
```

Обратите внимание на две важные тонкости:

1. **Зачем нужен свой тип `type ctxKey string`?** Ключ в `context.WithValue` сравнивается по паре `(динамический тип, значение)`. Если положить простую строку `"request_id"`, любая сторонняя библиотека, тоже решившая положить `"request_id"`, молча перезапишет ваше значение. Неэкспортируемый тип `ctxKey` в вашем пакете гарантирует полную защиту от коллизий ключей.
2. **Не создавайте `r.WithContext` зря и не мутируйте `r` напрямую.** Метод `r.WithContext(ctx)` возвращает мелкую копию структуры `http.Request` с новым контекстом — дальше по цепочке идёт именно она. При этом сам клиент тоже получает заголовок `X-Request-ID` в ответе: если пользователь сообщит об ошибке, по этому ID легко найти точную строку в логах.

## 2. Как логер узнаёт статус ответа: `statusRecorder`

В [[10. Структурированное логирование на log_slog]] мы познакомились со структурированным журналом `log/slog`. Но если посмотреть на интерфейс `http.ResponseWriter`, у него **нет** метода `StatusCode()`. Как `LoggingMiddleware` узнаёт, какой код вернул обработчик — `201`, `404` или `500`?

Приём прост — **встраивание интерфейса в обёртку** с перехватом метода `WriteHeader`:

```go
type statusRecorder struct {
	http.ResponseWriter
	status int
}

func (sr *statusRecorder) WriteHeader(code int) {
	sr.status = code
	sr.ResponseWriter.WriteHeader(code)
}
```

Внутри `LoggingMiddleware` мы создаём `rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}` и передаём `rec` дальше в `next.ServeHTTP(rec, r)`. Зачем сразу ставить `status: http.StatusOK`? По правилам `net/http`, если обработчик просто вызвал `w.Write(...)` без явного `w.WriteHeader(...)`, сервер автоматически отправляет статус `200 OK`. Начальное значение `http.StatusOK` учитывает этот случай.

После возврата из `next` логер пишет структурированное JSON-событие:

```go
logger.Info("http request",
	slog.String("request_id", RequestIDFromContext(r.Context())),
	slog.String("method", r.Method),
	slog.String("path", r.URL.Path),
	slog.Int("status", rec.status),
	slog.Int64("duration_ms", time.Since(start).Milliseconds()),
)
```

При реальном запуске `BookmarkFlow` в терминале появляется аккуратная JSON-строка, которую легко парсить любыми инструментами:

```json
{"time":"2026-11-23T20:03:57.35097461+04:00","level":"INFO","msg":"http request","request_id":"req-2","method":"POST","path":"/api/v1/bookmarks","status":201,"duration_ms":0}
```

## 3. Перехват паник: `RecoverMiddleware`

Стандартный `http.Server` действительно перехватывает панику внутри горутины запроса и не роняет процесс, но при этом просто **обрывает** TCP-соединение без HTTP-ответа и пишет сырой стек в `stderr`. Гораздо аккуратнее перехватить панику в своём `RecoverMiddleware` и отдать клиенту понятный `500 Internal Server Error` в формате JSON:

```go
func RecoverMiddleware(logger *slog.Logger) Middleware {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			defer func() {
				if rec := recover(); rec != nil {
					logger.Error("panic recovered",
						slog.String("request_id", RequestIDFromContext(r.Context())),
						slog.Any("panic", rec),
					)
					writeJSONError(w, http.StatusInternalServerError, "внутренняя ошибка сервера")
				}
			}()
			next.ServeHTTP(w, r)
		})
	}
}
```

Помните: `recover()` работает **только** в той же самой горутине, где произошла паника. Если обработчик породил фоновую горутину `go doWork()`, то `RecoverMiddleware` её панику не поймает — фоновые горутины нужно защищать отдельным `defer recover()` (либо вообще не допускать в них паник).

## Подводный камень: паника после начала записи ответа

Что случится, если обработчик сначала вызвал `w.WriteHeader(http.StatusOK)`, успел отправить половину JSON-тела, а потом запаниковал? В `RecoverMiddleware` сработает `writeJSONError(..., 500, ...)`, но статус `200` уже отправлен клиенту! `statusRecorder` при этом перезапишет поле `sr.status` на `500` (в логе останется 500), а клиент получит `200` с обрывком JSON и припиской ошибки. Если доработать `statusRecorder` булевым флагом `wroteHeader`, повторный `WriteHeader` можно отслеживать точнее.

> [!check] Проверь понимание
> В `RequestIDMiddleware` переменная `var seq atomic.Uint64` объявлена **вне** возвращаемой функции `http.HandlerFunc`, но внутри `RequestIDMiddleware()`. Как долго живёт этот счётчик и безопасно ли его инкрементировать из разных запросов?
>
> Счётчик захватывается замыканием и живёт всё время жизни обёрнутого сервера (один счётчик на один вызов `RequestIDMiddleware()`). Поскольку используется `atomic.Uint64`, одновременные вызовы `seq.Add(1)` из сотен горутин полностью потокобезопасны.

## Практика

**Упражнение 1 (Базовое). Проверка обёртки `statusRecorder`.**  
Что попадёт в поле `status` лога, если обработчик внутри маршрута сделает следующее:
```go
func(w http.ResponseWriter, r *http.Request) {
	w.Write([]byte("pong"))
}
```
А если он сначала вызовет `w.WriteHeader(http.StatusNoContent)`, а затем (по ошибке) `w.WriteHeader(http.StatusOK)`?

> [!solution] Показать решение
> В первом случае `WriteHeader` не вызывался напрямую, поэтому в `rec.status` останется начальное значение `200` (`http.StatusOK`) — и именно оно совпадает с реальным статусом ответа. Во втором случае первый вызов поставит `204` и отправит заголовки клиенту, а второй обновит `sr.status = 200`, хотя клиент реально получил `204`. Чтобы этого избежать, в `statusRecorder.WriteHeader` обычно добавляют флаг `wrote bool` и запоминают статус только при первом вызове.

**Упражнение 2 (Практическое). Защита от двойного `WriteHeader` в `statusRecorder`.**  
Доработайте `statusRecorder` так, чтобы:
1. При первом вызове `WriteHeader` или `Write` выставлялся флаг `wrote = true` (и при первом `Write` без предварительного `WriteHeader` фиксировался `sr.status = http.StatusOK`).
2. Повторный вызов `WriteHeader` уже не менял `sr.status`.

> [!solution] Показать решение
> ```go
> type statusRecorder struct {
> 	http.ResponseWriter
> 	status int
> 	wrote  bool
> }
>
> func (sr *statusRecorder) WriteHeader(code int) {
> 	if !sr.wrote {
> 		sr.status = code
> 		sr.wrote = true
> 	}
> 	sr.ResponseWriter.WriteHeader(code)
> }
>
> func (sr *statusRecorder) Write(b []byte) (int, error) {
> 	if !sr.wrote {
> 		sr.status = http.StatusOK
> 		sr.wrote = true
> 	}
> 	return sr.ResponseWriter.Write(b)
> }
> ```
> Теперь `sr.status` всегда строго соответствует первому реальному статусу, отправленному по сети.

**Упражнение 3 (Со звёздочкой \*). Валидация входящего `X-Request-ID`.**  
Сейчас `RequestIDMiddleware` доверяет заголовку `X-Request-ID` от клиента. Представьте, что злоумышленник передаёт в этом заголовке строку из 10 000 символов или управляющие символы. Как защититься, сохранив поддержку разумных клиентских ID (до 64 печатных ASCII-символов)?

> [!solution] Показать решение
> Добавьте компактную проверку `isValidRequestID(id)`: если длина равна 0, больше 64 или встречаются символы вне диапазона `[A-Za-z0-9._-]`, сгенерируйте собственный `req-%d` вместо доверия клиенту:
> ```go
> func isValidRequestID(id string) bool {
> 	if len(id) == 0 || len(id) > 64 {
> 		return false
> 	}
> 	for i := 0; i < len(id); i++ {
> 		c := id[i]
> 		isAlnum := (c >= 'a' && c <= 'z') || (c >= 'A' && c <= 'Z') || (c >= '0' && c <= '9')
> 		if !isAlnum && c != '-' && c != '_' && c != '.' {
> 			return false
> 		}
> 	}
> 	return true
> }
> ```

---

В `RequestIDMiddleware` мы уже коснулись контекста `r.Context()`. Но кроме передачи значений по цепочке вызовов у контекста в HTTP есть куда более важная роль — вовремя останавливать работу, когда клиент закрыл вкладку или серверный таймер истёк. Этому посвящён следующий урок.
