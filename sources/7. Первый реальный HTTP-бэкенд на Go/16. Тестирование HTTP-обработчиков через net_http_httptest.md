*Учимся тестировать HTTP-обработчики и middleware без поднятия сетевых сокетов через `httptest.NewRequest` и `httptest.NewRecorder` на примерах из `project/final/server_test.go`.*

> «Автор теста должен стремиться помочь программисту, которому придётся разбираться в причинах его падения.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

Если для каждого теста обработчика поднимать реальный сервер на TCP-порту `:8080`, тесты станут медленными, начнут спорить за свободные порты при параллельном запуске и будут зависеть от сетевых настроек машины. Но вспомните второй урок: любой обработчик в Go — это просто метод `ServeHTTP(w http.ResponseWriter, r *http.Request)`. Чтобы проверить его логику, реальный сокет не нужен: достаточно подставить искусственный запрос и записывающий буфер ответа в памяти.

Для этого в стандартной библиотеке Go есть пакет `net/http/httptest`.

## Два главных инструмента: `NewRequest` и `NewRecorder`

Пакет `httptest` предлагает два строительных блока для молниеносных модульных HTTP-тестов:

1. **`httptest.NewRequest(method, target, body)`** — создаёт готовый `*http.Request` специально для серверных обработчиков. В отличие от `http.NewRequest`, эта функция **не возвращает `error`** (паникует сразу на битом URL в тесте, убирая лишний `if err != nil`) и автоматически заполняет поля вроде `RemoteAddr` и `Proto`, как будто запрос действительно пришёл от клиента по сети.
2. **`httptest.NewRecorder()`** — возвращает `*httptest.ResponseRecorder`, реализующий интерфейс `http.ResponseWriter`. Вместо отправки байтов в TCP-сокет он просто складывает код статуса в поле `rec.Code`, заголовки в `rec.Header()` и тело ответа в буфер `rec.Body`.

Посмотрим, как в `project/final/server_test.go` на них проверяется `RecoverMiddleware` — меньше 15 строк без единого сокета:

```go
func TestRecoverMiddleware(t *testing.T) {
	panicking := http.HandlerFunc(func(http.ResponseWriter, *http.Request) {
		panic("unexpected bug")
	})
	h := Chain(panicking, RequestIDMiddleware(), RecoverMiddleware(slog.New(slog.DiscardHandler)))

	rec := httptest.NewRecorder()
	h.ServeHTTP(rec, httptest.NewRequest(http.MethodGet, "/boom", nil))
	if rec.Code != http.StatusInternalServerError {
		t.Fatalf("status = %d, want 500", rec.Code)
	}
	if !bytes.Contains(rec.Body.Bytes(), []byte("внутренняя ошибка сервера")) {
		t.Fatalf("unexpected recover body: %s", rec.Body.String())
	}
}
```

Заметьте новинку Go 1.24 — `slog.DiscardHandler`. В тестах нас интересуют HTTP-статус и тело ответа, а JSON-строка о перехваченной панике только засорила бы вывод `go test -v`. `slog.New(slog.DiscardHandler)` тихо отбрасывает все записи лога без лишних заглушек.

## Табличные тесты ошибок и валидации

В [[17. Табличные тесты, подтесты t.Run и временные каталоги t.TempDir]] мы освоили табличный стиль `[]struct{...}` и временную папку `t.TempDir()`. С `httptest` они сочетаются идеально. Взгляните на `TestBookmarkFlowValidationAndErrorCases` из `project/final/server_test.go`:

```go
func TestBookmarkFlowValidationAndErrorCases(t *testing.T) {
	store, err := OpenFileStore(filepath.Join(t.TempDir(), "b.json"))
	if err != nil {
		t.Fatalf("OpenFileStore failed: %v", err)
	}
	srv := NewServer(store, nil, slog.New(slog.DiscardHandler))

	tests := []struct {
		name       string
		method     string
		target     string
		body       string
		wantStatus int
	}{
		{
			name:       "invalid json syntax",
			method:     http.MethodPost,
			target:     "/api/v1/bookmarks",
			body:       `{"title":`,
			wantStatus: http.StatusBadRequest,
		},
		{
			name:       "unknown field rejected",
			method:     http.MethodPost,
			target:     "/api/v1/bookmarks",
			body:       `{"title":"Go","url":"https://go.dev","extra":1}`,
			wantStatus: http.StatusBadRequest,
		},
		{
			name:       "invalid url scheme",
			method:     http.MethodPost,
			target:     "/api/v1/bookmarks",
			body:       `{"title":"Go","url":"ftp://go.dev"}`,
			wantStatus: http.StatusUnprocessableEntity,
		},
		{
			name:       "invalid path id",
			method:     http.MethodGet,
			target:     "/api/v1/bookmarks/not-a-number",
			wantStatus: http.StatusBadRequest,
		},
		{
			name:       "not found id",
			method:     http.MethodGet,
			target:     "/api/v1/bookmarks/999",
			wantStatus: http.StatusNotFound,
		},
	}

	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			rec := httptest.NewRecorder()
			req := httptest.NewRequest(tc.method, tc.target, strings.NewReader(tc.body))
			srv.ServeHTTP(rec, req)
			if rec.Code != tc.wantStatus {
				t.Fatalf("got status %d, want %d (body: %s)", rec.Code, tc.wantStatus, rec.Body.String())
			}
		})
	}
}
```

Ключевая деталь здесь — мы вызываем `srv.ServeHTTP(rec, req)`, а **не** отдельный метод `srv.handleCreate(rec, req)` напрямую. Почему это так важно? При прямом вызове `srv.handleGet` мимо `ServeMux` вы бы не проверили ни шаблоны пути `{id}` (`r.PathValue("id")`), ни выбор метода, ни цепочку middleware. Прогон через `srv.ServeHTTP` тестирует всю сборку `NewServer` целиком за доли миллисекунды.

При падении любого кейса `t.Fatalf` печатает не только код, но и тело ответа `(body: %s)` — это сразу показывает причину ошибки без запуска отладчика.

## Подводный камень: `rec.Header()` против `rec.Result().Header` и переиспользование `rec`

Две мелкие ловушки `httptest.ResponseRecorder`, о которых полезно помнить:

1. **Не переиспользуйте один `rec` в двух запросах.** На каждый вызов `srv.ServeHTTP` создавайте свежий `rec := httptest.NewRecorder()`. Иначе старые заголовки и хвост `rec.Body` от первого запроса смешаются со вторым.
2. **Если обработчик вообще не вызывал `WriteHeader` и `Write`**, `rec.Code` по умолчанию равен `200` (`http.StatusOK`), как и в реальном `net/http`. А чтобы прочитать ответ как полноценный `*http.Response` (например, проверить `Cookie` или `Content-Length`), у рекордера есть метод `res := rec.Result(); defer res.Body.Close()`.

> [!check] Проверь понимание
> Можно ли в одном тесте проверить параметр пути `r.PathValue("id")`, вызвав напрямую метод `srv.handleGet(rec, req)` для URL `"/api/v1/bookmarks/42"`?
>
> Нет! Поле `r.PathValue("id")` заполняет именно маршрутизатор `http.ServeMux` в момент сопоставления шаблона `"/api/v1/bookmarks/{id}"`. Если вызвать `srv.handleGet` в обход `ServeMux`, `r.PathValue("id")` вернёт пустую строку `""`, и тест получит `400 Bad Request`. Тестируйте обработчики через `srv.ServeHTTP(rec, req)`.

## Практика

**Упражнение 1 (Базовое). Проверка JSON-ошибки, а не только статуса.**  
В таблице `TestBookmarkFlowValidationAndErrorCases` проверяется только `rec.Code`. Допишите внутри `t.Run` декодирование тела `rec.Body` в `var errResp struct { Error string ` + "`json:\"error\"`" + ` }` и убедитесь, что поле `errResp.Error` не пустое и заголовок `Content-Type` начинается с `"application/json"`.

> [!solution] Показать решение
> ```go
> ct := rec.Header().Get("Content-Type")
> if !strings.HasPrefix(ct, "application/json") {
> 	t.Fatalf("Content-Type = %q, want application/json", ct)
> }
> var errResp struct {
> 	Error string `json:"error"`
> }
> if err := json.Unmarshal(rec.Body.Bytes(), &errResp); err != nil {
> 	t.Fatalf("invalid json error body %q: %v", rec.Body.String(), err)
> }
> if errResp.Error == "" {
> 	t.Fatalf("empty error message in body: %s", rec.Body.String())
> }
> ```
> Такая проверка гарантирует соблюдение контракта JSON-ошибок, даже если кто-то случайно заменит `writeJSONError` на текстовый `http.Error`.

**Упражнение 2 (Практическое). Юнит-тест превышения лимита тела (`413`).**  
Напишите тест `TestBodyTooLarge`, который отправляет на `POST /api/v1/bookmarks` корректный JSON с заголовком длиной свыше 1 МиБ (`strings.Repeat("a", (1<<20)+100)`) и проверяет, что `Server` возвращает `http.StatusRequestEntityTooLarge` (`413`).

> [!solution] Показать решение
> ```go
> func TestBodyTooLarge(t *testing.T) {
> 	store, err := OpenFileStore(filepath.Join(t.TempDir(), "big.json"))
> 	if err != nil {
> 		t.Fatalf("OpenFileStore failed: %v", err)
> 	}
> 	srv := NewServer(store, nil, slog.New(slog.DiscardHandler))
>
> 	bigBody := fmt.Sprintf(`{"title":"%s","url":"https://go.dev"}`, strings.Repeat("a", (1<<20)+100))
> 	rec := httptest.NewRecorder()
> 	req := httptest.NewRequest(http.MethodPost, "/api/v1/bookmarks", strings.NewReader(bigBody))
> 	srv.ServeHTTP(rec, req)
>
> 	if rec.Code != http.StatusRequestEntityTooLarge {
> 		t.Fatalf("got status %d, want 413 (body: %s)", rec.Code, rec.Body.String())
> 	}
> }
> ```
> `MaxBytesReader` останавливает чтение ровно на границе `1 << 20`, и обработчик отдаёт `413` без выделения лишней памяти на весь запрос.

**Упражнение 3 (Со звёздочкой \*). Проверка сохранения переданного `X-Request-ID`.**  
Напишите тест для `RequestIDMiddleware`, который проверяет два случая: (1) без заголовка `X-Request-ID` сервер сам генерирует непустой `X-Request-ID` и кладёт его в `r.Context()` (читаем через `RequestIDFromContext`); (2) если клиент прислал `req.Header.Set("X-Request-ID", "trace-42")`, то обработчик и ответ получают именно `"trace-42"`.

> [!solution] Показать решение
> ```go
> func TestRequestIDMiddleware(t *testing.T) {
> 	var gotFromCtx string
> 	h := Chain(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
> 		gotFromCtx = RequestIDFromContext(r.Context())
> 		w.WriteHeader(http.StatusOK)
> 	}), RequestIDMiddleware())
>
> 	rec1 := httptest.NewRecorder()
> 	h.ServeHTTP(rec1, httptest.NewRequest(http.MethodGet, "/", nil))
> 	if gotFromCtx == "" || rec1.Header().Get("X-Request-ID") != gotFromCtx {
> 		t.Fatalf("generated id mismatch: ctx=%q header=%q", gotFromCtx, rec1.Header().Get("X-Request-ID"))
> 	}
>
> 	rec2 := httptest.NewRecorder()
> 	req2 := httptest.NewRequest(http.MethodGet, "/", nil)
> 	req2.Header.Set("X-Request-ID", "trace-42")
> 	h.ServeHTTP(rec2, req2)
> 	if gotFromCtx != "trace-42" || rec2.Header().Get("X-Request-ID") != "trace-42" {
> 		t.Fatalf("propagated id mismatch: ctx=%q header=%q", gotFromCtx, rec2.Header().Get("X-Request-ID"))
> 	}
> }
> ```

---

`httptest.NewRecorder` прекрасно проверяет внутреннюю логику маршрутов и middleware. Но в `BookmarkFlow` есть функция, которая сама ходит по сети — `LinkChecker`. Ходить в настоящий Интернет из тестов нельзя (они упадут без Wi-Fi и будут нестабильными). В следующем уроке поднимем настоящий локальный HTTP-сервер прямо внутри теста через `httptest.NewServer` и прогоним весь набор тестов под детектором гонок `go test -race`.
