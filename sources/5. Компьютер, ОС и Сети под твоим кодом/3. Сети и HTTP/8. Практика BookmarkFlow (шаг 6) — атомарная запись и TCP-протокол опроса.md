Раньше `BookmarkFlow` сохранял закладки простым `os.WriteFile` и жил в рамках одного консольного запуска. При переходе к фоновому сервису проявляются две системные проблемы: сбой питания посреди `os.WriteFile` оставляет на диске битый JSON, а внешние утилиты не могут безопасно опрашивать закладки, не конфликтуя с записью.

В **`project/step06/`** мы решаем обе задачи: защищаем диск атомарным переименованием и поднимаем поверх хранилища текстовый TCP-сервер.

## Атомарная запись и `AtomicStore` (`atomic_store.go`)

Чтобы не повредить рабочий файл, `WriteFileAtomic` создаёт временный файл в **том же каталоге** (`filepath.Dir(path)`), пишет туда весь новый снимок, сбрасывает буферы ядра на диск вызовом `Sync()`, закрывает файл и атомарно подменяет ссылку через `os.Rename`:

```go
func WriteFileAtomic(path string, data []byte) error {
	dir := filepath.Dir(path)
	tmp, err := os.CreateTemp(dir, ".bookmarkflow-*.tmp")
	if err != nil {
		return fmt.Errorf("создание временного файла: %w", err)
	}
	tmpName := tmp.Name()
	cleanup := true
	defer func() {
		if cleanup {
			_ = os.Remove(tmpName)
		}
	}()

	if _, err := tmp.Write(data); err != nil {
		_ = tmp.Close()
		return fmt.Errorf("запись временного файла: %w", err)
	}
	if err := tmp.Sync(); err != nil {
		_ = tmp.Close()
		return fmt.Errorf("синхронизация на диск: %w", err)
	}
	if err := tmp.Close(); err != nil {
		return fmt.Errorf("закрытие временного файла: %w", err)
	}
	if err := os.Rename(tmpName, path); err != nil {
		return fmt.Errorf("атомарное переименование: %w", err)
	}
	cleanup = false
	return nil
}
```

Флаг `cleanup` вместе с `defer` удалит недописанный временный файл при любой ошибке; после успешного `os.Rename` мы сбрасываем `cleanup = false`.

Поверх `WriteFileAtomic` работает `AtomicStore` с мьютексом `sync.RWMutex`: чтения `Get`/`List` идут параллельно под `RLock`, а запись `Add` берёт эксклюзивный `Lock` и вызывает `flushLocked()`:

```go
type AtomicStore struct {
	mu     sync.RWMutex
	path   string
	nextID int
	items  []Bookmark
}

func (s *AtomicStore) Add(title, rawURL string) (Bookmark, error) {
	s.mu.Lock()
	defer s.mu.Unlock()
	bm := Bookmark{ID: s.nextID, Title: title, URL: rawURL}
	s.nextID++
	s.items = append(s.items, bm)
	if err := s.flushLocked(); err != nil {
		return Bookmark{}, err
	}
	return bm, nil
}

func (s *AtomicStore) List() []Bookmark {
	s.mu.RLock()
	defer s.mu.RUnlock()
	return slices.Clone(s.items)
}

func (s *AtomicStore) flushLocked() error {
	data, err := json.MarshalIndent(snapshot{NextID: s.nextID, Items: s.items}, "", "  ")
	if err != nil {
		return err
	}
	return WriteFileAtomic(s.path, data)
}
```

`List()` возвращает копию через `slices.Clone`, исключая гонки вне блокировки. Суффикс `Locked` в `flushLocked` — соглашение Go: метод вызывают только при уже захваченном `s.mu.Lock()`. При старте `OpenAtomicStore(path)` читает JSON обратно в `snapshot{NextID, Items}` (а при `os.ErrNotExist` создаёт пустое хранилище с `nextID = 1`).

## Конкурентный `TCPServer` и протокол (`tcp_server.go`)

TCP доставляет поток байтов без границ сообщений, поэтому мы вводим построчный протокол с разделителем `\n`:

| Команда | Ответ сервера | Назначение |
|---|---|---|
| `PING` | `PONG` | Проверка доступности |
| `COUNT` | `COUNT <n>` | Число закладок |
| `LIST` | Строки `<id> <title> <url>`, затем `END` | Вывод всех закладок |
| `GET <id>` | `OK <id> <title> <url>` или `ERR ...` | Поиск одной закладки |
| `QUIT` | `BYE` и закрытие сокета | Завершение сеанса |

Для многострочного `LIST` маркер `END` на отдельной строке обозначает конец ответа. Жизненный цикл `TCPServer` строится на `net.Listener` и `sync.WaitGroup`:

```go
type TCPServer struct {
	store *AtomicStore
	ln    net.Listener
	wg    sync.WaitGroup
}

func StartTCPServer(addr string, store *AtomicStore) (*TCPServer, error) {
	ln, err := net.Listen("tcp", addr)
	if err != nil {
		return nil, err
	}
	srv := &TCPServer{store: store, ln: ln}
	srv.wg.Add(1)
	go srv.acceptLoop()
	return srv, nil
}

func (s *TCPServer) Close() error {
	err := s.ln.Close()
	s.wg.Wait()
	return err
}

func (s *TCPServer) acceptLoop() {
	defer s.wg.Done()
	for {
		conn, err := s.ln.Accept()
		if err != nil {
			if errors.Is(err, net.ErrClosed) {
				return
			}
			continue
		}
		s.wg.Add(1)
		go func() {
			defer s.wg.Done()
			defer conn.Close()
			s.handleConn(conn)
		}()
	}
}
```

Вызов `s.ln.Close()` разблокирует `Accept()` с ошибкой `net.ErrClosed`. Проверка `errors.Is(err, net.ErrClosed)` отличает плановую остановку от случайного сбоя, а `s.wg.Wait()` ждёт завершения `acceptLoop` и всех клиентских горутин. Важно вызывать `s.wg.Add(1)` **до** `go`, иначе `Close()` успеет пройти `wg.Wait()` раньше запуска горутины.

Внутри `handleConn` команды читаются через `bufio.NewScanner(conn)`, а ответы пишутся в `bufio.NewWriter(conn)`:

```go
func (s *TCPServer) handleConn(conn net.Conn) {
	scanner := bufio.NewScanner(conn)
	writer := bufio.NewWriter(conn)

	for scanner.Scan() {
		line := strings.TrimSpace(scanner.Text())
		if line == "" {
			continue
		}
		fields := strings.Fields(line)
		cmd := strings.ToUpper(fields[0])

		switch cmd {
		case "PING":
			_, _ = fmt.Fprintln(writer, "PONG")
		case "COUNT":
			_, _ = fmt.Fprintf(writer, "COUNT %d\n", len(s.store.List()))
		case "LIST":
			for _, it := range s.store.List() {
				_, _ = fmt.Fprintf(writer, "%d %s %s\n", it.ID, it.Title, it.URL)
			}
			_, _ = fmt.Fprintln(writer, "END")
		case "GET":
			if len(fields) != 2 {
				_, _ = fmt.Fprintln(writer, "ERR usage: GET <id>")
				break
			}
			id, err := strconv.Atoi(fields[1])
			if err != nil {
				_, _ = fmt.Fprintln(writer, "ERR invalid id")
				break
			}
			bm, err := s.store.Get(id)
			if err != nil {
				_, _ = fmt.Fprintln(writer, "ERR not found")
				break
			}
			_, _ = fmt.Fprintf(writer, "OK %d %s %s\n", bm.ID, bm.Title, bm.URL)
		case "QUIT":
			_, _ = fmt.Fprintln(writer, "BYE")
			_ = writer.Flush()
			return
		default:
			_, _ = fmt.Fprintf(writer, "ERR unknown command %q\n", cmd)
		}
		_ = writer.Flush()
	}
}
```

Ключевая строка — `_ = writer.Flush()` после каждой команды и перед `return` в `QUIT`: без неё короткий ответ `PONG\n` останется в 4-килобайтном буфере, и клиент зависнет в ожидании.

## Сквозной тест на `"127.0.0.1:0"` (`tcp_server_test.go`)

`TestAtomicStoreAndTCPProtocol` проверяет всю цепочку: сохранение в `t.TempDir()`, повторное открытие `OpenAtomicStore`, запуск `StartTCPServer("127.0.0.1:0", reloaded)` на свободном эфемерном порту и диалог через `net.Dial("tcp", srv.Addr())`:

```go
	srv, err := StartTCPServer("127.0.0.1:0", reloaded)
```

## Подводные камни

**Ловушка 1. Временный файл в `/tmp` вместо каталога цели.**  
При вызове `os.CreateTemp("", "...")` файл окажется в `/tmp` (часто отдельной файловой системе `tmpfs`). Тогда `os.Rename` вернёт ошибку `EXDEV` (`invalid cross-device link`), потому что атомарное переименование работает только в пределах одной файловой системы.

**Ловушка 2. Порядок `defer` для `srv.Close()` и `conn.Close()`.**  
`defer srv.Close()` объявлен раньше `defer conn.Close()`. В порядке LIFO сначала закроется клиент `conn`, `handleConn` выйдет из цикла, и только потом `srv.Close()` без зависания пройдёт `wg.Wait()`.

> [!check] Проверь понимание
> Почему `flushLocked()` не захватывает `s.mu.Lock()` самостоятельно, хотя читает поля `s.nextID` и `s.items`?
>
> `sync.RWMutex` в Go не реентерабельный: `Add` уже удерживает `s.mu.Lock()`, и повторный захват внутри `flushLocked()` мгновенно заблокирует горутину навечно (*deadlock*).

## Практика

**Упражнение 1 (Базовое). Сбой записи в `WriteFileAtomic`.**  
В `bookmarks.json` уже лежит 50 закладок. Во время `Add` место на диске кончилось на `tmp.Write(data)`. Что станет с временным файлом и содержимым `bookmarks.json`?

> [!solution] Показать решение
> `tmp.Write` вернёт ошибку, `tmp.Close()` закроет дескриптор, а `defer` удалит недописанный `.bookmarkflow-*.tmp` (так как `cleanup == true`). Исходный `bookmarks.json` не открывался на запись — все 50 закладок останутся целы.

**Упражнение 2 (Практическое). Команда `ADD` в `handleConn`.**  
Добавьте в `switch cmd` ветку `ADD <title> <url>` (без пробелов в аргументах), которая вызывает `s.store.Add(fields[1], fields[2])` и отвечает `OK <id>` или `ERR ...`.

> [!solution] Показать решение
> ```go
> case "ADD":
> 	if len(fields) != 3 {
> 		_, _ = fmt.Fprintln(writer, "ERR usage: ADD <title> <url>")
> 		break
> 	}
> 	bm, err := s.store.Add(fields[1], fields[2])
> 	if err != nil {
> 		_, _ = fmt.Fprintf(writer, "ERR save failed: %v\n", err)
> 		break
> 	}
> 	_, _ = fmt.Fprintf(writer, "OK %d\n", bm.ID)
> ```
> `s.store.Add` уже защищён `s.mu.Lock()`, поэтому конкурентные вызовы безопасны.

**Упражнение 3 (Со звёздочкой \*). Зависание `srv.Close()` на «молчаливом» клиенте.**  
Клиент подключился, послал `PING` и замолчал, не отправляя `QUIT`. Почему `srv.Close()` повиснет в `s.wg.Wait()` и как это исправить?

> [!solution] Показать решение
> `s.ln.Close()` закрывает только слушающий сокет, а не уже принятые `net.Conn`. Горутина клиента остаётся висеть в `scanner.Scan()`, поэтому `wg.Done()` не вызывается. Решения два: ставить `conn.SetReadDeadline` перед каждым чтением либо хранить активные `net.Conn` в реестре под мьютексом и закрывать их при `srv.Close()`.
