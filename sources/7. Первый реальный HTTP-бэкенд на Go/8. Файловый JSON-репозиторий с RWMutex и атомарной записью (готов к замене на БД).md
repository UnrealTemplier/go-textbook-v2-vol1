*Разбираем потокобезопасное файловое хранилище `FileStore`: блокировки `sync.RWMutex`, защитные копии от алиасинга слайсов, откат в памяти при сбое записи и атомарный `os.Rename`.*

> «Любая функция ввода-вывода обязана считаться с вероятностью сбоя, и лишь наивный программист верит, что простое чтение или запись не могут завершиться ошибкой. Именно тогда, когда внезапно отказывают самые надёжные операции, нам нужнее всего знать почему.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

Пока программа была однопоточной консольной утилитой, она читала JSON-файл в память, меняла срез и перезаписывала файл в конце работы. В веб-сервере всё иначе: десять клиентов могут одновременно читать список закладок через `GET`, пока одиннадцатый создаёт новую запись через `POST`. Если не защитить внутренний слайс `items` и файл на диске, сервер упадёт от гонки данных или перетрёт JSON-файл половиной буфера.

Взглянем на реализацию `FileStore` из `project/final/store.go` — она аккуратно решает сразу три инженерные задачи: конкурентный доступ, целостность в памяти и целостность на диске.

## Много читателей, один писатель: `sync.RWMutex`

Поля структуры `FileStore` просты:

```go
type FileStore struct {
	mu     sync.RWMutex
	path   string
	nextID int
	items  []Bookmark
}
```

Вспомните `sync.RWMutex` из Модуля 4: читать данные параллельно безопасно сколь угодно многим горутинам, если никто в этот момент не меняет слайс. Поэтому:

- `Get` и `List` берут разделяемую блокировку на чтение `f.mu.RLock()` + `defer f.mu.RUnlock()`;
- `Create`, `Update` и `Delete` берут эксклюзивную блокировку на запись `f.mu.Lock()` + `defer f.mu.Unlock()`.

Обратите внимание: `ValidateInput` вызывается **до** захвата `f.mu.Lock()`. Некорректный запрос с пустым заголовком не задерживает других пользователей даже на микросекунду.

## Защита от алиасинга: `cloneBookmark`

Внутри структуры `Bookmark` есть поле `Tags []string`. Вспомните заголовок слайса `(ptr, len, cap)` из Модуля 3. Если `Get(id)` вернёт структуру `it` напрямую по значению, её слайс `Tags` продолжит указывать на **тот же самый базовый массив**, который лежит внутри `f.items` под защитой мьютекса:

```go
func cloneBookmark(b Bookmark) Bookmark {
	b.Tags = slices.Clone(b.Tags)
	return b
}
```

Зачем нужно это копирование? После возврата из `Get` или `List` блокировка `RUnlock()` уже отпущена. Если внешний код (или тест, или будущий обработчик) изменит элемент `got.Tags[0] = "hacked"`, он без `cloneBookmark` молча испортит данные внутри хранилища, а при одновременном доступе создаст гонку данных.

## Откат в памяти при ошибке записи на диск

Что случится, если `Create` увеличил `f.nextID`, добавил закладку в `f.items`, а при сохранении JSON на диск кончилось место или не хватило прав? Если просто вернуть `err`, в памяти закладка останется «призраком» с несуществующим на диске состоянием — до первого перезапуска сервиса!

Поэтому в `project/final/store.go` каждая операция записи перед возвратом ошибки **откатывает** изменения в памяти под той же эксклюзивной блокировкой `Lock`:

```go
	f.nextID++
	f.items = append(f.items, bm)
	if err := f.saveLocked(); err != nil {
		// Откатываем изменение в памяти, если запись на диск не удалась.
		f.items = f.items[:len(f.items)-1]
		f.nextID--
		return Bookmark{}, err
	}
```

Ту же дисциплину соблюдают `Update` (сохраняет `prev := f.items[idx]` и восстанавливает при сбое) и `Delete` (клонирует слайс `prev := slices.Clone(f.items)` перед `slices.Delete`). Память и диск никогда не расходятся.

## Атомарная перезапись: `writeFileAtomic`

В [[12. Безопасное сохранение файлов — временный файл и атомарный os.Rename]] мы разбирали, почему `os.WriteFile(f.path, data, ...)` опасен: функция сперва обрезает целевой файл до нуля байт, и при падении процесса посреди записи вы теряете вообще все закладки.

В `FileStore` используется надёжный четырёхшаговый шаблон в `writeFileAtomic`:

1. `os.CreateTemp(dir, ".bookmarkflow-*.tmp")` создаёт временный файл **в том же каталоге**, что и целевой `f.path` (чтобы остаться на одной файловой системе — иначе `os.Rename` не сможет сработать атомарно).
2. `tmp.Write(data)` записывает весь сериализованный JSON.
3. `tmp.Sync()` сбрасывает буферы ядра ОС на физический носитель, а `tmp.Close()` закрывает дескриптор.
4. `os.Rename(tmpName, path)` атомарно переключает запись каталога на новый файл.

Если на любом из первых трёх шагов случилась ошибка, отложенный `defer` с флагом `cleanup` удалит осиротевший временный файл через `os.Remove(tmpName)`. Обратите внимание на суффикс `Locked` у метода `saveLocked()` — это принятое в Go соглашение в именах: оно напоминает программисту, что метод не берёт мьютекс сам и вызывать его разрешено **только** при уже захваченном `f.mu.Lock()`.

## Честные пределы файлового хранилища

У `FileStore` есть граница применимости, которую важно понимать честно:

- Каждое изменение целиком переписывает весь JSON-файл на диск: при 200 закладках это доли миллисекунды, но на 200 000 записей каждая вставка начнёт тормозить.
- Блокировка `sync.RWMutex` работает внутри **одного** процесса. Запускать два экземпляра `BookmarkFlow` на одном и том же файле нельзя — они перетрут изменения друг друга.

Именно поэтому за интерфейсом `Store` в Томе 2 на место `FileStore` придёт полноценная база данных с транзакциями и индексами, при этом код `server.go` менять не придётся.

> [!check] Проверь понимание
> Почему в `writeFileAtomic` временный файл создают в `filepath.Dir(path)`, а не в системном `/tmp` (`os.TempDir()`)?
>
> `/tmp` и рабочий каталог данных часто смонтированы как разные файловые системы. Вызов `os.Rename` между разными файловыми системами завершается ошибкой `EXDEV` (`invalid cross-device link`) и теряет атомарность.

## Практика

**Упражнение 1 (Базовое). Откат при сбое.**  
Представьте, что в `FileStore.Update` убрали строчку восстановления `f.items[idx] = prev` в ветке `if err := f.saveLocked(); err != nil`. Что увидит пользователь, который вызовет `PUT /api/v1/bookmarks/1` (получив `500`), затем `GET /api/v1/bookmarks/1`, а потом перезапустит сервер?

> [!solution] Показать решение
> До перезапуска сервера `GET /api/v1/bookmarks/1` вернёт **новые** данные (хотя `PUT` завершился ошибкой `500`). А после перезапуска сервера с диска прочитается старый файл, и изменения внезапно «исчезнут». Восстановление `f.items[idx] = prev` удерживает память и файл в едином состоянии.

**Упражнение 2 (Практическое). Добавление счётчика записей с учётом конкурентности.**  
Добавьте к `*FileStore` метод `Count() int`, который безопасно возвращает текущее число закладок без копирования самих структур `Bookmark`. Какую блокировку он должен использовать?

> [!solution] Показать решение
> ```go
> func (f *FileStore) Count() int {
> 	f.mu.RLock()
> 	defer f.mu.RUnlock()
> 	return len(f.items)
> }
> ```
> Достаточно разделяемой блокировки `RLock`, потому что метод только читает длину слайса и ничего не изменяет.

**Упражнение 3 (Со звёздочкой \*). Взаимная блокировка (`deadlock`) при вызове метода из метода.**  
Почему метод `Create` не вызывает `f.save()` (которая брала бы `f.mu.Lock()`), а вызывает именно `f.saveLocked()` без блокировки? Что произошло бы, если бы `save()` снова вызвала `f.mu.Lock()`?

> [!solution] Показать решение
> Мьютексы `sync.Mutex` и `sync.RWMutex` в Go **не реентерабельны**: одна и та же горутина не может захватить один и тот же `Lock()` дважды. Повторный вызов `f.mu.Lock()` внутри `Create` навсегда заблокировал бы горутину, ожидающую освобождения самой себя (*deadlock*), и заморозил бы весь сервер для всех остальных читателей и писателей.
