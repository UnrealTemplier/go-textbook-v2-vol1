*Как вживую подсмотреть системные вызовы Go-программы через `strace`, заглянуть в виртуальную файловую систему `/proc` и найти прожорливый процесс с помощью `ps` и `top`.*

В прошлом уроке мы поверили таймеру на слово: буферизованный `bufio.Writer` обогнал прямую запись в файл в двадцать раз, и мы объяснили это сокращением числа системных вызовов `write`. Но инженер не гадает, когда можно посмотреть напрямую. Linux даёт рентген для любого запущенного процесса — без пересборки кода и без отладчика.

## `strace` — перехват системных вызовов в реальном времени

Утилита **`strace`** (*system call trace*) запускает программу под наблюдением ядра и печатает каждый системный вызов вместе с аргументами и результатом. Если нужно увидеть только работу с файлами и записью, достаточно отфильтровать вывод флагом `-e`:

```bash
strace -f -e trace=file,write ./writer -mode=raw
```

Обратите внимание на флаг **`-f`** (*follow forks/threads*). Программа на Go почти всегда работает на нескольких потоках ОС одновременно. Без `-f` утилита `strace` следит только за главным потоком и легко пропустит вызовы `write`, которые рантайм выполнил на другом потоке.

Соберём короткую программу, которая записывает 1 000 строк в файл либо напрямую через `f.WriteString`, либо через `bufio.Writer`:

```go
package main

import (
	"bufio"
	"flag"
	"fmt"
	"os"
)

func main() {
	mode := flag.String("mode", "raw", "режим записи: raw или bufio")
	out := flag.String("out", "urls.txt", "путь к выходному файлу")
	flag.Parse()

	f, err := os.Create(*out)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer f.Close()

	const line = "https://go.dev/doc/\n"
	if *mode == "bufio" {
		bw := bufio.NewWriter(f)
		for range 1000 {
			if _, err := bw.WriteString(line); err != nil {
				fmt.Fprintln(os.Stderr, err)
				os.Exit(1)
			}
		}
		if err := bw.Flush(); err != nil {
			fmt.Fprintln(os.Stderr, err)
			os.Exit(1)
		}
		return
	}

	for range 1000 {
		if _, err := f.WriteString(line); err != nil {
			fmt.Fprintln(os.Stderr, err)
			os.Exit(1)
		}
	}
}
```

Соберём бинарник (`go build -o writer main.go`) и сравним число вызовов `write` в обоих режимах с помощью флага `-c` (*count* — сводная таблица вместо тысячи строк):

```text
$ strace -f -c -e trace=write ./writer -mode=raw -out=/tmp/raw.txt
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
100.00    0.004120           4      1000           write

$ strace -f -c -e trace=write ./writer -mode=bufio -out=/tmp/buf.txt
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
100.00    0.000042           8         5           write
```

Цифры снимают всякие сомнения. В режиме `raw` программа 1 000 раз пересекла границу ядра, передавая по 20 байт. С `bufio.Writer` 20 000 байт уложились ровно в **5 вызовов `write`** (по 4 096 байт и один остаток при `Flush`).

Если убрать `-c` и оставить `-e trace=file,write`, видны и точные пути файлов, и ошибки ядра вроде `-1 ENOENT (No such file or directory)`. Именно так за секунды находят, какой именно файл конфигурации программа безуспешно ищет при старте.

## Виртуальная файловая система `/proc`

В Linux существует каталог **`/proc`**, но на диске этих файлов нет. Это виртуальная файловая система (*procfs*): когда вы читаете файл внутри `/proc`, ядро на лету формирует текст прямо из своих внутренних таблиц процессов.

У каждого запущенного процесса есть собственный каталог `/proc/<PID>/`, а для текущей программы всегда работает символическая ссылка `/proc/self/`. Вот четыре файла и каталога, к которым разработчик обращается чаще всего:

| Путь в `/proc/<PID>/` | Что показывает | Когда пригождается |
|---|---|---|
| `status` | Имя процесса, `Pid`, `PPid`, число потоков `Threads`, реальная память `VmRSS` | Быстро проверить, не раздувается ли потребление памяти |
| `cmdline` | Командная строка запуска (аргументы разделены нулевым байтом `\x00`) | Узнать, с какими флагами запущен чужой или фоновый сервис |
| `environ` | Переменные окружения, с которыми стартовал процесс (разделены `\x00`) | Проверить, долетел ли `APP_ENV` или `PORT` до процесса |
| `fd/` | Каталог символических ссылок с номерами всех открытых файловых дескрипторов | Поймать утечку незакрытых файлов и сетевых сокетов |

Поскольку `cmdline` и `environ` разделяют элементы нулевым байтом, в терминале их удобно читать через `tr '\0' '\n'`:

```bash
cat /proc/4821/cmdline | tr '\0' ' '; echo
ls -la /proc/4821/fd
```

Последняя команда покажет привычную тройку `0`, `1`, `2` (потоки ввода-вывода) и каждый открытый файл или сокет с его номером дескриптора. Если число записей в `fd/` неуклонно растёт с каждой минутой работы сервера, значит где-то забыли `Close()`.

Поскольку `/proc` притворяется обычными файлами, Go-программа способна сама прочитать собственную статистику без всяких внешних утилит:

```go
package main

import (
	"bufio"
	"fmt"
	"os"
	"strings"
)

func main() {
	f, err := os.Open("/proc/self/status")
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	defer f.Close()

	scanner := bufio.NewScanner(f)
	for scanner.Scan() {
		line := scanner.Text()
		if strings.HasPrefix(line, "Pid:") ||
			strings.HasPrefix(line, "Threads:") ||
			strings.HasPrefix(line, "VmRSS:") {
			fmt.Println(line)
		}
	}

	fds, err := os.ReadDir("/proc/self/fd")
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Printf("Открытых дескрипторов: %d\n", len(fds))
}
```

*(NOTE: `/proc` — особенность Linux; на macOS и Windows этого каталога нет, там для похожей диагностики используют системные утилиты вроде `dtruss`/`lsof` или Process Monitor.)*

## Общая картина: `ps aux` и `top`

Прежде чем заглядывать в `/proc/<PID>/` или подключать `strace -p <PID>` к работающему сервису, нужно узнать его `PID` и понять, кто вообще нагружает машину.

Команда **`ps aux`** делает моментальный снимок всех процессов системы:

```text
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
ut        4821  0.3  0.2 712480 14208 ?        Ssl  11:10   0:04 ./bookmarkflow
```

Здесь `VSZ` — зарезервированная виртуальная память (у Go-программ она часто выглядит пугающе большой — сотни мегабайт), а **`RSS`** (*Resident Set Size*) — реально занятая оперативная память в килобайтах (в примере около 14 МБ). На нехватку памяти указывает именно рост `RSS`.

Если нужна не статическая фотография, а живой монитор, запускают **`top`**. Раз в пару секунд он обновляет список процессов, отсортированный по нагрузке на CPU. Клавиша `M` пересортирует таблицу по памяти (`RES`), клавиша `P` вернёт сортировку по процессору, а `q` закроет утилиту.

## Подводные камни

**Ловушка 1. Подключать `strace` к нагруженному боевому сервису.**  
Каждый системный вызов под `strace` дважды останавливает отслеживаемый процесс (на входе в ядро и на выходе). На сервисе с тысячами запросов в секунду это способно замедлить программу в разы. Используйте `strace` локально, на тестовом стенде или кратковременно с узким фильтром `-e`.

**Ловушка 2. Путать `VSZ` и `RSS` в `ps aux`.**  
Рантайм Go заранее резервирует крупный кусок виртуального адресного пространства, не заполняя его физическими страницами. Высокий `VSZ` при стабильном низком `RSS` — нормальное поведение, а не утечка памяти.

> [!check] Проверь понимание
> Вы запустили `strace -e trace=write ./app` для многопоточной Go-программы и увидели подозрительно мало вызовов `write`, хотя программа точно записала тысячу строк в файл. Что вы забыли добавить в команду?
>
> Флаг **`-f`** (`strace -f -e trace=write ./app`). Без него `strace` отслеживает только исходный поток ОС, тогда как рантайм Go мог выполнить часть вызовов `write` на других потоках.

## Практика

**Упражнение 1 (Базовое). Читаем след `strace`.**  
При запуске утилиты `bookmarkflow` вы получили три строки вывода `strace`:

```text
openat(AT_FDCWD, "/etc/bookmarkflow.json", O_RDONLY|O_CLOEXEC) = -1 ENOENT (No such file or directory)
openat(AT_FDCWD, "./bookmarks.json", O_RDONLY|O_CLOEXEC)       = 3
read(3, "{\"items\":[]}\n", 512)                                = 13
```

Опишите по шагам, что сделала программа, и какой номер дескриптора получил открытый файл.

> [!solution] Показать решение
> 1. Программа попыталась открыть `/etc/bookmarkflow.json` только для чтения, но ядро вернуло ошибку `ENOENT` — такого файла нет.
> 2. В качестве запасного варианта она открыла `./bookmarks.json` в текущем рабочем каталоге; ядро выдало файловый дескриптор **`3`** (дескрипторы `0`, `1`, `2` уже заняты `stdin`, `stdout` и `stderr`).
> 3. Программа прочитала 13 байт (`{"items":[]}\n`) из дескриптора `3` в буфер размером 512 байт.

**Упражнение 2 (Практическое). Проверка утечки дескрипторов через `/proc/self/fd`.**  
Напишите функцию `CountOpenFDs() (int, error)`, которая считает число записей в `/proc/self/fd`. В `main()` выведите счётчик до открытия временного файла `os.CreateTemp`, сразу после его создания и после `f.Close()`, убедившись, что число вернулось к исходному.

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"fmt"
> 	"os"
> )
>
> func CountOpenFDs() (int, error) {
> 	entries, err := os.ReadDir("/proc/self/fd")
> 	if err != nil {
> 		return 0, err
> 	}
> 	return len(entries), nil
> }
>
> func main() {
> 	before, err := CountOpenFDs()
> 	if err != nil {
> 		panic(err)
> 	}
>
> 	f, err := os.CreateTemp("", "fdcheck-*")
> 	if err != nil {
> 		panic(err)
> 	}
> 	defer os.Remove(f.Name())
>
> 	during, _ := CountOpenFDs()
> 	_ = f.Close()
> 	after, _ := CountOpenFDs()
>
> 	fmt.Printf("до: %d, открыт: %d, после Close: %d\n", before, during, after)
> }
> ```
> При чтении каталога `os.ReadDir` на мгновение открывает сам `/proc/self/fd` и закрывает его перед возвратом, поэтому на каждом замере разница между `before`, `during` и `after` точно равна `1` (выделенному файлу).

**Упражнение 3 (Со звёздочкой \*). Чтение `VmRSS` из `/proc`.**  
Напишите функцию `ReadProcField(pid int, key string) (string, error)`, которая читает `/proc/<pid>/status` (или `/proc/self/status`, если `pid <= 0`), находит строку, начинающуюся с `key + ":"`, и возвращает очищенное от пробелов значение справа от двоеточия. Проверьте её в `main()` на ключах `"Name"` и `"VmRSS"`.

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"bufio"
> 	"errors"
> 	"fmt"
> 	"os"
> 	"strings"
> )
>
> func ReadProcField(pid int, key string) (string, error) {
> 	path := "/proc/self/status"
> 	if pid > 0 {
> 		path = fmt.Sprintf("/proc/%d/status", pid)
> 	}
> 	f, err := os.Open(path)
> 	if err != nil {
> 		return "", err
> 	}
> 	defer f.Close()
>
> 	prefix := key + ":"
> 	scanner := bufio.NewScanner(f)
> 	for scanner.Scan() {
> 		line := scanner.Text()
> 		if val, ok := strings.CutPrefix(line, prefix); ok {
> 			return strings.TrimSpace(val), nil
> 		}
> 	}
> 	if err := scanner.Err(); err != nil {
> 		return "", err
> 	}
> 	return "", errors.New("поле не найдено")
> }
>
> func main() {
> 	name, err := ReadProcField(0, "Name")
> 	if err != nil {
> 		panic(err)
> 	}
> 	rss, err := ReadProcField(0, "VmRSS")
> 	if err != nil {
> 		panic(err)
> 	}
> 	fmt.Printf("процесс=%s, RSS=%s\n", name, rss)
> }
> ```
> Использование `strings.CutPrefix` избавляет от ручного вычисления индекса и делает разбор строк вида `VmRSS:\t   12480 kB` наглядным и безопасным.
