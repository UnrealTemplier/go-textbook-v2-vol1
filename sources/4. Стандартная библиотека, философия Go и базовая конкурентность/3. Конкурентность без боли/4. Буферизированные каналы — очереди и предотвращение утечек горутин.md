*Как буфер превращает канал в ограниченную очередь, помогает ограничивать число одновременных задач и спасает программу от тихих утечек горутин.*

> «В отличие от неиспользуемых переменных, утекшие горутины не собираются сборщиком мусора автоматически, поэтому важно следить, чтобы каждая горутина завершалась сама, как только перестаёт быть нужной.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

Представьте, что `BookmarkFlow` опрашивает три зеркала и возвращает **первый** ответ. Мы запускаем три горутины, читаем одно значение из небуферизированного канала `results` и выходим из функции.

Но две медленные горутины позже доходят до `results <- status` и застревают **навечно**, потому что читать больше некому. За миллион вызовов мёртвые горутины съедят всю память.

## Канал с буфером: очередь фиксированной ёмкости

Второй аргумент `make` задаёт **ёмкость буфера** (*capacity*):

```go
ch := make(chan string, 3) // буферизированный канал на 3 элемента
```

Буферизированный канал похож на постамат с тремя ячейками: курьер кладёт посылку в свободную ячейку и уходит, не дожидаясь получателя. Граница аналогии: когда все ячейки заняты, следующий отправитель всё равно блокируется, пока кто-то не заберёт элемент.

Правила блокировки:

| Состояние буфера | Отправка `ch <- v` | Приём `<-ch` |
|---|---|---|
| **Пустой** (`len == 0`) | Кладёт в буфер, **не блокируется** | **Блокируется**, ждёт отправителя |
| **Частично полон** (`0 < len < cap`) | Кладёт в буфер, **не блокируется** | Забирает старейший элемент, **не блокируется** |
| **Заполнен** (`len == cap`) | **Блокируется**, ждёт получателя | Забирает элемент и будит отправителя |

Элементы выходят в порядке поступления. `len(ch)` и `cap(ch)` возвращают текущее заполнение и ёмкость; в конкурентном коде `len(ch)` пригоден для метрик, но не для условий `if` — значение устаревает к следующей строке. Если закрыть непустой буферизированный канал, получатель сначала вычитает остаток буфера с `ok == true`, и лишь затем получит `ok == false`.

## Разбираем и лечим реальную утечку горутин

Вернёмся к нашей функции опроса трёх зеркал и посмотрим на утечку вживую:

```go
func checkMirrorsLeaky(mirrors []string) string {
	res := make(chan string) // ОШИБКА: небуферизированный канал
	for i, m := range mirrors {
		delay := time.Duration(40+i*40) * time.Millisecond
		go func() {
			time.Sleep(delay)
			res <- m // 2 из 3 горутин зависнут здесь навсегда!
		}()
	}
	return <-res
}
```

После `return <-res` никто больше не прочтёт из `res`. Сборщик мусора не имеет права уничтожить две оставшиеся горутины, пока они заблокированы на отправке. Это и есть **утечка горутин** (*goroutine leak*).

Починить эту конкретную утечку можно одной цифрой — выделив буфер под все запущенные горутины:

```go
package main

import (
	"fmt"
	"time"
)

func checkMirrors(mirrors []string) string {
	res := make(chan string, len(mirrors)) // места хватит для каждого ответа
	for i, m := range mirrors {
		delay := time.Duration(40+i*35) * time.Millisecond
		go func() {
			time.Sleep(delay)
			res <- fmt.Sprintf("%s (%v)", m, delay)
		}()
	}
	return <-res
}

func main() {
	mirrors := []string{"mirror-eu.go.dev", "mirror-us.go.dev", "mirror-asia.go.dev"}
	fmt.Println("Быстрейший ответ:", checkMirrors(mirrors))
	time.Sleep(150 * time.Millisecond) // даём медленным горутинам спокойно завершиться
}
```

Теперь медленные горутины кладут свои ответы в свободные ячейки буфера и спокойно выходят. Как только последний отправитель завершает работу, на канал `res` не остаётся ни одной ссылки, и сборщик мусора освобождает и сам канал, и невостребованные строки внутри буфера.

Точно так же для одиночной фоновой задачи, результат которой вызывающая сторона может не дождаться (например, из-за таймаута), спасает буфер размером **`1`**: `make(chan CheckResult, 1)`. А если сама фоновая работа может зависнуть надолго, одного буфера мало — понадобится отмена через `context.Context`, которую мы разберём в уроке 9.

## Буферизированный канал как семафор

Допустим, в `BookmarkFlow` 500 закладок. Запустить 500 горутин память позволяет легко, но удалённый сервер или ваш роутер захлебнутся от 500 одновременных запросов. Нужно ограничить число одновременно работающих проверок, скажем, тремя.

Буферизированный канал решает задачу в пять строк — такой приём называют **семафором** (*counting semaphore*):

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	urls := []string{
		"https://go.dev",
		"https://pkg.go.dev",
		"https://go.dev/doc",
		"https://go.dev/blog",
		"https://go.dev/tour",
	}

	const maxConcurrent = 2
	sem := make(chan struct{}, maxConcurrent)
	done := make(chan string, len(urls))

	start := time.Now()
	for _, url := range urls {
		sem <- struct{}{} // занимаем слот (если 2 заняты — ждём)
		go func() {
			defer func() { <-sem }() // освобождаем слот при любом выходе
			time.Sleep(60 * time.Millisecond)
			done <- fmt.Sprintf("%4dms | OK %s", time.Since(start).Milliseconds(), url)
		}()
	}

	for range len(urls) {
		fmt.Println(<-done)
	}
}
```

Вывод показывает, как задачи идут парами по 60 мс:

```text
  60ms | OK https://go.dev
  60ms | OK https://pkg.go.dev
 120ms | OK https://go.dev/doc
 120ms | OK https://go.dev/blog
 180ms | OK https://go.dev/tour
```

Почему типом элемента выбрали пустую структуру `struct{}`? Потому что значение `struct{}{}` занимает **0 байтов** в памяти и ясно сигнализирует читателю кода: нам важен сам факт наличия «жетона» в канале, а не передаваемые данные.

## Когда буфер вреден

Новички часто ставят случайный буфер вроде `make(chan int, 100)` «на всякий случай, чтобы не зависло». Делать так не стоит.

Случайный буфер не лечит ошибку архитектуры, а лишь **маскирует** её до дня, когда нагрузка вырастет со 100 до 101 задачи — и сервис внезапно зависнет в продакшене. Начинайте с небуферизированного канала; добавляйте буфер, только когда можете точно объяснить размер: `1` (защита от утечки одного отправителя), `len(tasks)` (все результаты точно поместятся) или `maxConcurrent` (семафор).

> [!check] Проверь понимание
> В буферизированный канал `ch := make(chan int, 2)` записали `10` и `20`, а затем вызвали `close(ch)`. Что вернут три подряд операции `v, ok := <-ch`?
>
> Сначала `(10, true)`, затем `(20, true)` и только на третьем чтении `(0, false)`. Закрытие канала не стирает элементы, которые уже лежат в буфере.

## Практика

**Упражнение 1 (Базовое). Проследи блокировку.**  
На какой строке зависнет эта программа и что она успеет вывести до падения с `deadlock`?

```go
package main

import "fmt"

func main() {
	ch := make(chan int, 2)
	ch <- 10
	ch <- 20
	fmt.Println("len:", len(ch), "cap:", cap(ch))
	ch <- 30
	fmt.Println(<-ch)
}
```

> [!solution] Показать решение
> Программа успеет напечатать `len: 2 cap: 2`, после чего зависнет на строке `ch <- 30` и упадёт с `fatal error: all goroutines are asleep - deadlock!`.
>
> Первые две отправки прошли без блокировки, потому что в буфере ёмкостью 2 были свободные места. Третья отправка заблокировала `main` в ожидании получателя, но чтение `<-ch` стоит строкой ниже в той же горутине.

**Упражнение 2 (Практическое). Первый успешный ответ без утечек.**  
Напишите функцию `firstResult(sources []string) string`, которая запускает по одной горутине на каждый источник из `sources` (имитируйте задержку `time.Duration(30+i*25)*time.Millisecond`), возвращает первый пришедший ответ и гарантирует, что остальные горутины завершатся без утечки. Проверьте функцию в `main`.

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"fmt"
> 	"time"
> )
>
> func firstResult(sources []string) string {
> 	ch := make(chan string, len(sources))
> 	for i, src := range sources {
> 		delay := time.Duration(30+i*25) * time.Millisecond
> 		go func() {
> 			time.Sleep(delay)
> 			ch <- src
> 		}()
> 	}
> 	return <-ch
> }
>
> func main() {
> 	winner := firstResult([]string{"cache-local", "mirror-eu", "mirror-us"})
> 	fmt.Println("Победитель:", winner)
> }
> ```
> Буфер размером `len(sources)` гарантирует, что ни одна из запущенных горутин не заблокируется на `ch <- src` после того, как `firstResult` заберёт первый ответ и вернёт управление.

**Упражнение 3 (Со звёздочкой \*). Где занимать слот семафора?**  
Сравните два варианта ограничения до `3` одновременных задач для списка из 100 000 ссылок:
* **Вариант A:** `sem <- struct{}{}` стоит *перед* `go func()`.
* **Вариант B:** `sem <- struct{}{}` стоит *внутри* `go func()`.

Оба варианта запустят не больше 3 проверок одновременно. В чём принципиальная разница по памяти и числу горутин?

> [!solution] Показать решение
> * В **варианте A** одновременно существует не больше **3 активных горутин** (плюс `main`). Пока все слоты заняты, сам цикл `for` приостанавливается и не создаёт лишние горутины.
> * В **варианте B** цикл мгновенно породит **100 000 горутин** (~200 МБ только под стеки), из которых 99 997 будут просто спать в очереди на `sem <- struct{}{}`.
>
> Поэтому в простом семафоре лучше занимать слот **до** запуска горутины (как в примере урока), а для сложных очередей использовать пул воркеров — мы соберём его в уроке 10.

---

Буферизированные каналы дают очередь, семафор и защиту от утечек. Но пока каждая горутина умеет слушать только **один** канал за раз — она не способна одновременно ждать ответ ссылки и следить за истечением таймаута. Этот инструмент даёт оператор `select`, которому посвящён урок [[5. Оператор select, неблокирующие операции и таймауты]].
