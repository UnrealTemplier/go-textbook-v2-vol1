*Собираем автономный статический бинарник Go без внешних библиотек, уменьшаем его размер флагами компоновки и разбираем многоэтапный `project/final/Dockerfile`.*

Обычная сборка `go build` на вашем ноутбуке создаёт исполняемый файл размером около 11 МБ, привязанный к системной динамической библиотеке C на вашей машине. Если просто скопировать такой файл в пустой минимальный контейнер, программа не сможет даже запуститься — ядро не найдёт нужный динамический загрузчик `/lib64/ld-linux-x86-64.so.2`. А если тащить в образ контейнера весь компилятор Go, размер образа раздуется с десятка мегабайт до сотен мегабайт, и внутри окажется лишний софт: пакетный менеджер, компилятор и оболочка `sh`.

Стандартное решение для сервисов на Go — **полностью статический бинарник** внутри **многоэтапной сборки Docker (*multi-stage build*)**.

## Статический бинарник и флаги сжатия

Посмотрите на строку сборки из `project/final/Dockerfile`:

```bash
CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o /out/bookmarkflow ./final/cmd/bookmarkflow
```

Сравним реальный результат обычной сборки `go build` и этой команды на нашем проекте `BookmarkFlow`:

```text
-rwxr-xr-x 1 ut ut 7.1M bookmarkflow          (статический, -trimpath -ldflags="-s -w")
-rwxr-xr-x 1 ut ut  11M bookmarkflow-default  (обычная сборка go build)
```

Если проверить оба файла системными утилитами `file` и `ldd`, разница видна сразу:

```text
bookmarkflow:         ELF 64-bit LSB executable, x86-64, statically linked, stripped
bookmarkflow-default: ELF 64-bit LSB executable, x86-64, dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, with debug_info, not stripped

$ ldd bookmarkflow
	not a dynamic executable
```

Разберём каждый флаг сборки:

1. **`CGO_ENABLED=0`** — отключает вызовы к библиотеке C операционной системы (`libc`). Вся сеть и DNS работают на чистом коде Go, и бинарник перестаёт зависеть от внешних `.so`-файлов (он запустится хоть на Ubuntu, хоть на Alpine, хоть на абсолютно пустом корневом образе).
2. **`GOOS=linux`** — явное указание целевой ОС Linux (полезно даже при сборке на macOS или Windows, когда Docker или локальная сборка нацелены на Linux-контейнер).
3. **`-trimpath`** — вырезает локальные пути вашей машины вроде `/home/ut/work/...` из трассировок стека. Сборка становится воспроизводимой и не раскрывает структуру ваших домашних каталогов.
4. **`-ldflags="-s -w"`** — передаёт флаги компоновщику Go: `-s` убирает таблицу символов, `-w` убирает отладочную информацию DWARF (сразу минус ~35% размера: с 11 МБ до 7.1 МБ). При этом паники по-прежнему печатают читаемые имена функций и номера строк! Недостаток один: такой бинарник нельзя пошагово отлаживать в отладчике Delve.

## Построчный разбор `project/final/Dockerfile`

Посмотрим целиком на `project/final/Dockerfile` (всего 25 строк):

```dockerfile
# syntax=docker/dockerfile:1

# Этап 1: сборка статического бинарника Go 1.24
FROM golang:1.24-alpine AS builder

WORKDIR /src
COPY go.mod ./
COPY final ./final

RUN CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o /out/bookmarkflow ./final/cmd/bookmarkflow

# Этап 2: минимальный образ без компилятора и оболочки
FROM gcr.io/distroless/static-debian12:nonroot

WORKDIR /app
COPY --from=builder /out/bookmarkflow /app/bookmarkflow

ENV BOOKMARKFLOW_ADDR=":8080" \
    BOOKMARKFLOW_DATA_FILE="/data/bookmarks.json" \
    BOOKMARKFLOW_CHECK_WORKERS="4"

EXPOSE 8080
USER nonroot:nonroot

ENTRYPOINT ["/app/bookmarkflow"]
```

Здесь работают четыре ключевые практики безопасности и компактности:

1. **Два отдельных этапа (`AS builder` → `distroless`).** Первый образ `golang:1.24-alpine` содержит компилятор и стандартную библиотеку только на время сборки. Во второй образ `gcr.io/distroless/static-debian12:nonroot` копируется **единственный** скомпилированный файл `/app/bookmarkflow` (`COPY --from=builder`). В финальном образе нет ни `gcc`, ни `curl`, ни даже оболочки `/bin/sh` — всего ~2 МБ базы плюс наш 7-мегабайтный бинарник. В нём также уже лежат корневые TLS-сертификаты для исходящих `https`-запросов `LinkChecker`.
2. **Точечное копирование `COPY go.mod ./`.** Если у проекта появятся внешние зависимости в `go.sum`, копирование `go.mod` *до* исходников позволяет Docker кэшировать слой загрузки модулей и не скачивать их заново при каждой правке `.go`-файла.
3. **Непривилегированный пользователь `USER nonroot:nonroot`.** Запускать сервис внутри контейнера от `root` — плохая привычка: при уязвимости в приложении злоумышленник получит лишние права. В образе `:nonroot` процесс работает от обычного пользователя с UID `65532`.
4. **Exec-форма `ENTRYPOINT ["/app/bookmarkflow"]`.** Запись в квадратных скобках (JSON-массив), а не строка `ENTRYPOINT /app/bookmarkflow`, принципиально важна для `Graceful Shutdown` из прошлого урока. В квадратных скобках наш бинарник запускается с **PID 1** и получает `SIGTERM` напрямую от Docker. Если же написать без скобок, Docker запустит оболочку `/bin/sh -c`, которая может не передать сигнал дочернему процессу, и контейнер прождёт 10 секунд до жёсткого `SIGKILL`.

## Зачем нужен `.dockerignore`

При запуске `docker build` клиент сперва отправляет весь контекст сборки демону Docker. Если в каталоге проекта лежат временные логи, локальные файлы `bookmarks.json` или кэш редактора, без файла `.dockerignore` они попадут в контекст сборки и могут случайно оказаться внутри образа. Хороший базовый `.dockerignore` выглядит так:

```text
.git
*.json
dist/
```

## Подводный камень: сборка под чужую архитектуру (`arm64` против `amd64`)

Если вы собираете бинарник на ноутбуке с процессором Apple Silicon (`arm64`) и копируете его на обычный облачный сервер `x86_64` (`amd64`), одного `GOOS=linux` недостаточно: нужно явно указать и `GOARCH=amd64`. А внутри `Dockerfile` при `FROM golang:1.24-alpine` компилятор по умолчанию собирает под архитектуру самого базового образа, поэтому `GOARCH` прописывать не обязательно (если только вы не делаете кросс-сборку с `TARGETARCH`).

> [!check] Проверь понимание
> Что произойдёт при попытке выполнить `docker exec -it <id> sh` на запущенном контейнере `BookmarkFlow`, собранном по нашему `Dockerfile`?
>
> Команда завершится ошибкой (`exec: "sh": executable file not found in $PATH`), потому что в образе `distroless/static-debian12:nonroot` намеренно вырезаны оболочка `sh` и любые посторонние системные утилиты ради минимальной поверхности атаки.

## Практика

**Упражнение 1 (Базовое). Зачем в `ENTRYPOINT` квадратные скобки?**  
Почему в `project/final/Dockerfile` написали `ENTRYPOINT ["/app/bookmarkflow"]`, а не `ENTRYPOINT /app/bookmarkflow`? Как это связано с уроком 15?

> [!solution] Показать решение
> Строковая форма `ENTRYPOINT /app/bookmarkflow` запускает команду через `/bin/sh -c "/app/bookmarkflow"`: во-первых, в образе `distroless` вообще нет `/bin/sh`, и контейнер даже не стартует; во-вторых, в обычных образах PID 1 забирает оболочка `sh`, которая часто не пробрасывает сигнал `SIGTERM` дочернему процессу Go — и `Graceful Shutdown` не срабатывает. Exec-форма `["/app/bookmarkflow"]` делает наш бинарник процессом с PID 1.

**Упражнение 2 (Практическое). Проверка статической сборки на своей машине.**  
Выполните локально из каталога `project/` команду сборки статического бинарника из этого урока в `/tmp/bookmarkflow-test`, проверьте её командами `ls -lh /tmp/bookmarkflow-test` и `file /tmp/bookmarkflow-test`, а затем удалите временный файл. (Флаг `-o` задайте на `/tmp/bookmarkflow-test`.)

> [!solution] Показать решение
> ```bash
> (cd project && CGO_ENABLED=0 GOOS=linux go build -trimpath -ldflags="-s -w" -o /tmp/bookmarkflow-test ./final/cmd/bookmarkflow)
> ls -lh /tmp/bookmarkflow-test
> file /tmp/bookmarkflow-test
> rm /tmp/bookmarkflow-test
> ```
> Утилита `file` покажет `statically linked` и `stripped`, а размер составит около 7 МБ.

**Упражнение 3 (Со звёздочкой \*). Кэш слоёв Docker при изменении кода.**  
Представьте, что разработчик объединил две строки `Dockerfile` в одну: `COPY . .` (вместо раздельных `COPY go.mod ./` и `COPY final ./final`), и в будущем у проекта появилось 20 внешних пакетов в `go.mod` (скачиваемых командой `RUN go mod download`). Почему пересборка образа после правки одной строчки в `server.go` станет в 5–10 раз медленнее?

> [!solution] Показать решение
> Docker строит кэш слоёв сверху вниз: как только любой файл, затронутый инструкцией `COPY`, изменился, кэш для этого слоя и **всех последующих инструкций** сбрасывается. При `COPY . .` правка одной строки в `server.go` сбрасывает слой `COPY` и заставляет Docker каждый раз заново выполнять `go mod download`. Разделение `COPY go.mod go.sum ./` → `RUN go mod download` → `COPY final ./final` сохраняет кэш зависимостей нетронутым, пока не меняется `go.mod`.
