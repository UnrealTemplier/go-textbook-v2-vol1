*Зачем процессор требует выравнивать данные по кратным адресам, откуда берутся «пустые байты» внутри структур Go и как порядок полей экономит треть памяти.*

Посчитаем размер простой структуры записи о закладке, в которой всего три поля: флаг активности `bool` (1 байт), идентификатор `int64` (8 байт) и флаг удаления `bool` (1 байт). Обычная арифметика даёт `1 + 8 + 1 = 10` байт.

Если попросить Go сообщить фактический размер этой структуры в памяти, компилятор ответит **24 байта** — почти в два с половиной раза больше суммы полей. А если просто перенести `int64` на первую строку, ничего не меняя в логике программы, структура мгновенно сожмётся до **16 байт**. Виной всему не ошибка компилятора, а способ, которым процессор читает оперативную память.

## Интуиция: процессор читает память «окнами», а не по байту

В уроке про кэш-линии мы видели, что процессор не таскает из памяти отдельные байты — шина данных передаёт сразу машинные слова по 4 или 8 байт (на 64-битных системах). Адреса этих слов кратны 8: `0, 8, 16, 24, ...`.

Представьте, что 8-байтовое число `int64` положили по адресу `1` — сразу за первым `bool`. Тогда семь его байтов попадут в первое слово (`0..7`), а восьмой байт окажется во втором слове (`8..15`). Чтобы прочитать одно такое число, процессору придётся выполнить два чтения памяти, сдвинуть куски и склеить их обратно — а на некоторых архитектурах невыровненное обращение и вовсе запрещено или ломает атомарность операций.

Чтобы избегать таких разрывов, компилятор соблюдает правило **выравнивания памяти** (*memory alignment*): каждое значение размером `N` байт (1, 2, 4 или 8) должно начинаться по адресу, кратному его собственному выравниванию. Промежутки между полями компилятор заполняет пустыми байтами — **паддингом** (*padding*).

## Как раскладываются два варианта одной структуры

Сравним побайтовую карту двух структур с одинаковым набором полей (`bool`, `int64`, `bool`). В первом варианте (`BadLayout`) компилятор вынужден вставить 7 байтов паддинга перед `ID` (чтобы `int64` лёг на адрес 8) и ещё 7 байтов в самом конце структуры:

```text
BadLayout (24 байта):
Смещение: 0   1  2  3  4  5  6  7   8..15         16   17 18 19 20 21 22 23
         [A] [    паддинг (7 Б)   ] [   ID (8Б)  ] [D] [   паддинг (7 Б)   ]

GoodLayout (16 байт):
Смещение: 0..7           8   9   10 11 12 13 14 15
         [   ID (8 Б)  ] [A] [D] [  паддинг (6 Б)  ]
```

Зачем нужен паддинг **в самом конце** структуры? Представьте слайс `[]BadLayout`, где элементы лежат в памяти вплотную друг за другом. Если бы структура весила 17 байт, то у второго элемента поле `ID` сдвинулось бы на некратный адрес. Поэтому общий размер структуры всегда округляется вверх до кратности её максимальному выравниванию (здесь — 8 байт).

Выравнивание базовых типов Go на 64-битной платформе (`amd64` / `arm64`) простое и предсказуемое:

| Тип Go | Размер (байт) | Выравнивание (байт) |
|---|---|---|
| `bool`, `int8`, `uint8`, `byte` | 1 | 1 |
| `int16`, `uint16` | 2 | 2 |
| `int32`, `uint32`, `float32` | 4 | 4 |
| `int64`, `uint64`, `int`, `float64`, указатель | 8 | 8 |
| `string` (указатель + длина) | 16 | 8 |
| `[]T` (указатель + длина + ёмкость) | 24 | 8 |

## Рабочий код: проверяем раскладку через `unsafe`

В стандартной библиотеке Go есть пакет `unsafe`. Его три функции — `unsafe.Sizeof`, `unsafe.Alignof` и `unsafe.Offsetof` — безопасны для чтения метаданных: они вычисляются компилятором и показывают точный размер, выравнивание и смещение каждого поля в байтах.

```go
package main

import (
	"fmt"
	"unsafe"
)

type BadLayout struct {
	Active  bool  // 1 байт
	ID      int64 // 8 байт
	Deleted bool  // 1 байт
}

type GoodLayout struct {
	ID      int64 // 8 байт
	Active  bool  // 1 байт
	Deleted bool  // 1 байт
}

func main() {
	var b BadLayout
	var g GoodLayout

	fmt.Printf("BadLayout:  size=%d, align=%d (Active=%d, ID=%d, Deleted=%d)\n",
		unsafe.Sizeof(b), unsafe.Alignof(b),
		unsafe.Offsetof(b.Active), unsafe.Offsetof(b.ID), unsafe.Offsetof(b.Deleted))

	fmt.Printf("GoodLayout: size=%d, align=%d (ID=%d, Active=%d, Deleted=%d)\n",
		unsafe.Sizeof(g), unsafe.Alignof(g),
		unsafe.Offsetof(g.ID), unsafe.Offsetof(g.Active), unsafe.Offsetof(g.Deleted))
}
```

Результат запуска точно совпадает со схемой:

```text
BadLayout:  size=24, align=8 (Active=0, ID=8, Deleted=16)
GoodLayout: size=16, align=8 (ID=0, Active=8, Deleted=9)
```

Переставив всего одну строку, мы сократили размер структуры с 24 до 16 байт — **экономия 33%**. На одном экземпляре это мелочь, но в слайсе из 10 миллионов записей разница составляет **80 МБ** оперативной памяти. Более того, в одну 64-байтовую кэш-линию CPU поместится уже 4 структуры `GoodLayout` вместо 2,6 структур `BadLayout`, что ускоряет обход слайса.

## Подводные камни

**Ловушка 1. Преждевременная сортировка полей в ущерб читаемости.**  
Не стоит перетряхивать поля в структуре конфигурации, которой в программе существует ровно один экземпляр — 8 сэкономленных байт не стоят потери логической группировки полей. Оптимизация раскладки окупается для «горячих» структур, которых в памяти десятки тысяч и миллионы (элементы больших слайсов, записи кэша, метрики).

**Ловушка 2. Пустая структура `struct{}` в конце другой структуры.**  
Сам по себе тип `struct{}` занимает `0` байт. Если поставить его в начале или в середине структуры, он не добавит ни байта. Но если поле `struct{}` стоит **самым последним**, компилятор Go добавит 1 байт паддинга (плюс выравнивание), чтобы указатель на это поле не случайно совпал с адресом соседнего объекта в памяти.

> [!check] Проверь понимание
> Сколько байтов займёт на 64-битной системе структура ниже?
> ```go
> type Packet struct {
>     Kind  uint8  // 1 байт
>     Port  uint16 // 2 байта
>     Flags uint8  // 1 байт
> }
> ```
>
> `6` байт. `Kind` лежит по смещению `0`. `Port` требует выравнивания 2, поэтому байт `1` уходит в паддинг, а `Port` занимает байты `2..3`. `Flags` занимает байт `4`. Поскольку максимальное выравнивание в структуре равно `2`, итоговый размер округляется до кратного двум — получается `6` байт (байт `5` — хвостовой паддинг). Если перенести `Port` на первое место, размер сократится до `4` байт.

## Практика

**Упражнение 1 (Базовое). Посчитайте размер на бумаге.**  
Не запуская Go, определите размер и смещения всех полей структуры на 64-битной архитектуре:
```go
type Event struct {
	OK        bool   // 1 байт
	Code      uint32 // 4 байта
	Retry     bool   // 1 байт
	Timestamp int64  // 8 байт
}
```

> [!solution] Показать решение
> Разбираем по смещениям:
> * `OK` — смещение `0` (1 байт), затем 3 байта паддинга;
> * `Code` — смещение `4` (байты `4..7`, кратно 4);
> * `Retry` — смещение `8` (1 байт), затем 7 байтов паддинга до ближайшего кратного 8;
> * `Timestamp` — смещение `16` (байты `16..23`, кратно 8).
>
> Итоговый размер `Event` — **24 байта** (10 байтов ушло в пустоту).

**Упражнение 2 (Практическое). Ужмите структуру записи лога.**  
Возьмите структуру `Event` из первого упражнения, переупорядочьте её поля от большего выравнивания к меньшему и напишите программу, которая через `unsafe.Sizeof` и `unsafe.Offsetof` печатает размеры до и после оптимизации, а также процент экономии.

> [!solution] Показать решение
> Сортируем поля по убыванию выравнивания: `int64` (8), `uint32` (4), `bool` (1), `bool` (1):
> ```go
> package main
>
> import (
> 	"fmt"
> 	"unsafe"
> )
>
> type EventRaw struct {
> 	OK        bool
> 	Code      uint32
> 	Retry     bool
> 	Timestamp int64
> }
>
> type EventPacked struct {
> 	Timestamp int64
> 	Code      uint32
> 	OK        bool
> 	Retry     bool
> }
>
> func main() {
> 	raw := unsafe.Sizeof(EventRaw{})
> 	packed := unsafe.Sizeof(EventPacked{})
> 	saved := float64(raw-packed) / float64(raw) * 100
> 	fmt.Printf("до: %d Б, после: %d Б (экономия %.1f%%)\n", raw, packed, saved)
> 	// Вывод: до: 24 Б, после: 16 Б (экономия 33.3%)
> }
> ```
> Все четыре поля теперь плотно укладываются в 14 байтов (`0..7`, `8..11`, `12`, `13`), и хвостовой паддинг составляет всего 2 байта.

**Упражнение 3 (Со звёздочкой \*). Проверка ловушки `struct{}` в конце.**  
Объявите две структуры: `EmptyFirst` с полями `pad struct{}; value int64` и `EmptyLast` с полями `value int64; pad struct{}`. Выведите их размеры через `unsafe.Sizeof` и объясните разницу в 8 байт.

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"fmt"
> 	"unsafe"
> )
>
> type EmptyFirst struct {
> 	pad   struct{}
> 	value int64
> }
>
> type EmptyLast struct {
> 	value int64
> 	pad   struct{}
> }
>
> func main() {
> 	fmt.Println("EmptyFirst:", unsafe.Sizeof(EmptyFirst{})) // 8
> 	fmt.Println("EmptyLast: ", unsafe.Sizeof(EmptyLast{}))  // 16
> }
> ```
> В `EmptyFirst` адрес `&e.pad` совпадает с началом самой структуры, то есть остаётся внутри её границ. В `EmptyLast` адрес последнего нулевого поля указал бы ровно за конец структуры — на чужой объект. Чтобы исключить это, компилятор дописывает 1 байт паддинга, который выравнивается до 8, раздувая структуру с 8 до 16 байт.
