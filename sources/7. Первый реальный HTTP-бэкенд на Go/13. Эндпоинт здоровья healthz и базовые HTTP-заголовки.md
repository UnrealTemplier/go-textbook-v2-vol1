*Разбираем назначение маршрута `GET /healthz`, отличие проверки живучести от проверки готовности и минимальный набор HTTP-заголовков безопасности для JSON API.*

Когда ваш сервис запущен в контейнере или за балансировщиком нагрузки, внешняя система не видит консоль и не читает ваши логи — ей нужен быстрый автоматический способ убедиться, что сервер вообще откликается на запросы. Если опрашивать обычный маршрут `/api/v1/bookmarks`, проверка будет каждый раз блокировать хранилище и возвращать потенциально мегабайты закладок только ради ответа «я жив». Для этого в веб-сервисах заводят специальный лёгкий маршрут проверки здоровья — `/healthz`.

## Зачем `/healthz`, и почему не `/api/v1/bookmarks`

В `project/final/server.go` маршрут здоровья зарегистрирован отдельной строкой:

```go
mux.HandleFunc("GET /healthz", s.handleHealth)
```

Сам обработчик занимает три строчки:

```go
func (s *Server) handleHealth(w http.ResponseWriter, _ *http.Request) {
	writeJSON(w, http.StatusOK, map[string]string{"status": "ok"})
}
```

Буква `z` в конце названия `/healthz` — инженерная традиция (используемая в облачных системах и оркестраторах контейнеров), чтобы служебный технический путь случайно не конфликтовал с пользовательскими страницами вроде `/health`. Ответ `{"status":"ok"}` весит всего 16 байт, не касается файла на диске и не создаёт нагрузки.

## Живучесть (*liveness*) против готовности (*readiness*)

По мере роста сервиса инженеры делят проверку здоровья на два разных вопроса. Понимать это различие важно уже в Томе 1, даже если пока у нас один эндпоинт:

1. **Живучесть (*liveness*, например `/healthz` или `/livez`):** *«Процесс не завис и событийный цикл HTTP отвечает?»* Если эта проба падает трижды подряд, оркестратор контейнеров считает, что программа ушла в бесконечный цикл или взаимную блокировку, и принудительно перезапускает процесс.
2. **Готовность (*readiness*, например `/readyz`):** *«Может ли сервер прямо сейчас обслуживать реальных пользователей?»* Представьте сервис, который запускается 5 секунд (прогревает индекс из огромного файла или проверяет доступность хранилища). В это время он уже **жив** (`liveness` = `200`), но ещё **не готов** принимать трафик (`readiness` = `503 Service Unavailable`), пока не завершит инициализацию или теряет связь с внешним хранилищем.

Золотое правило: **в `liveness`-пробе нельзя проверять внешние сети или сторонние сервисы**. Иначе при временной сетевой паузе соседа оркестратор решит, что «завис» сам ваш сервер, и начнёт бесполезно перезапускать здоровый процесс.

## Базовые HTTP-заголовки для JSON API

Вы уже видели, что на каждый запрос `BookmarkFlow` выставляет `Content-Type: application/json; charset=utf-8` и `X-Request-ID`. В живом запуске заголовок ответа выглядит так:

```http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
X-Request-Id: req-1
Date: Mon, 23 Nov 2026 16:03:57 GMT
Content-Length: 16
```

Когда этот же API выйдет наружу за пределы вашей локальной машины, к этим заголовкам полезно добавить ещё два защитных заголовка:

- **`X-Content-Type-Options: nosniff`** — запрещает браузеру «угадывать» тип содержимого по первым байтам тела. Если злоумышленник сумел сохранить HTML-тег в заголовке закладки, браузер ни при каких условиях не интерпретирует JSON-ответ как исполняемую веб-страницу.
- **`Cache-Control: no-store`** — запрещает браузерам и промежуточным прокси кэшировать динамические ответы API (чтобы после `PUT` или `DELETE` клиент не получил устаревшую версию закладки из кэша).

Добавлять такие заголовки удобно одним общим middleware перед маршрутизатором, чтобы не повторять их в каждом обработчике:

```go
func SecurityHeadersMiddleware() Middleware {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			w.Header().Set("X-Content-Type-Options", "nosniff")
			w.Header().Set("Cache-Control", "no-store")
			next.ServeHTTP(w, r)
		})
	}
}
```

Заголовок `Date` и `Content-Length` пакет `net/http` вычисляет и подставляет сам для коротких ответов.

## Подводный камень: чувствительность заголовков и статус `HEAD`

Имена HTTP-заголовков не зависят от регистра, и Go автоматически приводит их к каноническому виду через `textproto.CanonicalMIMEHeaderKey` (поэтому `X-Request-ID` в выводе `curl` превратился в `X-Request-Id`). Всегда используйте методы `w.Header().Set(...)` и `r.Header.Get(...)`, а не прямое обращение к мапе `w.Header()["x-request-id"]` — прямое обращение по неканоническому ключу в нижнем регистре вернёт пустоту!

А ещё помните: многие балансировщики опрашивают `/healthz` лёгким методом `HEAD` вместо `GET`. Поскольку в уроке 3 мы зарегистрировали маршрут как `"GET /healthz"`, `ServeMux` Go 1.22+ автоматически обслуживает и `HEAD /healthz` со статусом `200 OK` без тела.

> [!check] Проверь понимание
> Что пойдёт не так, если обратиться к мапе заголовков напрямую: `id := r.Header["x-request-id"]` вместо `r.Header.Get("X-Request-ID")`?
>
> При чтении HTTP-запроса `net/http` приводит все ключи мапы `r.Header` к каноническому виду (`"X-Request-Id"`). Прямой поиск ключа `"x-request-id"` в мапе вернёт `nil`, даже если клиент отправил заголовок. Метод `r.Header.Get(...)` нормализует регистр ключа автоматически.

## Практика

**Упражнение 1 (Базовое). Разграничение `liveness` и `readiness`.**  
На сервере `BookmarkFlow` закончилось свободное место на диске, и каталог с `bookmarks.json` перешёл в режим «только чтение». Как должны отвечать пробы `/healthz` (*liveness*) и гипотетическая `/readyz` (*readiness*), проверяющая доступность файла?

> [!solution] Показать решение
> `/healthz` (*liveness*) должен продолжать возвращать `200 OK` — сам процесс не завис, может отвечать на запросы чтения и корректно завершается по `SIGTERM`. А `/readyz` (*readiness*) должен вернуть `503 Service Unavailable`, чтобы балансировщик временно снял этот экземпляр с приёма нового трафика записи до решения проблемы с диском.

**Упражнение 2 (Практическое). Расширенный `readyz` с проверкой хранилища.**  
Напишите обработчик `handleReady(store Store)`, который проверяет, отвечает ли `store.List(ListFilter{})` без ошибки. При успехе он отдаёт `200 OK` с `{"status":"ready"}`, а при ошибке — `503 Service Unavailable` (`http.StatusServiceUnavailable`) с `{"status":"unavailable"}`.

> [!solution] Показать решение
> ```go
> func handleReady(store Store) http.HandlerFunc {
> 	return func(w http.ResponseWriter, _ *http.Request) {
> 		if _, err := store.List(ListFilter{}); err != nil {
> 			writeJSON(w, http.StatusServiceUnavailable, map[string]string{"status": "unavailable"})
> 			return
> 		}
> 		writeJSON(w, http.StatusOK, map[string]string{"status": "ready"})
> 	}
> }
> ```
> Вывод не раскрывает текст системной ошибки диска наружу, но даёт балансировщику точный статус `503`.

**Упражнение 3 (Со звёздочкой \*). Тихий лог на частые опросы `/healthz`.**  
Представьте, что балансировщик опрашивает `GET /healthz` каждые 2 секунды — за сутки в логах накопится 43 200 однотипных строк `"path":"/healthz"`. Как изменить `LoggingMiddleware`, чтобы успешные ответы `200` на `/healthz` не засоряли уровень `INFO` (или логировались на уровне `slog.LevelDebug`), но при этом ошибки `4xx`/`5xx` на любом пути всегда писались на уровне `INFO`?

> [!solution] Показать решение
> ```go
> if r.URL.Path == "/healthz" && rec.status < 400 {
> 	logger.Debug("health check",
> 		slog.String("request_id", RequestIDFromContext(r.Context())),
> 		slog.Int("status", rec.status),
> 	)
> 	return
> }
> ```
> При стандартном уровне логирования `slog.LevelInfo` успешные пробы не засоряют журнал, но стоит `/healthz` вернуть `500` или `503`, событие сразу попадёт в основной поток логов.
