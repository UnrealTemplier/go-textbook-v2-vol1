*Как устроен лёгкий протокол UDP с заголовком в 8 байт, почему отсутствие рукопожатия и повторов делает его незаменимым для DNS, видеосвязи и QUIC и как написать UDP-пинг на Go.*

Во время видеозвонка слабый сигнал Wi-Fi теряет один пакет со звуком двухсотмиллисекундной давности. Если звонок идёт поверх TCP, стек получателя **остановит воспроизведение всех свежих пакетов**, пока отправитель не перешлёт старый потерянный фрагмент. В итоге вместо едва заметного щелчка собеседник замирает на целую секунду, а затем звук рывком догоняет эфир. В задачах реального времени устаревшие данные бесполезны — их проще выбросить и показать следующий кадр.

## Что такое UDP и почему его заголовок весит всего 8 байт

**UDP** (*User Datagram Protocol*) — полная противоположность TCP. Он ничего не устанавливает, ничего не запоминает и ничего не пересылает повторно. Ваша программа отдаёт ядру готовый блок байтов — **датаграмму** (*datagram*), указывает IP и порт получателя, и ядро немедленно отправляет её в сеть.

Вся служебная обвязка UDP умещается в **8 байт** (у TCP минимальный заголовок весит 20 байт, а с опциями — ещё больше):

| Поле заголовка UDP | Размер | Назначение |
|---|---|---|
| Порт отправителя | 2 байта | Куда прислать ответ |
| Порт получателя | 2 байта | Какому процессу отдать датаграмму |
| Длина | 2 байта | Размер заголовка + данных в байтах |
| Контрольная сумма | 2 байта | Проверка, не повредились ли биты в пути |

Сравним оба транспортных протокола лицом к лицу:

| Свойство | TCP | UDP |
|---|---|---|
| Установка соединения | Тройное рукопожатие (1 RTT) | Нет (0 RTT — данные летят сразу) |
| Модель данных | Непрерывный поток байтов | Отдельные датаграммы (границы сохраняются) |
| Гарантия доставки и порядка | Да (повторная отправка + сортировка) | Нет (возможны потери, дубли и перестановка) |
| Контроль потока и перегрузки | Встроен в протокол | Отсутствует (ответственность приложения) |
| Минимальный заголовок | 20 байт | 8 байт |

Обратите внимание на вторую строку таблицы: **UDP сохраняет границы сообщений**. Если вы отправили две датаграммы по 10 байт, получатель заберёт их двумя отдельными вызовами чтения — либо не получит одну из них вовсе. Склеить их в один кусок ядро не имеет права.

## Потери, переупорядочивание и где UDP выигрывает

Поскольку UDP просто кладёт датаграмму внутрь IP-пакета и отпускает её в сеть, с ней может случиться всё, что случается с IP-пакетами:

* датаграмма может бесследно исчезнуть на перегруженном маршрутизаторе;
* вторая датаграмма способна обогнать первую и приехать раньше;
* изредка один и тот же пакет приходит дважды.

Именно эта минималистичность делает UDP победителем в четырёх больших классах задач:

1. **DNS-запросы.** Типичный вопрос «какой IP у `go.dev`?» и ответ влезают в один короткий пакет. Тратить целый RTT на рукопожатие TCP и ещё один обмен на `FIN` ради 40 байт ответа — лишнее утроение задержки. Если UDP-пакет пропал, DNS-клиент сам повторит запрос через таймаут.
2. **Аудио- и видеосвязь, стриминг.** Если кадр пропал, приложение маскирует пропуск и рисует следующий свежий кадр, не задерживая эфир.
3. **Онлайн-игры.** Сервер рассылает координаты игроков 30–60 раз в секунду. Потерянный снимок позиций десятимиллисекундной давности уже устарел — прямо следом прилетит новый.
4. **Протокол QUIC.** Современная основа веб-протокола HTTP/3 построена именно поверх UDP. Разработчики сознательно обошли жёсткую модель одного потока TCP, реализовав шифрование, независимые потоки и выборочные повторы поверх UDP-датаграмм в пользовательском пространстве.

## Короткий UDP-пинг на Go: `net.ListenPacket` и `net.Dial`

В стандартной библиотеке Go для UDP-сервера используется **`net.ListenPacket("udp", addr)`** — эта функция открывает пакетный сокет `net.PacketConn`, у которого есть методы `ReadFrom` (получить датаграмму и адрес отправителя) и `WriteTo` (отправить ответ ровно тому, кто написал). Клиент может открыть сокет через **`net.Dial("udp", addr)`**: никакого рукопожатия при этом не происходит — `Dial` лишь запоминает адрес назначения по умолчанию, чтобы можно было вызывать обычные `Write` и `Read`.

Напишем самодостаточный пример: запускаем UDP-эхо-сервер на свободном локальном порту `"127.0.0.1:0"`, посылаем ему `"PING"` и замеряем время отклика:

```go
package main

import (
	"fmt"
	"net"
	"time"
)

func main() {
	// Сервер слушает случайный свободный UDP-порт на localhost.
	pc, err := net.ListenPacket("udp", "127.0.0.1:0")
	if err != nil {
		panic(err)
	}
	defer pc.Close()

	done := make(chan struct{})
	go func() {
		defer close(done)
		buf := make([]byte, 1024)
		n, clientAddr, err := pc.ReadFrom(buf)
		if err != nil {
			return
		}
		reply := fmt.Sprintf("PONG (%s)", string(buf[:n]))
		_, _ = pc.WriteTo([]byte(reply), clientAddr)
	}()

	// Клиент "привязывает" адрес сервера (рукопожатия нет).
	conn, err := net.Dial("udp", pc.LocalAddr().String())
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	// В UDP потерянный пакет заставит Read ждать вечно — дедлайн обязателен.
	_ = conn.SetDeadline(time.Now().Add(time.Second))

	start := time.Now()
	if _, err := conn.Write([]byte("PING")); err != nil {
		panic(err)
	}

	reply := make([]byte, 1024)
	n, err := conn.Read(reply)
	if err != nil {
		panic(err)
	}
	fmt.Printf("Ответ: %q за %v\n", string(reply[:n]), time.Since(start))
	<-done
}
```

Запуск на локальной машине выдаёт что-то вроде:

```text
Ответ: "PONG (PING)" за 128.4µs
```

Один пакет туда, один обратно — и ни единого служебного сегмента `SYN` или `FIN`.

## Подводные камни

**Ловушка 1. Слишком маленький буфер при чтении UDP.**  
В TCP, если буфер `buf` оказался меньше пришедших данных, остаток спокойно дождётся следующего `Read`. В UDP всё иначе: если пришла датаграмма на 100 байт, а вы передали в `ReadFrom` буфер на 16 байт, ОС отдаст первые 16 байт, а **оставшиеся 84 байта молча выбросит навсегда**. Всегда выделяйте буфер с запасом под максимальный размер сообщения вашего протокола (обычно до 1 200–1 472 байт, чтобы датаграмма влезала в один Ethernet-кадр без фрагментации).

**Ловушка 2. Чтение UDP без дедлайна.**  
Если сервер недоступен или ответная датаграмма потерялась по дороге, UDP не закроет соединение с ошибкой (соединения просто нет). Вызов `conn.Read` повиснет навсегда, если вы не ограничили ожидание через `conn.SetReadDeadline` или `conn.SetDeadline`.

> [!check] Проверь понимание
> UDP-сервер получил датаграмму длиной 64 байта и прочитал её в буфер `buf := make([]byte, 20)`. Что вернёт следующий вызов `pc.ReadFrom(buf)`?
>
> Он **не** вернёт оставшиеся 44 байта — они были безвозвратно отброшены при первом чтении. Следующий `ReadFrom` будет ждать уже **новую** датаграмму.

**Упражнение 2 (Практическое). UDP-пинг с повтором при таймауте.**  
Доработайте клиентский код из примера урока в функцию `UDPPing(addr string, payload []byte, timeout time.Duration, retries int) ([]byte, time.Duration, error)`. Она отправляет `payload` по UDP, ждёт ответ не дольше `timeout` и при ошибке таймаута (`errors.Is(err, os.ErrDeadlineExceeded)`) повторяет попытку до `retries` раз. Проверьте её в `main()` на локальном UDP-сервере, который намеренно игнорирует первый пакет и отвечает только на второй.

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"errors"
> 	"fmt"
> 	"net"
> 	"os"
> 	"time"
> )
>
> func UDPPing(addr string, payload []byte, timeout time.Duration, retries int) ([]byte, time.Duration, error) {
> 	conn, err := net.Dial("udp", addr)
> 	if err != nil {
> 		return nil, 0, err
> 	}
> 	defer conn.Close()
>
> 	buf := make([]byte, 1024)
> 	var lastErr error
> 	for range retries {
> 		start := time.Now()
> 		_ = conn.SetDeadline(time.Now().Add(timeout))
> 		if _, err := conn.Write(payload); err != nil {
> 			return nil, 0, err
> 		}
> 		n, err := conn.Read(buf)
> 		if err == nil {
> 			return append([]byte(nil), buf[:n]...), time.Since(start), nil
> 		}
> 		lastErr = err
> 		if !errors.Is(err, os.ErrDeadlineExceeded) {
> 			return nil, 0, err
> 		}
> 	}
> 	return nil, 0, lastErr
> }
>
> func main() {
> 	pc, err := net.ListenPacket("udp", "127.0.0.1:0")
> 	if err != nil {
> 		panic(err)
> 	}
> 	defer pc.Close()
>
> 	go func() {
> 		buf := make([]byte, 1024)
> 		// Первый пакет намеренно "теряем".
> 		_, _, _ = pc.ReadFrom(buf)
> 		// На второй отвечаем.
> 		n, addr, err := pc.ReadFrom(buf)
> 		if err == nil {
> 			_, _ = pc.WriteTo(append([]byte("OK:"), buf[:n]...), addr)
> 		}
> 	}()
>
> 	resp, rtt, err := UDPPing(pc.LocalAddr().String(), []byte("PING"), 50*time.Millisecond, 3)
> 	if err != nil {
> 		panic(err)
> 	}
> 	fmt.Printf("Ответ %q получен за %v\n", resp, rtt)
> }
> ```
> Так на практике добавляют простейшую устойчивость к единичным потерям поверх UDP — именно по такому принципу работают DNS-резолверы.
