*Почему в памяти нет «отрицательного нуля», откуда берётся асимметрия `int8` от `-128` до `+127` и как ловить переполнение целых чисел в Go.*

Прибавьте единицу к максимальному числу типа `int8` (`127`). Интуиция подсказывает получить `128` или ошибку переполнения. Вместо этого Go без единого предупреждения вернёт `-128`. Похожий сбой в 1996 году погубил ракету Ariane 5 через 37 секунд после старта, а в обычных веб-сервисах он тихо портит счётчики, балансы и идентификаторы.

Чтобы переполнение перестало казаться загадочным фокусом, нужно увидеть, как компьютер кодирует знак числа одними нулями и единицами.

## Почему наивная идея «бит знака» провалилась

Первая мысль, которая приходит в голову каждому: отдадим старший бит байта под знак (`0` — плюс, `1` — минус), а оставшиеся семь битов оставим под модуль числа. Такой формат действительно существовал в ранних компьютерах и назывался *прямым кодом* (*sign-magnitude*).

Но у него сразу обнаружились две тяжёлые болезни:

1. **Два разных нуля.** Комбинация `0000_0000` означала `+0`, а `1000_0000` — `-0`. Каждое сравнение с нулём приходилось проверять дважды.
2. **Сложный сумматор.** Сложение `5 + (-3)` нельзя было просто пропустить через обычную схему сложения: процессору приходилось отдельно сравнивать знаки, вычитать меньшее из большего и подставлять знак победителя.

Инженеры нашли гораздо более остроумный способ, при котором одна и та же схема сложения работает одинаково и для положительных, и для отрицательных чисел.

## Модель: одометр и дополнительный код

Представьте механический счётчик пробега автомобиля (одометр), у которого, для простоты, всего 3 двоичных разряда (значения от `000` до `111`). Аналогия бьёт точно в цикличность счёта: после максимума счётчик обнуляется, а при прокрутке на один щелчок назад от `000` показывает `111`. Граница аналогии: одометр не знает про знак — это мы договариваемся считать верхнюю половину циферблата отрицательной.

Посмотрим на круг из 8 значений для 3-битного числа со знаком:

```text
          000 (0)
     111 (-1)   001 (+1)
  110 (-2)         010 (+2)
     101 (-3)   011 (+3)
          100 (-4)
```

В такой записи:
* `000` — единственный ноль;
* шаг вправо (прибавление `+1`) всегда увеличивает число, пока мы не перешагнём границу `+3 → -4`;
* сложим `3 + (-2)` обычным двоичным сложением: `011 + 110 = 1001`. Отбрасываем четвёртый бит переноса (в 3 бита он не влезает) и получаем `001` — ровно `+1`.

Этот формат называется **дополнительным кодом** (*two's complement*). В современном мире его используют абсолютно все процессоры и язык Go.

## Точное правило и асимметрия `int8`

В $N$-битном числе в дополнительном коде старший бит имеет **отрицательный вес** $-2^{N-1}$, а все остальные биты — обычные положительные веса $2^{N-2}, \dots, 2^0$.

Для 8-битного `int8` веса битов выглядят так:

```text
Бит:   7     6    5    4    3   2   1   0
Вес:  -128  +64  +32  +16  +8  +4  +2  +1
```

Отсюда мгновенно следуют три факта, которые больше не нужно зубрить:

1. **Единственный ноль:** `0000_0000 = 0`.
2. **Число `-1` — это все единицы:** `-128 + 64 + 32 + 16 + 8 + 4 + 2 + 1 = -1` (`1111_1111`).
3. **Асимметрия границ `[-128, +127]`:**
   * максимум — `0111_1111 = +127`;
   * минимум — `1000_0000 = -128`.
   Положительных чисел 127, ноль занимает одну комбинацию, а на отрицательные остаётся ровно 128 комбинаций. Поэтому для самого минимального числа `-128` в типе `int8` **нет противоположного положительного** (`+128` не помещается).

Чтобы вручную получить `-x` в дополнительном коде, достаточно **инвертировать все биты и прибавить `1`**: `-x = ^x + 1`. Проверим для `x = 5` (`0000_0101`): инверсия даёт `1111_1010`, плюс `1` равно `1111_1011` (`-128 + 64 + 32 + 16 + 8 + 2 + 1 = -5`).

## Рабочий код: переполнение и безопасное сложение

В Go переполнение целых типов во время выполнения **не вызывает панику** — числа оборачиваются по кругу (*wrap-around*), строго по арифметике модуля $2^N$. Единственное исключение — целочисленные константы: компилятор проверяет их на этапе сборки и не даст записать `var x int8 = 128`.

Проверим поведение знакового и беззнакового переполнения и напишем функцию безопасного сложения через константы пакета `math`:

```go
package main

import (
	"errors"
	"fmt"
	"math"
)

var ErrOverflow = errors.New("целочисленное переполнение")

// SafeAddInt64 складывает a и b, не допуская тихого переполнения.
func SafeAddInt64(a, b int64) (int64, error) {
	if b > 0 && a > math.MaxInt64-b {
		return 0, ErrOverflow
	}
	if b < 0 && a < math.MinInt64-b {
		return 0, ErrOverflow
	}
	return a + b, nil
}

func main() {
	var s int8 = math.MaxInt8 // 127 (0111_1111)
	var u uint8 = math.MaxUint8 // 255 (1111_1111)

	fmt.Printf("int8:  %d + 1 = %d\n", s, s+1)
	fmt.Printf("uint8: %d + 1 = %d\n", u, u+1)

	// Асимметрия минимума: -(-128) остаётся -128.
	var minS int8 = math.MinInt8
	fmt.Printf("int8:  -(%d) = %d\n", minS, -minS)

	// Безопасная проверка перед сложением.
	if sum, err := SafeAddInt64(math.MaxInt64-10, 20); err != nil {
		fmt.Println("SafeAdd:", err)
	} else {
		fmt.Println("SafeAdd:", sum)
	}
}
```

Вывод программы:

```text
int8:  127 + 1 = -128
uint8: 255 + 1 = 0
int8:  -(-128) = -128
SafeAdd: целочисленное переполнение
```

Посмотрите на условие в `SafeAddInt64`: мы проверяем `a > math.MaxInt64 - b`, а **не** `a + b > math.MaxInt64`. Если бы мы сначала сложили `a + b`, переполнение уже случилось бы, сумма ушла бы в отрицательную область, и сравнение с `math.MaxInt64` обмануло бы нас. Вычитание `math.MaxInt64 - b` при `b > 0` гарантированно остаётся внутри допустимого диапазона `int64`.

## Подводные камни

**Ловушка 1. Ложный «модуль» минимального числа.**  
Наивная функция `abs(x int8)` с проверкой `if x < 0 { return -x }` вернёт `-128` на входе `-128`! Потому что `^1000_0000 + 1 = 0111_1111 + 1 = 1000_0000`, то есть снова `-128`. Та же ловушка действует и для `math.MinInt` / `math.MinInt64`.

**Ловушка 2. Разность беззнаковых чисел.**  
Если вы храните количество элементов или индекс в `uint`, вычитание большего из меньшего даст гигантское положительное число вместо отрицательного:

```go
var have, need uint = 3, 5
diff := have - need // На 64-битной системе: 18446744073709551614
```

Поэтому в Go даже длина слайса `len(s)` имеет знаковый тип `int`, а не `uint`: цикл обратного отсчёта `for i := len(s) - 1; i >= 0; i--` завершается штатно, когда `i` становится `-1`, а не зацикливается навечно.

**Ловушка 3. Арифметический сдвиг отрицательного числа.**  
При сдвиге `int8(-8) >> 1` старший бит (единица знака) копируется слева, чтобы сохранить знак числа: `1111_1000 >> 1 = 1111_1100` (`-4`). Для `uint8` слева всегда дописываются нули.

> [!check] Проверь понимание
> Что вернёт выражение `int8(-1) == int8(^0)` и какое двоичное представление у `int8(-2)`?
>
> Выражение вернёт `true`: побитовая инверсия нуля даёт все единицы (`1111_1111`), а в дополнительном коде это ровно `-1`. Число `-2` меньше `-1` на единицу, поэтому его двоичный код — `1111_1110`.

## Практика

**Упражнение 1 (Базовое). Перевод в дополнительный код вручную.**  
Запишите числа `-1`, `-6` и `-127` в 8-битном дополнительном коде (`int8`), используя правило `^x + 1`, и проверьте себя суммой весов разрядов.

> [!solution] Показать решение
> * `-1`: `1 = 0000_0001` → инверсия `1111_1110` → `+1` → `1111_1111` (`-128 + 127 = -1`).
> * `-6`: `6 = 0000_0110` → инверсия `1111_1001` → `+1` → `1111_1010` (`-128 + 64 + 32 + 16 + 8 + 2 = -6`).
> * `-127`: `127 = 0111_1111` → инверсия `1000_0000` → `+1` → `1000_0001` (`-128 + 1 = -127`).

**Упражнение 2 (Практическое). Почини обратный цикл на `uint`.**  
Код ниже задуман для печати индексов от `2` до `0`, но зависает в бесконечном цикле. Объясните причину и исправьте программу.

```go
for i := uint(2); i >= 0; i-- {
	fmt.Println(i)
}
```

> [!solution] Показать решение
> Тип `uint` не может быть отрицательным, поэтому условие `i >= 0` истинно **всегда**: после `0` вычитание `i--` переполняет счётчик до `math.MaxUint` (`18446744073709551615`). Правильно использовать знаковый `int`:
> ```go
> package main
>
> import "fmt"
>
> func main() {
> 	for i := 2; i >= 0; i-- {
> 		fmt.Println(i)
> 	}
> }
> ```
> Как только `i` уменьшается с `0` до `-1`, условие `i >= 0` становится ложным и цикл завершается.

**Упражнение 3 (Со звёздочкой \*). Безопасное умножение `SafeMulInt64`.**  
Напишите функцию `SafeMulInt64(a, b int64) (int64, error)`, которая возвращает `ErrOverflow`, если произведение `a * b` выходит за пределы `[math.MinInt64, math.MaxInt64]`. Учтите пограничный случай `math.MinInt64 * (-1)` и деление на ноль.

> [!solution] Показать решение
> Сначала обрабатываем нули и особый случай `MinInt64 * (-1)`, а затем проверяем границу делением (или обратным делением `prod / a != b` после обработки `MinInt64 / -1`):
> ```go
> package main
>
> import (
> 	"errors"
> 	"fmt"
> 	"math"
> )
>
> var ErrOverflow = errors.New("целочисленное переполнение")
>
> func SafeMulInt64(a, b int64) (int64, error) {
> 	if a == 0 || b == 0 {
> 		return 0, nil
> 	}
> 	if (a == math.MinInt64 && b == -1) || (b == math.MinInt64 && a == -1) {
> 		return 0, ErrOverflow
> 	}
> 	prod := a * b
> 	if prod/a != b {
> 		return 0, ErrOverflow
> 	}
> 	return prod, nil
> }
>
> func main() {
> 	cases := [][2]int64{
> 		{1_000_000, 1_000_000},
> 		{math.MaxInt64, 2},
> 		{math.MinInt64, -1},
> 		{math.MinInt64, 1},
> 	}
> 	for _, c := range cases {
> 		res, err := SafeMulInt64(c[0], c[1])
> 		fmt.Printf("%d * %d => %d, err=%v\n", c[0], c[1], res, err)
> 	}
> }
> ```
> Особая проверка для `MinInt64` и `-1` нужна не случайно: в Go деление `math.MinInt64 / -1` само переполняется (возвращает `math.MinInt64`, а на некоторых архитектурах CPU без защиты компилятора вызвало бы аппаратное исключение). Исключив эту пару заранее, мы делаем проверку `prod/a != b` полностью безопасной.

Целые числа в дополнительном коде точны до единицы, но не умеют хранить дробные доли вроде `0.1` или гигантские величины вроде расстояния до галактик. Для таких задач инженеры придумали формат с плавающей точкой — и заплатили за диапазон точностью.
