*Как интерфейс устроен в памяти в виде пары (тип, значение), почему `err != nil` иногда срабатывает на `nil`-указателе и зачем держать интерфейсы маленькими.*

> «Новым типам проще удовлетворять маленьким интерфейсам. Хорошее практическое правило проектирования интерфейсов: требуйте только то, что вам действительно нужно.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

Взгляните на безобидную на вид функцию проверки URL для `BookmarkFlow`:

```go
package main

import (
	"fmt"
	"strings"
)

type ValidationError struct {
	Field, Msg string
}

func (e *ValidationError) Error() string {
	if e == nil {
		return "<пустая ошибка>"
	}
	return fmt.Sprintf("%s: %s", e.Field, e.Msg)
}

func validateURL(raw string) error {
	var verr *ValidationError // сейчас здесь nil
	if !strings.HasPrefix(raw, "https://") {
		verr = &ValidationError{Field: "url", Msg: "нужен префикс https://"}
	}
	return verr // ловушка
}

func main() {
	err := validateURL("https://go.dev")
	if err != nil {
		fmt.Println("Неожиданная ошибка:", err)
		return
	}
	fmt.Println("URL корректен")
}
```

Строка `"https://go.dev"` начинается с `https://`. Ветка `if` не сработала, `verr` равен `nil`. Но запуск печатает:

```text
Неожиданная ошибка: <пустая ошибка>
```

Как `nil` оказался не равен `nil`? Чтобы убрать мистику, посмотрим на устройство интерфейсной переменной.

## Честная модель: коробка из двух слотов

Переменная интерфейсного типа (`error`, `any`, `BookmarkStore`) — не одиночный указатель, а **пара из двух слотов**:

1. **Динамический тип** — какой конкретный тип сейчас лежит внутри.
2. **Динамическое значение** — само значение (или указатель на него).

Сравним три состояния переменной `err` типа `error`:

```text
1. Истинный nil (return nil):
   err = [ тип: nil              | значение: nil      ]  -->  err == nil : true

2. Типизированный nil (var verr *ValidationError = nil; return verr):
   err = [ тип: *ValidationError | значение: nil      ]  -->  err == nil : false

3. Настоящая ошибка (return &ValidationError{...}):
   err = [ тип: *ValidationError | значение: 0xc0001a ]  -->  err == nil : false
                                              |
                                              v
                                ValidationError{Field: "url", ...}
```

Железное правило Go: **интерфейс равен `nil` только тогда, когда оба слота — и тип, и значение — равны `nil`.**

На строке `return verr` компилятор упаковал `*ValidationError` внутрь интерфейса `error`. В слот типа записалось `*ValidationError`, в слот значения — `nil`. Тип не пуст, значит `err != nil` истинно.

*(Примечание: в рантайме Go эта пара устроена чуть по-разному для пустых и непустых интерфейсов с таблицами методов; точную раскладку в памяти разберём в Томе 5.)*

Если убрать из метода `Error()` защитную проверку `if e == nil`, то вызов `fmt.Println(..., err)` позовёт `err.Error()`, разыменует `e.Field` у нулевого указателя и уронит программу паникой `invalid memory address or nil pointer dereference`.

## Как избежать ловушки навсегда

Правило короткое: **на успешном пути функция с возвратом `error` всегда возвращает явный `nil`, а не переменную конкретного типа.**

```go
func validateURL(raw string) error {
	if !strings.HasPrefix(raw, "https://") {
		return &ValidationError{Field: "url", Msg: "нужен префикс https://"}
	}
	return nil
}
```

Если нужно накопить ошибку в переменной, объявляйте её сразу с интерфейсным типом `var err error`, а не `var verr *ValidationError`. Тогда оба слота останутся `nil`, пока вы не положите туда реальную ошибку.

## Правило маленьких интерфейсов

Понимание механики спасает от багов, а дисциплина проектирования — от раздутого кода. Разработчики из языков с иерархиями классов часто начинают пакет с гигантского интерфейса «на вырост» из 7–10 методов (`Add`, `Get`, `Update`, `Delete`, `List`, `Count`, `ExportText`).

У такого подхода три минуса: любая тестовая заглушка обязана реализовать все методы; по сигнатуре функции не ясно, читает она данные или меняет их; почти всегда у такого интерфейса ровно одна реализация.

Авторы *The Go Programming Language* предупреждают прямо:

> «Проектируя новый пакет, начинающие Go-программисты часто сначала заводят набор интерфейсов и лишь потом определяют конкретные типы под них. В итоге рождается множество интерфейсов с единственной реализацией. Не делайте так. Это лишние абстракции, которые к тому же стоят накладных расходов во время выполнения. Скрыть методы типа или поля структуры от внешнего кода можно обычными правилами экспорта. Интерфейсы нужны только тогда, когда есть два или более конкретных типа, с которыми требуется работать единообразно.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

Три рабочих правила Go:
1. **Требуйте только нужное (*ask only for what you need*).** Функции сводки достаточно `type Counter interface { Count() int }`. В хорошем Go-коде большинство интерфейсов состоят из 1–3 методов.
2. **Объявляйте интерфейс на стороне потребителя.** Пакет хранилища экспортирует конкретный `*MemoryStore`, а вызывающий пакет сам описывает крошечный контракт под свои нужды.
3. **Не создавайте интерфейс под одну реализацию.** Начните со структуры. Когда появится вторая реализация или тестовая заглушка, выделить интерфейс займёт минуту.

> [!check] Проверь понимание
> Выполняются две строки: `var s *MemoryStore = nil` и `var st BookmarkStore = s`. Что выведет `fmt.Println(s == nil, st == nil)`?
>
> `true false`. Указатель `s` равен `nil`, но в интерфейсе `st` слот типа занят `*MemoryStore`, поэтому `st == nil` ложно.

## Практика

**Упражнение 1 (Базовое). Двухслотовая трассировка.**  
Определите вывод кода ниже и распишите пару `[тип | значение]` для `a`, `b` и `c`.

```go
var p *int
var a any
var b any = p
var c any = nil
fmt.Println(a == nil, b == nil, c == nil)
```

> [!solution] Показать решение
> Вывод: `true false true`.
> - `a`: `[nil | nil]` → `true`;
> - `b`: `[*int | nil]` → `false` (слот типа не пуст);
> - `c`: `[nil | nil]` → `true`.

**Упражнение 2 (Практическое). Почини типизированный `nil`.**  
Исправьте функцию `checkTitle`, чтобы корректный заголовок давал `err == nil`, а пустой или длиннее 80 рун возвращал `*TitleError`.

```go
type TitleError struct{ Reason string }
func (e *TitleError) Error() string { return "заголовок: " + e.Reason }

func checkTitle(title string) error {
	var err *TitleError
	if title == "" {
		err = &TitleError{Reason: "пустая строка"}
	} else if len([]rune(title)) > 80 {
		err = &TitleError{Reason: "длиннее 80 символов"}
	}
	return err
}
```

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"fmt"
> 	"strings"
> )
>
> type TitleError struct{ Reason string }
>
> func (e *TitleError) Error() string { return "заголовок: " + e.Reason }
>
> func checkTitle(title string) error {
> 	trimmed := strings.TrimSpace(title)
> 	if trimmed == "" {
> 		return &TitleError{Reason: "пустая строка"}
> 	}
> 	if len([]rune(trimmed)) > 80 {
> 		return &TitleError{Reason: "длиннее 80 символов"}
> 	}
> 	return nil
> }
>
> func main() {
> 	fmt.Println("ok:", checkTitle("Документация Go") == nil) // Вывод: ok: true
> 	fmt.Println("empty:", checkTitle(""))                    // Вывод: empty: заголовок: пустая строка
> }
> ```
> Убрав `var err *TitleError` и возвращая явный `nil`, мы гарантируем пустые слоты `[nil | nil]` при успехе.

**Упражнение 3 (Со звёздочкой \*). Сужаем интерфейс.**  
Функция `FormatTitles(s Store) string` принимает интерфейс с четырьмя методами (`Add`, `Delete`, `List() []string`, `Count`), но вызывает только `List()`. Перепишите её контракт по правилу *ask only for what you need* и объясните, придётся ли править `MemoryStore`.

> [!solution] Показать решение

> func FormatTitles(l TitleLister) string {
