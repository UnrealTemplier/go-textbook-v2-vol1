*Почему исключения прячут реальные пути выполнения программы, зачем Go превратил ошибки в обычные значения и как сокращать повторяющиеся проверки без потери ясности.*

> «Для многих других функций — даже в безупречно написанной программе — успех не гарантирован, потому что зависит от обстоятельств вне контроля программиста. Любая функция ввода-вывода обязана считаться с вероятностью сбоя, и лишь наивный программист верит, что простое чтение или запись не могут завершиться ошибкой. Именно тогда, когда внезапно отказывают самые надёжные операции, нам нужнее всего знать почему.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

В первые недели с Go почти каждого раздражает строчка `if err != nil`. Она повторяется после открытия файла, разбора JSON и записи на диск. Кажется, что компилятор навязывает лишний шум там, где в Python или Java всё «чисто» спрятано в `try/catch`.

Это ощущение держится ровно до первого ночного сбоя в чужом коде на исключениях.

## Скрытый поток управления в `try/catch`

Посмотрим на пять строк псевдокода в стиле языков с исключениями:

```text
func publishReport(path, text):
    data = renderTemplate(text)
    file = openFile(path)
    writeHeader(file)
    writeBody(file, data)
    updateIndex(path)
```

Код выглядит спокойным и линейным, но это иллюзия. На деле **каждая** строка может внезапно прервать работу и выбросить управление на пять уровней вверх по стеку.

Глядя на этот блок, вы не видите ответов на главные инженерные вопросы: может ли упасть `renderTemplate`? Закроется ли `file`, если `writeBody` бросит исключение на середине? Останется ли индекс согласованным, если `updateIndex` сломается? Исключения вводят **невидимый оператор `goto`**, пробивающий границы функций. Когда всё хорошо, код короче; когда ломается диск или сеть, разбор сбоя превращается в детектив.

## Явность как сознательный замысел

В Go ошибка внешнего мира — не катастрофа, а нормальный исход вызова. Файл может отсутствовать, JSON может оказаться битым, диск — переполненным.

> «В отличие от этого, программы на Go реагируют на ошибки обычными конструкциями управления потоком — такими как `if` и `return`. Бесспорно, такой стиль заставляет уделять обработке ошибок больше внимания — но ровно в этом и состоит его замысел.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

Возврат `(T, error)` даёт три практических плюса:

1. **Точки отказа видны глазами** прямо в строке вызова — без скрытых прыжков.
2. **Контекст нарастает на месте.** Оборачивая ошибку через `fmt.Errorf("сохранение %s: %w", path, err)`, каждый слой дописывает свою часть причины.
3. **Чёткая граница между ошибкой и багом.** Ошибки внешнего мира идут через `error`, а паника (`panic`) остаётся только для программных дефектов вроде выхода за границы слайса.

## Ошибки — это значения, их можно программировать

В известной заметке *Errors are values* (2015) Роб Пайк сформулировал простую мысль: если `if err != nil` превращается в однообразную стену, вы, скорее всего, ещё не начали **программировать** ошибки как обычные значения.

Раз `error` — значение, его можно положить в поле структуры и проверить один раз после серии однотипных операций. Именно так устроен `bufio.Scanner` из Подраздела 4.1: цикл `for scanner.Scan()` читает тысячи строк без проверок внутри, а ошибку вы забираете один раз через `scanner.Err()`.

Применим тот же приём к экспорту отчёта `BookmarkFlow`. Вместо проверки каждой записи завернём `io.Writer` в маленький накопитель ошибки `errWriter`:

```go
package main

import (
	"bytes"
	"fmt"
	"io"
)

type errWriter struct {
	w   io.Writer
	err error
}

func (ew *errWriter) writeln(format string, args ...any) {
	if ew.err != nil {
		return // первая ошибка уже зафиксирована
	}
	_, ew.err = fmt.Fprintf(ew.w, format+"\n", args...)
}

func ExportReport(w io.Writer, titles []string) error {
	ew := &errWriter{w: w}
	ew.writeln("=== Отчёт BookmarkFlow ===")
	ew.writeln("Всего закладок: %d", len(titles))
	ew.writeln("---")
	for i, title := range titles {
		ew.writeln("%d. %s", i+1, title)
	}
	return ew.err
}

func main() {
	var buf bytes.Buffer
	if err := ExportReport(&buf, []string{"Go Docs", "Go Playground"}); err != nil {
		fmt.Println("Ошибка экспорта:", err)
		return
	}
	fmt.Print(buf.String())
}
```

Вывод терминала:

```text
=== Отчёт BookmarkFlow ===
Всего закладок: 2
---
1. Go Docs
2. Go Playground
```

Внутри `ExportReport` нет повторяющихся `if err != nil`, но ни одна ошибка не потеряна: при первом сбое `ew.err` запоминает первопричину, остальные вызовы `writeln` мгновенно выходят, а наверх возвращается обычный `error`.

## Честная граница приёма

Накопитель ошибки подходит для однородного потока шагов (запись отчёта, разбор строк), где после первого сбоя продолжать бессмысленно. Если же между шагами нужно закрывать ресурсы, откатывать состояние или по-разному реагировать на разные сбои, явный `if err != nil` на каждом шаге остаётся самым надёжным выбором.

> [!check] Проверь понимание
> Чем `errWriter` принципиально отличается от игнорирования ошибок через `_ = fmt.Fprintln(...)`?
>
> При `_ = ...` ошибка теряется, а программа продолжает писать в сломанный поток. В `errWriter` первая ошибка сохраняется в `ew.err`, останавливает дальнейшие записи и возвращается вызывающему коду.

## Практика

**Упражнение 1 (Базовое). Трассировка `errWriter`.**  
Тестовый `io.Writer` возвращает ошибку `"диск переполнен"` на **второй** вызов `Write`. Сколько раз реально вызовется `w.Write`, если в `titles` передано 100 закладок, и что вернёт `ExportReport`?

> [!solution] Показать решение
> `w.Write` вызовется ровно **2 раза**: первый запишет заголовок, второй вернёт `"диск переполнен"` и запишет её в `ew.err`. Остальные 101 вызов `writeln` увидят `ew.err != nil` и сразу вернутся. `ExportReport` вернёт `"диск переполнен"`.

**Упражнение 2 (Практическое). Счётчик байтов в `errWriter`.**  
Добавьте в `errWriter` поле `n int64` для подсчёта записанных байтов до первой ошибки и измените сигнатуру `ExportReport` на:

```go
func ExportReport(w io.Writer, titles []string) (int64, error)
```

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"bytes"
> 	"fmt"
> 	"io"
> )
>
> type errWriter struct {
> 	w   io.Writer
> 	n   int64
> 	err error
> }
>
> func (ew *errWriter) writeln(format string, args ...any) {
> 	if ew.err != nil {
> 		return
> 	}
> 	written, err := fmt.Fprintf(ew.w, format+"\n", args...)
> 	ew.n += int64(written)
> 	ew.err = err
> }
>
> func ExportReport(w io.Writer, titles []string) (int64, error) {
> 	ew := &errWriter{w: w}
> 	ew.writeln("=== Отчёт BookmarkFlow ===")
> 	ew.writeln("Всего закладок: %d", len(titles))
> 	for i, title := range titles {
> 		ew.writeln("%d. %s", i+1, title)
> 	}
> 	return ew.n, ew.err
> }
>
> func main() {
> 	var buf bytes.Buffer
> 	n, err := ExportReport(&buf, []string{"Go Docs"})
> 	fmt.Printf("Байтов: %d, ошибка: %v\n", n, err)
> }
> ```
> Прибавляем `written` независимо от `err`, так как `Write` мог успеть записать часть буфера до сбоя.

**Упражнение 3 (Со звёздочкой \*). Где накопитель опасен.**  
Функция создаёт временный файл, пишет данные, закрывает файл и переименовывает его. Почему эти четыре шага нельзя просто спрятать в общий накопитель без отдельных `if err != nil`?

> [!solution] Показать решение
> У каждого этапа своя очистка: если файл не создался — его не нужно удалять; если упала запись — нужно закрыть и удалить временный файл, не вызывая переименование; если упало закрытие — данные могли не дойти до диска, и переименовывать файл опасно.

Ошибки в Go опираются на однометодный интерфейс `error`. Точно так же устроена и вся система типов языка: вместо деревьев наследования — композиция и маленькие контракты. Об этом следующее эссе — [[3. Композиция, маленькие интерфейсы и правило «требуй только нужное»]].
