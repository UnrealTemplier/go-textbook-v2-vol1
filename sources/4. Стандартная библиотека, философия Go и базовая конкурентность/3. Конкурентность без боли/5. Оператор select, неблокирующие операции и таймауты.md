*Как слушать несколько каналов одновременно, не зависать навечно на медленном ответе, не сжигать процессор в цикле с `default` и чисто отключать закрытые ветки.*

В `BookmarkFlow` осталась проблема: если удалённый сервер «подвис», горутина на обычном `<-results` зависнет навечно и не услышит ни таймер, ни другой канал. Чтобы слушать сразу несколько каналов и реагировать на первый сработавший, в Go есть оператор `select`.

## Мультиплексирование каналов: как работает `select`

Внешне `select` похож на `switch`, но в каждом `case` стоит операция с каналом:

```go
select {
case res := <-results:
	fmt.Println("Ответ:", res)
case err := <-errs:
	fmt.Println("Ошибка:", err)
}
```

Правила работы:

1. **Ни одна ветка не готова (и нет `default`)** — горутина засыпает до готовности хотя бы одного канала.
2. **Готова одна ветка** — выполняется она.
3. **Готовы несколько веток** — Go выбирает одну **псевдослучайно** (равновероятно), чтобы первый в коде канал не морил голодом остальные.

## Таймауты: `time.After` и `time.NewTimer`

Функция `time.After(d)` возвращает `<-chan time.Time`, в который через время `d` приходит отметка времени. В паре с `select` это даёт чистый таймаут:

```go
package main

import (
	"errors"
	"fmt"
	"time"
)

func checkWithTimeout(url string, work, limit time.Duration) (string, error) {
	// Буфер 1 обязателен: если сработает таймаут, горутина не утечёт
	res := make(chan string, 1)
	go func() {
		time.Sleep(work)
		res <- "OK " + url
	}()

	select {
	case msg := <-res:
		return msg, nil
	case <-time.After(limit):
		return "", errors.New("превышен таймаут для " + url)
	}
}

func main() {
	for _, tc := range []struct {
		url  string
		work time.Duration
	}{
		{"https://go.dev", 40 * time.Millisecond},
		{"https://slow.example", 200 * time.Millisecond},
	} {
		msg, err := checkWithTimeout(tc.url, tc.work, 100*time.Millisecond)
		if err != nil {
			fmt.Println("FAIL:", err)
			continue
		}
		fmt.Println(msg)
	}
}
```

Вывод:

```text
OK https://go.dev
FAIL: превышен таймаут для https://slow.example
```

Буфер `1` в `make(chan string, 1)` страхует от утечки горутины, если победит таймаут.

**Оговорка про циклы.** Для разового ожидания `time.After` идеален. В длинном цикле `for` вызывать `time.After` на каждой итерации расточительно — каждая итерация создаёт новый таймер (хотя в Go 1.23+ неиспользуемые таймеры уже собираются сборщиком мусора). В цикле заведите один `time.NewTimer`, закройте его через `defer timer.Stop()` и сбрасывайте через `timer.Reset(limit)` (в Go 1.23+ `Reset` безопасен без ручной прокачки канала):

```go
timer := time.NewTimer(limit)
defer timer.Stop()

for range n {
	timer.Reset(limit)
	select {
	case item := <-in:
		process(item)
	case <-timer.C:
		return errors.New("таймаут ожидания элемента")
	}
}
```

## Неблокирующие операции через `default` и ловушка 100% CPU

Ветка `default` делает `select` неблокирующим: если каналы не готовы прямо сейчас, мгновенно сработает `default`. Это удобно, когда при полном буфере логов запись проще отбросить, чем тормозить сервис:

```go
select {
case logCh <- entry:
	// положили в буфер
default:
	// буфер полон — пропускаем запись
}
```

Но `default` внутри бесконечного `for` — опасная ловушка:

```go
// НЕ ДЕЛАЙТЕ ТАК: сжигает 100% ядра процессора впустую!
for {
	select {
	case res := <-results:
		handle(res)
	default:
	}
}
```

Пока канал пуст, цикл прокручивается сотни миллионов раз в секунду, сжигая **100% ядра CPU**. Если нужно ждать данные — уберите `default`: рантайм усыпит горутину с нулевой нагрузкой на процессор.

## Трюк с `ch = nil`: чистое отключение ветки `select`

Из урока 3 мы знаем два свойства: чтение из **закрытого** канала срабатывает мгновенно с `ok == false`, а чтение из **`nil`-канала** блокируется навсегда — то есть ветка в `select` просто отключается.

Когда нужно дочитать два канала до конца, после закрытия одного присвойте переменной `nil`, иначе `select` утонет в нулевых значениях:

```go
package main

import "fmt"

func drainBoth(a, b <-chan string) {
	for a != nil || b != nil {
		select {
		case v, ok := <-a:
			if !ok {
				a = nil // выключаем ветку a
				continue
			}
			fmt.Println("из A:", v)
		case v, ok := <-b:
			if !ok {
				b = nil // выключаем ветку b
				continue
			}
			fmt.Println("из B:", v)
		}
	}
}

func main() {
	chA := make(chan string, 1)
	chB := make(chan string, 2)
	chA <- "https://go.dev"
	close(chA)
	chB <- "https://pkg.go.dev"
	chB <- "https://go.dev/blog"
	close(chB)

	drainBoth(chA, chB)
}
```

Как только закрывается первый канал, его переменная становится `nil` и ветка засыпает навсегда. Цикл продолжает спокойно дочитывать второй канал, а когда оба станут `nil`, условие `a != nil || b != nil` обратится в `false` и функция завершится.

> [!check] Проверь понимание
> Что сделает пустой блок `select {}` без единого `case` и без `default`?
>
> Он заблокирует текущую горутину **навсегда**, потому что ждать нечего, а `default` отсутствует. Если в программе нет других активных горутин, это приведёт к `deadlock`.

## Практика

**Упражнение 1 (Базовое). Выбор при одновременной готовности.**  
Оба канала `a` и `b` уже содержат по одному значению к моменту входа в `select`. Что выведет эта программа — всегда `"A"`, всегда `"B"` или возможны оба результата?

```go
package main

import "fmt"

func main() {
	a := make(chan string, 1)
	b := make(chan string, 1)
	a <- "A"
	b <- "B"

	select {
	case v := <-a:
		fmt.Println(v)
	case v := <-b:
		fmt.Println(v)
	}
}
```

> [!solution] Показать решение
> Возможны оба результата — примерно в половине запусков напечатается `"A"`, в другой половине — `"B"`. Когда к моменту входа в `select` готовы сразу несколько веток, Go выбирает одну из них псевдослучайно, не отдавая приоритета порядку записи в коде.

**Упражнение 2 (Практическое). Неблокирующая отправка в буфер.**  
Напишите функцию `tryPublish(ch chan<- string, msg string) bool`, которая пытается отправить `msg` в канал `ch` без блокировки. Если отправка удалась сразу — вернуть `true`, если канал занят — немедленно вернуть `false`. Проверьте её на буферизированном канале ёмкостью `1`, отправив две строки подряд.

> [!solution] Показать решение
> ```go
> package main
>
> import "fmt"
>
> func tryPublish(ch chan<- string, msg string) bool {
> 	select {
> 	case ch <- msg:
> 		return true
> 	default:
> 		return false
> 	}
> }
>
> func main() {
> 	events := make(chan string, 1)
> 	fmt.Println("Первая:", tryPublish(events, "bookmark_added"))   // true
> 	fmt.Println("Вторая:", tryPublish(events, "bookmark_deleted")) // false
> }
> ```
> При первом вызове в буфере есть свободный слот, и `select` выбирает ветку отправки. При втором буфер полон, поэтому немедленно срабатывает `default`.

**Упражнение 3 (Со звёздочкой \*). Почини слияние двух каналов.**  
Функция ниже должна собрать все элементы из каналов `a` и `b` в один слайс, но при запуске зависает в бесконечном цикле, забивая память пустыми строками. Найдите ошибку и исправьте её.

```go
func mergeAll(a, b <-chan string) []string {
	var out []string
	for {
		select {
		case v := <-a:
			out = append(out, v)
		case v := <-b:
			out = append(out, v)
		}
	}
}
```

> [!solution] Показать решение
> Ошибка в том, что функция не проверяет `ok` при чтении и не имеет условия выхода. Как только любой канал закрывается, `select` начинает мгновенно считывать из него пустые строки `""` бесконечно.
>
> Исправление — проверять `v, ok`, выключать закрытые ветки присваиванием `nil` и останавливать цикл, когда оба канала станут `nil`:
> ```go
> package main
>
> import "fmt"
>
> func mergeAll(a, b <-chan string) []string {
> 	var out []string
> 	for a != nil || b != nil {
> 		select {
> 		case v, ok := <-a:
> 			if !ok {
> 				a = nil
> 				continue
> 			}
> 			out = append(out, v)
> 		case v, ok := <-b:
> 			if !ok {
> 				b = nil
> 				continue
> 			}
> 			out = append(out, v)
> 		}
> 	}
> 	return out
> }
>
> func main() {
> 	a := make(chan string, 1)
> 	b := make(chan string, 1)
> 	a <- "https://go.dev"
> 	close(a)
> 	b <- "https://pkg.go.dev"
> 	close(b)
> 	fmt.Println(mergeAll(a, b))
> }
> ```

---

С оператором `select` мы получили контроль над несколькими каналами и временем ожидания. Но часто нам не нужно собирать данные по каналу — достаточно запустить группу горутин и просто дождаться, когда **все** они завершат работу, чтобы потом закрыть выходной канал или вывести итог. Для этого в стандартной библиотеке есть специальный счётчик — разберём его в уроке [[6. Ожидание завершения группы задач — sync.WaitGroup]].
