*Разбираем `POST /api/v1/bookmarks/check` и `project/final/checker.go`: ограниченный пул воркеров, таймауты исходящего `http.Client`, запись результатов без мьютекса и уважение `r.Context()`.*

В Модуле 4 (шаг 5) мы писали консольный чекер доступности ссылок. Теперь тот же механизм запускается по HTTP-запросу `POST /api/v1/bookmarks/check`. На первый взгляд задача кажется простой: прочитать список закладок из `Store`, запустить `go check(bm)` на каждую из них и вернуть JSON-массив отчётов.

Но представьте, что пользователь сохранил 10 000 закладок. Безудержный запуск 10 000 одновременных горутин мгновенно откроет тысячи TCP-сокетов, упрётся в лимит файловых дескрипторов процесса (`ulimit -n` из Модуля 5) и вызовет шквал отказов по таймаутам DNS и сети. Поэтому реальный сервис всегда ограничивает степень параллелизма пулом воркеров.

## Устройство `LinkChecker` в `project/final/checker.go`

Посмотрите на структуру чекера и его конструктор:

```go
type LinkChecker struct {
	client  *http.Client
	workers int
}

func NewLinkChecker(client *http.Client, workers int) *LinkChecker {
	if client == nil {
		client = &http.Client{Timeout: 5 * time.Second}
	}
	return &LinkChecker{
		client:  client,
		workers: max(workers, 1),
	}
}
```

Первое золотое правило исходящего HTTP в Go: **никогда не используйте `http.DefaultClient` или функцию `http.Get(url)` в серверном коде**. У стандартного клиента по умолчанию **нет таймаута** (`Timeout: 0`). Один «зависший» удалённый сервер, принявший TCP-соединение и молчащий часами, навсегда повесит вашу горутину-воркер. Явный `&http.Client{Timeout: 5 * time.Second}` гарантирует, что ни одна ссылка не задержит воркер дольше пяти секунд.

Вторая деталь — встроенная функция `max(workers, 1)` (появилась в Go 1.21): даже если пользователь по ошибке передал `0` или отрицательное число, чекер запустит минимум одного воркера и не зависнет без исполнителей.

## Пул воркеров без мьютекса и с сохранением порядка

Взгляните на главный метод `CheckAll` из `project/final/checker.go`:

```go
func (c *LinkChecker) CheckAll(ctx context.Context, items []Bookmark) []CheckResult {
	if len(items) == 0 {
		return []CheckResult{}
	}

	type job struct {
		idx int
		bm  Bookmark
	}

	workers := min(c.workers, len(items))
	jobs := make(chan job)
	results := make([]CheckResult, len(items))

	var wg sync.WaitGroup
	for range workers {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := range jobs {
				results[j.idx] = c.checkOne(ctx, j.bm)
			}
		}()
	}

	for i, bm := range items {
		select {
		case <-ctx.Done():
			results[i] = CheckResult{
				BookmarkID: bm.ID,
				URL:        bm.URL,
				Reachable:  false,
				Error:      ctx.Err().Error(),
			}
		case jobs <- job{idx: i, bm: bm}:
		}
	}
	close(jobs)
	wg.Wait()

	return results
}
```

Разберём четыре инженерных приёма в этом коде:

1. **Запись в `results[j.idx]` без `sync.Mutex`.** Заранее выделяется срез `results` ровно на `len(items)` элементов. Каждый воркер пишет строго в свою уникальную ячейку `results[j.idx]`, а главный цикл при отмене контекста пишет в остальные `results[i]`. Разные горутины никогда не обращаются к одному и тому же индексу одновременно, а `wg.Wait()` создаёт барьер памяти до чтения `results` — гонок данных нет. Плюс результат сохраняет точный порядок закладок, хотя сайты отвечают с разной скоростью.
2. **Не создаём лишних горутин.** `workers := min(c.workers, len(items))`: если закладок всего две, а в конфиге стоит `4` воркера, запустится ровно два воркера.
3. **Уважение `ctx.Done()` при раздаче задач.** Цикл отправки в канал `jobs` завёрнут в `select`. Если клиент закрыл вкладку или истёк таймаут запроса, раздача новых задач моментально прекращается, оставшиеся индексы честно помечаются ошибкой `ctx.Err().Error()`, канал закрывается, и сервер не тратит время на ненужные запросы.
4. **Возврат пустого не-`nil` слайса.** При пустом списке закладок `return []CheckResult{}` выдаст в JSON `{"results":[],"count":0}`, а не `null`.

## Детали `checkOne`: `HEAD`, контекст и `Body.Close()`

Внутри `checkOne` каждая ссылка проверяется лёгким методом `HEAD`, который запрашивает только заголовки без скачивания всей HTML-страницы:

```go
	req, err := http.NewRequestWithContext(ctx, http.MethodHead, bm.URL, nil)
	if err != nil {
		...
	}
	resp, err := c.client.Do(req)
	if err != nil {
		...
	}
	defer resp.Body.Close()
```

Здесь обязательны две вещи: `http.NewRequestWithContext` (чтобы отмена запроса прерывала уже идущий сетевой вызов) и `defer resp.Body.Close()` (чтобы соединение вернулось в пул и не утекли файловые дескрипторы).

## Подводный камень: серверы, не любящие метод `HEAD`

Некоторые реальные сайты в интернете отвечают на `HEAD` статусом `405 Method Not Allowed` или `403`, хотя на обычный `GET` спокойно отдают `200 OK`. В `BookmarkFlow` проверка `resp.StatusCode >= 200 && resp.StatusCode < 400` считает успешными ответы `2xx` и редиректы `3xx`, а при доработке чекера под реальные сайты при ответе `405` на `HEAD` обычно делают повторный запрос методом `GET` с ограничением чтения тела.

> [!check] Проверь понимание
> В `CheckAll` на старте создаётся небуферизованный канал `jobs := make(chan job)`. Что произойдёт, если убрать строку `close(jobs)` перед `wg.Wait()`?
>
> Все воркеры выполнят свои задачи, а затем навсегда зависнут на цикле `for j := range jobs` в ожидании новых сообщений, и `wg.Wait()` никогда не завершится — обработчик `POST /api/v1/bookmarks/check` зависнет навечно (утечка горутин и блокировка ответа).

## Практика

**Упражнение 1 (Базовое). Зачем в `results[j.idx]` не нужен мьютекс?**  
Представьте, что разработчик заменил предварительно выделенный срез `results := make([]CheckResult, len(items))` на пустой `var results []CheckResult` и внутри воркеров написал `results = append(results, res)` без мьютекса. Почему это сломает программу и какие две проблемы сразу появятся?

> [!solution] Показать решение
> 1. **Гонка данных (`DATA RACE`) и потеря записей:** несколько воркеров одновременно будут читать и перезаписывать общий заголовок слайса `results` при `append` — детектор гонок сразу зафиксирует ошибку, часть результатов потеряется или программа упадёт с повреждением памяти.
> 2. **Нарушение порядка:** быстрые сайты окажутся в начале списка, а медленные — в конце.

**Упражнение 2 (Практическое). Повторный запрос `GET` при отказе `HEAD`.**  
Доработайте логику `checkOne`: если удалённый сервер вернул на `HEAD` статус `http.StatusMethodNotAllowed` (`405`), закройте первое тело `resp.Body.Close()` и выполните повторный `http.MethodGet` на тот же `bm.URL` с тем же `ctx`.

> [!solution] Показать решение
> ```go
> 	resp, err := c.client.Do(req)
> 	if err != nil {
> 		return CheckResult{BookmarkID: bm.ID, URL: bm.URL, LatencyMS: time.Since(start).Milliseconds(), Error: err.Error()}
> 	}
> 	if resp.StatusCode == http.StatusMethodNotAllowed {
> 		resp.Body.Close()
> 		reqGet, errGet := http.NewRequestWithContext(ctx, http.MethodGet, bm.URL, nil)
> 		if errGet != nil {
> 			return CheckResult{BookmarkID: bm.ID, URL: bm.URL, LatencyMS: time.Since(start).Milliseconds(), Error: errGet.Error()}
> 		}
> 		resp, err = c.client.Do(reqGet)
> 		if err != nil {
> 			return CheckResult{BookmarkID: bm.ID, URL: bm.URL, LatencyMS: time.Since(start).Milliseconds(), Error: err.Error()}
> 		}
> 	}
> 	defer resp.Body.Close()
> ```
> Закрыть первый `resp.Body` до повторного вызова необходимо, чтобы не утекал сетевой ресурс при перезаписи переменной `resp`.

**Упражнение 3 (Со звёздочкой \*). Предотвращение быстрой перезаписи при отмене контекста.**  
В цикле отправки `CheckAll` есть нюанс: если `ctx` отменился, `select` может на одной итерации выбрать `case jobs <- ...` (если воркер как раз свободен), а на следующей — `case <-ctx.Done()`. Что если `ctx` отменился уже *после* того, как все 10 задач ушли в канал `jobs` и ещё выполняются воркерами? Защищает ли текущий код в этом случае от лишней работы?

> [!solution] Показать решение
> Да, защищает. Поскольку `ctx` передаётся внутрь `c.checkOne(ctx, j.bm)` и используется в `http.NewRequestWithContext(ctx, ...)`, `http.Client` внутри воркера немедленно прервёт уже идущие сетевые соединения и вернёт ошибку `context canceled` или `context deadline exceeded`. После этого все воркеры быстро завершатся, а `wg.Wait()` отпустит обработчик.
