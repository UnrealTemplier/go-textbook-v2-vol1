*Ставим два практических эксперимента на Go, чтобы увидеть в миллисекундах и наносекундах, как порядок обхода матрицы и замена `[]record` на `[]*record` влияют на работу кэшей процессора.*

> «Цель вычислений — понимание сути, а не числа.»
> — Ричард Хэмминг

В уроках про пирамиду памяти и кэш-линии мы утверждали две вещи: последовательное чтение массива выигрывает у прыжков по памяти на порядок, а слайс структур по значению `[]record` заметно быстрее слайса указателей `[]*record`. На бумаге обе мысли выглядят логично, но настоящая инженерная привычка требует измерить эффект на реальной машине.

В этом уроке мы проведём небольшую лабораторную работу на Go. Сначала замерим разницу простым секундомером `time.Since`, а затем познакомимся со встроенным инструментом бенчмарков `go test -bench=.` и новой конструкцией `b.Loop()` из Go 1.24.

## Дизайн двух экспериментов

В обоих опытах программа выполняет **ровно одинаковое количество сложений** над одними и теми же числами. Меняется только маршрут, по которому процессор ходит в память:

1. **Матрица `4096 × 4096` из `int64` (128 МБ):** хранится в плоском слайсе `grid` строка за строкой. Функция `sumByRows` читает соседние элементы подряд (`grid[base+col]`), попадая в 64-байтовые кэш-линии. Функция `sumByCols` шагает по столбцам с прыжком в `4096 × 8 = 32 КБ` на каждом шаге, промахиваясь мимо кэша L1.
2. **Слайс структур `[]record` против `[]*record` (500 000 записей):** в первом случае все структуры лежат плотно в одном массиве. Во втором мы создаём структуры в куче и перемешиваем указатели, имитируя реальный долгоживущий сервис, где записи создаются в разное время и разбросаны по памяти.

```text
[]record  (подряд в памяти):   [rec0][rec1][rec2][rec3] -> 1 кэш-линия грузит сразу 2 записи
[]*record (по указателям):     [ptr0][ptr1][ptr2] -> прыжки в случайные адреса кучи
```

## Рабочий код: замер через `time.Since`

Создайте временный каталог, выполните `go mod init locbench` и сохраните следующий код в `main.go`:

```go
package main

import (
	"fmt"
	"math/rand/v2"
	"time"
)

const matrixSide = 4096

func sumByRows(grid []int64, side int) int64 {
	var total int64
	for row := range side {
		base := row * side
		for col := range side {
			total += grid[base+col]
		}
	}
	return total
}

func sumByCols(grid []int64, side int) int64 {
	var total int64
	for col := range side {
		for row := range side {
			total += grid[row*side+col]
		}
	}
	return total
}

type record struct {
	ID      int64
	Score   int64
	Updated int64
	Flags   uint64
}

func sumValues(items []record) int64 {
	var total int64
	for i := range items {
		total += items[i].Score
	}
	return total
}

func sumPointers(items []*record) int64 {
	var total int64
	for _, p := range items {
		total += p.Score
	}
	return total
}

func main() {
	grid := make([]int64, matrixSide*matrixSide)
	for i := range grid {
		grid[i] = int64(i%7 + 1)
	}

	start := time.Now()
	s1 := sumByRows(grid, matrixSide)
	dRows := time.Since(start)

	start = time.Now()
	s2 := sumByCols(grid, matrixSide)
	dCols := time.Since(start)

	fmt.Printf("По строкам:  сумма=%d, время=%v\n", s1, dRows)
	fmt.Printf("По столбцам: сумма=%d, время=%v (медленнее в %.1f×)\n",
		s2, dCols, float64(dCols)/float64(dRows))

	const n = 500_000
	vals := make([]record, n)
	ptrs := make([]*record, n)
	for i := range n {
		vals[i] = record{ID: int64(i), Score: int64(i % 100)}
		ptrs[i] = &record{ID: int64(i), Score: int64(i % 100)}
	}
	rng := rand.New(rand.NewPCG(42, 7))
	rng.Shuffle(len(ptrs), func(i, j int) {
		ptrs[i], ptrs[j] = ptrs[j], ptrs[i]
	})

	start = time.Now()
	vSum := sumValues(vals)
	dVals := time.Since(start)

	start = time.Now()
	pSum := sumPointers(ptrs)
	dPtrs := time.Since(start)

	fmt.Printf("[]record:  сумма=%d, время=%v\n", vSum, dVals)
	fmt.Printf("[]*record: сумма=%d, время=%v (медленнее в %.1f×)\n",
		pSum, dPtrs, float64(dPtrs)/float64(dVals))
}
```

Запуск `go run .` на настольном процессоре `Intel Core i9-12900K` (Linux, Go 1.24+) выдаёт показательную картину:

```text
По строкам:  сумма=67108861, время=6.559501ms
По столбцам: сумма=67108861, время=102.625887ms (медленнее в 15.6×)
[]record:  сумма=24750000, время=645.228µs
[]*record: сумма=24750000, время=3.473138ms (медленнее в 5.4×)
```

В обеих парах итоговая сумма совпадает до единицы, число арифметических операций идентично, но обход по столбцам проигрывает в **15,6 раза**, а слайс указателей — в **5,4 раза**. На вашем ноутбуке абсолютные миллисекунды будут другими, но соотношение останется кратным.

## Более строгие замеры: `go test -bench=.` и `b.Loop()`

Разовый замер через `time.Since` хорош для первой прикидки, но чувствителен к случайному шуму: в этот момент ОС могла переключить ядро или разбудить фоновую задачу. Для повторяемых измерений в Go встроен инструмент **бенчмарков** (*benchmarks*) — функции вида `BenchmarkXxx(b *testing.B)` в файле `*_test.go`.

Начиная с Go 1.24, цикл бенчмарка пишут предельно ясно через `for b.Loop()`: рантайм сам сбрасывает таймер после подготовки данных до цикла, автоматически подбирает число повторений и не даёт компилятору выкинуть вычисление как неиспользуемое.

Сохраним рядом файл `locality_test.go`:

```go
package main

import (
	"math/rand/v2"
	"testing"
)

var benchSink int64

func BenchmarkMatrixRows(b *testing.B) {
	const side = 1024
	grid := make([]int64, side*side)
	for i := range grid {
		grid[i] = int64(i%7 + 1)
	}
	var sum int64
	for b.Loop() {
		sum = sumByRows(grid, side)
	}
	benchSink = sum
}

func BenchmarkMatrixCols(b *testing.B) {
	const side = 1024
	grid := make([]int64, side*side)
	for i := range grid {
		grid[i] = int64(i%7 + 1)
	}
	var sum int64
	for b.Loop() {
		sum = sumByCols(grid, side)
	}
	benchSink = sum
}

func BenchmarkSliceValues(b *testing.B) {
	const n = 200_000
	vals := make([]record, n)
	for i := range n {
		vals[i] = record{ID: int64(i), Score: int64(i % 100)}
	}
	var sum int64
	for b.Loop() {
		sum = sumValues(vals)
	}
	benchSink = sum
}

func BenchmarkSlicePointers(b *testing.B) {
	const n = 200_000
	ptrs := make([]*record, n)
	for i := range n {
		ptrs[i] = &record{ID: int64(i), Score: int64(i % 100)}
	}
	rng := rand.New(rand.NewPCG(42, 7))
	rng.Shuffle(len(ptrs), func(i, j int) {
		ptrs[i], ptrs[j] = ptrs[j], ptrs[i]
	})
	var sum int64
	for b.Loop() {
		sum = sumPointers(ptrs)
	}
	benchSink = sum
}
```

Запустим бенчмарки командой `go test -bench=. -benchmem`:

```text
BenchmarkMatrixRows-24          5066     233156 ns/op    0 B/op    0 allocs/op
BenchmarkMatrixCols-24           552    2089358 ns/op    0 B/op    0 allocs/op
BenchmarkSliceValues-24        13246      90054 ns/op    0 B/op    0 allocs/op
BenchmarkSlicePointers-24       5473     215826 ns/op    0 B/op    0 allocs/op
```

Четыре колонки читаются так: число прогонов (`5066`), среднее время одной операции (`233156 ns/op`, то есть ~0,23 мс), байт выделено в куче (`0 B/op`) и число аллокаций (`0 allocs/op`).

Обратите внимание на честную деталь: для матрицы `1024 × 1024` (8 МБ) разрыв составил **9×** (вместо 15,6× на 128 МБ), а для 200 000 записей (6,4 МБ) — **2,4×** (вместо 5,4× на 500 000 записей). Причина — размер кэша L3: пока рабочий набор помещается в L3, промахи стоят около 10–15 нс; как только данные перерастают L3 и уходят в RAM (~100 нс), штраф за плохую локальность резко растёт.

## Подводные камни

**Ловушка 1. Выкинутый результат и переменная `benchSink`.**  
Если вызвать функцию внутри цикла и никуда не сохранить результат, компилятор может понять, что вычисление ни на что не влияет, и просто удалить его. В `for b.Loop()` компилятор Go 1.24 защищает аргументы и результаты внутри цикла лучше старого `for i := 0; i < b.N; i++`, но присваивание итоговой суммы в переменную уровня пакета `benchSink` остаётся хорошей привычкой.

**Ловушка 2. Искусственно «красивые» указатели без перемешивания.**  
Если в эксперименте создать `ptrs[i] = &record{...}` в цикле подряд и **не перемешать** слайс, аллокатор Go уложит соседние структуры почти вплотную друг к другу. Замер покажет обманчиво маленькую разницу, которая исчезнет в реальном приложении после тысяч вставок и удалений.

> [!check] Проверь понимание
> Почему в `BenchmarkMatrixCols` колонка `allocs/op` показывает `0`, хотя функция работает в 9 раз медленнее `BenchmarkMatrixRows`?
>
> Потому что `sumByCols` вообще не выделяет новую память в куче — вся матрица была выделена один раз до цикла `b.Loop()`. Замедление в 9 раз вызвано исключительно промахами мимо кэшей процессора, а не работой сборщика мусора.

**Упражнение 1 (Базовое). Прочитайте строку бенчмарка.**  
Вы запустили `go test -bench=. -benchmem` и получили:
```text
BenchmarkFormat-8    400000    2850 ns/op    512 B/op    4 allocs/op
```
Сколько микросекунд в среднем занимает один вызов, сколько байтов памяти он выделяет в куче и на скольких логических CPU выполнялся тест?

> [!solution] Показать решение
> * Среднее время одного вызова: `2850 нс = 2,85 мкс`.
> * Выделяется `512` байт в куче за `4` отдельные аллокации на каждый вызов.
> * Суффикс `-8` означает значение `GOMAXPROCS = 8` (8 логических процессоров).

**Упражнение 2 (Практическое). Сравните «структуру массивов» и «массив структур».**  
В задаче выше мы суммировали только одно поле `Score` из четырёх полей структуры `record` (32 байта). Добавьте в `locality_test.go` бенчмарк `BenchmarkScoresOnly`, где оценки лежат в отдельном плотном слайсе `scores := make([]int64, 200_000)` (8 байт на элемент вместо 32). Запустите `go test -bench=BenchmarkSlice\|BenchmarkScores` и объясните разницу в скорости.

> [!solution] Показать решение
> ```go
> func sumScores(scores []int64) int64 {
> 	var total int64
> 	for _, s := range scores {
> 		total += s
> 	}
> 	return total
> }
>
> func BenchmarkScoresOnly(b *testing.B) {
> 	const n = 200_000
> 	scores := make([]int64, n)
> 	for i := range n {
> 		scores[i] = int64(i % 100)
> 	}
> 	var sum int64
> 	for b.Loop() {
> 		sum = sumScores(scores)
> 	}
> 	benchSink = sum
> }
> ```
> В `[]int64` одна 64-байтовая кэш-линия несёт **8 полезных оценок**, а в `[]record` — только **2** (остальные 48 байт заняты полями `ID`, `Updated`, `Flags`, которые циклу не нужны). Поэтому плотный слайс `[]int64` читает в 4 раза меньше кэш-линий и оказывается заметно быстрее.

**Упражнение 3 (Со звёздочкой \*). Влияние шага (stride) на промахи кэша.**  
Напишите бенчмарк с подтестами (`b.Run`), который суммирует элементы слайса `[]int64` размером 8 МБ с шагом `stride = 1, 2, 4, 8, 16, 32` (`for i := 0; i < len(data); i += stride`). Пересчитайте время на **одно сложение** и объясните, почему резкий скачок времени начинается именно около `stride = 8`.

> [!solution] Показать решение
> Добавьте импорт `"fmt"` в `locality_test.go` и следующий бенчмарк:
> ```go
> func BenchmarkStride(b *testing.B) {
> 	const size = 1 << 20 // 1 048 576 элементов * 8 Б = 8 МБ
> 	data := make([]int64, size)
> 	for i := range data {
> 		data[i] = int64(i % 7)
> 	}
>
> 	for _, stride := range []int{1, 2, 4, 8, 16, 32} {
> 		b.Run(fmt.Sprintf("stride=%d", stride), func(b *testing.B) {
> 			var sum int64
> 			for b.Loop() {
> 				var s int64
> 				for i := 0; i < len(data); i += stride {
> 					s += data[i]
> 				}
> 				sum = s
> 			}
> 			benchSink = sum
> 		})
> 	}
> }
> ```
> Один `int64` занимает 8 байт, а кэш-линия — **64 байта**, то есть ровно 8 элементов `int64`. При `stride = 1..4` процессор использует несколько чисел из каждой загруженной кэш-линии. Начиная со `stride = 8` (64 байта) каждый шаг попадает в **новую** кэш-линию — число обращений к памяти перестаёт уменьшаться пропорционально шагу, и стоимость одного сложения подскакивает.
