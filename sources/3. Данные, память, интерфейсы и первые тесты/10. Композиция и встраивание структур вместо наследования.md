*Почему в Go нет наследования классов, как переиспользовать код через явную композицию и встраивание структур и где проходит граница продвижения методов.*

> «Когда вы осваиваете новый язык, возникает естественное желание писать на нём так же, как на языке, который вы уже знаете. Замечайте в себе эту привычку при изучении Go и старайтесь ей не поддаваться.»  
> — Алан Донован и Брайан Керниган, *The Go Programming Language*

Представьте: в `BookmarkFlow` уже есть `MemoryStore`, хранящее закладки в памяти. Теперь нужно `FileStore` — та же логика, но с сохранением на диск после каждой правки. В Java, C++ или Python здесь написали бы `class FileStore extends MemoryStore`. В Go нет ни классов, ни `extends` — это осознанный отказ от хрупких иерархий.

## Почему Go выбрал композицию вместо наследования

Глубокие деревья наследования тяжело стареют: потомок привязан к внутреннему состоянию родителя, и правка базового класса способна незаметно сломать десяток подклассов.

Go выбирает **композицию**. Вместо вертикальной иерархии (*is-a*) мы собираем новый тип из независимых деталей по принципу «содержит внутри» (*has-a*):

```text
  FileStore
  ├── path: "bookmarks.json"
  └── mem ──▶ MemoryStore (готовая логика поиска, валидации, ID)
```

## Явная композиция: выбор по умолчанию

Самый чистый способ построить `FileStore` поверх `MemoryStore` — обычное именованное поле `mem *MemoryStore`:

```go
type FileStore struct {
	path string
	mem  *MemoryStore
}

func (f *FileStore) Count() int { return f.mem.Count() }

func (f *FileStore) Add(title string) error {
	if err := f.mem.Add(title); err != nil {
		return err
	}
	return f.sync()
}
```

При **явной композиции** вы полностью контролируете публичный API: ни один внутренний метод `MemoryStore` не утечёт наружу случайно, а сохранение на диск вызывается ровно там, где нужно. Именно так устроен `FileStore` в `BookmarkFlow`.

## Встраивание структур (*struct embedding*) и продвижение

Когда хочется перенять поля и методы вспомогательной структуры без десятка однострочных обёрток, используют **встраивание структур** (*struct embedding*) — указывают тип **без имени поля**:

```go
type AuditMeta struct {
	CreatedBy string
	Version   int
}

func (a *AuditMeta) Touch() { a.Version++ }

type Bookmark struct {
	AuditMeta // встроенная структура
	ID        int
	Title     string
}
```

Поля и методы `AuditMeta` **продвигаются** (*method promotion*) на уровень `Bookmark`: можно писать `b.CreatedBy` и `b.Touch()` напрямую — это сокращение для `b.AuditMeta.CreatedBy` и `b.AuditMeta.Touch()`.

Встраивать можно и указатель (`*MemoryStore`), но не забывайте инициализировать его при создании (`&TrackedStore{MemoryStore: &MemoryStore{}}`), иначе вызов продвинутого метода упадёт на `nil`.

## Перекрытие имён (*shadowing*) и конфликты

Если внешняя структура объявит метод с тем же именем, что у встроенной, внешний метод **перекроет** (*shadow*) встроенный. При этом встроенный метод доступен явно по имени типа: `t.MemoryStore.Add(title)`.

Если же два разных встроенных типа на одном уровне содержат одинаковое имя `Name`, компилятор откажется гадать (`ambiguous selector x.Name`) и попросит указать путь явно (`x.First.Name`).

## Главная граница: встраивание — это НЕ наследование

У встраивания два жёстких правила, которые отличают его от ООП-наследования:

1. **Получатель продвинутого метода остаётся встроенным типом.** Если `MemoryStore.Banner()` вызывает `m.Kind()`, а `TrackedStore` перекрыл `Kind()`, то `ts.Banner()` всё равно вызовет **`MemoryStore.Kind()`**. Встроенный метод ничего не знает о внешней структуре:

```text
  ts.Banner() ──▶ ts.MemoryStore.Banner() ──▶ m.Kind()  (всегда MemoryStore.Kind!)
```

2. **Внешний тип не считается подтипом встроенного.** В функцию `printStats(s *MemoryStore)` передать `*TrackedStore` нельзя:

```go
printStats(ts)
// compile error: cannot use ts (variable of type *TrackedStore) as *MemoryStore value in argument to printStats
```

**Встраивание делегирует вызовы, но не создаёт полиморфизм.**

## Рабочий пример

Убедимся в обоих правилах — перекрытии и границе получателя — на живой программе:

```go
package main

import (
	"errors"
	"fmt"
	"strings"
)

type MemoryStore struct {
	titles []string
}

func (m *MemoryStore) Kind() string { return "memory" }

func (m *MemoryStore) Banner() string {
	return fmt.Sprintf("[%s] записей: %d", m.Kind(), len(m.titles))
}

func (m *MemoryStore) Add(title string) error {
	clean := strings.TrimSpace(title)
	if clean == "" {
		return errors.New("пустое название")
	}
	m.titles = append(m.titles, clean)
	return nil
}

type TrackedStore struct {
	*MemoryStore // встраивание указателя
	writes       int
}

func (t *TrackedStore) Kind() string { return "tracked" }

// Перекрываем Add и делегируем базовую работу встроенному MemoryStore
func (t *TrackedStore) Add(title string) error {
	if err := t.MemoryStore.Add(title); err != nil {
		return err
	}
	t.writes++
	return nil
}

func main() {
	ts := &TrackedStore{MemoryStore: &MemoryStore{}}
	_ = ts.Add("Go Spec")
	_ = ts.Add("Go stdlib")

	fmt.Println("ts.Kind():  ", ts.Kind())
	fmt.Println("ts.Banner():", ts.Banner())
	fmt.Println("Записей прошло через Add:", ts.writes)
}
```

Вывод программы:

```text
ts.Kind():   tracked
ts.Banner(): [memory] записей: 2
Записей прошло через Add: 2
```

Вглядитесь во вторую строку вывода: `ts.Kind()` вернуло `"tracked"`, но `ts.Banner()` напечатало `[memory]`, потому что внутри `Banner` получателем остаётся `*MemoryStore`. Как только вы держите эту модель в голове, встраивание перестаёт быть загадкой.

Как выбирать между двумя подходами? По умолчанию используйте **явную композицию** (`mem *MemoryStore`): она честнее и не выставляет наружу лишних методов. К **встраиванию** прибегайте тогда, когда внешний тип действительно обязан перенять весь набор полей или методов встроенного компонента без ограничений.

> [!check] Проверь понимание
> В коде выше мы добавили бы функцию `func countOf(s *MemoryStore) int { return len(s.titles) }`. Можно ли вызвать `countOf(ts)`, если `ts` имеет тип `*TrackedStore`?
>
> Нет, компилятор отвергнет вызов: `*TrackedStore` и `*MemoryStore` — разные типы. Чтобы передать встроенное хранилище, нужно явно написать `countOf(ts.MemoryStore)`.

## Практика

**Упражнение 1 (Базовое). Встраивание метаданных.**  
Объявите структуру `Revision` с полем `Version int` и методом `(r *Revision) Bump()`, увеличивающим `Version` на `1`. Встройте `Revision` по значению в `Bookmark` (`ID int`, `Title string`). Создайте `Bookmark`, дважды вызовите `b.Bump()` напрямую и выведите `b.Version`.

> [!solution] Показать решение
> ```go
> package main
>
> import "fmt"
>
> type Revision struct {
> 	Version int
> }
>
> func (r *Revision) Bump() {
> 	r.Version++
> }
>
> type Bookmark struct {
> 	Revision
> 	ID    int
> 	Title string
> }
>
> func main() {
> 	b := Bookmark{ID: 1, Title: "Go Spec"}
> 	b.Bump()
> 	b.Bump()
> 	fmt.Println("Version:", b.Version) // Вывод: Version: 2
> }
> ```
> Поскольку `Revision` встроена по значению, нулевое значение `Bookmark` сразу содержит готовую `Revision{Version: 0}`, а компилятор сам берёт адрес при вызове `b.Bump()`.

**Упражнение 2 (Практическое). Журналирующее хранилище через явную композицию.**  
На основе `MemoryStore` из примера урока напишите структуру `AuditedStore`, которая содержит явное поле `mem *MemoryStore` и поле `events []string`. Реализуйте конструктор `NewAuditedStore() *AuditedStore` и методы `Add(title string) error` (при успехе добавляет в `events` строку `"add: " + title`), `Count() int` и `Events() []string`.

> [!solution] Показать решение
> ```go
> type AuditedStore struct {
> 	mem    *MemoryStore
> 	events []string
> }
>
> func NewAuditedStore() *AuditedStore {
> 	return &AuditedStore{mem: &MemoryStore{}}
> }
>
> func (a *AuditedStore) Add(title string) error {
> 	if err := a.mem.Add(title); err != nil {
> 		return err
> 	}
> 	a.events = append(a.events, "add: "+strings.TrimSpace(title))
> 	return nil
> }
>
> func (a *AuditedStore) Count() int       { return len(a.mem.titles) }
> func (a *AuditedStore) Events() []string { return a.events }
> ```
> Явная композиция гарантирует, что внешний код не обойдёт журналирование через случайный вызов продвинутого метода `MemoryStore`.

**Упражнение 3 (Со звёздочкой \*). Две поломки в одном фрагменте.**  
Найдите обе ошибки в коде ниже (одна не скомпилируется, другая уронит программу паникой при запуске) и объясните каждую:
```go
type LoggedStore struct {
	*MemoryStore
}

func showBanner(m *MemoryStore) {
	fmt.Println(m.Banner())
}

func main() {
	ls := &LoggedStore{}
	_ = ls.Add("Go")
	showBanner(ls)
}
```

> [!solution] Показать решение
> 1. **Ошибка компиляции** в строке `showBanner(ls)`: `*LoggedStore` не подтип `*MemoryStore`, передавать нужно `ls.MemoryStore` (или перейти к интерфейсу).
> 2. **Паника во время выполнения** в строке `ls.Add("Go")`: встроенный указатель `ls.MemoryStore` остался `nil`, поэтому обращение к `m.titles` внутри `MemoryStore.Add` вызовет разыменование `nil`-указателя.
>
> Исправление: инициализировать `&LoggedStore{MemoryStore: &MemoryStore{}}` и передавать `showBanner(ls.MemoryStore)`.
