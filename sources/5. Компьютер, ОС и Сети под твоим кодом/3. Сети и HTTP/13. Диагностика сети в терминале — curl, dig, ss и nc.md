*Четыре базовых инструмента сетевой диагностики в терминале Linux: проверяем DNS через `dig`, открытые сокеты через `ss`, сырой TCP-диалог через `nc` и HTTP/TLS-запросы через `curl`.*

«На моём ноутбуке всё работает, а на сервере клиент получает ошибку подключения.» Когда сеть молчит, угадывать причину по коду можно часами. За две минуты в терминале четыре стандартные утилиты показывают, на каком именно слое оборвалась цепочка: не разрешается имя (`dig`), процесс не слушает нужный порт (`ss`), сбоит TCP-протокол (`nc`) или расходятся HTTP-заголовки и сертификат (`curl`).

## `dig` — проверяем DNS без догадок

Утилита **`dig`** отправляет прямые DNS-запросы и показывает записи вместе со сроком жизни `TTL`:

```text
$ dig +short go.dev A
216.239.38.21

$ dig +short go.dev AAAA
2001:4860:4802:32::15

$ dig @1.1.1.1 go.dev A +noall +answer
go.dev.                 287     IN      A       216.239.38.21

$ dig www.github.com CNAME +noall +answer
www.github.com.         3512    IN      CNAME   github.com.
```

Ключевые флаги:
- **`+short`** — печатает только итоговое значение без лишнего текста;
- **`A`, `AAAA`, `CNAME`** (а также `TXT`, `MX`) — выбор типа записи;
- **`@1.1.1.1`** — запрос напрямую к выбранному резолверу в обход локального кэша провайдера;
- **`+noall +answer`** — компактная строка ответа, где число `287` — оставшийся **`TTL` в секундах**.

## `ss` — кто и на каком адресе слушает порты

Утилита **`ss`** (*Socket Statistics*) читает таблицу сокетов напрямую из ядра Linux и сразу отвечает на вопросы «кто занял порт» и «доступен ли сервер извне».

Главная команда — **`ss -tlnp`**: `-t` (TCP), `-l` (слушающие сокеты), `-n` (числовые порты без DNS), `-p` (имя процесса и `PID`):

```text
$ ss -tlnp
State   Recv-Q Send-Q Local Address:Port  Peer Address:Port Process
LISTEN  0      4096   127.0.0.1:9090      0.0.0.0:*         users:(("bookmarkflow",pid=18421,fd=3))
LISTEN  0      4096   0.0.0.0:8080        0.0.0.0:*         users:(("api-gateway",pid=9104,fd=6))
```

Одна таблица даёт три факта: `bookmarkflow` (PID `18421`, дескриптор `fd=3`) слушает `9090`, но только на **`127.0.0.1`** — с соседней машины подключиться не выйдет. А `api-gateway` слушает **`0.0.0.0:8080`** на всех интерфейсах. Сокеты в `TIME_WAIT` смотрят командой `ss -tan state time-wait`.

## `nc` (*netcat*) — сырой TCP-диалог с `TCPServer` из шага 6

Утилита **`nc`** (*netcat*) связывает `stdin`/`stdout` терминала напрямую с TCP-сокетом. Это лучший способ вручную поговорить с собственным текстовым протоколом.

Подключимся к `TCPServer` из `project/step06/`, запущенному на `127.0.0.1:9090` с одной закладкой `GoDoc`:

```text
$ nc 127.0.0.1 9090
PING
PONG
COUNT
COUNT 1
LIST
1 GoDoc https://pkg.go.dev
END
GET 1
OK 1 GoDoc https://pkg.go.dev
QUIT
BYE
```

Каждая набранная строка попадает в `scanner.Scan()` метода `handleConn`, а ответ после `writer.Flush()` сразу возвращается в терминал. Для быстрой проверки доступности порта без передачи данных используют флаг `-z` (сканирование) и `-v` (подробный вывод):

```text
$ nc -zv 127.0.0.1 9090
Connection to 127.0.0.1 9090 port [tcp/*] succeeded!
```

Ответ `Connection refused` означает, что машина доступна, но порт закрыт; долгое зависание обычно указывает на фаервол.

## `curl` — инспектируем HTTP и TLS целиком

Главный терминальный клиент для HTTP/HTTPS — **`curl`**. Самые ходовые флаги:
- **`curl -i <url>`** — заголовки ответа плюс тело;
- **`curl -I <url>`** — запрос `HEAD` (только статус и заголовки);
- **`curl -v <url>`** — полная трассировка: `*` (DNS, TCP, TLS), `>` (исходящий запрос), `<` (входящий ответ);
- **`curl -X POST -H ... -d ...`** — отправка JSON-запроса к API:

```text
$ curl -i -X POST \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  -d '{"title":"GoDoc","url":"https://pkg.go.dev"}' \
  http://127.0.0.1:8080/bookmarks
```

Фрагмент подробного вывода `curl -v -I https://go.dev` связывает воедино весь подраздел:

```text
$ curl -v -I https://go.dev
* Host go.dev:443 was resolved.
* IPv4: 216.239.38.21
* Connected to go.dev (216.239.38.21) port 443
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
* TLSv1.3 (IN), TLS handshake, Server hello (2):
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384
*  subject: CN=go.dev
> HEAD / HTTP/2
> Host: go.dev
> Accept: */*
>
< HTTP/2 200
< content-type: text/html; charset=utf-8
<
```

## Лестница диагностики снизу вверх

| Шаг | Вопрос | Команда |
|---|---|---|
| 1. DNS | В какой IP разрешается домен и каков `TTL`? | `dig +noall +answer host A` |
| 2. Сокеты | Слушает ли процесс порт на нужном интерфейсе? | `ss -tlnp` |
| 3. TCP | Принимает ли порт соединения и что отвечает протокол? | `nc -zv host port` / `nc host port` |
| 4. TLS / HTTP | Валиден ли сертификат, какие заголовки и статус приходят? | `curl -v <url>` |

## Подводные камни

**Ловушка 1. `curl` по умолчанию не идёт по редиректам.**  
На `301`/`302` `curl` покажет пустой ответ и остановится. Чтобы следовать за заголовком `Location`, добавляйте флаг **`-L`**.

**Ловушка 2. Пустая колонка `Process` в `ss -tlnp`.**  
Без прав суперпользователя ядро скрывает имена чужих процессов — сокет виден, но колонка `Process` пуста. Для полной картины запускайте `sudo ss -tlnp`.

> [!check] Проверь понимание
> На сервере `curl http://127.0.0.1:8080/health` возвращает `200 OK`, но с вашего ноутбука `nc -zv <IP-сервера> 8080` мгновенно выдаёт `Connection refused`. Что покажет `ss -tlnp` на сервере?
>
> В `Local Address:Port` будет **`127.0.0.1:8080`** вместо `0.0.0.0:8080` (или `[::]:8080`): программа слушает только петлевой интерфейс.

## Практика

**Упражнение 1 (Базовое). Выбор инструмента.**  
Какую команду вы запустите первой: (а) сервер падает с `address already in use` на `8080`; (б) после смены IP домен ведёт на старый сервер; (в) `POST /bookmarks` отвечает `415`; (г) нужно вручную послать `PING` в `TCPServer` из `step06`?

> [!solution] Показать решение
> (а) `ss -tlnp`; (б) `dig +noall +answer <домен> A`; (в) `curl -v -X POST -H "Content-Type: application/json" -d '...' <url>`; (г) `nc 127.0.0.1 <порт>`.

**Упражнение 2 (Практическое). Запрос `PUT` через `curl`.**  
Напишите команду `curl`, которая шлёт `PUT` на `http://127.0.0.1:8080/bookmarks/3` с JSON `{"title":"Go Spec","url":"https://go.dev/ref/spec"}`, заголовками `Content-Type` и `Accept` для JSON и выводит заголовки ответа с телом.

> [!solution] Показать решение
> ```text
> curl -i -X PUT \
>   -H "Content-Type: application/json" \
>   -H "Accept: application/json" \
>   -d '{"title":"Go Spec","url":"https://go.dev/ref/spec"}' \
>   http://127.0.0.1:8080/bookmarks/3
> ```
> `-i` включает вывод заголовков ответа, `-X PUT` задаёт метод, `-d` передаёт тело.

**Упражнение 3 (Со звёздочкой \*). Почему `nc` не подходит для HTTPS.**  
Почему `nc 127.0.0.1 9090` отлично общается с нашим `TCPServer`, а попытка набрать `GET / HTTP/1.1` через `nc go.dev 443` обрывается сервером?

> [!solution] Показать решение
> Порт `443` ждёт первым пакетом бинарный TLS **`ClientHello`**, а не текстовую строку HTTP. `nc` не реализует TLS и шлёт открытые байты; сервер видит некорректный заголовок записи и закрывает соединение. Для HTTPS нужен клиент с поддержкой TLS (`curl -v` или `openssl s_client`).
