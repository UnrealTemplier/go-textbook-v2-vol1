*Как интерфейсы в Go описывают поведение вместо иерархий типов, работают без ключевого слова `implements` и снимают «магию» со встроенных `error` и `fmt.Stringer`.*

В `BookmarkFlow` мы уже храним закладки в структуре `MemoryStore`. Скоро понадобится хранилище в файле и лёгкая заглушка для тестов. Пока функция добавления закладки жёстко привязана к одному конкретному типу:

```go
func SaveBookmark(s *MemoryStore, title, rawURL string) error
```

С появлением `FileStore` придётся копировать логику под новый параметр и править каждую проверку в двух местах сразу.

## Поведение вместо «родословной»

Функции `SaveBookmark` безразлично, что лежит внутри хранилища — слайс, мапа или путь к файлу. Ей важно одно: умеет ли переданное значение сохранять закладку и считать их число.

Так устроена электрическая розетка: ей всё равно, лампа это или зарядка ноутбука, лишь бы совпали контакты вилки. Граница аналогии: розетка проверяет совместимость при включении, а компилятор Go — ещё до запуска.

Контракт поведения в Go называется **интерфейсом** (`interface`). Он описывает **что значение умеет делать**, а не **чем оно является** — только сигнатуры методов, без полей:

```go
type BookmarkStore interface {
	Add(title, rawURL string) int
	Count() int
}
```

## Неявная реализация: без `implements`

В Java или C# класс обязан явно написать `implements BookmarkStore`. В Go такого слова нет. **Если тип имеет все методы из интерфейса с точно такими же сигнатурами, он автоматически реализует этот интерфейс** (удовлетворяет ему).

Вы можете объявить интерфейс в своём пакете — и готовый тип из стандартной библиотеки удовлетворит ему без единой правки в исходном пакете.

## Снимаем «магию» с `error` и `fmt.Stringer`

В Модуле 2 `error` был чёрным ящиком. Откроем крышку: встроенный `error` — обычный интерфейс с одним методом `Error() string`. Любой тип с таким методом автоматически становится ошибкой Go.

Точно так же `fmt.Println` печатает пользовательские структуры красиво: он проверяет, удовлетворяет ли значение стандартному интерфейсу `fmt.Stringer` с единственным методом `String() string`.

Посмотрим на оба контракта вместе:

```go
package main

import (
	"fmt"
	"strings"
)

type Bookmark struct {
	ID    int
	Title string
	URL   string
}

func (b Bookmark) String() string {
	return fmt.Sprintf("#%d %s (%s)", b.ID, b.Title, b.URL)
}

type ValidationError struct {
	Field, Message string
}

func (e ValidationError) Error() string {
	return fmt.Sprintf("поле %s: %s", e.Field, e.Message)
}

func NewBookmark(id int, title, rawURL string) (Bookmark, error) {
	if strings.TrimSpace(title) == "" {
		return Bookmark{}, ValidationError{Field: "title", Message: "не может быть пустым"}
	}
	return Bookmark{ID: id, Title: title, URL: rawURL}, nil
}

func main() {
	b, err := NewBookmark(1, "Документация Go", "https://go.dev")
	if err != nil {
		fmt.Println("Ошибка:", err)
		return
	}
	fmt.Println("Создано:", b)

	_, err = NewBookmark(2, "   ", "https://example.org")
	fmt.Println("Ошибка:", err)
}
```

Вывод:

```text
Создано: #1 Документация Go (https://go.dev)
Ошибка: поле title: не может быть пустым
```

Мы нигде не объявляли привязку к `error` или `fmt.Stringer` — совпали сигнатуры, и пакет `fmt` подхватил оба типа.

## Наборы методов: `T` против `*T`

При присваивании интерфейсу критично различать получатель-значение `(T)` и получатель-указатель `(*T)`:

| Тип значения | Методы в наборе |
|---|---|
| Значение `T` | Только методы с `(T)` |
| Указатель `*T` | Методы с `(T)` и с `(*T)` |

Если `MemoryStore` изменяет внутренний слайс в методе с получателем-указателем `func (s *MemoryStore) Add(...) int`, интерфейсу `BookmarkStore` удовлетворяет `*MemoryStore`, но не `MemoryStore`:

```go
package main

import "fmt"

type BookmarkStore interface {
	Add(title, rawURL string) int
	Count() int
}

type MemoryStore struct{ titles []string }

func (s *MemoryStore) Add(title, _ string) int {
	s.titles = append(s.titles, title)
	return len(s.titles)
}

func (s *MemoryStore) Count() int { return len(s.titles) }

var _ BookmarkStore = (*MemoryStore)(nil) // проверка контракта при сборке

func seed(st BookmarkStore) {
	st.Add("Go Tour", "https://go.dev/tour")
	fmt.Println("Всего закладок:", st.Count())
}

func main() {
	mem := MemoryStore{}
	seed(&mem)
}
```

Попробуйте передать значение `seed(mem)` — компилятор остановит сборку:

```text
cannot use mem (variable of type MemoryStore) as BookmarkStore value in argument to seed: MemoryStore does not implement BookmarkStore (method Add has pointer receiver)
```

При копировании значения `mem` внутрь интерфейса у этой копии нет адреса для вызова мутирующего метода `Add`. Указатель `&mem` решает задачу.

## Проверка контракта на этапе компиляции

Строка выше — стандартная идиома Go:

```go
var _ BookmarkStore = (*MemoryStore)(nil)
```

Безымянная переменная `_` не выделяет объект в памяти, но заставляет компилятор немедленно проверить: реализует ли `*MemoryStore` интерфейс `BookmarkStore`. Если кто-то переименует метод `Count` в `Len`, сборка упадёт прямо на этой строке.

> [!check] Проверь понимание
> У структуры `Counter` есть `func (c *Counter) Inc()` и `func (c Counter) Value() int`. Интерфейс `Gauge` требует только `Value() int`. Удовлетворяет ли значение `Counter{}` интерфейсу `Gauge`?
>
> Да. `Gauge` требует только `Value() int`, а он объявлен с получателем-значением `(c Counter)`, поэтому входит в набор методов `Counter`.

## Практика

**Упражнение 1 (Базовое). Цена через `fmt.Stringer`.**  
Объявите `type PriceKop int64` и метод `String() string`, чтобы `fmt.Println(PriceKop(1250))` выводило `12.50 RUB`, а `PriceKop(5)` — `0.05 RUB`.

> [!solution] Показать решение
> ```go
> package main
>
> import "fmt"
>
> type PriceKop int64
>
> func (p PriceKop) String() string {
> 	rub, kop := p/100, p%100
> 	if kop < 0 {
> 		kop = -kop
> 	}
> 	return fmt.Sprintf("%d.%02d RUB", rub, kop)
> }
>
> func main() {
> 	fmt.Println(PriceKop(1250), PriceKop(5)) // Вывод: 12.50 RUB 0.05 RUB
> }
> ```
> Спецификатор `%02d` добавляет ведущий ноль к копейкам, а получатель-значение работает и для `PriceKop`, и для `*PriceKop`.

**Упражнение 2 (Практическое). Интерфейс `Notifier`.**  
Объявите `type Notifier interface { Notify(msg string) error }` и две реализации: `ConsoleNotifier` (печатает `[NOTIFY] <msg>`) и `RecorderNotifier` (накапливает сообщения в `Messages []string` через получатель-указатель). Добавьте проверки `var _ Notifier = ...` и функцию `Broadcast(targets []Notifier, msg string) error`.

> [!solution] Показать решение
> ```go
> package main
>
> import "fmt"
>
> type Notifier interface{ Notify(msg string) error }
>
> type ConsoleNotifier struct{}
>
> func (ConsoleNotifier) Notify(msg string) error {
> 	fmt.Println("[NOTIFY]", msg)
> 	return nil
> }
>
> type RecorderNotifier struct{ Messages []string }
>
> func (r *RecorderNotifier) Notify(msg string) error {
> 	r.Messages = append(r.Messages, msg)
> 	return nil
> }
>
> var (
> 	_ Notifier = ConsoleNotifier{}
> 	_ Notifier = (*RecorderNotifier)(nil)
> )
>
> func Broadcast(targets []Notifier, msg string) error {
> 	for _, t := range targets {
> 		if err := t.Notify(msg); err != nil {
> 			return err
> 		}
> 	}
> 	return nil
> }
>
> func main() {
> 	rec := &RecorderNotifier{}
> 	_ = Broadcast([]Notifier{ConsoleNotifier{}, rec}, "бэкап готов")
> 	fmt.Println("Сохранено:", len(rec.Messages))
> }
> ```
> `ConsoleNotifier` не мутирует состояние и работает по значению; `RecorderNotifier` изменяет слайс и передаётся как указатель.

**Упражнение 3 (Со звёздочкой \*). Что сломается?**  
Почему фрагмент ниже не скомпилируется? Назовите два способа исправления и объясните, какой из них лучше для `LogEntry`.

```go
type Formatter interface{ Format() string }
type LogEntry struct{ Level, Text string }

func (e *LogEntry) Format() string { return "[" + e.Level + "] " + e.Text }

func printFormatted(f Formatter) { fmt.Println(f.Format()) }

// В main():
entry := LogEntry{Level: "WARN", Text: "диск 90%"}
printFormatted(entry)
```

> [!solution] Показать решение
> `Format()` объявлен на `*LogEntry`, поэтому значение `LogEntry` не удовлетворяет `Formatter` (`method Format has pointer receiver`).
>
> Два исправления: передать `&entry` либо сменить получатель на значение `func (e LogEntry) Format() string`. Второй способ лучше: `Format` ничего не изменяет, структура маленькая, а с получателем-значением `Formatter` реализуют и `LogEntry`, и `*LogEntry`.
