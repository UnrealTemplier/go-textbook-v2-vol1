*Зачем в HTTP разные методы запросов, чем безопасность отличается от идемпотентности, как читать семейства кодов ответа и как клиент с сервером согласуют формат данных.*

Представьте, что мобильный клиент `BookmarkFlow` отправил запрос на создание закладки, и в лифте пропала связь. Ответа нет — клиент не знает, успел ли сервер сохранить запись. Можно ли автоматически повторить запрос? Для чтения списка закладок — можно без раздумий. Для создания новой — слепой повтор породит дубликат.

HTTP не заставляет программы гадать. Смысл действия, допустимость повторов и исход операции закодированы прямо в протоколе: в **методах**, **кодах статуса** и **заголовках формата**.

## Методы HTTP: безопасность и идемпотентность

Два свойства методов определяют, как клиенты, кэши и прокси имеют право обращаться с запросом:

- **Безопасность (*safe*).** Метод только читает данные и не меняет состояние сервера. Такой запрос можно кэшировать и повторять сколько угодно раз.
- **Идемпотентность (*idempotent*).** Отправка одного и того же запроса 1 раз или 10 раз подряд оставляет сервер в **одном и том же итоговом состоянии**.

Всякий безопасный метод идемпотентен, но не всякий идемпотентный безопасен: `PUT` и `DELETE` меняют данные.

| Метод | Назначение | Безопасный | Идемпотентный | Пример |
|---|---|---:|---:|---|
| **`GET`** | Получить ресурс | Да | Да | `GET /bookmarks/42` |
| **`HEAD`** | Как `GET`, но только заголовки без тела | Да | Да | Проверка наличия или размера |
| **`POST`** | Создать ресурс или запустить действие | Нет | Нет | `POST /bookmarks` |
| **`PUT`** | Полностью заменить ресурс по адресу | Нет | Да | `PUT /bookmarks/42` |
| **`PATCH`** | Частично обновить поля ресурса | Нет | Зависит от операции | `PATCH /bookmarks/42` |
| **`DELETE`** | Удалить ресурс | Нет | Да | `DELETE /bookmarks/42` |

Разница между `PUT` и `PATCH` принципиальна. `PUT` передаёт полную версию ресурса: пять одинаковых `PUT /bookmarks/42` дадут один и тот же результат. `PATCH` передаёт частичное изменение: установка `title = "Go"` идемпотентна, а «прибавить 1 к счётчику кликов» — нет.

Заметьте тонкость с `DELETE`: первый вызов вернёт `204 No Content`, второй — `404 Not Found`. Разные статусы не нарушают идемпотентность, ведь **состояние сервера** одинаково: закладки `#42` больше нет.

## Семейства кодов ответа (`2xx`–`5xx`)

Первая цифра кода сразу задаёт класс результата:
- **`2xx`** — успех;
- **`3xx`** — перенаправление или актуальный кэш;
- **`4xx`** — ошибка клиента (повторять тот же запрос без правок бессмысленно);
- **`5xx`** — ошибка сервера (сбой на бэкенде или шлюзе).

Ключевые коды, которые встречаются в разработке каждый день:

| Код | Название | Смысл |
|---|---|---|
| **`200`** | `OK` | Успешно, результат в теле (`GET`, `PUT`, `PATCH`) |
| **`201`** | `Created` | Ресурс создан (`POST`) |
| **`204`** | `No Content` | Успешно, тело пустое (`DELETE`) |
| **`301`** | `Moved Permanently` | Постоянный переезд на URL из `Location` |
| **`304`** | `Not Modified` | Данные не менялись, берите из кэша |
| **`400`** | `Bad Request` | Битый JSON или неверные параметры |
| **`401`** | `Unauthorized` | Не аутентифицирован («кто вы?») |
| **`403`** | `Forbidden` | Опознан, но прав нет («вам сюда нельзя») |
| **`404`** | `Not Found` | Ресурс не найден |
| **`409`** | `Conflict` | Конфликт состояния (например, дубликат URL) |
| **`429`** | `Too Many Requests` | Превышен лимит частоты запросов |
| **`500`** | `Internal Server Error` | Внутренняя ошибка сервера |
| **`502`** | `Bad Gateway` | Некорректный ответ от нижележащего сервиса |
| **`503`** | `Service Unavailable` | Сервер временно перегружен |
| **`504`** | `Gateway Timeout` | Шлюз не дождался ответа бэкенда |

Семантика методов и кодов напрямую ложится в правило автоматического повтора запроса (на чистом Go, без HTTP-пакетов):

```go
func CanRetry(method string, code int) bool {
	idempotent := method == "GET" || method == "HEAD" || method == "PUT" || method == "DELETE"
	if !idempotent {
		return false
	}
	return code == 429 || code == 502 || code == 503 || code == 504
}
```

Повторять запрос допустимо лишь тогда, когда метод идемпотентен, а статус указывает на временный сбой (`429`, `502`–`504`), а не на ошибку клиента вроде `400` или `404`.

## Согласование форматов: `Content-Type` и `Accept`

Тело HTTP-сообщения — просто байты. Чтобы получатель знал, как их разобрать, используют **MIME-типы** (`тип/подтип`: `application/json`, `text/plain`, `text/html`, `image/png`) и два заголовка:

- **`Content-Type`** описывает формат тела, которое **отправляется прямо сейчас**. В запросе `POST` клиент ставит `Content-Type: application/json`; в ответе сервер ставит `Content-Type: application/json; charset=utf-8`.
- **`Accept`** сообщает серверу, какой формат клиент **ждёт в ответе** (например, `Accept: application/json`).

Если клиент прислал неподдерживаемый формат тела, сервер отвечает `415 Unsupported Media Type`; если не может сформировать запрошенный `Accept` — `406 Not Acceptable`.

## Подводные камни

**Ловушка 1. Мутация данных через `GET`.**  
Эндпоинт вида `GET /bookmarks/delete?id=5` опасен: предзагрузчик браузера или поисковый робот случайно удалят данные, просто пройдя по ссылкам. Любые изменения обязаны идти через `POST`, `PUT`, `PATCH` или `DELETE`.

**Ловушка 2. Ответ `200 OK` с ошибкой внутри JSON.**  
Возвращать `200 OK` с телом `{"error": "not found"}` — ловушка для кэшей, балансировщиков и мониторинга: инфраструктура считает такой ответ успешным. Отдавайте честный `404` или `500`.

> [!check] Проверь понимание
> Пользователь предъявил валидный токен, но пытается удалить чужую закладку без прав доступа. Какой код вернёт сервер — `401` или `403`?
>
> **`403 Forbidden`**. Код `401` означает, что сервер не опознал пользователя; здесь личность установлена, но действие запрещено правами.

## Практика

**Упражнение 1 (Базовое). Контракт для `BookmarkFlow`.**  
Подберите метод и код успешного ответа для четырёх операций: (а) список всех закладок; (б) создание новой; (в) полная замена закладки `#7`; (г) удаление `#7` без тела ответа.

> [!solution] Показать решение
> (а) `GET /bookmarks` → **`200 OK`**;  
> (б) `POST /bookmarks` → **`201 Created`**;  
> (в) `PUT /bookmarks/7` → **`200 OK`**;  
> (г) `DELETE /bookmarks/7` → **`204 No Content`**.

**Упражнение 2 (Практическое). Классификатор кодов на Go.**  
Напишите функцию `StatusClass(code int) string`, возвращающую `"2xx"`–`"5xx"` для `[200..599]` и `"unknown"` для остальных чисел.

> [!solution] Показать решение
> ```go
> func StatusClass(code int) string {
> 	switch code / 100 {
> 	case 2:
> 		return "2xx"
> 	case 3:
> 		return "3xx"
> 	case 4:
> 		return "4xx"
> 	case 5:
> 		return "5xx"
> 	default:
> 		return "unknown"
> 	}
> }
> ```
> Деление `code / 100` выделяет первую цифру статуса за одну операцию.

**Упражнение 3 (Со звёздочкой \*). Граница идемпотентности `PATCH`.**  
Приведите два JSON-тела для `PATCH /bookmarks/10`: идемпотентное и неидемпотентное. Объясните разницу.

> [!solution] Показать решение
> - **Идемпотентное:** `{"title": "Go Spec"}` — после 1 и после 5 вызовов заголовок один и тот же.
> - **Неидемпотентное:** `{"add_clicks": 1}` — каждый повтор увеличивает счётчик ещё на единицу.
>
> Поэтому идемпотентность `PATCH` зависит не от имени метода, а от семантики конкретного изменения.
