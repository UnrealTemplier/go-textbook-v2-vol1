*Почему одно и то же число `0x12345678` лежит в памяти x86 и в сетевом пакете задом наперёд и как пакет `encoding/binary` избавляет от путаницы при работе с бинарными форматами.*

Представьте, что вы проектируете компактный бинарный протокол для обмена сообщениями в `BookmarkFlow`. Каждый пакет начинается с 4-байтового целого числа `uint32` — длины тела сообщения, например `0x12345678` (в десятичной системе `305 419 896`). Когда вы читаете это число на бумаге слева направо, старший байт `0x12` идёт первым, а младший `0x78` — последним.

Но если заглянуть в оперативную память вашего ноутбука на процессоре x86-64 или ARM64, там окажется ровно обратная последовательность байтов: `78 56 34 12`. Если отправить сырые байты из памяти напрямую по сети, а другой компьютер прочитает их в привычном порядке слева направо, вместо `305 419 896` он получит `2 018 915 346` — и протокол мгновенно развалится.

## Интуиция: два соглашения о порядке байтов

Проблема касается только **многобайтовых** чисел (`uint16`, `uint32`, `uint64`, `float64`). У одного байта (`uint8`) порядок байтов бессмысленен — он один. А вот четыре байта числа `0x12345678` можно уложить в четыре соседние ячейки памяти двумя равноправными способами:

```text
Число: 0x12345678   (старший байт = 0x12, младший байт = 0x78)

Адрес памяти:        +0     +1     +2     +3
                   +------+------+------+------+
Big-Endian:        | 0x12 | 0x34 | 0x56 | 0x78 |  <- старший байт по младшему адресу
                   +------+------+------+------+

Адрес памяти:        +0     +1     +2     +3
                   +------+------+------+------+
Little-Endian:     | 0x78 | 0x56 | 0x34 | 0x12 |  <- младший байт по младшему адресу
                   +------+------+------+------+
```

Название **порядок байтов** (*endianness*) пришло из шутки Дэнни Коэна в технической записке IEN 137 (1980 год), который сравнил спор инженеров о порядке байтов с войной остроконечников и тупоконечников из «Путешествий Гулливера» Свифта — спором о том, с какого конца разбивать яйцо.

* **Big-Endian** («сначала старший байт») привычен для чтения в шестнадцатеричном дампе: байты идут слева направо так же, как мы пишем числа. Исторически его закрепили как **сетевой порядок байтов** (*network byte order*) в заголовках IP, TCP, UDP и многих бинарных форматов (например, PNG и JPEG).
* **Little-Endian** («сначала младший байт») стал стандартом для процессоров `x86` / `x86-64` и подавляющего большинства современных систем `ARM64`. Аппаратно он удобен тем, что адрес младшего байта 64-битного числа совпадает с адресом его 32-битной и 16-битной части.

У обоих подходов нет абсолютного победителя — важно лишь, чтобы отправитель и получатель **заранее договорились** об одном порядке и явно кодировали числа, не полагаясь на архитектуру конкретного процессора.

## Пакет `encoding/binary` в Go

В стандартной библиотеке Go эту задачу решает пакет `encoding/binary`. Он предоставляет две глобальные реализации интерфейса `binary.ByteOrder`:

* `binary.BigEndian` — для сетевых протоколов и форматов с порядком «сначала старший байт»;
* `binary.LittleEndian` — для форматов, ориентированных на `x86` / `ARM64` (например, ZIP, WAV или файловых заголовков некоторых систем).

Для чтения и записи целых чисел без лишних аллокаций у обоих объектов есть симметричные методы:

| Размер | Запись в срез байтов | Чтение из среза байтов |
|---|---|---|
| 2 байта | `PutUint16(b, v)` | `Uint16(b)` |
| 4 байта | `PutUint32(b, v)` | `Uint32(b)` |
| 8 байт | `PutUint64(b, v)` | `Uint64(b)` |

Также есть удобные функции `AppendUint16` / `AppendUint32` / `AppendUint64`, которые дописывают закодированные байты в конец слайса `[]byte`, как обычный `append`.

## Рабочий код: кодируем бинарный заголовок сообщения

Соберём наглядный пример: сначала проверим раскладку `0x12345678` в обоих порядках, а затем закодируем и декодируем 14-байтовый бинарный заголовок сетевого кадра (версия `uint16` + длина `uint32` + идентификатор `uint64`) в сетевом порядке `BigEndian`:

```go
package main

import (
	"encoding/binary"
	"fmt"
)

type FrameHeader struct {
	Version uint16 // 2 байта: смещение 0..1
	Length  uint32 // 4 байта: смещение 2..5
	ID      uint64 // 8 байт:  смещение 6..13
}

const headerSize = 14

func EncodeHeader(h FrameHeader) []byte {
	buf := make([]byte, headerSize)
	binary.BigEndian.PutUint16(buf[0:2], h.Version)
	binary.BigEndian.PutUint32(buf[2:6], h.Length)
	binary.BigEndian.PutUint64(buf[6:14], h.ID)
	return buf
}

func DecodeHeader(buf []byte) (FrameHeader, error) {
	if len(buf) < headerSize {
		return FrameHeader{}, fmt.Errorf("заголовок слишком короткий: %d байт", len(buf))
	}
	return FrameHeader{
		Version: binary.BigEndian.Uint16(buf[0:2]),
		Length:  binary.BigEndian.Uint32(buf[2:6]),
		ID:      binary.BigEndian.Uint64(buf[6:14]),
	}, nil
}

func main() {
	var be, le [4]byte
	binary.BigEndian.PutUint32(be[:], 0x12345678)
	binary.LittleEndian.PutUint32(le[:], 0x12345678)
	fmt.Printf("BigEndian:    % X\n", be)
	fmt.Printf("LittleEndian: % X\n", le)

	raw := EncodeHeader(FrameHeader{Version: 1, Length: 512, ID: 42})
	fmt.Printf("Заголовок:    % X\n", raw)

	decoded, err := DecodeHeader(raw)
	if err != nil {
		fmt.Println("ошибка:", err)
		return
	}
	fmt.Printf("Декодировано: %+v\n", decoded)
}
```

Вывод программы подтверждает каждый байт:

```text
BigEndian:    12 34 56 78
LittleEndian: 78 56 34 12
Заголовок:    00 01 00 00 02 00 00 00 00 00 00 00 00 2A
Декодировано: {Version:1 Length:512 ID:42}
```

Обратите внимание на строку `Заголовок`:
* `00 01` — это `Version = 1`;
* `00 00 02 00` — это `Length = 512` (`0x0200`, потому что $2 \times 256 = 512$);
* `00 00 00 00 00 00 00 2A` — это `ID = 42` (`0x2A`).

Заметьте также, что в бинарном буфере нет **никакого паддинга**: структура `FrameHeader` в памяти Go весила бы 16 байт (из-за выравнивания), а в сетевом буфере она занимает ровно `2 + 4 + 8 = 14` байт. Код `EncodeHeader` и `DecodeHeader` работает одинаково на любой архитектуре — независимо от того, на `x86`, `ARM` или сервере Big-Endian запущена программа.

## Подводные камни

**Ловушка 1. Паника при коротком буфере.**  
Методы `PutUint32` и `Uint32` не возвращают ошибку: если передать им слайс короче 4 байтов, программа мгновенно упадёт с паникой `index out of range`. Поэтому в `DecodeHeader` мы обязательно проверили `if len(buf) < headerSize` до первого чтения.

**Ловушка 2. Путаница между порядком байтов и порядком битов.**  
Endianness переставляет **байты**, а не биты внутри байта. Число `0x12` в двоичном виде (`00010010`) остаётся `0x12` и в Little-Endian, и в Big-Endian. Именно поэтому текстовые строки в ASCII и UTF-8 (последовательность отдельных байтов) от порядка байтов не зависят.

> [!check] Проверь понимание
> По сети пришли два байта `[0x01, 0x00]`. Какое десятичное число `uint16` они обозначают в `BigEndian` и какое — в `LittleEndian`?
>
> В `BigEndian` первый байт `0x01` — старший (`1 × 256 + 0 = 256`). В `LittleEndian` первый байт `0x01` — младший (`0 × 256 + 1 = 1`). Один и тот же пакет даёт 1 или 256 в зависимости от выбранного порядка.

## Практика

**Упражнение 1 (Базовое). Прочитайте дамп вручную.**  
В файле формата `LittleEndian` записано 4-байтовое беззнаковое число в виде байтов `0xE8, 0x03, 0x00, 0x00`. Запишите это число в привычном шестнадцатеричном виде (`0x...`) и переведите в десятичную систему.

> [!solution] Показать решение
> В `LittleEndian` байты идут от младшего к старшему, поэтому для привычной записи разворачиваем их задом наперёд: `0x000003E8` (или `0x3E8`).  
> Переводим в десятичную систему: $3 \times 256 + 14 \times 16 + 8 = 768 + 224 + 8 = 1000$.

**Упражнение 2 (Практическое). Упаковка сообщения с полезной нагрузкой.**  
Напишите функции `MarshalPacket(id uint64, payload []byte) []byte` и `UnmarshalPacket(data []byte) (id uint64, payload []byte, err error)`. Формат пакета в `BigEndian`: первые 8 байт — `id`, следующие 4 байта — длина `payload` (`uint32`), далее — сами байты `payload`. При декодировании проверьте, что длина `data` достаточна и для заголовка, и для заявленного `payload`.

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"encoding/binary"
> 	"errors"
> 	"fmt"
> )
>
> func MarshalPacket(id uint64, payload []byte) []byte {
> 	buf := make([]byte, 12+len(payload))
> 	binary.BigEndian.PutUint64(buf[0:8], id)
> 	binary.BigEndian.PutUint32(buf[8:12], uint32(len(payload)))
> 	copy(buf[12:], payload)
> 	return buf
> }
>
> func UnmarshalPacket(data []byte) (uint64, []byte, error) {
> 	if len(data) < 12 {
> 		return 0, nil, errors.New("неполный заголовок пакета")
> 	}
> 	id := binary.BigEndian.Uint64(data[0:8])
> 	n := int(binary.BigEndian.Uint32(data[8:12]))
> 	if len(data)-12 < n {
> 		return 0, nil, errors.New("неполное тело пакета")
> 	}
> 	payload := make([]byte, n)
> 	copy(payload, data[12:12+n])
> 	return id, payload, nil
> }
>
> func main() {
> 	raw := MarshalPacket(7, []byte("ping"))
> 	id, body, err := UnmarshalPacket(raw)
> 	fmt.Printf("id=%d body=%q err=%v\n", id, body, err)
> 	// Вывод: id=7 body="ping" err=<nil>
> }
> ```
> Проверка `len(data)-12 < n` защищает от паники, если повреждённый пакет заявил длину больше реального буфера, а копирование `payload` не удерживает в памяти весь входной буфер `data`.

**Упражнение 3 (Со звёздочкой \*). Проверка сигнатуры и размеров PNG-файла.**  
Заголовок любого изображения PNG начинается с 8-байтовой сигнатуры (`89 50 4E 47 0D 0A 1A 0A`), за которой идёт блок `IHDR`: 4 байта длины блока, 4 байта типа `"IHDR"`, затем ширина (`uint32`) и высота (`uint32`) в `BigEndian`. Напишите функцию `ParsePNGSize(header []byte) (width, height uint32, err error)`, проверяющую сигнатуру (достаточно первых 24 байтов файла) и возвращающую ширину и высоту изображения.

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"bytes"
> 	"encoding/binary"
> 	"errors"
> 	"fmt"
> )
>
> var pngSig = []byte{0x89, 'P', 'N', 'G', '\r', '\n', 0x1A, '\n'}
>
> func ParsePNGSize(header []byte) (uint32, uint32, error) {
> 	if len(header) < 24 || !bytes.Equal(header[:8], pngSig) {
> 		return 0, 0, errors.New("некорректный заголовок PNG")
> 	}
> 	if string(header[12:16]) != "IHDR" {
> 		return 0, 0, errors.New("отсутствует блок IHDR")
> 	}
> 	w := binary.BigEndian.Uint32(header[16:20])
> 	h := binary.BigEndian.Uint32(header[20:24])
> 	return w, h, nil
> }
>
> func main() {
> 	sample := make([]byte, 24)
> 	copy(sample[:8], pngSig)
> 	copy(sample[12:16], "IHDR")
> 	binary.BigEndian.PutUint32(sample[16:20], 1920)
> 	binary.BigEndian.PutUint32(sample[20:24], 1080)
>
> 	w, h, err := ParsePNGSize(sample)
> 	fmt.Printf("%dx%d (err=%v)\n", w, h, err) // Вывод: 1920x1080 (err=<nil>)
> }
> ```
> Именно так реальные библиотеки изображений читают размеры файла за микросекунды, не декодируя миллионы пикселей.
