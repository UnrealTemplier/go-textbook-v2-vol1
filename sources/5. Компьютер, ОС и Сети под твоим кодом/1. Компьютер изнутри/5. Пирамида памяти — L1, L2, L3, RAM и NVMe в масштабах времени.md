*Сколько тактов процессор простаивает в ожидании байта из RAM, как устроена иерархия кэшей L1–L3 и что означают наносекунды в человеческом масштабе.*

Современное ядро процессора работает на частоте около `3 ГГц` — один такт длится примерно **0.3 наносекунды**. За этот миг ядро способно сложить два 64-битных числа в регистрах. Но если нужного числа в процессоре нет и за ним приходится идти в оперативную память (RAM), ожидание растягивается примерно на **100 наносекунд**.

Пока летит один-единственный ответ из оперативной памяти, процессор успел бы выполнить около 300 тактов полезной работы — но вместо этого сидит без дела. За последние сорок лет процессоры ускорились в тысячи раз, а задержка доступа к RAM уменьшилась едва ли в десяток раз. Инженеры называют этот разрыв *стеной памяти* (*memory wall*).

## Зачем компьютеру пирамида памяти

Сделать всю память такой же быстрой, как регистры, мешает физика. Статическая память (**SRAM**), из которой строят кэши внутри CPU, тратит 6 транзисторов на бит, занимает много площади кристалла и стоит дорого. Динамическая память (**DRAM**) в модулях RAM обходится одним транзистором и конденсатором на бит — она на порядки плотнее и дешевле, но зарядка и считывание конденсатора занимают десятки наносекунд.

![Планка оперативной памяти DDR4 SDRAM](media/ddr4-ram-module.webp)

Поэтому память организована как многоступенчатая **пирамида**: наверху — крошечные и молниеносные уровни прямо в ядре; ниже — огромные, но медленные хранилища.

```text
                       /\
                      /  \        Регистры   (~1 КБ,   ~0.3 нс)
                     /----\
                    /  L1  \      Кэш L1     (32–64 КБ на ядро, ~1 нс)
                   /--------\
                  /    L2    \    Кэш L2     (256 КБ–1 МБ на ядро, ~4 нс)
                 /------------\
                /      L3      \  Кэш L3     (8–64 МБ общий, ~15 нс)
               /----------------\
              /       RAM        \ RAM (ОЗУ) (8–128 ГБ, ~100 нс)
             /--------------------\
            /       NVMe SSD       \ Диск    (0.5–4 ТБ, ~100 мкс)
           /------------------------\
          /           Сеть           \ Сеть  (дата-центр / мир, 1–50 мс)
         /____________________________\
```

При чтении байта процессор сначала проверяет **L1**. Нашёл — это **попадание в кэш** (*cache hit*, ~1 нс). Не нашёл (**промах кэша**, *cache miss*) — запрос спускается в **L2**, затем в общий **L3**, и только потом уходит в **RAM**, по пути копируя свежие данные обратно в кэши.

## Задержки в человеческом масштабе

Разница между наносекундой ($10^{-9}$ с), микросекундой ($10^{-6}$ с) и миллисекундой ($10^{-3}$ с) плохо ощущается на глаз. Растянем время в миллиард раз — пусть **1 наносекунда станет 1 секундой**:

| Уровень | Типичный объём | Реальная задержка | Если 1 нс = 1 секунда | Бытовой ориентир |
|---|---|---|---|---|
| Регистр CPU | сотни байтов | ~0.3 нс | ~0.3 секунды | одно моргание |
| Кэш L1 | 32–64 КБ / ядро | ~1 нс | 1 секунда | взять ручку со стола |
| Кэш L2 | 256 КБ–1 МБ / ядро | ~4 нс | 4 секунды | потянуться к полке |
| Кэш L3 | 8–64 МБ (общий) | ~15 нс | 15 секунд | подойти к шкафу |
| RAM (ОЗУ) | 8–128 ГБ | ~100 нс | ~1.5 минуты (100 с) | сходить на кухню |
| NVMe SSD | 0.5–4 ТБ | ~100 мкс | ~28 часов | больше суток |
| Сеть (ЦОД / мир) | — | 1–50 мс | ~11 дней – 1.5 года | от отпуска до переезда |

Именно эти скачки порядков определяют скорость реальных программ:

* **L1 → RAM:** в **~100 раз** дольше (сходить на кухню вместо того, чтобы взять ручку со стола).
* **RAM → NVMe SSD:** ещё в **~1 000 раз** дольше (и в 100 000 раз дольше L1), поэтому буферизация через `bufio` ускоряет запись файлов на порядки.
* **NVMe SSD → сеть:** ещё в **10–500 раз** дольше — один лишний сетевой вызов в цикле дороже миллионов операций в памяти.

![Твердотельный накопитель формата M.2 NVMe SSD](media/nvme-m2-ssd.webp)

*(Точные цифры зависят от модели CPU, DDR4/DDR5 и SSD, но соотношение порядков сохраняется на любой современной машине.)*

## Почему процессор простаивает на RAM

Когда код читает `v := items[idx]` и байта нет в L1–L3, ядро упирается в **простой памяти** (*memory stall*). Пока данные идут из модулей DRAM по шине платы, следующая инструкция `sum += v` не может выполниться — ей нечего складывать. Если каждый шаг цикла зависит от предыдущего чтения из памяти, конвейер быстро встаёт и сотни тактов ждёт ответа.

## Рабочий код: нащупываем границы L1, L2, L3 и RAM из Go

Мы можем «простучать» пирамиду памяти прямо из обычной программы на Go. Заведём целочисленный массив разного размера — от `16 КБ` (помещается в L1) до `64 МБ` (вываливается в RAM) — и выстроим внутри него случайную цепочку переходов `idx = next[idx]`. Поскольку каждый следующий индекс становится известен только после чтения текущего, процессор не может заранее угадать адрес и честно платит задержку того уровня памяти, куда поместился массив:

```go
package main

import (
	"fmt"
	"math/rand/v2"
	"time"
)

// makeRandomCycle строит один длинный цикл по всем элементам слайса,
// чтобы каждое обращение data[idx] зависело от предыдущего чтения.
func makeRandomCycle(n int) []int {
	perm := rand.New(rand.NewPCG(1, 2)).Perm(n)
	next := make([]int, n)
	for i := range n - 1 {
		next[perm[i]] = perm[i+1]
	}
	next[perm[n-1]] = perm[0]
	return next
}

func measureStep(bytes int, steps int) float64 {
	n := bytes / 8 // 8 байтов на один int на 64-битной системе
	next := makeRandomCycle(n)

	idx := 0
	// Небольшой прогрев кэша.
	for range min(n, 100_000) {
		idx = next[idx]
	}

	start := time.Now()
	for range steps {
		idx = next[idx]
	}
	elapsed := time.Since(start)
	if idx < 0 { // не даём компилятору выкинуть цикл
		fmt.Println(idx)
	}
	return float64(elapsed.Nanoseconds()) / float64(steps)
}

func main() {
	const steps = 4_000_000
	sizes := []struct {
		label string
		bytes int
	}{
		{"16 КБ (L1)", 16 << 10},
		{"256 КБ (L2)", 256 << 10},
		{"4 МБ (L3)", 4 << 20},
		{"64 МБ (RAM)", 64 << 20},
	}

	for _, s := range sizes {
		ns := measureStep(s.bytes, steps)
		fmt.Printf("%-14s -> %5.1f нс/шаг\n", s.label, ns)
	}
}
```

На 64-битном ноутбуке или сервере вывод отчётливо показывает ступеньки пирамиды (точные числа зависят от объёма кэшей вашего CPU):

```text
16 КБ (L1)     ->   1.2 нс/шаг
256 КБ (L2)    ->   4.5 нс/шаг
4 МБ (L3)      ->  14.8 нс/шаг
64 МБ (RAM)    ->  72.4 нс/шаг
```

Один и тот же цикл из одной строки `idx = next[idx]` замедлился в десятки раз лишь от того, что рабочий набор перестал помещаться в кэши процессора.

## Подводные камни

**Ловушка 1. Иллюзия «раз данные в RAM, значит мгновенно».**  
Сравнение с диском приучает считать оперативную память «мгновенной». Но внутри горячего цикла разница между L1 (~1 нс) и RAM (~100 нс) — два порядка. Алгоритм, который держит рабочий набор в нескольких килобайтах, легко обгоняет на порядок алгоритм, прыгающий по десяткам мегабайт.

**Ловушка 2. Мелкие небуферизованные записи на диск.**  
Вызов `file.Write([]byte("line\n"))` в цикле на 100 000 строк — это 100 000 обращений к операционной системе и подсистеме хранения вместо десятка крупных записей. Обёртка `bufio.NewWriter(file)` копит байты в буфере в RAM (по умолчанию `4 КБ`) и сбрасывает их на диск крупными порциями — за счёт разницы между наносекундами памяти и микросекундами диска.

> [!check] Проверь понимание
> Программа обрабатывает 1 миллион записей. В первом варианте каждая запись требует одного случайного чтения из RAM (~100 нс), во втором — одного чтения с NVMe SSD (~100 мкс). Оцените время обеих версий.
>
> Первый вариант займёт около `1 000 000 × 100 нс = 100 мс` (десятая доля секунды). Второй — около `1 000 000 × 100 мкс = 100 секунд` (почти две минуты). Разница ровно в 1 000 раз.

## Практика

**Упражнение 1 (Базовое). Оценка в человеческом масштабе.**  
Сервер делает 1 обращение в RAM (`100 нс`), 1 чтение с NVMe SSD (`100 мкс`) и 1 сетевой запрос к соседнему сервису (`2 мс`). Какая доля общего времени уходит на RAM, какая — на SSD и какая — на сеть? Что имеет смысл оптимизировать первым?

> [!solution] Показать решение
> Переведём всё в наносекунды:
> * RAM: `100 нс` (~0.005%);
> * NVMe SSD: `100 000 нс` (~4.76%);
> * сеть: `2 000 000 нс` (~95.24%);
> * всего: `2 100 100 нс` (`~2.1 мс`).
>
> Более 95% времени съедает один сетевой запрос. Оптимизация обращения к RAM здесь не даст заметного эффекта, пока не сокращено число или время сетевых вызовов.

**Упражнение 2 (Практическое). Ускорьте запись 50 000 строк в файл.**  
Функция ниже пишет строки прямо в `*os.File` по одной. Перепишите её с использованием `bufio.NewWriter` (не забудьте сбросить буфер `Flush` и проверить его ошибку).

```go
func writeLines(w *os.File, lines []string) error {
	for _, line := range lines {
		if _, err := w.WriteString(line + "\n"); err != nil {
			return err
		}
	}
	return nil
}
```

> [!solution] Показать решение
> Буферизованный `bufio.Writer` собирает сотни коротких строк в памяти и отправляет их ядру ОС крупными блоками. Проверка ошибки `bw.Flush()` обязательна: последняя порция данных уходит на диск именно там.

> package main
>
> import (
> 	"bufio"
> 	"fmt"
> 	"os"
> )
>

> 	bw := bufio.NewWriter(w)
> 	for _, line := range lines {
> 		if _, err := bw.WriteString(line); err != nil {
> 			return err
> 		}
> 		if err := bw.WriteByte('\n'); err != nil {
> 			return err
> 		}
> 	}
> 	return bw.Flush()
> }
>
> func main() {
> 	f, err := os.CreateTemp("", "lines-*.txt")
> 	if err != nil {
> 		panic(err)
> 	}
> 	defer os.Remove(f.Name())
> 	defer f.Close()
>
> 	if err := writeLines(f, []string{"first", "second", "third"}); err != nil {
> 		panic(err)
> 	}
> 	fmt.Println("Записано в", f.Name())
> }
> ```

**Упражнение 3 (Со звёздочкой \*). Сколько поместится в L1?**  
Пусть кэш данных L1 одного ядра равен `32 КБ`. Сколько элементов типа `int64` поместится в него целиком? А сколько структур `type Point struct { X, Y float64 }`? Проверьте, во сколько раз изменится число элементов, если хранить не сами `Point`, а указатели `*Point` (на 64-битной системе), учитывая память и под слайс указателей, и под сами структуры.

> [!solution] Показать решение
> `32 КБ = 32 768 байтов`.
> * Один `int64` занимает `8` байтов: `32 768 / 8 = 4 096` чисел.
> * Структура `Point` (`float64` + `float64`) занимает `16` байтов: `32 768 / 16 = 2 048` точек подряд.
> * Для слайса `[]*Point` на каждую точку тратится `8` байтов на указатель в слайсе плюс `16` байтов на саму структуру — итого минимум `24` байта (в полтора раза больше), а значит, в те же 32 КБ влезет не более `1 365` точек — и это ещё не считая потерь из-за разброса адресов в памяти.
