*Разбираем сырые байты запроса и ответа HTTP/1.1 поверх TCP: стартовую строку, заголовки, пустую строку `\r\n\r\n`, границы тела и постоянные соединения `Keep-Alive`.*

В повседневной разработке HTTP кажется чем-то сложным и скрытым внутри браузеров и фреймворков. На деле **HTTP/1.1** — это простой текстовый протокол поверх того самого потокового TCP, с которым мы только что работали в `project/step06/`. Чтобы отправить полноценный HTTP-запрос, вам не нужны специальные библиотеки: достаточно открыть сокет через `net.Dial("tcp", ...)` и записать в него несколько строк текста.

## Анатомия запроса и ответа в байтах

Любое сообщение HTTP/1.1 состоит из трёх частей: **стартовой строки**, блока **заголовков** и необязательного **тела**. Строки в HTTP/1.1 разделяются не одиночным `\n`, а двухбайтовой парой **CRLF** — `\r\n` (возврат каретки `0x0D` и перевод строки `0x0A`).

Вот дословный текст простейшего HTTP/1.1-запроса на получение списка закладок:

```http
GET /bookmarks HTTP/1.1\r\n
Host: bookmarkflow.local\r\n
User-Agent: raw-tcp-client/1.0\r\n
Accept: application/json\r\n
\r\n
```

Разберём каждую часть по порядку:
- **Стартовая строка запроса (*request line*)** — `GET /bookmarks HTTP/1.1`. Три поля через пробел: метод (`GET`), путь ресурса (`/bookmarks`) и версия протокола (`HTTP/1.1`).
- **Заголовки (*headers*)** — пары `Имя: Значение`. В HTTP/1.1 заголовок `Host` строго обязателен: на одном IP-адресе часто работает несколько сайтов, и именно по `Host` сервер решает, к какому из них обращается клиент. Регистр имён заголовков не имеет значения (`content-type` и `Content-Type` эквивалентны).
- **Пустая строка (`\r\n\r\n`)** — жёсткий маркер конца заголовков. Два перевода строки подряд сообщают получателю: метаданные закончились, со следующего байта начинается тело сообщения (у `GET`-запроса тела обычно нет).

Сервер отвечает в точно таком же формате, только стартовая строка называется **строкой статуса** (*status line*):

```http
HTTP/1.1 200 OK\r\n
Content-Type: application/json\r\n
Content-Length: 36\r\n
Connection: close\r\n
\r\n
{"items":[{"id":1,"title":"GoDoc"}]}
```

Здесь `HTTP/1.1` — версия протокола, `200` — числовой код результата, `OK` — поясняющая фраза для человека. После пустой строки `\r\n\r\n` идут ровно 36 байтов JSON-тела.

## Граница тела: `Content-Length` против `Transfer-Encoding: chunked`

Из урока 5 мы помним главное свойство TCP: в потоке байтов нет границ сообщений. Как клиент, прочитавший заголовки до `\r\n\r\n`, узнает, сколько байтов тела нужно прочесть до конца ответа? У HTTP/1.1 есть два механизма.

**Способ 1. Явная длина — `Content-Length`.**  
Если отправитель заранее знает полный размер тела, он записывает его в заголовок `Content-Length` — строго в **байтах** (не в символах и не в рунах). В примере выше строка `{"items":[{"id":1,"title":"GoDoc"}]}` занимает ровно 36 байтов, поэтому получатель читает ровно 36 байтов после `\r\n\r\n` и останавливается.

**Способ 2. Потоковая нарезка — `Transfer-Encoding: chunked`.**  
Часто сервер начинает отдавать ответ, ещё не зная его итоговой длины — например, собирает большой экспорт на лету или транслирует поток событий. Тогда заголовок `Content-Length` опускается, а вместо него ставится `Transfer-Encoding: chunked`.

Тело режется на произвольные кусочки (*чанки*). Перед каждым кусочком пишется его длина в **шестнадцатеричной системе** и `\r\n`, затем сами байты данных и снова `\r\n`. Конец всего тела обозначает нулевой чанк `0\r\n\r\n`:

```text
HTTP/1.1 200 OK\r\n
Content-Type: text/plain\r\n
Transfer-Encoding: chunked\r\n
\r\n
6\r\n
GoDoc\n\r\n
d\r\n
BookmarkFlow\n\r\n
0\r\n
\r\n
```

Первый чанк имеет длину `6` байтов (`GoDoc\n`), второй — `0xd` (13 в десятичной системе, `BookmarkFlow\n`), а строка `0\r\n\r\n` сообщает клиенту, что тело полностью доставлено.

## Постоянные соединения (`Keep-Alive`)

В старом HTTP/1.0 действовало правило «один запрос — одно TCP-соединение»: после отправки ответа сервер сразу закрывал сокет. Для веб-страницы из 40 файлов браузеру приходилось 40 раз проходить TCP-рукопожатие, 40 раз разогревать скорость передачи и 40 раз проходить TLS-рукопожатие. На медленной мобильной сети на одни только рукопожатия уходили секунды.

В HTTP/1.1 **постоянные соединения (`Keep-Alive`) включены по умолчанию**. Клиент и сервер не закрывают TCP-сокет после первого ответа, а переиспользуют его для следующих запросов подряд — до тех пор, пока одна из сторон явно не пришлёт заголовок `Connection: close` или не истечёт таймер простоя.

Теперь видно, почему точная граница тела (`Content-Length` или `chunked`) жизненно необходима. Если соединение не закрывается после ответа №1, клиент обязан знать точный последний байт этого ответа — иначе он никогда не поймёт, где начинается стартовая строка `HTTP/1.1 200 OK` ответа №2.

## Отправляем сырой HTTP/1.1 через `net.Dial`

Убедимся, что HTTP/1.1 работает поверх обычных TCP-сокетов Go безо всяких высокоуровневых HTTP-пакетов. Следующая программа поднимает крошечный TCP-сервер на `127.0.0.1:0`, подключается к нему через `net.Dial("tcp", ...)`, отправляет сырые байты запроса и печатает сырой ответ:

```go
package main

import (
	"fmt"
	"io"
	"net"
)

func main() {
	ln, err := net.Listen("tcp", "127.0.0.1:0")
	if err != nil {
		panic(err)
	}
	defer ln.Close()

	go func() {
		conn, err := ln.Accept()
		if err != nil {
			return
		}
		defer conn.Close()
		buf := make([]byte, 1024)
		_, _ = conn.Read(buf)

		body := `{"items":[{"id":1,"title":"GoDoc"}]}`
		resp := fmt.Sprintf(
			"HTTP/1.1 200 OK\r\nContent-Type: application/json\r\nContent-Length: %d\r\nConnection: close\r\n\r\n%s",
			len(body), body,
		)
		_, _ = conn.Write([]byte(resp))
	}()

	conn, err := net.Dial("tcp", ln.Addr().String())
	if err != nil {
		panic(err)
	}
	defer conn.Close()

	req := "GET /bookmarks HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n"
	if _, err := conn.Write([]byte(req)); err != nil {
		panic(err)
	}
	raw, err := io.ReadAll(conn)
	if err != nil {
		panic(err)
	}
	fmt.Println(string(raw))
}
```

Запуск программы показывает в терминале точную анатомию HTTP/1.1 без каких-либо прослоек:

```text
$ go run main.go
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 36
Connection: close

{"items":[{"id":1,"title":"GoDoc"}]}
```

Обратите внимание, зачем мы передали `Connection: close`. Функция `io.ReadAll(conn)` читает сокет до получения `io.EOF` (закрытия соединения сервером). Если сервер держит соединение открытым по `Keep-Alive`, `io.ReadAll` зависнет в ожидании закрытия — настоящие HTTP-клиенты сначала разбирают заголовки, смотрят на `Content-Length` или `chunked` и читают ровно столько байтов, сколько указано. В Модуле 7 за нас эту рутину возьмёт стандартная HTTP-библиотека Go.

## Подводные камни

**Ловушка 1. Забытый заголовок `Host` в HTTP/1.1.**  
Если отправить `GET / HTTP/1.1\r\n\r\n` без строки `Host: ...`, любой стандартный сервер обязан немедленно ответить `400 Bad Request`. В HTTP/1.1 `Host` — единственный строго обязательный заголовок каждого запроса.

**Ловушка 2. Подсчёт `Content-Length` в символах вместо байтов UTF-8.**  
Русское слово `"Закладки"` состоит из 8 символов (рун), но в кодировке UTF-8 занимает **16 байтов** (`len("Закладки") == 16`). Если ошибочно указать `Content-Length: 8`, клиент обрежет ответ ровно посередине и потеряет вторую половину текста.

> [!check] Проверь понимание
> Сервер отправил клиенту HTTP/1.1-ответ без `Connection: close`, без `Content-Length` и без `Transfer-Encoding: chunked`, но не закрыл TCP-соединение. Что произойдёт на стороне клиента?
>
> Клиент не сможет определить, где заканчивается тело ответа: он продолжит ждать либо новых байтов тела, либо закрытия TCP-соединения сервером до срабатывания собственного таймаута.

**Упражнение 2 (Практическое). Конструктор сырого запроса.**  
Напишите функцию `BuildGETRequest(host, path string) string`, которая формирует корректный HTTP/1.1-запрос для `GET` по указанному `path` (если `path` пуст, подставьте `"/"`), включает заголовки `Host`, `Accept: application/json` и `Connection: close`, использует строго `\r\n` и заканчивается пустой строкой `\r\n\r\n`.

> [!solution] Показать решение

> func BuildGETRequest(host, path string) string {

> ```
> Все строки разделены `\r\n`, заголовок `Host` заполнен, а завершающая пара `\r\n\r\n` чётко обозначает границу заголовков.

**Упражнение 3 (Со звёздочкой \*). Декодирование `chunked`-тела.**  
Клиент получил по сети фрагмент тела с заголовком `Transfer-Encoding: chunked`:
```text
5\r\n
Hello\r\n
1\r\n
 \r\n
a\r\n
Go 1.24!!!\r\n
0\r\n
\r\n
```
Какая итоговая строка получится после склейки всех чанков и сколько в ней байтов?

> [!solution] Показать решение
> Переводим шестнадцатеричные длины в десятичные: `0x5` = 5 (`"Hello"`), `0x1` = 1 (`" "`), `0xa` = 10 (`"Go 1.24!!!"`), затем нулевой чанк `0` завершает передачу. После склейки (без служебных `\r\n` вокруг размеров) получаем итоговую строку `"Hello Go 1.24!!!"` длиной **16 байтов**.
