*Что происходит внутри команды `go build` от текстового файла `.go` до готового бинарника, зачем нужны флаги `-ldflags="-s -w"` и `-trimpath` и как работает кросс-компиляция через `GOOS` и `GOARCH`.*

Когда вы запускаете скрипт на Python или JavaScript на новом сервере, одного файла с кодом недостаточно: на машине должны стоять совместимый интерпретатор, виртуальная машина и десятки системных пакетов. Стоит версии среды разойтись на один минорный номер — и программа падает ещё до первой полезной строки.

Программа на Go ведёт себя иначе: вы собираете один исполняемый файл, копируете его на чистый Linux-сервер без установленного Go — и он запускается напрямую. Никакой магии здесь нет: за эту автономность отвечает конвейер компиляции и линковки, спрятанный за одной командой `go build`.

## Конвейер `go build`: от текста к машинным инструкциям

Процессор ничего не знает о словах `func`, `range` или `struct` — он умеет выполнять только машинные команды конкретной архитектуры (например, `amd64` или `arm64`). Превращение исходного кода в такие команды проходит через пять последовательных этапов:

```text
  main.go (текст)
       │
       ▼  1. Лексер и парсер
  Дерево разбора (AST)
       │
       ▼  2. Проверка типов
  Проверенный код (ошибки типов ловятся здесь)
       │
       ▼  3. Промежуточное представление и оптимизации
  Упрощённый код (встраивание функций, удаление мёртвого кода)
       │
       ▼  4. Кодогенерация
  Объектный файл с машинными инструкциями (.o / .a)
       │
       ▼  5. Линковка (+ пакеты stdlib + рантайм Go)
  Единый исполняемый бинарник (ELF / Mach-O / PE)
```

Разберём, за что отвечает каждый шаг.

1. **Лексер и парсер.** Лексер режет текст на элементарные токены (`func`, `main`, `(`, `)`, `{`), а парсер складывает их в синтаксическое дерево. Опечатка вроде пропущенной скобки обрывает сборку уже здесь.
2. **Проверка типов.** Компилятор убеждается, что вы не передаёте `string` туда, где ждут `int`, и что все методы интерфейсов реализованы. Именно этот этап даёт раннюю диагностику ещё до запуска.
3. **Промежуточное представление и оптимизации.** Компилятор переводит код в унифицированную внутреннюю форму, упрощает выражения, встраивает короткие функции прямо в место вызова (*inlining*) и выбрасывает недостижимые ветки.
4. **Генерация машинного кода.** Оптимизированные операции переводятся в конкретные инструкции целевого процессора (`x86-64`, `ARM64` и других) с учётом регистров и выравнивания памяти.
5. **Линковка (*linking*).** Компоновщик склеивает объектные файлы ваших пакетов, нужные части стандартной библиотеки и **рантайм Go** (планировщик горутин, сборщик мусора, обработчик паник) в один исполняемый файл.

Внутреннюю кухню оптимизаций и соглашений вызовов компилятора мы подробно разберём в Томе 5. Для повседневной работы важно понимать главное следствие пятого шага: поскольку весь рантайм и стандартная библиотека вшиваются в итоговый файл при линковке, на целевой машине программе на чистом Go не нужны внешние библиотеки.

## Форматы исполняемых файлов и почему «Hello, World» весит 2 МБ

Операционная система не может просто прыгнуть в случайный байт файла — ей нужен заголовок, который описывает, куда загрузить код, где лежат константы и с какой инструкции начинать. У каждой семьи ОС свой формат такого контейнера:

| Операционная система | Формат бинарника | Типичное расширение |
|---|---|---|
| Linux (и большинство BSD) | **ELF** (*Executable and Linkable Format*) | без расширения |
| macOS | **Mach-O** (*Mach Object*) | без расширения |
| Windows | **PE** (*Portable Executable*) | `.exe` |

Отсюда сразу ясен ответ на частый вопрос новичков: почему простейшая программа с `fmt.Println` весит около **2 МБ** (против ~16 КБ на Си)? В эти два мегабайта уже упакованы планировщик горутин, сборщик мусора, таблицы типов для рефлексии и отладочная информация (имена файлов и номера строк для читаемых трассировок стека при панике).

## Рабочий код: релизная сборка и кросс-компиляция

Напишем небольшую консольную утилиту, которая печатает собственную версию и целевую платформу. Версию зададим переменной `version`, которую можно подменять прямо на этапе линковки:

```go
package main

import (
	"fmt"
	"runtime"
)

var version = "dev"

func main() {
	fmt.Printf("greet %s (%s/%s)\n", version, runtime.GOOS, runtime.GOARCH)
}
```

Соберём два варианта — обычный и релизный — и сравним размер и свойства бинарника в терминале:

```bash
go build -o greet-debug .
go build -trimpath -ldflags="-s -w -X main.version=1.2.0" -o greet-release .
ls -lh greet-debug greet-release
file greet-release
./greet-release
```

Вывод на 64-битном Linux:

```text
-rwxr-xr-x 1 ut ut 2.3M greet-debug
-rwxr-xr-x 1 ut ut 1.5M greet-release
greet-release: ELF 64-bit LSB executable, x86-64, statically linked, ..., stripped
greet 1.2.0 (linux/amd64)
```

Разберём флаги, которые уменьшили файл на треть и сделали сборку чистой:

* `-ldflags="-s -w"` передаёт компоновщику указание вырезать таблицу символов (`-s`) и отладочную информацию DWARF (`-w`). Бинарник становится меньше (2.3 МБ → 1.5 МБ), но при этом сохраняет способность печатать имена функций и строки в панике.
* `-X main.version=1.2.0` подставляет значение строковой переменной уровня пакета во время линковки — удобно для простановки номера релиза или хеша коммита из системы сборки.
* `-trimpath` вырезает абсолютные пути к вашей домашней папке (`/home/ut/work/...`) из бинарника. Во-первых, вы не светите локальные пути в продакшне; во-вторых, сборка становится воспроизводимой на разных машинах.

А чтобы прямо с Linux-ноутбука собрать бинарник для Windows или macOS на Apple Silicon, достаточно задать две переменные окружения — `GOOS` (целевая ОС) и `GOARCH` (целевая архитектура):

```bash
GOOS=windows GOARCH=amd64 go build -o greet.exe .
GOOS=darwin  GOARCH=arm64 go build -o greet-macos .
```

Компилятор Go изначально поставляется с кодогенераторами под десятки платформ (полный список показывает `go tool dist list`), поэтому кросс-компиляция работает из коробки без установки сторонних наборов инструментов.

## Подводные камни

**Ловушка 1. Флаг `-X` работает только для `var` типа `string`.**  
Если объявить `const version = "dev"`, компоновщик тихо проигнорирует `-X main.version=1.2.0` или выдаст ошибку, потому что константы подставляются на ранних этапах компиляции и к моменту линковки уже не существуют как отдельные ячейки памяти.

**Ловушка 2. Бинарник для другой ОС или архитектуры не запустится локально.**  
Если вы собрали файл с `GOOS=darwin GOARCH=arm64` на Linux-машине и попытаетесь запустить его локально, ядро Linux сразу вернёт `cannot execute binary file: Exec format error` — оно умеет читать формат ELF под `amd64`, но не Mach-O под `arm64`.

> [!check] Проверь понимание
> Что сломается, если собрать программу с флагами `-ldflags="-s -w"`? Перестанет ли она печатать стек вызовов при `panic`?
>
> Нет, трассировка стека при панике продолжит работать: Go хранит таблицу имён функций и строк в отдельной секции рантайма (`pclntab`), которую `-s -w` не удаляет. Пострадает только интерактивная отладка через внешний отладчик вроде Delve или GDB — без DWARF они не смогут сопоставлять машинные адреса с переменными исходного кода.

## Практика

**Упражнение 1 (Базовое). Разберите вывод `file`.**  
Команда `file` вывела для бинарника строку `ELF 64-bit LSB executable, x86-64, statically linked, stripped`. Что означает каждая из четырёх частей (`ELF`, `x86-64`, `statically linked`, `stripped`) и какие флаги `go build` привели к появлению слова `stripped`?

> [!solution] Показать решение
> * `ELF` — формат исполняемого файла для Linux.
> * `x86-64` — целевая архитектура процессора (`GOARCH=amd64`).
> * `statically linked` — бинарник не требует внешних динамических системных библиотек при запуске.
> * `stripped` — таблица символов и отладочные секции удалены; за это отвечает флаг `-ldflags="-s -w"`.

**Упражнение 2 (Практическое). Вшивание метаданных сборки.**  
Доработайте программу `greet` так, чтобы она хранила две строковые переменные `version` (по умолчанию `"dev"`) и `commit` (по умолчанию `"none"`) и выводила строку вида `greet 2.1.0 (commit abc1234, linux/amd64)`. Напишите точную команду `go build`, которая собирает релизный бинарник под Linux ARM64 без локальных путей и с обеими подставленными переменными.

> [!solution] Показать решение
> Код `main.go`:
> ```go
> package main
>
> import (
> 	"fmt"
> 	"runtime"
> )
>
> var (
> 	version = "dev"
> 	commit  = "none"
> )
>
> func main() {
> 	fmt.Printf("greet %s (commit %s, %s/%s)\n",
> 		version, commit, runtime.GOOS, runtime.GOARCH)
> }
> ```
> Команда сборки под Linux ARM64:
> ```bash
> GOOS=linux GOARCH=arm64 go build -trimpath \
>   -ldflags="-s -w -X main.version=2.1.0 -X main.commit=abc1234" \
>   -o greet-linux-arm64 .
> ```
> Внутри `-ldflags` можно перечислять несколько флагов `-X` через пробел.

**Упражнение 3 (Со звёздочкой \*). Проверка работы `-trimpath`.**  
Соберите одну и ту же программу с паникой (`panic("boom")`) дважды: сначала обычным `go build -o p1 .`, затем `go build -trimpath -o p2 .`. Запустите оба бинарника и объясните, чем отличаются пути к файлу `main.go` в трассировке стека.

> [!solution] Показать решение
> Минимальная программа:
> ```go
> package main
>
> func main() {
> 	panic("boom")
> }
> ```
> При запуске `./p1` в трассировке стека будет полный путь с вашей машины, например `/home/user/projects/greet/main.go:4`. При запуске `./p2` (собранного с `-trimpath`) вместо домашней директории останется только имя модуля и относительный путь — `greet/main.go:4`. Это защищает приватные пути и делает сборку воспроизводимой.

---

В выводе команды `file` выше мелькнула неприметная аббревиатура **LSB** (*Least Significant Byte*) — она указывает, в каком порядке процессор раскладывает байты многобайтовых чисел в памяти. Что произойдёт, если передать бинарный файл или сетевой пакет между машинами с разным порядком байтов, и как надёжно читать и записывать бинарные форматы в Go — разберём в следующем уроке: [[11. Порядок байтов (endianness) и чтение бинарных форматов]].
