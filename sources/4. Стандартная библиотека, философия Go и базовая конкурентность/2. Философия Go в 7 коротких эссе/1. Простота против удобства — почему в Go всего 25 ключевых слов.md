*Почему создатели Go отказались от десятков привычных «удобных» конструкций, чем простота отличается от удобства и как 25 ключевых слов экономят внимание команды.*

> «Как сформулировал Роб Пайк, «сложность мультипликативна»: решая задачу за счёт усложнения одной части системы, вы медленно, но верно добавляете сложность во все остальные. Под постоянным давлением сроков и требований добавить ещё фич, опций и настроек легко поступиться простотой — хотя в долгосрочной перспективе именно простота служит ключом к хорошему ПО.»  
> — Алан Донован и Брайан Керниган (цитируя Роба Пайка), *The Go Programming Language*

Почти каждый, кто приходит в Go из других языков, в первую же неделю составляет список «чего не хватает». Нет тернарного оператора `cond ? a : b`. Нет параметров по умолчанию `func Save(path string, timeout = 5)`. Нет перегрузки операторов, циклов `while` и наследования классов.

Каждая такая просьба по отдельности кажется невинной. Заменить четырёхстрочный `if/else` одной строкой — удобно же. Почему Роберт Гризмер, Роб Пайк и Кен Томпсон годами отвечали на сотни подобных предложений отказом?

## Мультипликативность сложности

Интуиция подсказывает, что сложность языка складывается: добавили три конструкции — выучили три правила. На деле сложность **перемножается**. Новая возможность сразу вступает во взаимодействие со всеми остальными частями языка: типами, интерфейсами, указателями, дженериками и инструментами анализа.

Возьмём параметры по умолчанию. Как только они появляются в языке, возникает лавина вопросов:

* Совместима ли функция `func(string, int = 5) error` с функциональным типом `func(string) error`?
* Удовлетворяет ли метод `Write(p []byte, flush bool = true)` интерфейсу `io.Writer`?
* Когда вычисляется значение по умолчанию, если это вызов функции или изменяемый слайс?

Одна «удобная мелочь» тянет за собой десятки оговорок в спецификации и столько же тонких багов. Сложность растёт как таблица умножения между всеми фичами.

## Простота против удобства

В предисловии к *The Go Programming Language* Алан Донован и Брайан Керниган разводят два понятия, которые часто путают:

> «Простота требует больше труда в начале проекта — чтобы очистить идею до самой сути — и больше дисциплины на всём сроке его жизни, чтобы отличать хорошие изменения от плохих и вредоносных. При должном усилии хорошее изменение вписывается в систему, не разрушая того, что Фред Брукс назвал «концептуальной целостностью» архитектуры; плохое — разрушает, а вредоносное разменивает простоту на её поверхностного двойника — удобство. Только простота архитектуры позволяет системе оставаться устойчивой, безопасной и цельной по мере роста.»  
> — Алан Донован и Брайан Керниган (со ссылкой на Фреда Брукса), *The Go Programming Language*

**Удобство** экономит секунды при *написании* кода. **Простота** экономит месяцы *чтения*, отладки и сопровождения. Когда в языке пять способов записать один цикл, каждый участник команды вырабатывает свой диалект, и чтение соседнего пакета превращается в расшифровку чужих привычек.

## 25 ключевых слов на практике

В спецификации Go 1.24 ровно **25 ключевых слов** (против 50+ в Java, 75+ в C# и 90+ в C++). Вместо трёх циклов — один `for`. Вместо параметров по умолчанию — явная структура настроек:

```go
package main

import "fmt"

type FormatOptions struct {
	Currency string
	ShowSign bool
}

func FormatMoney(kopecks int64, opts FormatOptions) string {
	currency := opts.Currency
	if currency == "" {
		currency = "RUB"
	}
	sign := ""
	if kopecks < 0 {
		sign = "-"
		kopecks = -kopecks
	} else if opts.ShowSign && kopecks > 0 {
		sign = "+"
	}
	return fmt.Sprintf("%s%d.%02d %s", sign, kopecks/100, kopecks%100, currency)
}

func main() {
	fmt.Println(FormatMoney(125050, FormatOptions{}))
	fmt.Println(FormatMoney(125050, FormatOptions{ShowSign: true}))
	fmt.Println(FormatMoney(-4200, FormatOptions{Currency: "USD"}))
}
```

Вывод терминала:

```text
1250.50 RUB
+1250.50 RUB
-42.00 USD
```

Присмотритесь к `FormatMoney`: значения по умолчанию видны прямо в коде, поля названы явно (`ShowSign: true` вместо загадочного позиционного `true`), а новый инженер прочитает функцию за десять секунд.

## Ортогональность и честная цена

Аскетизм Go держится на **ортогональности**: независимые механизмы сочетаются без особых случаев. Любой пользовательский тип — даже `type Duration int64` — может иметь методы и неявно удовлетворять интерфейсам. Один `for` покрывает счётчик, условие, бесконечный цикл и `range` (включая `for i := range n`). Даже дженерики в Go 1.18 вписали в существующую модель интерфейсов, не добавив ни одного нового ключевого слова.

Цена очевидна: код на Go порой многословнее, чем на Python или Rust. Создатели сознательно пожертвовали краткостью записи ради того, чтобы база на 500 000 строк оставалась линейной и прозрачной для всей команды.

> [!check] Проверь понимание
> Что означает тезис Роба Пайка о мультипликативности сложности?
>
> Каждая новая возможность языка взаимодействует со всеми остальными (типами, интерфейсами, компилятором, инструментами). Поэтому одна «маленькая фича» порождает целую матрицу новых правил и граничных случаев, а не изолированное дополнение.

## Практика

**Упражнение 1 (Базовое). Простота против удобства.**  
Почему в Go нет тернарного оператора `cond ? a : b`, хотя он короче `if/else`? Приведите два аргумента с точки зрения читателя кода.

> [!solution] Показать решение
> Во-первых, вложенные тернарные выражения (`a ? b : c ? d : e`) резко ухудшают читаемость. Во-вторых, единый способ записи ветвлений (`if`/`switch`) сохраняет одинаковый стиль во всём проекте: читатель сразу видит поток управления без расшифровки однострочников.

**Упражнение 2 (Практическое). Структура настроек вместо позиционных флагов.**  
Перепишите сигнатуру и тело функции фильтрации заголовков закладок `FilterTitles(titles []string, query string, caseSensitive, exactMatch bool) []string` через структуру `FilterOptions` (нулевое значение: без учёта регистра и по подстроке).

> [!solution] Показать решение
> ```go
> package main
>
> import (
> 	"fmt"
> 	"strings"
> )
>
> type FilterOptions struct {
> 	CaseSensitive bool
> 	ExactMatch    bool
> }
>
> func FilterTitles(titles []string, query string, opts FilterOptions) []string {
> 	q := strings.TrimSpace(query)
> 	if !opts.CaseSensitive {
> 		q = strings.ToLower(q)
> 	}
> 	var out []string
> 	for _, title := range titles {
> 		cand := title
> 		if !opts.CaseSensitive {
> 			cand = strings.ToLower(cand)
> 		}
> 		if (opts.ExactMatch && cand == q) || (!opts.ExactMatch && strings.Contains(cand, q)) {
> 			out = append(out, title)
> 		}
> 	}
> 	return out
> }
>
> func main() {
> 	titles := []string{"Go Tour", "go spec", "Effective Go"}
> 	fmt.Println(FilterTitles(titles, "go", FilterOptions{}))
> 	fmt.Println(FilterTitles(titles, "Go Tour", FilterOptions{CaseSensitive: true, ExactMatch: true}))
> }
> ```
> Именованные поля делают место вызова самодокументируемым, а пустой литерал `FilterOptions{}` задаёт безопасный режим по умолчанию.

**Упражнение 3 (Со звёздочкой \*). Цена перегрузки функций.**  
Представьте, что в Go разрешили объявить одновременно `Open(path string)` и `Open(path string, mode os.FileMode)`. Назовите два конфликта с существующими правилами языка.

> [!solution] Показать решение
> 1. **Неоднозначность значений функций:** в выражении `fn := Open` компилятор не сможет вывести тип `fn` из правой части.
> 2. **Сложные правила разрешения методов и интерфейсов:** одинаковые имена с разными сигнатурами потребуют сложной таблицы приоритетов (как в C++/Java), и по тексту вызова станет труднее понять, какая именно функция исполняется.
