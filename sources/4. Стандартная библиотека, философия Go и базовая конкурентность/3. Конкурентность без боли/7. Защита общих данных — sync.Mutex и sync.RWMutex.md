*Когда мьютекс проще и яснее канала, чем `sync.RWMutex` отличается от обычного `sync.Mutex` и какие три ошибки превращают блокировку в зависание.*

В третьем уроке этого подраздела мы приводили пословицу Go: «Не общайтесь через общую память — вместо этого делитесь памятью через общение». Каналы хороши для передачи задач и сборки конвейеров.

Но представьте хранилище закладок `SafeStore`, где восемь горутин одновременно добавляют записи (`Add`) и читают список (`List`). Если прятать слайс `items` и `nextID` за горутиной-владельцем с каналами запросов и ответов, 15 строк состояния превратятся в 60 строк обвязки. Для защиты внутреннего состояния структуры проще и яснее мьютекс.

## Взаимное исключение: `Mutex` и `RWMutex`

Слово *mutex* — сокращение от *mutual exclusion* (взаимное исключение). Его удобно представлять как единственный ключ от шкафа: кто взял ключ, тот меняет содержимое и возвращает его; остальные ждут. Граница аналогии: в Go мьютекс **не привязан** компилятором к полям структуры. Если один метод взял замок, а другой изменил поле без него, компилятор промолчит — дисциплина держится на коде.

В пакете `sync` два родственных замка:

- **`sync.Mutex`** — эксклюзивная блокировка: между `Lock()` и `Unlock()` находится не более одной горутины.
- **`sync.RWMutex`** — блокировка «читатели–писатель»: сколько угодно читателей держат `RLock()` одновременно, но писатель через `Lock()` получает эксклюзивный доступ, когда все читатели вызвали `RUnlock()`.

| Состояние замка | Новая горутина: `RLock()` | Новая горутина: `Lock()` |
|---|---|---|
| Свободен | Входит сразу | Входит сразу |
| У читателей (`RLock`) | Входит сразу *(если нет ждущего писателя)* | Ждёт всех `RUnlock()` |
| У писателя (`Lock`) | Ждёт `Unlock()` | Ждёт `Unlock()` |

*(Когда писатель встал в очередь на `Lock()`, новые читатели ждут за ним, чтобы запись не «голодала». Алгоритмы ожидания разобраны в Томе 5.)*

## Правила работы с замками

Оба типа работают с нулевым значением — конструктор не нужен. По соглашению Go поле `mu` ставят прямо над защищаемыми полями, а освобождение пишут сразу следующей строкой через `defer`:

```go
s.mu.Lock()
defer s.mu.Unlock()
```

Для чтения в `RWMutex` пара аналогична: `s.mu.RLock()` и `defer s.mu.RUnlock()`. `defer` гарантирует открытие замка даже при раннем `return` или панике.

Выбирайте `sync.RWMutex` там, где чтений заметно больше, чем записей, и они нетривиальны (например, клонирование списка). Для простого счётчика обычный `sync.Mutex` проще и быстрее.

## Рабочий код: от счётчика к `SafeStore`

Начнём со счётчика на `sync.Mutex` и сразу перейдём к потокобезопасному хранилищу закладок `SafeStore` на `sync.RWMutex`:

```go
package main

import (
	"fmt"
	"slices"
	"sync"
)

type Bookmark struct {
	ID    int
	Title string
	URL   string
}

type SafeStore struct {
	mu     sync.RWMutex
	nextID int
	items  []Bookmark
}

func NewSafeStore() *SafeStore { return &SafeStore{nextID: 1} }

func (s *SafeStore) Add(title, rawURL string) Bookmark {
	s.mu.Lock()
	defer s.mu.Unlock()
	bm := Bookmark{ID: s.nextID, Title: title, URL: rawURL}
	s.nextID++
	s.items = append(s.items, bm)
	return bm
}

func (s *SafeStore) List() []Bookmark {
	s.mu.RLock()
	defer s.mu.RUnlock()
	return slices.Clone(s.items)
}

func main() {
	store := NewSafeStore()
	var wg sync.WaitGroup
	for i := range 4 {
		wg.Add(1)
		go func(n int) {
			defer wg.Done()
			store.Add(fmt.Sprintf("Link %d", n), "https://go.dev")
		}(i)
	}
	wg.Wait()
	fmt.Println("total bookmarks:", len(store.List())) // Вывод: total bookmarks: 4
}
```

Ключевая деталь `List` — строка `return slices.Clone(s.items)`. Верни мы `s.items` напрямую, вызывающий код читал бы внутренний массив **после** `RUnlock()`, пока другая горутина вызывает `Add`. Клонирование под замком отдаёт безопасный независимый снимок.

## Три смертельные ошибки с мьютексами

### 1. Копирование мьютекса по значению

Методы структуры с мьютексом **всегда** принимают получатель-указатель (`*SafeStore`), иначе копируется сам замок:

```go
// НЕПРАВИЛЬНО: копирует SafeStore вместе с mu
func (s SafeStore) Count() int {
	s.mu.RLock()
	defer s.mu.RUnlock()
	return len(s.items)
}
```

Копия не синхронизирована с оригиналом, а при захваченном оригинале родится уже заблокированной и зависнет. `go vet` ловит это сразу (`passes lock by value`).

### 2. Повторный захват (deadlock)

**В Go `sync.Mutex` нереентерабельный** (*non-reentrant*): повторный `Lock()` в той же горутине гарантированно вешает программу:

```go
func (s *SafeStore) Count() int {
	s.mu.Lock()
	defer s.mu.Unlock()
	return len(s.items)
}

func (s *SafeStore) AddAndCount(title, rawURL string) int {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.items = append(s.items, Bookmark{ID: s.nextID, Title: title, URL: rawURL})
	s.nextID++
	return s.Count() // DEADLOCK: s.mu уже захвачен этой горутиной
}
```

Решение: вынесите общую логику в неэкспортируемый метод `countLocked()` без захвата замка и вызывайте его только внутри уже заблокированных методов.

### 3. Слишком широкая критическая секция

Удержание замка на время медленных операций — диска, сети или `time.Sleep` — выстраивает все остальные горутины в глухую очередь:

```go
// ПЛОХО: медленная проверка держит замок
s.mu.Lock()
ok := probeURL(rawURL)
s.status[rawURL] = ok
s.mu.Unlock()

// ХОРОШО: под замком только запись в память
ok := probeURL(rawURL)
s.mu.Lock()
s.status[rawURL] = ok
s.mu.Unlock()
```

> [!check] Проверь понимание
> Может ли горутина, удерживающая `mu.RLock()`, прямо внутри этой секции вызвать `mu.Lock()`, чтобы «повысить» права до записи?
>
> Нет. Вызов `Lock()` обязан дождаться, пока завершатся все текущие читатели — включая саму эту горутину. Программа немедленно попадёт в deadlock. Нужно сначала отпустить `RUnlock()`, затем взять `Lock()` и заново проверить условие, которое могло измениться в промежутке.

## Практика

**Упражнение 1 (Базовое). Двойной диагноз.**  
В типе `SafeNote` ниже допущены две ошибки из разобранной тройки. Найдите обе и исправьте код:

```go
type SafeNote struct {
	mu   sync.Mutex
	text string
}

func (n SafeNote) Get() string {
	n.mu.Lock()
	defer n.mu.Unlock()
	return n.text
}

func (n *SafeNote) SetIfEmpty(v string) bool {
	n.mu.Lock()
	defer n.mu.Unlock()
	if n.Get() != "" {
		return false
	}
	n.text = v
	return true
}
```

> [!solution] Показать решение
> Первая ошибка: `Get()` объявлен с получателем-значением `SafeNote`, из-за чего мьютекс копируется. Вторая: как только мы исправим `Get` на `*SafeNote`, вызов `n.Get()` внутри `SetIfEmpty` приведёт к deadlock из-за повторного захвата `n.mu`.
> ```go
> func (n *SafeNote) Get() string {
> 	n.mu.Lock()
> 	defer n.mu.Unlock()
> 	return n.text
> }
>
> func (n *SafeNote) SetIfEmpty(v string) bool {
> 	n.mu.Lock()
> 	defer n.mu.Unlock()
> 	if n.text != "" {
> 		return false
> 	}
> 	n.text = v
> 	return true
> }
> ```
> Внутри `SetIfEmpty` замок уже захвачен, поэтому поле `n.text` читается напрямую.

**Упражнение 2 (Практическое). Потокобезопасный кэш статусов.**  
Реализуйте структуру `StatusCache` с `sync.RWMutex` поверх `map[string]bool` и тремя методами: `Set(url string, ok bool)`, `Get(url string) (bool, bool)` и `Snapshot() map[string]bool`. Не забудьте безопасно инициализировать мапу и вернуть в `Snapshot` её копию через `maps.Clone`.

> [!solution] Показать решение
> Конструктор инициализирует мапу, `Set` берёт `Lock`, а `Get` и `Snapshot` используют `RLock`:
> ```go
> type StatusCache struct {
> 	mu    sync.RWMutex
> 	items map[string]bool
> }
>
> func NewStatusCache() *StatusCache {
> 	return &StatusCache{items: make(map[string]bool)}
> }
>
> func (c *StatusCache) Set(rawURL string, ok bool) {
> 	c.mu.Lock()
> 	defer c.mu.Unlock()
> 	c.items[rawURL] = ok
> }
>
> func (c *StatusCache) Get(rawURL string) (bool, bool) {
> 	c.mu.RLock()
> 	defer c.mu.RUnlock()
> 	ok, exists := c.items[rawURL]
> 	return ok, exists
> }
>
> func (c *StatusCache) Snapshot() map[string]bool {
> 	c.mu.RLock()
> 	defer c.mu.RUnlock()
> 	return maps.Clone(c.items)
> }
> ```
> `maps.Clone` создаёт независимую копию мапы под `RLock`, поэтому вызывающий код может свободно обходить снимок без конфликтов с `Set`.

**Упражнение 3 (Со звёздочкой \*). Сужаем критическую секцию.**  
Метод `CheckAndCache` ниже проверяет URL с помощью функции `probe(url string) bool` и кэширует результат, но удерживает `Lock()` на время вызова `probe`. Перепишите его так, чтобы `probe` выполнялась без замка, а быстрое чтение из кэша проходило под `RLock()`.

```go
func (c *StatusCache) CheckAndCache(rawURL string, probe func(string) bool) bool {
	c.mu.Lock()
	defer c.mu.Unlock()
	if ok, exists := c.items[rawURL]; exists {
		return ok
	}
	ok := probe(rawURL)
	c.items[rawURL] = ok
	return ok
}
```

> [!solution] Показать решение
> Разделим работу на три шага: быстрый поиск под `RLock()`, вызов `probe` вне замка и короткая запись результата под `Lock()`:
> ```go
> func (c *StatusCache) CheckAndCache(rawURL string, probe func(string) bool) bool {
> 	if ok, exists := c.Get(rawURL); exists {
> 		return ok
> 	}
> 	ok := probe(rawURL)
> 	c.Set(rawURL, ok)
> 	return ok
> }
> ```
> Теперь медленная проверка не блокирует кэш для других URL. *(Компромисс: если две горутины одновременно запросят один и тот же отсутствующий URL, обе вызовут `probe`, но кэш останется согласованным и быстрым.)*
