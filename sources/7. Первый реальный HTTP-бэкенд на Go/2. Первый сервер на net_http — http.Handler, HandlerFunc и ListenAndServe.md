*Разбираем главный интерфейс пакета `net/http` — `http.Handler`, его адаптер `http.HandlerFunc` и ловушку глобального мультиплексора `http.DefaultServeMux`.*

В [[7. Сетевые сокеты в Go — пишем TCP-эхо-сервер на пакете net]] мы принимали соединения вручную: вызывали `net.Listen`, крутили цикл `Accept()` и запускали горутину для каждого клиента. С протоколом HTTP такой ручной разбор превратился бы в сотни строк парсинга стартовых строк, заголовков, кодировки чанков и повторного использования соединений Keep-Alive. Пакет `net/http` берёт эту рутину на себя, а от вашего кода просит лишь реализовать один компактный интерфейс.

## Один интерфейс для всего сервера

Посмотрите на определение `http.Handler` в стандартной библиотеке Go:

```go
type Handler interface {
	ServeHTTP(ResponseWriter, *Request)
}
```

Весь веб-сервер в Go держится на единственном методе `ServeHTTP`. Когда клиент присылает HTTP-запрос, `net/http` парсит байты из TCP-сокета, собирает структуру `*http.Request`, готовит буфер ответа `http.ResponseWriter` и вызывает `ServeHTTP` в новой горутине.

У двух аргументов метода чёткое разделение ролей:

- **`r *http.Request`** — всё, что пришло от клиента (имя метода `r.Method`, URL и query-параметры `r.URL`, заголовки `r.Header`, тело запроса `r.Body` как `io.ReadCloser`, контекст `r.Context()`).
- **`w http.ResponseWriter`** — интерфейс для отправки ответа обратно: установка заголовков `w.Header()`, запись HTTP-статуса `w.WriteHeader(code)` и отправка тела ответа через `w.Write([]byte)` (тем самым он реализует знакомый нам `io.Writer`!).

Обратите внимание, что `ResponseWriter` передаётся как интерфейс (без звёздочки `*`), а `*http.Request` — как указатель на структуру. Это одно из самых частых мест, где новички путаются и получают ошибку компиляции `*http.ResponseWriter is pointer to interface, not interface`.

## От структуры к функции через `http.HandlerFunc`

Создавать отдельный тип с методом `ServeHTTP` ради каждого небольшого маршрута было бы утомительно. Для обычных функций в пакете `net/http` предусмотрен изящный приём — функциональный тип `http.HandlerFunc`:

```go
type HandlerFunc func(ResponseWriter, *Request)

func (f HandlerFunc) ServeHTTP(w ResponseWriter, r *Request) {
	f(w, r)
}
```

Это не обычная функция, а **именованный тип функции**, у которого объявлен метод `ServeHTTP`. Преобразование типа `http.HandlerFunc(myFunc)` не вызывает функцию сразу, а оборачивает её в значение, удовлетворяющее интерфейсу `http.Handler`. Метод `mux.HandleFunc(pattern, fn)` делает ровно это преобразование за вас и регистрирует результат через `mux.Handle`.

Посмотрим на обе формы в одном рабочем файле: одна структура `Server` с методом `ServeHTTP` и один точечный обработчик-функция:

```go
package main

import (
	"fmt"
	"log"
	"net/http"
)

type statusHandler struct {
	serviceName string
}

func (s *statusHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	w.Header().Set("Content-Type", "text/plain; charset=utf-8")
	fmt.Fprintf(w, "Сервис %s работает, метод %s\n", s.serviceName, r.Method)
}

func main() {
	mux := http.NewServeMux()
	mux.Handle("GET /status", &statusHandler{serviceName: "BookmarkFlow"})
	mux.HandleFunc("GET /ping", func(w http.ResponseWriter, _ *http.Request) {
		fmt.Fprintln(w, "pong")
	})

	log.Println("Старт на http://127.0.0.1:8080")
	if err := http.ListenAndServe("127.0.0.1:8080", mux); err != nil {
		log.Fatal(err)
	}
}
```

Если в методе `ServeHTTP` случайно поставить звёздочку перед `http.ResponseWriter`, компилятор сразу остановит сборку понятным сообщением:

```text
cannot use &statusHandler{...} (value of type *statusHandler) as http.Handler value in argument to mux.Handle:
    *statusHandler does not implement http.Handler (wrong type for method ServeHTTP)
        have ServeHTTP(*http.ResponseWriter, *http.Request)
        want ServeHTTP(http.ResponseWriter, *http.Request)
```

## Как `BookmarkFlow` использует `http.Handler`

В финальном проекте `project/final/server.go` структура `Server` сама реализует `http.Handler`. Внутри `NewServer` она собирает `http.ServeMux`, заворачивает его в цепочку middleware и сохраняет получившийся `http.Handler` в поле `s.handler`:

```go
func (s *Server) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	s.handler.ServeHTTP(w, r)
}
```

Благодаря этому `*Server` можно передать и в настоящий `http.Server`, и напрямую в тестовый вызов `srv.ServeHTTP(rec, req)` без единого сетевого сокета. Мы разберём тестирование этой схемы в уроке 16.

## Ловушка глобального `http.DefaultServeMux`

Во многих коротких примерах из интернета пишут `http.HandleFunc("/hello", fn)` и передают `nil` вторым аргументом в `http.ListenAndServe(":8080", nil)`. Когда вторым параметром стоит `nil`, Go молча подставляет пакетную глобальную переменную `http.DefaultServeMux`.

В реальном сервисе так делать не стоит по двум причинам:

1. **Чужой код может зарегистрировать маршруты тайком.** Любой импортированный сторонний пакет в своей функции `init()` способен повесить скрытый отладочный или служебный маршрут на глобальный `http.DefaultServeMux`, и ваш сервер неожиданно начнёт отдавать его наружу.
2. **Труднее тестировать в изоляции.** Разные тесты в одном процессе разделяют один глобальный мультиплексор и начинают конфликтовать за одинаковые пути.

Всегда создавайте локальный экземпляр `mux := http.NewServeMux()` и передавайте его явно.

> [!check] Проверь понимание
> Что произойдёт, если вызвать `http.ListenAndServe(":8080", nil)` без единого вызова `http.HandleFunc`?
>
> Сервер запустится, но будет использовать пустой `http.DefaultServeMux` и на любой входящий запрос ответит `404 page not found`.

## Практика

**Упражнение 1 (Базовое). Чтение контракта.**  
Почему в сигнатуре `ServeHTTP(w http.ResponseWriter, r *http.Request)` первый параметр передаётся как значение интерфейса, а второй — как указатель?

> [!solution] Показать решение
> `http.ResponseWriter` — это интерфейс (внутри него уже хранится ссылка на конкретную структуру ответа соединения), поэтому указатель на интерфейс `*http.ResponseWriter` почти никогда не нужен. А `http.Request` — довольно крупная структура с заголовками, URL и контекстом: её передают по указателю `*http.Request`, чтобы не копировать целиком на каждый вызов и позволить обработчикам работать с общим экземпляром (например, обновлять контекст через `r.WithContext`).

**Упражнение 2 (Практическое). Переход от `HandlerFunc` к структуре с состоянием.**  
Напишите структуру `InfoHandler` с полями `Version string` и `UptimeStart time.Time`, реализующую `http.Handler`. При запросе `GET /info` обработчик должен выводить строку вида `BookmarkFlow v1.0, работает 12s\n` (округлив длительность до секунд через `.Round(time.Second)`).

> [!solution] Показать решение
> ```go
> type InfoHandler struct {
> 	Version     string
> 	UptimeStart time.Time
> }
>
> func (h *InfoHandler) ServeHTTP(w http.ResponseWriter, _ *http.Request) {
> 	w.Header().Set("Content-Type", "text/plain; charset=utf-8")
> 	up := time.Since(h.UptimeStart).Round(time.Second)
> 	fmt.Fprintf(w, "BookmarkFlow %s, работает %s\n", h.Version, up)
> }
> ```
> Состояние `Version` и `UptimeStart` хранится в самой структуре и доступно всем запросам без глобальных переменных.

**Упражнение 3 (Со звёздочкой \*). Что сломается при передаче функции?**  
Разработчик написал функцию `func health(w http.ResponseWriter, r *http.Request) { fmt.Fprintln(w, "ok") }` и попытался передать её в `mux.Handle("GET /healthz", health)`. Код не скомпилировался. Как исправить строку двумя способами и в чём их разница?

> [!solution] Показать решение
> Функция `health` имеет подходящую сигнатуру, но у обычной функции нет метода `ServeHTTP`, поэтому она не реализует `http.Handler`. Исправить можно двумя способами:
> 1. Явно привести её к типу-адаптеру: `mux.Handle("GET /healthz", http.HandlerFunc(health))`.
> 2. Использовать вспомогательный метод мультиплексора: `mux.HandleFunc("GET /healthz", health)`, который внутри сам выполняет то же приведение `http.HandlerFunc(health)`.
